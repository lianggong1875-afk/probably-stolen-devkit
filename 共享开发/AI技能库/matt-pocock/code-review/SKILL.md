对`HEAD`与用户给出的基准点之间的差异（diff）做两轴评审：

- **标准维度（Standards）**：代码是否符合本仓库已文档化的编码标准？
- **规格维度（Spec）**：代码是否忠实实现了最初的工单/规格说明？

两条轴都以**并行子智能体**运行，彼此不污染对方的上下文，随后由本技能汇总它们的发现。每个子智能体都从全新上下文窗口起步。

工单系统应该已经提供给你。如果没有，让用户运行`/setup-matt-pocock-skills`。

## 流程

### 1. 钉住基准点

用户指定的那个东西就是基准点（commit SHA、分支名、tag、`main`、`HEAD~5`等）。用户没指定就问。

把diff命令确定下来，只写一次：`git diff <fixed-point>...HEAD`（三点，对比基准是合并基点）。再用`git log <fixed-point>..HEAD --oneline`记下提交列表。

继续往下之前，先确认基准点能解析（`git rev-parse <fixed-point>`）、差异非空。错误的ref或空差异要在这里失败，不能留到两个并行子智能体里面才失败。

### 2. 确定规格说明来源

按以下顺序寻找最初的规格说明：

1. 提交信息里的工单引用（`#123`、`Closes #45`、GitLab的`!67`等），按工单系统文档里的流程取回。
2. 用户作为参数传进来的路径。
3. `docs/`、`specs/`或`.scratch/`下，与分支名或功能名对得上的规格说明文件。
4. 什么都没找到，就问用户规格说明在哪。用户说没有，**规格维度**子智能体就跳过，并报告“无可用规格说明”。

### 3. 确定标准来源

在仓库里搜出每一个记录“代码该怎么写”的文件。只要`CODING_STANDARDS.md`或`CONTRIBUTING.md`存在，它就必须在这份清单上。

不管仓库文档写了什么，标准维度都始终带上下面这份**异味基线（smell baseline）**：一组固定的Fowler代码异味（_Refactoring_，第3章），即使仓库什么都没写也照样适用。两条规则约束它：

- **仓库优先。** 已文档化的仓库标准永远胜出；如果它认可了基线会标记的写法，就把这条异味压掉。
- **永远只是判断题（judgement call）。** 每条异味都是带标签的启发式结论（“可能是Feature Envy”），绝不是硬性违规。和这里的任何标准一样，工具链已经强制的项一律跳过。

每条异味的写法是*它是什么* → *怎么改*；拿它去和差异对照：

- **神秘命名（Mysterious Name）**：函数、变量或类型的名字看不出它在做什么、装着什么。→ 改名；如果实在想不出诚实的名字，说明设计本身含混。
- **重复代码（Duplicated Code）**：同一种逻辑形状在本次改动的多个差异块（hunk）或多个文件里出现。→ 把共用的形状提取出来，两处都调它。
- **特性依恋（Feature Envy）**：一个方法伸手去够别的对象的数据，比够自己的还多。→ 把这个方法搬到它依恋的那份数据上。
- **数据泥团（Data Clumps）**：同样的几个字段或参数总是结伴出现（一个想出生的类型）。→ 把它们捆成一个类型，传那个类型。
- **基本类型偏执（Primitive Obsession）**：用基本类型或字符串顶替一个本该有自己的类型的领域概念。→ 给这个概念一个自己的小类型。
- **重复的switch（Repeated Switches）**：对同一类型的同一套`switch`/`if`级联在改动里反复出现。→ 换成多态，或换成一个两处共用的映射表。
- **霰弹式修改（Shotgun Surgery）**：一个逻辑上的改动逼着你在差异里的许多文件中四处乱改。→ 把总是一起变的东西收进同一个模块。
- **发散式变化（Divergent Change）**：一个文件或模块因为几个互不相干的原因被改。→ 拆开，让每个模块只为一个原因变化。
- **夸夸其谈通用性（Speculative Generality）**：为规格说明里并不存在的需求添加的抽象、参数或钩子。→ 删掉它，一直内联回去，直到真实需求出现。
- **过长的消息链（Message Chains）**：调用方不该依赖的长串`a.b().c().d()`导航。→ 把这一串走位藏进第一个对象上的一个方法里。
- **中间人（Middle Man）**：一个类或函数，绝大部分时候只是继续往下转发。→ 砍掉它，直接调真正的目标。
- **被拒绝的遗赠（Refused Bequest）**：子类或实现者忽略或覆盖掉自己继承来的大部分东西。→ 放弃继承，改用组合。

### 4. 并行派发两个子智能体

两个子智能体调用一起发出，都在前台，然后汇总它们返回的报告。

**标准维度子智能体的提示词**应包含：

- 完整的diff命令与提交列表。
- 你在第3步找到的标准来源文件清单，**外加第3步的异味基线**全文粘贴（子智能体没有别的途径拿到它）。
- 任务书：“报告，在相关处按文件/差异块给出：(a) 差异违反某条已文档化标准的每一处，引用该标准（文件 + 规则）；(b) 你发现的任何基线异味，说出它的名字并引用对应差异块。区分硬性违规与判断题：违反已文档化标准可以是硬性违规，但基线异味永远是判断题，而且已文档化的仓库标准覆盖基线。工具链已经强制的项跳过。400词以内。”

**规格维度子智能体的提示词**应包含：

- diff命令与提交列表。
- 规格说明的路径，或已取回的内容。
- 任务书：“报告：(a) 规格说明要求了、但缺失或只做了一半的需求；(b) 差异里属于范围蔓延（scope creep）的行为，没人要求过它；(c) 看起来实现了、但实现方式看起来不对的需求。每条发现都引用规格说明原文那一行。400词以内。”

规格说明缺失，就跳过规格维度子智能体，并在最终报告里注明这一点。

### 5. 汇总

把两份报告分别放在`## Standards`和`## Spec`标题下，照原样或轻度清理。**不要**合并或重排发现的问题，因为两条轴是刻意分开的（见*为什么用两条轴*）。

结尾给一行小结：每条轴发现的问题总数，以及每个轴*内部*最严重的问题（如果有）。不要跨轴挑一个总冠军：那正是这种分开所要防止的重排。

## 为什么用两条轴

一次改动可能过了其中一条轴，却败在另一条轴上：

- 遵守了每一条标准、但实现错了东西的代码 → **标准维度通过，规格维度失败。**
- 完全照工单要求做、但破坏了项目约定的代码 → **规格维度通过，标准维度失败。**

分开报告，才能让一条轴不至于掩盖另一条轴。
