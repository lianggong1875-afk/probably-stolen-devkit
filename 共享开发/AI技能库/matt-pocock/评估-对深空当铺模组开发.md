# 评估：这套技能对《深空当铺》模组开发有没用

结论先说：**有用，但用处集中在两头**。动手前把需求钉死，提交前把代码审干净。中间那段写代码，它帮不上多少。

## 它是什么层的东西

流程层，不是领域层。

它不知道 `ModHook` 怎么挂，不知道访问 `PlayerStore.Instance` 前要判 `HasInstance`，不知道 `realCondition` 是唯一可信的成色字段，更不知道 Slot 0 不能碰。这些在你自己的《模组制作经验库》和 `probably-stolen-moddev` 技能里。

它管的是另一件事：**怎么把一件事想清楚，怎么证明做对了**。所以两者不冲突，一层管方法，一层管事实。真正落地时是叠加关系：先用它把方案问清楚，再用经验库把代码写对。

## 真会常态用到的

### 1. `grilling` / `grill-me` / `grill-with-docs`：拷问式对齐 ★★★★★

我们最贵的浪费不是写错代码，是**写对了一个没被要过的东西**。

典型场景：你说「做个鉴定台的放大镜检视」，我直接开始拆文件、写补丁、接纸张。写完你一看：检视层级不对、纸张交互顺序不对、跟计算器的联动也不是那个意思。一轮返工。

这个技能的做法是反的：把设计拆成一棵决策树，把当下能答的问题**一轮问完**，每个问题附上我推荐的答案，你回「是」就等于确认。下一轮再问那些被前面答案解锁的问题。前沿清空才算对齐。

对项目的具体收益：动手前 10 到 20 个问题，抵掉一整轮返工。

它有一条纪律值得单独说：**查事实是我的活，决策才是你的**。接口叫什么、重载有几个、生命周期怎么走，我去读反编译产物和经验库；只把「要 A 还是 B」这种只能由你定的事抛给你。

### 2. `codebase-design`：深模块 ★★★★☆

`AGENTS.md` 里那条「严禁为了离线假测试把功能拆成 `*Policy / *Bridge / *Seams / *Patch` 五六个文件」是一条禁令。这个技能给的是**禁令背后的替代标准**：深模块，大量行为藏在一个小接口后面，摆在一道干净的接缝上，通过那个接口就能测。

三个工具最有用：

- **删除测试**：把这个模块删掉，复杂度是消失了，还是原样散到调用方去了？散过去了，说明它只是个装样子的浅封装，该删。
- **接口就是测试面**：测公开接口的行为，不测内部结构。这直接判死了我们那条「`Contains(源码, "某变量名")` 式断言」，那种断言测的是实现，重构一次就碎。
- **一个适配器只是假想接缝，两个才是真接缝**：别为一个想象中的未来提前抽象。我们大量的套娃就是这么长出来的。

### 3. `code-review`：两轴评审 ★★★★

我们现实里的审查流程就是主模型审执行模型写的代码。两轴正好对应两份必须分开做的检查：

- **标准维度**：符不符合 `AGENTS.md` 六条（异常策略、Harmony 用法、物品判定铁律、发布零能力…）
- **规格维度**：是不是真把需求做了。很多真 bug 是「代码没错，但做的不是这件事」

它要求两轴用**并行子智能体、各开全新上下文**分开跑，避免一边的判断污染另一边。这一条在 DSH 里能直接照做。

### 4. `diagnosing-bugs`：诊断纪律 ★★★★

核心一句话：**在拿到一条已经是红的紧反馈回路之前，不许提出任何理论**。

反馈回路的意思是「一条命令，跑一下，红在这个 bug 上」。我们对付坏档、权限扫描失败、热重载崩溃时最容易犯的错，就是「看日志猜一下，改一版试试」。这个技能强制先把失败变成可稳定复现的一次运行（哪怕是把日志里的异常变成一条断言），再动手，最后补一条回归测试把修复钉死。

### 5. `domain-modeling`：术语表与 ADR ★★★☆

我们的术语密度高得离谱：`realCondition`、`DirectoryMaster.Has<T>`、`EnableTag`、`HotReloadPrepare` / `Activate`、`GraphUtils.CanAccept` / `TryAccept`、`fakeCondition`、成色、真伪、品类。

建一份 `GLOSSARY.md` 有两份收益：模型少猜（省 token，也少误用），我们命名统一。

ADR 适合记「为什么坚决不写 IL Transpiler」「为什么只用 `EnableTag` 不碰 `SetGameItemType`」这类**难回退的决策**。记下来的好处不是留档好看，是下次不会再被推翻重议一遍。

### 6. `prototype`：一次性原型 ★★★☆

Unity 里验证一个交互要编译、装机、进场景，一轮几分钟到十几分钟。这个技能主张把纯状态问题挪到单个 HTML 文件里跑，回答「这个状态模型顺不顺手」「这个界面该长什么样」，答完再进 Unity 实现。

对纸张交互、计算器逻辑、检视层级这类**不依赖引擎渲染**的问题特别划算。

## 有用但不天天用

| 技能 | 什么时候用 |
| --- | --- |
| `retro` | 每次大改完提一条环境改进。长期收益最高，也最容易被跳过 |
| `handoff` | 跨会话的长任务，比如真机测试做到一半要走开 |
| `research` | 反编译查证的流程化。思路对，但落点要从「在线文档」改成「反编译产物 + 经验库」 |
| `to-spec` / `to-tickets` | 只在跨多次会话的大功能上用，比如关系网科技树 |
| `improve-codebase-architecture` | 定期普查加深机会。两个项目代码量上来后值得跑 |
| `writing-for-agents` | 写 `AGENTS.md`、写技能文档时用。这套中文化本身就在用它的原则 |
| `wait-what` | 我某段话没讲清时，一句话让我重讲 |

## 用不上的，诚实说

| 技能 | 为什么用不上 |
| --- | --- |
| `triage` | 没有外部缺陷报告流，工单都是自己造的 |
| `wayfinder` | 单人开发，单个玩法系统够不上「一个会话装不下」 |
| `pr` | 本地 Git 直接提交，不走 PR |
| `wizard` | 生成 bash 交互向导，Windows 上要重写成 PowerShell 才有用 |
| `to-questionnaire` | 没有「知道答案的别人」可问 |
| `implement-spec` | 并行前沿要工单图 + 多个实现子智能体，我们的规模用不上 |
| `teach` | 教学向。真要吃透某个 Unity 概念时才有用 |

## 三个坑

1. **它假设你有 issue tracker 和 pnpm**。照搬会在「跑 `pnpm test`」「发到 issue tracker」这类步骤上卡住。映射表已经写在 `_本工作区落地.md` 里，照着换。
2. **`disable-model-invocation: true` 在 DSH 里不生效**。这个字段是 Claude Code 的语义，用来标记「只能用户手动触发」。DSH 忽略它，副作用是 `teach`、`to-questionnaire` 这类技能也可能被模型自动触发。真碍事就改它的 `description` 限定触发条件，或者干脆不装。
3. **它是流程约束，不是能力注入**。上下文紧张、任务催得急的时候，模型会自己抄近路跳过流程。所以真正能落地的只有两个触发点：**动手前 grill 一次，提交前 review 一次**。别的都是加分项。

## 建议的用法

前两周只开三个：

- 动手前 `grilling`
- 提交前 `code-review`
- 卡住时 `diagnosing-bugs`

跑顺了再加 `codebase-design`（改架构时）和 `domain-modeling`（术语开始乱、决策要留档时）。

**不要一次性把所有流程都套上**。把七八个流程叠在一次小改动上，那只是换了种形式的套娃，跟 `AGENTS.md` 反对的东西是一回事。
