# 加深

在给定依赖的前提下，如何安全地把一簇浅模块加深。假定你已掌握 [SKILL.md](SKILL.md) 里的词汇：**模块**、**接口**、**接缝**、**适配器**。

## 依赖分类

评估一个加深候选时，先给它的依赖分类。类别决定了加深后的模块如何跨接缝测试。

### 1. 进程内

纯计算、内存状态、没有 I/O。永远可以加深：把模块合并，直接通过新接口测试。不需要适配器。

### 2. 可本地替换

带有本地测试替身的依赖（Postgres 用 PGLite，内存文件系统）。只要替代物存在就可以加深。加深后的模块在测试套件中带着替代物运行来测试。接缝是内部的；模块的外部接口上没有端口（port）。

### 3. 远程但自有（端口与适配器）

你自己的服务，隔着网络边界（微服务、内部 API）。在接缝处定义一个**端口**（接口）。深模块拥有逻辑；传输层作为**适配器**注入。测试用内存适配器。生产用 HTTP/gRPC/队列适配器。

建议的说法：*“在接缝处定义端口，生产环境实现一个 HTTP 适配器，测试环境实现一个内存适配器，这样即使逻辑跨网络部署，它仍然落在一个深模块里。”*

### 4. 真正的外部（模拟）

你不掌控的第三方服务（Stripe、Twilio 等）。加深后的模块把外部依赖作为注入的端口接收；测试提供一个模拟适配器。

## 接缝纪律

- **一个适配器只是假想接缝，两个才是真接缝。** 除非至少有两个适配器站得住（通常是生产 + 测试），否则不要引入端口。单适配器的接缝只是多绕一层。
- **内部接缝与外部接缝。** 深模块可以有内部接缝（对其实现私有，供自身的测试使用），也可以有位于接口处的外部接缝。不要仅仅因为测试在用，就把内部接缝暴露到接口上。

## 测试策略：替换，不要叠加

- 一旦加深后模块接口处的测试存在，浅模块上的旧单元测试就成了废物；删掉它们。
- 在加深后模块的接口处写新测试。**接口就是测试面**。
- 测试断言通过接口可观察到的结果，不断言内部状态。
- 测试应当能挺过内部重构，因为它们描述的是行为，不是实现。如果实现一改测试就得改，那它就是在绕过接口去测。
