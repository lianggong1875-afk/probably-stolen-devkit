# 代码库设计

设计**深模块**：让小接口背后承载大量行为，把它放在干净的接缝上，并且能通过该接口测试。凡是在设计或重构代码的地方，都用这套语言和这些原则。目标是给调用方杠杆、给维护者局部性、给所有人可测试性。

## 术语表

严格按这些词来用：不要换成“component”、“service”、“API”或“boundary”。语言一致就是全部意义所在。

**模块**：任何有接口和实现的东西。刻意与规模无关：一个函数、一个类、一个包，或者一段跨层次的切片。_避免使用_：unit、component、service。

**接口**：调用方要正确使用该模块所必须知道的全部内容：类型签名，还包括不变量、顺序约束、错误模式、必需的配置以及性能特征。_避免使用_：API、signature（太窄，只指类型层面的表面）。

**实现**：模块内部的东西，即它的代码主体。与**适配器**不同：一个东西可以是小适配器配大实现（一个 Postgres 仓库），也可以是大适配器配小实现（一个内存假实现）。接缝是话题时用“适配器”，其余情况用“实现”。

**深度**：接口处的杠杆。调用方（或测试）每学习一单位接口能触发的行为量。当大量行为藏在小接口后面时，模块就是**深**的；当接口复杂到几乎和实现一样时，模块就是**浅**的。

**接缝** _（Michael Feathers）_：一个能在不改动该处的前提下改变行为的位置；也就是模块接口所在的*位置*。接缝放在哪里本身就是一项设计决策，与它背后放什么无关。_避免使用_：boundary（与 DDD 的限界上下文撞名）。

**适配器**：在某个接缝上满足某个接口的具体东西。描述的是*角色*（填哪个槽），不是实体（里面是什么）。

**杠杆**：调用方从深度中得到的东西。每学习一单位接口就换来更多能力。一份实现能在 N 个调用点和 M 个测试上回本。

**局部性**：维护者从深度中得到的东西。改动、缺陷、知识和验证集中在一处，而不是散布到各个调用方。改一次，处处已改。

## 深与浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（要避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘
```

设计接口时问自己：

- 方法数量能减少吗？
- 参数能简化吗？
- 能往里面多藏一些复杂度吗？

## 原则

- **深度是接口的属性，不是实现的属性。** 深模块内部可以由小的、可 mock 的、可替换的部件拼成；它们只是不属于接口。模块可以有**内部接缝**（对其实现私有，供自身的测试使用），也可以有位于接口处的**外部接缝**。
- **删除测试。** 想象把这个模块删掉。如果复杂度随之消失，那它只是个传声筒。如果复杂度在 N 个调用方那里重新出现，那它对得起自己的位置。
- **接口就是测试面。** 调用方和测试穿过同一个接缝。如果你想*绕过*接口去测，那模块的形状多半不对。
- **一个适配器只是假想接缝，两个才是真接缝。** 除非确实有东西跨越接缝发生变化，否则不要引入接缝。

## 为可测试性而设计

好的接口让测试变得自然：

1. **接收依赖，不要自己造依赖。**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **表面积要小。** 方法越少 = 需要的测试越少。参数越少 = 测试准备越简单。

## 关系

- 一个**模块**恰好有一个**接口**（它呈现给调用方和测试的那个面）。
- **深度**是**模块**的属性，以它的**接口**为标尺衡量。
- **接缝**是**模块**的**接口**所在的地方。
- **适配器**坐在**接缝**上，满足**接口**。
- **深度**为调用方产出**杠杆**，为维护者产出**局部性**。

## 已否决的表述

- **把深度当成实现行数与接口行数的比值**（Ousterhout）：这会奖励往实现里灌水。我们改用深度即杠杆。
- **把“接口”当成 TypeScript 的 `interface` 关键字或类的公开方法**：太窄：这里的接口包括调用方必须知道的每一条事实。
- **“边界”**：与 DDD 的限界上下文撞名。要说**接缝**或**接口**。
