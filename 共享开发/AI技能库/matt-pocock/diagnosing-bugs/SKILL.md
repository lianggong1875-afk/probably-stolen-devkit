# 诊断 bug

面对疑难 bug 的一套纪律。仅在明确说明理由时才跳过阶段。

探索代码库时，读 `GLOSSARY.md`（若存在），以建立相关模块的清晰心智模型；并检查你正要改动的区域里的 ADR。

## 脱敏

本技能要求你展示命令、输出和捕获的产物。**先把每一处密钥脱敏**：在原位写 `<REDACTED>`。让回路跑在环境变量上，这样凭据留在环境里，而不出现在你展示的内容里。捕获的产物带着认证头：只引用承载信号的那几行。

如果脱敏后的输出不足以诊断出这个 bug，就直说，并向用户索要。

## 阶段 1：建立反馈回路

**这一步才是技能本体。** 其余环节都是机械操作。只要你对这个 bug 有了一个**紧致**的通过/失败信号（一个在 _这个_ bug 上会变红的信号），你就能找到根因；二分、假设检验、埋点观测都只是在消费它。没有它，盯着代码看多久也救不了你。

在这里投入不成比例的努力。**要猛。要有想象力。不许放弃。**

### 构建反馈回路的方式，大致按此顺序

1. **失败测试**，落在任何能触达该 bug 的接缝上：单元、集成、端到端。
2. **Curl / HTTP 脚本**，打到正在运行的开发服务器。
3. **CLI 调用**，喂一份固定输入（fixture），把 stdout 与已知良好的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer），驱动 UI 并对 DOM、控制台、网络做断言。
5. **回放捕获的轨迹。** 把真实的网络请求、载荷、事件日志存到磁盘；再把它单独回放进那条代码路径。
6. **一次性宿主环境。** 拉起系统的最小个子集（一个服务、依赖做模拟），用一次函数调用就能跑通该 bug 的代码路径。
7. **属性 / 模糊测试回路。** 如果这个 bug 是“输出有时是错的”，就跑 1000 组随机输入，找出故障模式。
8. **二分宿主环境。** 如果这个 bug 出现在两个已知状态之间（提交、数据集、版本），就把“在状态 X 启动、检查、重复”自动化，这样你就能用 `git bisect run` 跑它。
9. **差分回路。** 把同一份输入分别跑过旧版本和新版本（或两套配置），再对比输出。
10. **HITL bash 脚本。** 最后手段。如果必须由人来点击，就用 `scripts/hitl-loop.template.sh` 驱动 _这个人_，让回路仍然保持结构。捕获的输出再回灌给你。

把反馈回路建对，这个 bug 就已经修掉九成。

### 把回路收紧

把回路当成产品来做。一旦你有了_一个_回路，就**收紧**它：

- 能更快吗？（缓存初始化、跳过无关的初始化、缩小测试范围。）
- 信号能更锐利吗？（断言具体症状，而不是“没崩”。）
- 能更确定吗？（钉住时间、给随机数生成器播种、隔离文件系统、冻结网络。）

一个 30 秒的不稳定回路比起没有回路好不了多少；一个 2 秒的确定性回路才叫紧致，那是调试的超能力。

### 非确定性 bug

目标不是干净复现，而是**更高的复现率**。把触发器循环 100 次、并行化、加压、收窄时间窗口、插入 sleep。50% 概率复现的 bug 是可调试的；1% 就不是，所以要一直提高复现率，直到它可调试。

### 当你确实造不出回路时

停下来，并明确说出来。列出你试过的东西。向用户索要：(a) 能复现它的那个环境的访问权限，(b) 一份脱敏后的捕获产物（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 在生产环境加临时埋点观测的许可。**绝不要**在没有回路的情况下就去做假设。

### 完成标准：一个会变红的紧致回路

阶段 1 在回路**紧致**且**能变红**时才算完成：你能说出**一条命令**（一个脚本路径、一次测试调用、一条 curl），并且**已经至少跑过一次**（展示该调用和它的输出，已脱敏），且它满足：

- [ ] **能变红**：它驱动的是真正的 bug 代码路径，并断言**用户描述的确切症状**，所以它会在这个 bug 上变红、在修好后变绿。不是“跑起来不报错”；它必须能_抓住这个具体的 bug_。
- [ ] **确定性**：每次运行结论相同（不稳定 bug：按上文，钉住一个高的复现率）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **智能体可运行**：你能无人值守地跑它；人介入只能通过 `scripts/hitl-loop.template.sh`。

如果你发现自己在命令还不存在时就去读代码编理论，**停下：直接跳到假设，正是本技能要防的那种失败。** 没有能变红的命令，就没有阶段 2。

## 阶段 2：复现 + 最小化

跑回路。看着它随 bug 出现而变红。

确认：

- [ ] 回路复现的是**用户**描述的故障模式，而不是恰好就在旁边的另一个故障。搞错 bug 就是搞错修法。
- [ ] 该故障在多次运行中都能复现（或对非确定性 bug 而言，能以足够高的复现率支撑调试）。
- [ ] 你已经捕获了确切症状（报错信息、错误输出、变慢的耗时），以便后续阶段验证修复真的解决了它。

### 最小化

一旦它变红，就把复现缩到**仍然会变红的最小场景**。**一次只砍一样**：输入、调用方、配置、数据、步骤；每砍一次就重跑回路，只留下对故障承重的部分。

为什么要这么做：最小复现会缩小阶段 3 的假设空间（可怀疑的活动部件更少），并成为阶段 5 那个干净的回归测试。

**剩下的每个元素都承重**时才算完成：去掉其中任何一个，回路都会变绿。

没做到**既**复现**又**最小化，就不要往下走。

## 阶段 3：提出假设

在检验任何一个之前，先产出**3 到 5 个排出次序的假设**。一次只生成一个假设，会让你锚定在第一个看似合理的点子上。

每个假设都必须**可证伪**：说出它给出的预测。

> 格式：“如果 <X> 是原因，那么 <改动 Y> 会让 bug 消失 / <改动 Z> 会让它更糟。”

如果你说不出预测，这个假设就只是一种感觉：丢掉它，或者把它磨锋利。

**在开始检验前把排序后的清单给用户看。** 他们常有领域知识能立刻重排序（“我们刚给第 3 条上线了一个改动”），或者知道他们已经排除过的假设。检查点很便宜，省下的时间很多。不要卡在这里；用户不在（AFK）就按你的排序往下走。

## 阶段 4：埋点观测

每个探针都必须对应阶段 3 的某条具体预测。**一次只改一个变量。**

工具优先级：

1. **调试器 / REPL 检查**，前提是环境支持。一个断点胜十条日志。
2. **定向日志**，打在能区分各假设的边界上。
3. 绝不要“全部打日志再 grep”。

**给每条调试日志打标签**，用唯一前缀，例如 `[DEBUG-a4f2]`。收尾清理时只需一次 grep。没打标签的日志会留下来；打了标签的会被干掉。

**性能分支。** 对性能回归来说，日志通常是错的手段。改走这条路：先建立基线测量（计时的宿主环境、`performance.now()`、profiler、查询计划），再二分。先测量，后修。

## 阶段 5：修复 + 回归测试

**先于修复**写回归测试，但前提是存在**正确的接缝**。

正确的接缝，是指测试能在调用点真实发生的位置上跑出**真正的 bug 模式**。如果唯一可用的接缝太浅（bug 需要多个调用方，却只能做单调用方测试；或者单元测试复现不了触发该 bug 的那条链），在那里写回归测试只会给出虚假的信心。

**如果不存在正确的接缝，这本身就是一条发现。** 把它记下来。是代码库的架构在阻止这个 bug 被锁住。把它标记出来，交给下一阶段。

如果存在正确的接缝：

1. 把最小化后的复现改造成该接缝上的一个失败测试。
2. 看着它失败。如果你是通过改动代码或固定输入来强制它变红的，就先与未改动的副本做 `diff`，证明改动确实落地了，再相信这个红。
3. 应用修复。
4. 看着它通过。
5. 对原始的（未最小化的）场景重跑阶段 1 的反馈回路。

## 阶段 6：收尾清理

宣布完成之前必须做到：

- [ ] 原始复现不再复现（重跑阶段 1 的回路）
- [ ] 回归测试通过（或已记录接缝的缺失）
- [ ] 所有 `[DEBUG-...]` 埋点观测都已移除（`grep` 该前缀）
- [ ] 一次性原型已删除（或移到明确标记的调试位置）
- [ ] 最终被证明正确的那个假设已写进提交 / 拉取请求（PR）消息，让下一个调试的人能学到
