# 原型

原型是**用来回答某个问题的一次性代码**。问题决定形态。

## 选择分支

判断正在回答的是哪个问题，依据用户的提示词、周边代码，或者用户在场时直接问：

- **“这段逻辑/状态模型说得通吗？”** → [LOGIC.md](LOGIC.md)。构建一个可分享的单文件HTML（自由操作按钮，加上分标签页的引导式演练），把状态机推过那些在纸上很难推演的情形，并且让非开发者也能自己驱动。
- **“这东西该长什么样？”** → [UI.md](UI.md)。在单一路由上生成若干个风格迥异的UI变体，通过URL查询参数和底部浮动条切换。

两个分支的产物差别极大，选错就白做整个原型。如果问题确实模棱两可，又联系不上用户，就选更贴合周边代码的那个分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部写明这个假设。

## 两个分支都适用的规则

1. **从第一天起就是一次性的，并且明确标注出来。** 把原型代码放在它将来真正会被使用的位置附近（紧挨着它正在做原型的模块或页面），上下文才一目了然；但命名要让随手翻到的人看得出这是原型，不是生产代码。一次性的UI路由，遵守项目已有的路由约定；不要另造一套顶层结构。
2. **运行起来毫不费力。** UI原型从项目任务运行器的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>`等。逻辑演示是用户双击就能打开的单文件HTML。两种方式都不需要动脑就能起来。
3. **默认不做持久化。** 状态活在内存里。持久化是原型要_检验_的东西，不是它该依赖的东西。如果问题明确涉及数据库，就接一个临时DB或一个本地文件，名字里写清“PROTOTYPE, wipe me”。
4. **跳过打磨。** 不写测试，错误处理只做到让原型_能跑起来_为止，不做抽象。目的是尽快学到东西。
5. **把状态露出来。** 每次操作之后（逻辑），或每次切换变体之后（UI），把完整的相关状态打印或渲染出来，让用户看见变了什么。
6. **做完就归档。** 把验证过的决策并进真实代码，然后把原型本身作为**一手来源**归档：提交到一个一次性分支，移出main，并在实现工单上留一个指向该分支的上下文指针。答案也要归档（结论，以及它定下的那个问题），写进工单或某个提交里。main分支只保留验证过的决策。
