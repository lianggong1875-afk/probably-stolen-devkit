# UI原型

在单一路由上生成**若干个差别极大的UI变体**，通过底部浮动条切换。用户在浏览器里来回翻看各个变体，挑一个（或者从每个里各偷一点），然后把剩下的扔掉。

如果问题关乎逻辑/状态，而不是某样东西长什么样，那就是走错分支了。用[LOGIC.md](LOGIC.md)。

## 什么情况下用这个形态

- “这个页面该长什么样？”
- “我想在定下来之前先看看这个仪表盘的几个方案。”
- “给设置界面试个不一样的布局。”
- 任何用户本来要在脑子里对着三个模糊的设计稿纠结一整天的场合。

## 两种子形态：强烈偏向子形态A

当UI原型**紧贴着应用的其余部分**时，判断起来容易得多：真实的顶栏、真实的侧栏、真实的数据、真实的密度。孤立的一次性路由是一个真空：每个变体单看都不错。只要有一个说得通的既有页面能承载这些变体，就默认走子形态A。只有当这个原型确实没有就近的落脚处时，才去够子形态B。

### 子形态A：调整既有页面（首选）

路由已经存在。变体渲染**在同一条路由上**，由`?variant=`这个URL查询参数控制。既有的数据获取、参数和鉴权全部保留。只换渲染。这是默认做法；除非有具体理由不用，否则就选它。

如果要成型的那个东西还没有页面，但*本来就很自然地住在某个页面里*（仪表盘的某个新区域、设置界面上的一个新卡片、既有流程里的一个新步骤），那仍然算子形态A。把变体挂在宿主页面内部。

### 子形态B：新建页面（最后手段）

只当要成型的东西确实没有既有页面可以住进去时才用（比如一个全新的顶层界面，或者一个嵌不进任何合理位置的流程）。

新建一条**一次性路由**，遵守项目已有的路由约定。不要另造一套顶层结构。命名要让人一眼看出是原型（比如在路径或文件名里带上`prototype`这个词）。`?variant=`的用法相同。

选定子形态B之前先自查：真的没有既有页面能把它嵌进去吗？空路由会掩盖设计问题，而一个有内容的页面会把这些问题暴露出来。

两种子形态下，底部浮动条完全相同。

## 流程

### 1. 陈述问题并定下N

默认**3个变体**。超过5个就不再是差别极大，而开始变成噪音，所以上限卡在5个。

用一句话写下计划，放在原型所在的位置，或者放在文件开头的注释里：

> “设置页面的三个变体，通过`?variant=`切换，落在既有的`/settings`路由上。”

无论用户是不是在旁边提反对意见，这句都管用。

### 2. 生成差别极大的变体

逐个起草变体。每个都要满足：

- 页面的用途，以及它能拿到的数据。
- 项目的组件库/样式系统（TailwindCSS、shadcn、MUI、纯CSS，随便哪种）。
- 清晰的导出组件名，比如`VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**：布局不同、信息层级不同、主要可供性不同，而不只是颜色不同。三个微调过的卡片网格不算UI原型，那叫壁纸。如果两份草稿做得太像，就带着明确的“不要用卡片网格”重做其中一个。

### 3. 把它们接起来

在路由上做一个切换器组件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态A（既有页面）：把既有的数据获取全部留在切换器之上；每个变体只改变被渲染的子树。

子形态B（新建页面）：`/prototype/<name>`下的一次性路由挂载同一个切换器。

### 4. 构建浮动切换器

屏幕底部居中的一个小尺寸固定定位条，包含三部分：

- **左箭头**：切到上一个变体（到头回绕）。
- **变体标签**：显示当前变体的键，如果该变体还导出了名字，也显示那个名字。比如`B (Sidebar layout)`。
- **右箭头**：向前切（到头回绕）。

行为：

- 点箭头会更新URL查询参数（用框架自带的路由，比如Next上用`router.replace`，React Router上用`navigate`，等等），这样变体可分享、刷新后稳定。
- 键盘：`←`和`→`方向键也能切换。焦点在`<input>`、`<textarea>`或`[contenteditable]`上时，不要去拦截方向键。
- 在视觉上与页面区分开（比如高对比度的胶囊、克制的阴影），一眼看出它不是被评估的那份设计的一部分。
- 在生产构建里隐藏：用`process.env.NODE_ENV !== 'production'`或等效判断设卡，免得哪次误合的原型把这条浮动条带到用户面前。

把切换器放进一个共享组件里，让两种子形态都能复用。放在项目里共享UI所在的位置。

### 5. 交给对方

把URL（以及各个`?variant=`键）亮出来。用户有空就会自己翻。有价值的反馈通常是**“我要B的顶栏配C的侧栏”**，那才是他真正想要的设计。

### 6. 归档答案并清理

某个变体胜出后，先归档答案（哪个变体，以及为什么），再按[SKILL](SKILL.md)里讲的方式归档原型。把胜出者并进真实代码，其余的移到一次性分支，不要进main：

- **子形态A**：把胜出者并进既有页面；从main里去掉落选的变体和切换器。
- **子形态B**：把胜出的变体提升为真实路由；从main里去掉一次性路由和切换器。

整套变体就是一手来源，所以它落在一次性分支上，而不是垃圾箱里，因为留在main分支里的变体组件和切换器会很快腐烂，把下一个读者绕晕。

## 反模式

- **只在颜色或文案上不同的变体。** 那是微调，不是原型。真正的变体在结构上互相分歧。
- **变体之间共享太多代码。** 共享一个`<Header>`没问题；共享`<Layout>`就把整件事废了。每个变体都该有自由推翻布局。
- **把变体接到真实的写操作上。** 只读原型就够用。如果某个变体需要写数据，就把它指向一个桩（stub）：问题问的是“这东西该长什么样”，不是“后端能不能用”。
- **把原型直接提升为生产代码。** 变体代码是在原型的约束下写的（不写测试、错误处理极小）。并进来的时候要认真重写。
