用户要求做一次**复盘**。你的任务是提议改进编码智能体的**环境**，让之后的运行效果更好。

## 步骤

1. 调用 Skill 工具加载 `writing-for-agents`，取得写作风格指南。

2. 读用户指定那次会话的一手来源。这可能意味着在本机翻查会话日志。用户没指定会话时，默认用当前这次。

3. 在下面这些类别里找可改进的候选。

- **导航（Navigation）**：智能体找到正确文件有多容易？文件之间有隐藏依赖吗？加一个**导航指针**会不会更容易？_适用时机_：这次会话花了很长时间才找到某条信息。
- **自动化检查（Automated checks）**：有没有自动化检查能抓住智能体犯的错？代码静态检查（lint）、类型检查、测试、文件系统静态检查工具？先读仓库自己的检查命令（它的 `package.json`/构建工具的 `lint`/`check` 脚本、它的 CI 工作流），这样一个已经存在却没接上、或悄悄坏掉的检查就是你的发现，而不是另起炉灶。没有**护栏**（guardrail）的仓库本身就是一条发现（既没有 pre-commit 钩子，也没有跑 lint/typecheck/test 的 CI 任务）：一个没接静态检查的仓库是长期存在的漏网机会，不是中性的默认状态。_适用时机_：智能体犯了自动化检查本可抓住的错，或者仓库压根没有护栏。
- **编码规范（Coding standards）**：要不要给**评审智能体**加一条新规则去执行？现有规则有没有该删或该写清楚的？先给违规分类：**机械式**的违规（固定的语法模式、被禁的 API、import 的写法、文件位置规则）就上确定性检查，没有例外：仓库自带静态检查里的自定义规则、一个新的 pre-commit 钩子，或者一个新的 CI 任务，看仓库的语言和现有护栏哪种最便宜。默认建检查，而不是写规则。`CODING_STANDARDS.md` 只留给真正的**判断题**（judgement calls：跨文件一致性、“与周围风格一致”、任何护栏永远替代不了的东西）。_适用时机_：评审智能体漏掉了一个错误。
- **全局 AGENTS.md**：有没有引导指令该改放到编码规范（或自动化检查）里？_适用时机_：AGENTS.md 文件特别大，不管是仓库里的还是用户全局范围里的。
- **工具开销（Tool economy）**：智能体有没有做过本可精简的高开销工具调用？有没有特别费 token 的自定义工具（CLI、MCP）？_适用时机_：智能体做过一次高开销的工具调用。
- **空转项（No-ops）**：找出引导文件里那些不改变智能体行为的指令。_适用时机_：引导文件又大又笨重。
- **信息获取（Information access）**：找机会扩大智能体获取信息的渠道。把开发服务器日志 tee 出来、对第三方服务开只读访问。_适用时机_：有一条关键信息智能体拿不到。

4. 按严重程度排序，把这些候选呈现给用户。

## 参考

### 实现与评审

记住，所有工作都经过两个阶段：实现与评审。实现智能体的**上下文压力**最大。探索、写代码、调试失败都由它负责。

评审智能体的上下文压力最小，它拿到的是差异（diff），所以不需要探索。它通常既不用写代码也不用调试。

这意味着编码规范该由评审智能体来负责执行，而不是实现智能体。

### 文件

你可以访问仓库里的若干文件：

- `CLAUDE.md`/`AGENTS.md`：这些文件会被推入任何在此仓库工作的智能体的上下文窗口。它们该被极其节制地使用，通常只用来放指向其他文件的**导航指针**。
- `CODING_STANDARDS.md`：这个文件在评审时读，实现时不读。标准文件超过 1,000 行时，往 docs 目录加**导航指针**。
- 文档：把文档当成参考文件，由其他文件指向它们。写新文档前先找有没有现成的。
- 技能：文档用技能来放（因为技能自己的 description 会进入智能体的上下文窗口），或者用来放用户触发的命令。遵循 `writing-for-agents` 技能里的建议。
