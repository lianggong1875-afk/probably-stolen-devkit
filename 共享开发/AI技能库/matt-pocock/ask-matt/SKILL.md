# 技能路由（Ask Matt）

你记不住每一个技能，所以来问。

在说出某个技能做什么、或建议跳过某一步之前，先读那个技能的 SKILL.md：这里的摘要只用于认路。

**流程**是穿过若干技能的一条路径。多数路径都沿着同一条**主流程**走，另有两条**汇入口**并入主流程。剩下的要么是独立技能，要么是垫在下面的一层词汇。

## 主流程：从一个想法到交付

多数工作走的就是这条路。你有个想法，想把它做出来。

1. **`/grill-with-docs`** 用访谈把想法磨清楚。只要你是**在一个工作目录里干活**，就从这里起步：它是有状态的，会把学到的东西留在 `GLOSSARY.md` 和 ADR 里。（没有工作目录？改用 `/grill-me`，见「独立技能」一节。两者跑的是同一个 `/grilling` 原语；`grill-with-docs` 是那个会留下纸面痕迹的，所以只要手边有仓库可留，它就是两者中更好的选择。）
2. **分支：所有问题都能靠对话谈定吗？** 如果某个问题需要跑起来才能答（状态、业务逻辑、必须亲眼看的界面），就绕道去搭原型，两个方向都用 **`/handoff`** 搭桥（原型住在自己的目录里，这正是 `/handoff` 的用武之地；见「阶段边界」）：
   - 先用 **`/handoff`** 交接出去，再针对那份文件开一个新会话，
   - 用 **`/prototype`** 拿一次性代码把问题答掉，
   - 再把学到的用 **`/handoff`** 交回来，并在原本的想法讨论串里引用它。
3. **分支：这是一次跨多个会话的开发吗？**
   - **是** → 先用 **`/to-spec`** 把讨论串变成规格说明，再用 **`/to-tickets`** 拆成曳光弹工单，每张工单声明自己的**阻塞关系**。然后按两种方式之一推进工单：
     - 每张工单跑一次 **`/implement`**，**每张之间都 `/clear` 掉上下文**。在本地工单系统里，就是 `.scratch/<feature>/issues/` 下每张工单一个文件，按阻塞关系、先解阻塞者的顺序手工推进；在真工单系统里，阻塞关系变成原生的阻塞链接，于是任何阻塞项已完成的工单都能被直接抓走。每张工单都是自足的，所以上一张的上下文可以随手丢掉。
     - 整份规格说明一次跑完，用 **`/implement-spec`**。它把工单读成一张**任务图**，让多个实现子智能体在已就绪的**前沿**上并行推进，最后全部落在同一个**集成分支**上。当你更想统筹这次开发、而不是亲手逐张推工单时，就用它。
   - **否** → 就地用 **`/implement`**，就在同一个上下文窗口里做。

   两种方式都一样：代码是靠驱动 **`/tdd`** 写出来的（一次一个红绿切片），收尾用 **`/code-review`**，对 diff 做两轴评审（标准 + 规格）。`/implement` 每张工单都跑这两步；`/implement-spec` 的各个实现者各自驱动 `/tdd`，最后对整个集成分支跑一次 `/code-review`。只想要把一个具体行为用测试先行做出来、不打算写完整规格说明时，单独用 **`/tdd`**；想针对某个基准点评审分支或 PR 时，单独用 **`/code-review`**。

   工作以拉取请求形式上浮时，**`/pr`** 负责正文的写法：用最小的图把改动讲清、给出改动前后确实生效的证据、并判断这是一扇单向门还是双向门。它是模型触发的，所以智能体每次写 PR 都会自己去用它。

4. **`/retro`** 收口。一次开发之后，尤其是走歪了的那种，它回头看整个会话，并针对智能体的**环境**（不是代码）提改进建议：导航指针、自动化检查、`/code-review` 执行的那套编码标准、引导文件、工具链。机械性失误变成确定性检查；需要判断的地方变成编码标准。下一次开发就从更好的环境起步。

### 上下文卫生

把第 1 到第 3 步保持在**同一个不被打断的上下文窗口**里（`/to-tickets` 之前不要压缩、不要清空），这样拷问、规格说明和工单都建立在同一套思考之上。之后每个 `/implement` 都从工单起步、开一个干净窗口。`/retro` 要在它回头看的那次会话里跑，趁清空之前；已经清空了，就把它指向那次会话的日志。

这条做法的上限是**[智能区间](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型还能保持锐利推理的那个窗口（当前顶尖模型上约 150k token）。如果还没到 `/to-tickets` 会话就逼近它，不要在推理退化的情况下硬推；在最近的阶段边界 `/compact` 一次，然后继续（见「阶段边界」）。

## 汇入口

一类会自己生出工作、然后并入主流程的起点情形。

- **缺陷和需求堆起来了** → **`/triage`**。它让工单在分诊角色之间流转，产出智能体可直接开工的工单，之后由 **`/implement`** 接手。

  分诊只针对**你没创建过**的工单：缺陷报告、外部提来的功能需求，任何原样砸过来的东西。`/to-tickets` 产出的工单已经是智能体可直接开工的状态，所以**不要拿它们去分诊**。

- **有东西坏了** → **`/diagnosing-bugs`**。专治硬骨头：一眼看不穿的缺陷、时隐时现的抖动、在两次已知良好状态之间爬进来的回归。在拿到一条**紧的反馈回路**（一条已经是红的命令，红在**这个**缺陷上）之前，它拒绝提出任何理论；然后补一条回归测试把修复钉住。修好之后，在同一个会话里跑 **`/retro`**，问一句本来什么能防住它；如果真正的结论是没有一道合适的接缝把它锁住，那就是 **`/improve-codebase-architecture`** 的活。

- **一大坨看不清的活儿：全新项目、或者大到一个会话装不下的功能开发** → **`/wayfinder`**，本库里认知负荷最重的流程。当前往目的地的路还看不见时，它在工单系统上画出一张**共享地图**，由一个又一个**决策工单**组成，逐个解决，产出的是**决策而不是交付物**，直到雾被推开、路显出来。`/grill-with-docs` 磨的是你一个会话就能攥住的想法，探路者对付的是攥不住的那种；它更慢、更密，所以只留给出这种活儿的时候，绝不要拿它去处理边界清楚的功能。

  地图清空后，**它只交接，不动手建**：在 **`/to-spec`** 处并入主流程，由它把地图上互相关联的决策收敛成一份可施工的计划，之后照常 `/to-tickets`、`/implement`。把地图直接接到 `/implement` 会跳过这次收敛，把互相关联的细节全扔掉；只有发现这活儿其实很小的时候，才直接进 `/implement`。

## 代码库健康

不是做功能，是日常养护。

- **`/improve-codebase-architecture`** 随时有空就跑一次，让代码库保持适合智能体在里面干活的状态。它把**加深机会**翻出来；挑中一个，就等于**长出一个想法**，可以带进主流程的 `/grill-with-docs`。它负责普查、找出候选项；**`/codebase-design`**（见下）是你把选中的那个拿出来设计的台面。

## 垫在下面的词汇层

两个模型触发的参考技能，垫在其余技能*下面*运行，各自是自己那套词汇的唯一出处。当问题出在**词**上而不是流程上时，直接去用它；也可以让上面的技能把它们拉进来。

- **`/domain-modeling`**：打磨项目的*领域*语言：挑战一个含混的词、拆开一个身兼数职的词（比如 "account" 同时干三件事）、把难以回退的决策记成 ADR。它是 `/grill-with-docs` 驱动的那门主动功夫，用来让 `GLOSSARY.md` 保持成一份干净的术语表。
- **`/codebase-design`** 是深模块那套词汇（module、interface、depth、seam、adapter、leverage、locality），用来设计一个模块的*形状*：大量行为藏在小接口后面，摆在一道干净的接缝上。`/tdd` 和 `/improve-codebase-architecture` 说的都是这套话。

## 阶段边界

**阶段**是会话里的一块工作：那段拷问、那段实现、那段质检。在两个阶段之间的**边界**上，你有五个选项，而在这五个里挑，是整张地图上最模糊的一个决定：

- **继续**：原地不动。不花代价，也不丢东西。
- **`/clear`**：清空窗口，前提是这里的东西对下一步都不重要。
- **`/handoff`** 写出一份可携带的 markdown 文件。适用范围窄：只在换**新宿主环境**、换**新目录**、交给**同事**、或在**阶段中途**分叉出一个支线任务时用。它买到的是可携带性。
- **子智能体**：把边界收得很紧的任务送进它自己的窗口，然后拿回一份报告。
- **`/compact`** 把当前上下文压缩，再用它播种一个新会话。这是**默认选项**，排在判定树最底下，而不是第一反应。

有序判定树见 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md)：那五个问题、每个分支背后的道理，以及为什么一手来源的代价让**继续**成为第一个该被排除的选项。决定要在边界**上**做；阶段中途，要么继续，要么把剩下的活拆给子智能体。

## 独立技能

完全在主流程之外。

- **`/grill-me`**：和 `/grill-with-docs` 同样不松手的访谈，但**无状态**：不在本地存任何东西，也不建 `GLOSSARY.md`。当**你不在工作目录里**干活时用它（磨一份计划、一个设计、一篇文章，任何底下没有仓库的东西）。如果你就在工作目录里，改用 `/grill-with-docs`：它跑同一场访谈，还留下纸面痕迹，所以严格来说更好。
- **`/grilling`** 就是访谈这个原语本身：按轮推进、算前沿、事实归智能体查而决策归你定。`/grill-me` 和 `/grill-with-docs` 是两条挂名的入口，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部跑它。只有当你想要一场外面不套任何壳的纯访谈时，才直接用它。
- **`/prototype`** 是一个小而一次性的程序，只为回答一个设计问题：这个状态模型顺不顺手，或者这个界面该长什么样。一次性是对代码写法的约束，不是承诺要把它毁掉：答案会折进真正的代码里，而原型本身作为**一手来源**保留在从主分支出来的 `prototype/<name>` 分支上，并由实现工单指过去。它是主流程第 2 步的那个绕道，任何时候一个设计问题在纸上谈不定，都可以用它。
- **`/research`**：把跑读资料的体力活交给**后台智能体**：它对着**一手来源**查一个问题，然后在仓库里留下一份带引注的 Markdown。它读它的，你继续干你的。它产出的文件是拿去*喂进*主流程的信息，在 `/grill-with-docs` 处并入，因为调研是给思考供料，不是替掉思考。
- **`/to-questionnaire`** 用在卡住你的东西既不在你脑子里、也不在代码库里，而在**别人**脑子里的时候：它写一份问卷让对方填。它和 `/grill-me` 正好相反：不问你主题本身，而是问你**这次发出去**（发给谁、你要拿回什么），然后把问题对准那道缺口。收回来的东西就是 `/grill-with-docs` 或 `/to-spec` 的原料。
- **`/wizard`** 用于只有**人**能做的那些步骤：开通基础设施、配置凭据或 CI 密钥、在一个陌生的第三方后台里点来点去、跑一次性的迁移或切换上线。它生成一个交互式 bash 脚本，逐个打开网址、逐个取值，写进 `.env` 和 GitHub secrets，于是这类流程不再需要每次都向智能体重讲一遍。模型触发，所以智能体一撞上只有你能过的那堵墙就会去用它。如果智能体自己动手就能办，那它就该自己办；这个技能是为人真正必须参与其中的场合准备的。
- **`/wait-what`** 是给「没接住」的消息准备的纠正手段。在对话中途、任何别的技能里都能用，智能体会把刚说过的话带上你缺的那点背景重讲一遍，用大白话，并且用 `GLOSSARY.md` 里的词。它是事后的；`/grill-with-docs` 才是事前的疗法，因为早早谈定的共同语言才能让黑话根本不来。
- **`/teach`**：跨多次会话学一个概念，把当前目录当作有状态的教学工作区。
- **`/writing-for-agents`** 是写「给智能体读的文档」的参考：技能、AGENTS.md、被指针指过去的文档。
