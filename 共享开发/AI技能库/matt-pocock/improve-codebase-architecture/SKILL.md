# 改进代码库架构

把架构摩擦摆到台面上，提出**深化机会**：把浅模块变成深模块的那类重构。目标是可测试性与 AI 可导航性。

本命令*依据*项目领域模型，并建立在一套共享设计词汇之上：

- 调用 Skill 工具加载 codebase-design，取得架构词汇（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆**、**局部性**）及其原则（删除测试、“接口即测试面”、“一个适配器只是假想接缝，两个才是真接缝”）。每一条建议都严格用这些术语，不要漂移到 “component”、“service”、“API” 或 “boundary”。
- `GLOSSARY.md` 里的领域语言为好接缝命名；`docs/adr/` 里的 ADR 记录了本命令不应重新翻案的决定。

## 流程

### 1. 探索

**先定范围再扫描：YAGNI。** 深化一个模块的回报，是让它未来的改动更省事，所以要把额外权重放在最近发生改动的那部分代码上。动手看之前先决定*看哪里*：

- 用户点名了方向（某个模块、某个子系统、某个痛点），就照它走，跳过下面的推断。
- 否则沿提交历史往回走足够一段（`git log --oneline`），找出代码库的热点，也就是反复出现的文件和区域，先让这些路径牵引你的注意力。如果改动零散、没有明显热点，就把网撒大。

先读项目的领域术语表（`GLOSSARY.md`），以及你要触碰的那片区域里的所有 ADR。

接着派一个带全新上下文窗口的子智能体去走查代码库。不要套用死板的启发式规则；有机地探索，并记下你在哪些地方遇到摩擦：

- 哪些地方为了理解一个概念，得在许多小模块之间来回跳？
- 哪些地方的模块是**浅**的，接口复杂得几乎和实现一样？
- 哪些地方纯函数只是为了可测试性被抽出来，真正的 bug 却藏在调用方式里（没有**局部性**）？
- 哪些地方的紧耦合模块从接缝处泄漏出去？
- 代码库的哪些部分没有测试，或者难以通过现有接口测试？

对任何你怀疑是浅的东西套用**删除测试**：删掉它会把复杂度集中起来，还是只是把它挪个地方？“是，集中了”才是你要的信号。

### 2. 把候选方案做成 HTML 报告

把一个自包含的 HTML 文件写到操作系统临时目录，保证什么都不落进仓库。临时目录优先取 `$TMPDIR`，取不到就回退到 `/tmp`（Windows 上是 `%TEMP%`），文件写到 `<tmpdir>/architecture-review-<timestamp>.html`，这样每次运行都拿到新文件。替用户打开它（Linux 用 `xdg-open <path>`，macOS 用 `open <path>`，Windows 用 `start <path>`），并告诉他们绝对路径。

报告用**通过 CDN 引入的 Tailwind** 做布局和样式，用**通过 CDN 引入的 Mermaid** 画图，前提是图、流程、时序能可靠表达结构。Mermaid 与手写 CSS/SVG 视觉要混着用：关系呈图状（调用图、依赖、时序）时用 Mermaid，想要更具编辑感的东西（体量图、剖面图、折叠动画）时用手写 div/SVG。每个候选方案都要有**改前/改后对比可视化**。要视觉化。

每个候选方案渲染一张卡片，包含：

- **涉及文件**：牵涉哪些文件、哪些模块
- **问题**：当前架构为什么产生摩擦
- **方案**：用平实的话描述会改什么
- **收益**：用局部性和杠杆来解释，以及测试会如何改善
- **改前/改后对比图**：左右并排、手工绘制，画出浅在哪、深化在哪
- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 三选一，渲染成徽标

报告以**首选推荐**一节收尾：先动哪个候选方案，为什么。

**领域词用 `GLOSSARY.md` 的词汇，架构词用 `/codebase-design` 的词汇。** 如果 `GLOSSARY.md` 定义了 “Order”，就说“Order 接单模块”，不要说 “FooBarHandler”，也不要说 “Order 服务”。

**ADR 冲突**：如果某个候选方案与现有 ADR 相矛盾，只有当摩擦真实到值得重新审视该 ADR 时才摆出来。在卡片里标清楚（例如一个警告块：*“与 ADR-0007 相矛盾，但值得重开，因为……”*）。不要列出 ADR 禁止的每一个理论上的重构。

完整的 HTML 骨架、图表模式与样式指导见 [HTML-REPORT.md](HTML-REPORT.md)。

此时不要提出接口方案。文件写完后问用户：“这些里面你想深入哪一个？”

### 3. 拷问循环

用户选定一个候选方案后，调用 Skill 工具加载 grilling，和他一起走决策树：约束、依赖、深化后模块的形态、接缝背后是什么、哪些测试能活下来。

决策一旦定型，副作用就地发生；边推进边调用 Skill 工具加载 domain-modeling，让领域模型保持最新：

- **用一个 `GLOSSARY.md` 里没有的概念给深化后的模块命名？** 把这个术语加进 `GLOSSARY.md`。文件不存在就按需创建。
- **在对话中把一个模糊术语磨清晰了？** 就地更新 `GLOSSARY.md`。
- **用户用一个承重的理由否掉这个候选方案？** 提议写一份 ADR，说法是：*“要我把这条记成 ADR，好让以后的架构评审不再重复建议它吗？”* 只有当未来的探索者确实需要这条理由、才能避免重复建议同一件事时才提议；临时性理由（“现在不值得做”）和自明的理由跳过。
- **想为深化后的模块探索备选接口？** 调用 Skill 工具加载 codebase-design，用它的 design-it-twice 并行子智能体模式。
