# ADR 格式

ADR 放在 `docs/adr/` 下，按顺序编号：`0001-slug.md`、`0002-slug.md` 等。

`docs/adr/` 目录按需创建：只在需要第一份 ADR 时才建。

## 模板

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

就这样。一份 ADR 可以只有一段。价值在于记下*做过*某个决策以及*为什么*，而不在于把各个小节填满。

## 可选小节

只有确实带来价值时才写这些。多数 ADR 用不上。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决策会被重新审视时有用
- **Considered Options**：只在被否掉的选项值得记住时才写
- **Consequences**：只在有不显然的下游影响需要点明时才写

## 编号

扫一遍 `docs/adr/`，找出已有的最大编号，加一。

## 什么时候提议写 ADR

以下三条必须全部成立：

1. **难以回头**：以后改主意的代价不小
2. **脱离上下文会让人意外**：将来的读者看着代码会想“他们到底为什么这么做？”
3. **真实取舍的产物**：确实存在别的选项，而你是出于具体理由选了这一个

决策容易回头就跳过：你到时候直接改回来就是了。不让人意外，就没人会追问为什么。本来没有别的选项，那除了“我们做了显而易见的事”也没什么可记的。

### 哪些算数

- **架构形态。**“我们用的是 monorepo。”“写模型是事件溯源的，读模型投影进 Postgres。”
- **上下文之间的集成模式。**“Ordering 与 Billing 靠领域事件通信，不用同步 HTTP。”
- **会带来锁定的技术选择。**数据库、消息总线、鉴权提供方、部署目标。不是每个库都要记：只记那些换掉要花一个季度的。
- **边界与范围决策。**“Customer 数据归 Customer 上下文所有；其他上下文只用 ID 引用。”明说的“不做”和明说的“做”一样有价值。
- **刻意偏离显而易见的路子。**“因为 X，我们裸写 SQL 而不用 ORM。”凡是讲道理的读者会默认反着理解的事。这些记录能拦住下一位工程师去“修”一个本就刻意的设计。
- **代码里看不出的约束。**“因为合规要求，我们不能用 AWS。”“因为合作方的 API 合同，响应时间必须低于 200ms。”
- **否决理由不显然的被否方案。**如果你考虑过 GraphQL，却出于微妙的理由选了 REST，就记下来；否则半年后有人会再提一次 GraphQL。
