# 分诊

让项目工单系统里的工单走完一个小型的分诊角色状态机。

如果本仓库把外部拉取请求（PR）当作一种需求入口（见工单系统配置），分诊也覆盖它们：**一个 PR 就是附带代码的工单**，用同一批角色、同一批状态、同一台状态机，差别只在下面标注“针对 PR”的少数几处。遇到裸写的 `#42`，按工单系统配置判定它是工单还是 PR。

分诊期间发到工单系统的每一条评论或工单，**必须**以这段免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何写长期有效的智能体简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库如何运作

## 角色

两个**分类**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：维护者需要评估
- `needs-info`：等报告者补充信息
- `ready-for-agent`：规格已写全，可交给无人值守智能体
- `ready-for-human`：需要人来实现
- `wontfix`：不予处理

对 PR 来说，同一批状态要对着它附带的代码来读：`ready-for-agent` 表示已附上简报，应由智能体在差异（diff）上走下一步；`ready-for-human` 表示可以交给人类合并了。

每个已分诊的工单应恰好带一个分类角色和一个状态角色。若状态角色互相冲突，先标出冲突并问维护者，再动别的。

以上是规范角色名。工单系统里实际使用的标签字符串可能不同。映射关系本应已经提供给你。若没有，让用户运行 `/setup-matt-pocock-skills`。

状态流转：未打标签的工单通常先进 `needs-triage`；从这里再转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 回到 `needs-triage`。维护者随时可以改判；遇到看着不寻常的流转，先标出来，问过再动手。

## 调用方式

维护者调用 `/triage`，用自然语言说明想要什么。理解请求，然后执行。示例：

- “把需要我关注的东西都列出来”
- “看看 #42”（工单或 PR）
- “把 #42 移到 ready-for-agent”
- “有哪些已经可以交给智能体接手？”

## 列出需要关注的内容

查询工单系统，按最旧的在前，给出三个分组：

1. **未打标签**：从未分诊。
2. **`needs-triage`**：正在评估中。
3. **`needs-info` 且上次分诊记录之后报告者有活动**：需要重新评估。

当 PR 在范围内时，把外部 PR 也放进这些分组，并给每一行标上 `[PR]` 或 `[issue]`。发现流程只暴露*外部* PR（谁算外部由工单系统配置定义），所以协作者手上正在进行的 PR 不算分诊工作。这道过滤只作用于发现环节；明确点名的 PR 一律分诊，不看作者是谁。

显示数量，并为每一项给一行摘要。让维护者来挑。

## 分诊某个具体工单或 PR

1. **收集上下文。** 完整读工单或 PR（正文、评论、标签、作者、日期；PR 还要读差异（diff））。解析已有的分诊记录，避免重复追问已解决的问题。用项目的领域术语表探索代码库，遵守该范围的架构决策记录（ADR）。对代码库做两项检查：(a) **冗余**：按领域概念（不只看请求的措辞）搜索所要求行为的现有实现，并报告你查过哪些地方。若找到，就属于已实现的 `wontfix`（第 5 步）。(b) **既往驳回**：读 `.out-of-scope/*.md`，把与此请求相似的文件列出来。

2. **给建议。** 把你的分类与状态建议连同理据告诉维护者，再附一段与请求相关的代码库简要说明（包括它是否已实现）。等指示。

3. **验证说法。** 开始任何拷问之前，先确认这个说法站得住。对 bug，按报告者的步骤复现。对 PR，确认差异（diff）确实做到了它声称的事：检出该分支，跑相关测试或命令。报告结果：已确认（给出代码路径）、失败，或细节不足（这是很强的 `needs-info` 信号）。经过确认的验证能让智能体简报强得多。

4. **拷问（按需）。** 若请求需要充实，调用 Skill 工具加载 grilling 和 domain-modeling（共两次），一轮一轮地问，把它问成形，边问边磨快领域术语，并在决定落地时同步更新 `GLOSSARY.md`/ADR。

5. **落地结论：**
   - `ready-for-agent`：发一条智能体简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：结构同智能体简报，但要写明为何无法委派（需要判断取舍、需要外部访问、涉及设计决策、需要手工测试）。
   - `needs-info`：发分诊记录（模板见下）。
   - 对 `wontfix`，关闭工单，评论内容取决于*为什么*：
     - **已实现**：该改动在代码库里已经存在。指出它在哪；**不要**写入 `.out-of-scope/`（那个知识库只收*被驳回*的请求，不收已建成的）。
     - **驳回（bug）**：给出客气说明，然后关闭。
     - **驳回（enhancement）**：写入 `.out-of-scope/`，在评论里链过去，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：打上该角色。若有部分进展，可选发评论。

## 快速改状态

若维护者说“把 #42 移到 ready-for-agent”，就相信维护者的判断，直接打上该角色。先确认你接下来要做什么（改角色、发评论、关闭），再动手。跳过拷问。若在没有拷问会话的情况下移到 `ready-for-agent`，问维护者要不要写智能体简报。

## needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把拷问期间定下来的所有内容都写进“established so far”一节，别让这些工作丢掉。问题必须具体、可执行，不能是“请补充更多信息”。

## 接续此前的会话

若工单或 PR 上已有分诊记录，先读它们，检查报告者是否已回答未解决的问题，然后在继续之前给出更新后的全貌。不要重复追问已解决的问题。
