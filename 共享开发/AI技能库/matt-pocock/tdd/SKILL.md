# 测试驱动开发

TDD 就是红 → 绿这个循环。本技能是让这个循环产出值得留下的测试的参照：什么是好测试、测试放在哪里、有哪些反模式，以及循环的规则。每一节在每一轮循环里都适用：要在循环之前和循环进行中查阅，不是循环之后。

探索代码库时，读 `GLOSSARY.md`（如果存在），让测试名和接口词汇与项目的领域语言对齐；同时遵守你所触及范围内的架构决策记录（ADR）。

## 什么是好测试

测试通过公开接口验证行为，不碰实现细节。代码可以彻底改掉；测试不该跟着改。好测试读起来像一份规格说明：“user can checkout with valid cart”直接告诉你存在什么能力；它不关心内部结构，所以能扛住重构。

示例见 [tests.md](tests.md)，模拟（mock）指南见 [mocking.md](mocking.md)。

## 接缝：测试放在哪里

**接缝**（seam）是你做测试的公开边界：在这个接口上观察行为，不用伸手进去。测试落在接缝上，绝不针对内部实现。

**只在事先商定的接缝上测试。**动手写任何测试之前，先写下这次要测的接缝，并与用户确认。绝不在未经确认的接缝上写测试。你测不了所有东西，所以事先把接缝谈定，测试精力才会落在关键路径和复杂逻辑上，而不是每个边界情况上。

要问：“公开接口是什么，我们应该测哪些接缝？”给每个提议的接缝写一行说明：它接住什么，漏掉什么。

当接口本身的形状都有疑问时（模块有多深、接缝该落在哪里、接口该暴露什么），调用 Skill 工具加载 codebase-design 拿术语。它是模块、接口、深度、接缝、适配器、杠杆、局部性这些词的共同来源；它是一份供查阅的参照，不是要跑起来的一场会话。

## 反模式

- **实现耦合**：模拟内部协作者、测私有方法，或者走侧路验证（查数据库而不用接口）。识别特征：一重构测试就挂，行为却没变。
- **同义反复**：断言按代码的算法把期望值重算一遍（`expect(add(a, b)).toBe(a + b)`、按同样方式手工推导出的快照、把常量断言为等于自身），所以它按构造就通过，永远不可能和代码不一致。期望值必须来自独立的事实来源：已知正确的字面量、算好的例子、规格说明。
- **横向切片**：先写完所有测试，再写所有实现。批量测试验证的是*想象出来的*行为：你测的是东西的*形状*而不是面向用户的行为，测试对真实改动变得不敏感，而且你在还没理解实现之前就把测试结构定死了。改用**垂直切片**：一个测试 → 一份实现 → 重复，每个测试都是一颗**曳光弹**，回应上一轮循环教给你的东西。

## 循环的规则

- **先红后绿。**先写会失败的测试，然后只写刚好让它通过的代码。不要预判未来的测试，也不要添加投机功能。
- **一次一片。**每轮循环一个接缝、一个测试、一份最小实现。
- **重构不属于这个循环。**它归评审阶段（见 `code-review` 技能），不属于红 → 绿的实现循环。
