## 模组行为

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 热重载后自家物品全变紫问号、名字空、价格 0，柜台一排问号 | `GameItem.SetSpriteAndShapeFromMod` 第一句 `ModLoader.Mods.Find(m => m.Manifest.ID.Equals(modId))` 不判空，热重载后表里有 `Manifest == null` 的登记 → NRE → 工厂全程没跑 | `ArcSpriteFix` 用 Prefix 接管这一步（自己查 `Sprites`、自己算占格），其余情况放行原版 |
| 柜台/背包里盒装盘只有左上角一格有碰撞，其余穿模 | 原版占格按每格**正中心 1 像素**判实心，盘盒中心孔正好落在中心点 | 改区域采样（内缩 2px、alpha>0.1 的像素 ≥8 算实心）+ 零格时整块兜底 |
| 玩家一眼能从贴图看出盗版 | 盗版盘和正版共用同一张贴图（刻意） | 唯一破绽途径是放大镜看印刷细节；要不要加"看得见的伪造痕迹"美术由用户定 |

| 以为原版 `CreateCustomerConfrontDialog()` 会 NRE | 它末尾有兜底 `dialog_expose_label_generic`「这标签是骗人的。我按实际的算。」 | 不会炸；补台词只需 Postfix 换那一句 |
| 补的台词不显示但价格掉了 | 台词挂错位置（比如改了 `GetClientExposeDialog` 的 Prefix 却没设 `priority`） | 改挂 `CreateCustomerConfrontDialog()` 的 Postfix，只用 `dialogue.SetText("CLIENT", ...)` |

## 编译期与命名空间

游戏 `Assembly-CSharp` 往**全局命名空间**里放了一批短名类型，它们会抢在 `using` 之前被绑定到，模组里写惯用短名就编译不过。

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| `CS0122: "Debug" 不可访问，因为它具有一定的保护级别` | 游戏有全局 `internal static class Debug`，写 `Debug.LogError` 先绑定到它，而它是 `internal` | 全限定 `UnityEngine.Debug.LogError(...)`，或用自己的 `ModLog`。⚠️ 附带：游戏的 `Debug.Log(object)` 只在 `VerboseLog.IsVerbose` 为真时才真正输出，`LogWarning/LogError` 才无条件转发 —— 想"日志里一定看得到"就别用 `Debug.Log` |
| `CS0234: 命名空间"Directory"中不存在类型或命名空间名"Exists"` | 游戏有全局 `class Directory`，顶掉了 `System.IO.Directory` | 全限定 `System.IO.Directory.Exists/.EnumerateFiles/...`（`File`/`Path` 暂时没撞，但也别赌） |
| `Harmony.GetAllPatchedMethods()` 返回几千条，报告全是模组互打 | 没按 `DeclaringType.Assembly` 过滤，模组自己内部方法的补丁也被算成"原版方法被补丁" | 只保留 `Assembly-CSharp` / `Assembly-CSharp-firstpass`；运行时补丁矩阵的读法见 [03](03-原版接口速查.md) 的「运行时补丁矩阵怎么读」 |

## 脚本与文件系统

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| `.ps1` 报 `Cannot bind argument to parameter 'Path' because it is null` | 文件是无 BOM 的 UTF-8，5.1 按 GBK 解码，中文注释把 `$PSScriptRoot` 那行吃掉了 | 补 UTF-8 BOM（`[IO.File]::WriteAllText($p, [IO.File]::ReadAllText($p,[Text.Encoding]::UTF8), [Text.UTF8Encoding]::new($true))`） |
| 新目录里的 `.ps1` 报 `is not digitally signed`，`$PSScriptRoot` 也空 | 目录带 `Low Mandatory Level` 且缺当前用户显式 ACE | `icacls /grant '*<SID>:(OI)(CI)(F)' /t` + `icacls '/setintegritylevel' '(OI)(CI)Medium' /t`（括号要引号） |
| 用 PowerShell 读改写文本后中文全变「鍏抽敭」 | `Get-Content -Raw` / `Set-Content` 走了 ANSI 往返，不可逆 | 一律用 edit/write 工具改文本，不要 PowerShell 往返 |
| 手改 `saves_index.es3` 后文件从 1826 B 变 1824 B | 字符串替换少算字节 | 用 `slot_index.py`（正则 + 自动备份）；出事从 `缓存文件夹\save-backup-*\` 还原 |
| 同名 `-RunId` 目录被拒绝 | 运行器不允许覆写历史产物 | 换新 RunId，别删旧目录 |
| 工作区里一堆 `wx-*-build`、`*.cache` 目录，几十上百 MB | 每个任务新建一个缓存目录、用完不管 | 缓存统一 `缓存文件夹`，一次性产物用完删；长期工具进 `工具库` |
| 新建的 `.ps1` 一跑就 `Unexpected token '}'` | write 工具写出的文件**无 UTF-8 BOM**，PowerShell 5.1 按 ANSI 读中文注释，解析直接崩 | 新建 `.ps1` 后立刻补 BOM：`[IO.File]::WriteAllText($p,[IO.File]::ReadAllText($p,[Text.Encoding]::UTF8),[Text.UTF8Encoding]::new($true))` |
| `Remove-Item` 报 `nul.json` 找不到（明明刚建的） | `nul` 是 Windows 保留设备名，任何操作都被重定向到空设备 | 别拿 `nul`/`con`/`aux`/`prn` 当临时文件名；建了基本删不掉，只能留着 |

## 跨模组 Patch 重叠（2026-11-27 静态扫描实证）

用 `工具库\workshop-tools\conflict_scan.py` 把「深空电玩 + 深空当铺：可能是群友 + 13 个工坊蒸馏模组」放在一起扫的结果（报告：`缓存文件夹\conflict-report.md`）：

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| **我们自己两个模组 Patch 了同样 6 个方法**：`LocHelper.GetLocalizedClientName`、`PlayerStore.DismissCurrentClient`、`SpriteDict.GetSprite`、`StoreUIManager.EnterShootingMode` / `ExitShootingMode` / `Shoot`（群友侧 `Shoot` 还有第二个拦截 Prefix） | 两个项目都做了「顾客称呼 / 顾客退场 / 贴图 / 射击模式」相关功能，各自独立 Patch | **✅ 2026-11-27 已修复**：电玩侧 6 个类全部加 `[HarmonyPriority(Priority.High)]` + `[HarmonyBefore("mod.freya_cornell")]`，群友侧 7 个类加 `[HarmonyPriority(Priority.Normal)]` + `[HarmonyAfter("mod.deepspace_arcade")]`；两处 `Shoot` 的 Postfix 改为接收 `bool __runOriginal`，被别的 Prefix 拦下（不开枪）时不再记「被打死的人」。约定写死：**电玩先跑、群友后跑**。编译 + 零能力扫描 + 回归 170 条全过 |
| `StoreUIManager.Update` 被 3 个模组同时 Patch（我们两个 + 工坊 ContainerLink） | 每帧方法，大家都往里塞 | **任何 `Update` 类 Patch 必须极轻**（< 0.1ms），重活改事件驱动；新增时要算「每帧开销 × 玩家装的模组数」 |
| 深空电玩 Patch 了 `GameItem.GetDisplayName`（全局显示名） | `ArcLabeler` 要把「（盒装正版）」改显示成「（仿冒）」 | 这是工坊冲突检测器认定的**红色热点**（与「改名/显示增强」类模组互斥）。**✅ 2026-11-27 已加固**：`[HarmonyPriority(Priority.Low)]` 让我们的改写最后执行（保证自己的盘面标记显示出来）；守卫已有三层（名称必须以我们的后缀结尾 + `LabelTarget.DiscLicense` + 当前条件是仿冒），其它物品原样返回；注释里写明只影响显示、不影响真伪判定 |
| 工坊侧 3 个模组同时 Patch `ChemicalHelper.RunNightlyChemicalSimulation`（ContainerLink / SleepLagOptimizer / ProgressBar） | SleepLag 与 ProgressBar 都**整段替换**了这个方法 | 实证了「整段替换原版入口 = 与同类模组互斥」：玩家同时装这两个优化模组，过夜优化只会有一个生效。**我们自己绝不这么干** |

### 教训：静态重叠 ≠ 真冲突，必须读守卫条件

`conflict_scan.py` 只能看到"同一个原版方法被多个模组 Patch"。判真伪要看每个 Patch 的**守卫条件**：

我们两个模组的 `DismissCurrentClient` 都是 `Prefix` + 条件守卫，条件**互斥**，所以同时装是安全的：

- 深空电玩 `ArcExpressions.cs:517`：只在 `ArcExpressions.IsCurrentOurs()`（我们那个角色）+ 店 OPEN + 非自己发起 + 未成交时拦截，其余 `return true`。
- 群友 `FreyaExpressions.cs:579`：只处理已注册差分表情集的角色（伞萝萝/塞壬），`set == null` 直接放行，原版客户与剧情线一律不拦。

**结论**：这一处三方重叠是"条件互斥型"，不是"抢执行型"。以后写 Patch 要主动做成这种形态——**Prefix 第一句先判"这是不是我的场景"，不是就 return true**（Container Link 也是同一套做法：`if (!IsLinked) return true;`）。

### 第三方框架在我们改过的方法上也有补丁（2026-11-27，Probably Extend Framework）

`Probably Extend Framework`（工坊 3841909877，立绘/贴图引擎框架）在 **`SpriteDict.GetSprite`** 上同时有：

- 一个**会短路的 Prefix**（`PlanPort.Prefix`：key 是 `texext_*` 或 `IsExtra(key)` 时 `return false`）；
- 一个 **Postfix，在 `Plan.Mode == Original` 时会把 `__result` 覆写成原版图**。

我们两个模组（`ArcPortrait.cs` / `FreyaPortrait.cs`）在同一方法上也各有一个**会短路的 Prefix**（key 是我们的、但字典里丢了 → 补注册后 `return false` 给图）。

**真实风险**：Harmony 里 `Prefix return false` 只跳过原版方法体，**Postfix 照样执行**。所以框架那个"覆写成原版图"的 Postfix 有可能把我们刚自愈出来的立绘覆盖掉。

两条处置：
1. **排序别写错**：该框架用的是 `new Harmony("Lune.ProbablyExtendFramework")` —— **裸 id，不是 `"mod." + manifest.ID`**。想跟它排序必须 `[HarmonyAfter("Lune.ProbablyExtendFramework")]`，写 `mod.` 前缀根本匹配不到。
2. **用兜底 Postfix 加固**（我们已做）：在我们的自愈 Prefix 之外再挂一个 `Priority.Low` 的 Postfix，只要"key 是我们的且 `__result` 不是我们的图"就再补一次——不管谁在后面覆写过，最终结果都是对的。

> 通用教训：**给原版方法挂 Prefix 时，一定要假设"别的模组可能会在 Postfix 里改返回值"**。要保证结果，就得在自己的 Postfix 里再确认一次，而不是只靠 Prefix 的短路。

| `StoreUIManager.Update` | ContainerLink / Machine Link / Liquid Pipe Hub + 群友 + 电玩 | ⚠️ 谁先跑随缘（每帧方法，靠"各自只做自己的事"） |

**判断与处置（诚实记录）**：

- `SpriteDict.GetSprite` 已经是**工坊换立绘的公共入口**，5 方叠加是常态。我们**不去硬编码 `HarmonyAfter` 到那两个工坊模组**（它们不是我们的依赖，id 也不稳定），因为：
  1. 我们已用 `Priority.Low` 的**兜底 Postfix**，会在所有 `Priority.Normal` 的 Postfix 之后执行 → 只要对方的 Postfix 用默认优先级，我们就能最后修正；
  2. 我们的 Prefix/Postfix 都**只认自己的 key**（`ArcPortrait.IsOurKey` / `IsOurPortraitKey`），别人的 key 一路 `return true` 放行。
  这两条合起来等于"**不管谁先谁后，我们的图最终一定在**"，比依赖排序更稳。
- `DismissCurrentClient` 上联机模组没声明顺序，我们**管不了**（它的 Patch 有自己的守卫：真人顾客场景）。我们的守卫是"当前不是我们的人就放行"，两类顾客互斥，实际不打架。
- `StoreUIManager.Update` 五方共用，是**性能**问题不是语义问题；任何新增 `Update` Patch 都要按"已有 4 个"的预算来算。

### 与「鉴定助手 Appraisal Assistant」共存的红线（2026-11-27，45 万订阅的那个）

它是工坊里最"防守型"的模组：**不对外暴露任何服务**（49 个类型只有 2 个 public），兼容手段是三层"宁可不说话"——① 硬编码 IL 指纹（SHA256→Base64）② `Harmony.GetPatchInfo` 沿依赖图递归查补丁 ③ 外来鉴定规则不在对方程序集里执行、只用自带 IL 解释器算。**任一处被"污染"，它就显示"当前估价规则尚未核验"，绝不给错的数。**

**后果：只要我们在它的指纹方法上挂了补丁，它对"第三方注册的鉴定品类"就整体闭嘴**（原版三品类走另一条直接调用分支，不受影响）。

### 工具链事故：CLI 子命令忘了 return，往工坊建了 4 个空物品（2026-11-27，已清理）

`WorkshopUploader` 里给"研读别人模组"加的 `--sub` / `--unsub` 分支**没有 return**，于是订阅/退订成功后继续往下走，进入 `CreateItem()` + `SubmitItemUpdate()` —— **在玩家自己的创意工坊里创建并提交了空物品**。

实测后果：4 个私有、0 字节、无标题的空物品（`3846690177` / `3846699004` / `3846720992` / `3846725035`），玩家看不到（私有），但污染账号。已用新加的 `--delete` 全部删除，复查只剩两个真模组（`3846263756` 群友 9.63 MB / `3846263529` 电玩 5.91 MB）。

| 教训 | 具体做法 |
| --- | --- |
| **每个 CLI 分支必须 return** | 命令式 if 链里，每处理完一个分支就 `return`，别让它"落"到后面的默认路径 |
| **破坏性默认路径要有守卫** | 在"默认落到上传"之前加前置校验：既没有 `--content` 也没有 `--id`/`--verify` 就直接报错退出。**默认行为永远不该是"创建线上资源"** |
| **线上写操作要可自查、可回滚** | 工具必须自带 `--list-mine`（列自己发布的物品）与 `--delete`（删自己发布的），否则误创建后无从下手 |
| **日志里意料之外的动作行要当红灯** | 这次是 `[submit] 提交成功` 出现在 `--sub` 的日志里才被发现。过滤日志时**别把不认识的行动行过滤掉** |
