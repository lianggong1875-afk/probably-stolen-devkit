# 03 原版接口速查

宿主反编译快照在 `共享开发\reference\Assembly-CSharp\`（**只读参考，不参与编译**，游戏更新后要重新核对）。下面每条都标了文件名，要精读就去那里看。

## 物品

| 想干什么 | 用哪个 |
| --- | --- |
| 造一件空物品 | `ItemDirectory.CreateEmptyItem()` |
| 按 id 造（目录里的） | `DirectoryMaster.Create<GameItem>(id)` |
| 列出所有物品 id | `DirectoryMaster.GetIdentifierList<GameItem>(null)` |
| 挂模组贴图 + 算占格 | `GameItem.SetSpriteAndShapeFromMod(modId, spriteKey)`（见 `GameItem.cs`） |
| 只换贴图不算占格 | `GameItem.SetSpriteAndShape(atlasPath, spriteName)`（原版图集用） |
| 直接钉死占格 | `item.SetShape(new GridShapeBuilder().SetData(cells, w))`，格 = `UISettings.current.gridSize`（16px） |

`SetSpriteAndShapeFromMod` 内部第一句是 `ModLoader.Mods.Find(m => m.Manifest.ID.Equals(modId))`，**不判空**：热重载后 `ModLoader.Mods` 里会留一条 `Manifest == null` 的登记，这句直接 NRE，整个物品工厂从第一行抛异常，宿主返回空白占位物品（名字空、紫问号、价格 0）。我们的 `ArcSpriteFix` 用 Prefix 接管了这一步。

占格采样的坑：原版按每格**正中心 1 个像素**判实心，中间镂空的图案（光盘盒中心孔、风扇、散热格栅）会被算成空格 → 柜台穿模。我们改成**区域采样**（去 2px 边距，格内 alpha>0.1 的像素 ≥8 就算实心），外加"一格都没采到就整块实心"兜底。

## 贴图到底从哪来（排障必读）

原版渲染模组物品走 `GameItemElement.ResolveSpriteByName`（`GameItemElement.cs`）：

```
if (useSpriteFromMod) → ModLoader.Mods.Find(m => m.Manifest.ID == spriteAtlasPath).Sprites[spritePath]
else                  → RenderHandler.LoadFromAtlas(spriteAtlasPath, spritePath)
```

而 `RenderHandler.LoadFromAtlasRaw` 只有一句 `Resources.LoadAll<Sprite>(atlasPath)`——**只查 Unity 打包资源，从来不查模组贴图**。

所以：任何"第三方用自己的方式读物品图标"的代码（比如护肝修改器 `DeepSpaceTrainer` 的 `GetItemSprite`，它走 `RenderHandler.TryLoadFromAtlas`）在我们物品上都会拿到 `unknownSprite`（`Items/itematlas` 的 `unknown`，就是那个问号）。**这是对方没走 `useSpriteFromMod` 分支，不是我们的数据错。**

## 条件与特征（真伪系统的地基）

- `ItemFeature` 有 `category`、`realCondition`、`fakeCondition`、`WillClientExposeFeature()`。
- `ItemFeature.WillClientExposeFeature()`：`realCondition.modValue < fakeCondition.modValue`（真实比伪装差才算"值得识破"）。
- 找特征：`item.FindItemFeatureByCategory(categoryId)`。
- **判定只认 `realCondition.identifier`**；`fakeCondition` 是"印在标签上的那层"，也就是玩家能看见的那层。名字、显示条件、贴纸文字都在公开层，标签打印机能把它们全改成"正版"。

## 客户识破假货

调用链（`StoreClient.cs` / `ItemFeature.cs`）：

```
StoreClient.ClientExposeFeature()
  → StartDialogue(feature.GetClientExposeDialog())
  → StoreReputation.ModReputation(faction, -4)
  → feature.ExposeFeature(lowkey: true, playBad: true)     // 价格从伪装的掉到真实的
```

`GetClientExposeDialog()` 里台词走 `CreateCustomerConfrontDialog()`，按 `category` 分支；**没写的 category 有兜底**：`dialog_expose_label_generic` =「这标签是骗人的。我按实际的算。」——所以不会 NRE，也不会有空台词。

给新品类补台词的正确做法：挂 `CreateCustomerConfrontDialog()` 的 **Postfix**，只在自己的 category + 真实条件命中时换那一句，别的原样返回。

### 谁会识破：能力清单，不是概率（2026-11 查证）

**原作没有「鉴别力」数值，也没有 roll。** 判两问：这件货值不值得识破 × 这位客人有没有那个本事。

值不值得（`StoreClient.CanClientExposeThisFeature`，`StoreClient.cs` 715-743）：`isDisabled` / `IsFeatureMatch()`（真假一致）/ `!IsRealFeatureCheaper()`（真实不比标称差）/ `IsExposed()`（已曝光）任一成立就直接 false。**所以「正版贴盗版标」不会被抓，「盗版贴正版标」才会。**

有没有本事（`ClientCanExposeFunc`）：九档静态函数，**每档就是一份「能查的 category 清单」**：

| 档 | 查什么 |
| --- | --- |
| `BasicClientExposeCapacity` | 水质手电 + 香烟 |
| `TouristClientExposeCapacity` | 水质手电（最弱，连香烟都不查） |
| `ULClientExposeCapacity` | 水质 + 注射器 + 化学品 |
| `ScavClientExposeCapacity` / `LLClient…` / `SecClient…` / `RevClient…` | 水质试纸 + 香烟 + 注射器 + 化学品 |
| `TradeBoardExposeCapacity` | **通查**：`conditionLookup` 里任何 category，只要 `!IsFeatureMatch()` 就识破 |
| `ALLExposeCapacity` / `OdinExposeCapacity` | 各自更窄或更宽的固定组合 |

**关键**：赝品 `CATEGORY_REPLICA`、假印花 `CATEGORY_GENUINE_STAMP`、开盒 `CATEGORY_OPEN_BOX` 只有 `TradeBoard` 那档在查——所以普通散客、游客、上层区客人**看不出贴假标**，这是原版刻意的强弱设计。自定义品类要接进这套，就写一个同构的能力清单函数。

谁挂档位：`StoreClient.CompleteClientCreation(bool IgnoreExposeFunc = false)` 按 `IsTag("SCAV")` → `clientFaction`（LOWER_LEVEL / BLACK_MARKET → LL，TOURIST → Tourist，SECURITY → Sec，UPPER_LEVEL → UL，其余 → Basic）自动挂。

⚠ **`IgnoreExposeFunc: true` 的副作用**：它跳过的**不只是**识破档位——同一段函数里后面那套 `noAcceptingContraband` 禁收计算（`isSecurity`、SCAV 按声望概率、`LOWER_LEVEL_CITIZEN` 35%）也一起被跳过。想让原作的禁收规矩生效就别传 true；要自定义识破能力，就在 `CompleteClientCreation()` **之后**包装它（先跑原档、再判自己那档），而不是替换 —— 替换会把这客人对原版货（水/香烟/注射器）的眼力一起抹掉。

## 禁收（客户拒收某件货）

`StoreClient.IsClientRefusingItem(GameItem, bool ignoreContents = false)` 是**一票否决**，且 `IsClientBuyingThisItem` 第一条就调它 —— **先于** `clientBuyingTagList` / `clientBuyingIdList` / `willAcceptItem` 所有正面条件。所以「这个客人绝对不收什么」只能写在这里；写 `willAcceptItem` 是白写（那是 OR 链里的正项，只要留一条宽泛标签就整体绕过去了）。

它认的字段全是现成的：

| 字段 | 判据 |
| --- | --- |
| `clientBlackIdList` | `gameItem.identifier` 精确命中 |
| `clientBlackTagList` | `gameItem.GetGameItemType()`（= `itemTypes`，**不是** `IsTag`）命中 |
| `noAcceptingContraband` | `ContrabandHelper.IsContraband()`，即物品实例有没有 `CONTRABAND_ITEM_TAG` |
| `isRequireVariety` | `IsItemInVarietyList` |
| 其他 | 化学品等级门槛、危废、危险水标签、奢侈品、内容物递归 |

注意 `clientBlackTagList` 比的是 **itemTypes**（`SetGameItemType` 那套），不是 `EnableTag` 的实例标签 —— 只 EnableTag 的物品挂黑名单不会命中，得用 `clientBlackIdList`。

身份初始化别手写阵营字符串，用 `StoreClientFactionSetup.InitScav / InitWorker / InitLowerLevelCitizen / InitSecurity / InitUpperLevelCitizen / InitTourist / InitRev / InitBlackMarket`：它同时设 `clientFaction` 和对应 tag，`CompleteClientCreation` 才认得出该挂哪一档。

## 事件与日程

`StoreEventManager`：

| 成员 | 说明 |
| --- | --- |
| `activeEvents` / `futurEvents` / `futurEventsDay` / `eventTracker` | 两条表并列（事件对象 + 相对天数），遍历要同时维护 |
| `HandleFuturEvent()` | 每天先把未来队列每条 wait 减一，减到 0 当场 `ActivateEvent`（第一件事是 `IsKnown = true`） |

## 机器类物品：周期只在「过夜」跑一次（2026-11-26 真机实测，同日补正）

- **夜晚回调有三个，不是只有一个**。`PlayerStore.EndNight()` 分三段在 `FindAllItem()` 上跑：

  | 段 | 源码位置 | 回调 | 时机 |
  | --- | --- | --- | --- |
  | 早 | L1705 | `onCycleEndEarlySlotItemFunc` | 服务扣费之前 |
  | 主 | L1757 | `onCycleEndSlotItemFunc`（前面先跟一次 `StolenHelper.UpdateStolenItem(i)`） | 服务/事件全都处理完之后 |
  | 晚 | L1763 | `onCycleEndLateSlotItemFunc` | `MachineFridge.HandleColdFeatureExpiry()` 之前 |

  三段的顺序**有语义**：冰箱保冷标记、部分机器产出都挂在早段/晚段上。**只调中间那一个就是漏逻辑。**

- **游戏自带「跳过夜晚（机器部分）」**：`DebugPanel.SkipNightMachine()` 是 `public static`，内部就是这个顺序，外加 `MachineFridge.ClearColdMarkers()` 和 `HandleColdFeatureExpiry()`。要模拟一晚，**调它比自己按 `EndNight` 抄一遍可靠**。

- **`FindAllItem(bool isOwn = true)` 默认只返回带 `IS_OWNED_TAG` 的物品**。要扫「世界里实际存在的全部东西」（含丢了 owned 标记的、别人扔在地上的），必须传 `false`。以前所有"扫不到某件东西"的判断，都要按这个参数重新看一遍。

- `FindAllItem()` 扫 `frontInvWindow / backInvWindow / backInvinvElementCounter / invWindow / showcaseWindow / trashInvWindow / docInvWindow / hiddenWindow / afterhourWindow / vendingFountainWindow / vendingMachineWindow`（最后 `Distinct()`），
  所以**背包里的机器也会做工**，不必摆到柜台上；但**游离机器**（`ItemSpawner` 造出来没进任何容器）一个都不在这些窗口里，永远不会被扫到。
  —— 一台机器一晚在主段只做一次工，白天放料后状态停在 `STATE_READY` 是正常的。
- `ContinueProgressTypeMachine(m)` = `MACHINE_PROGRESS_CURRENT_TAG += CURRENT_PROCESSING_SPEED_TAG`。
  `InitProgressTypeMachine(m, baseSpeed)` 的第二个参数就是「每天干多少」。原版 target 常见 150/125/100/75/60/50，**要多晚完成是原版设计**，不是 bug。
- `StartProgressTypeMachine(m, sourceItem)` 会把 `MACHINE_STATE_TAG` 设成 `STATE_WORKING`、CURRENT 归零、target 取自 sourceItem 的 `PROGRESS_ITEM_TARGET_TAG`。
- `CanStart(sourceItem, machine)` **只校验 requiredMachineTag**；`HasRequiredAdditionalItems` 只做「在场检查」；
  真正吃掉附料的是 `ConsumeRequiredAdditionalItems`（逐个 `Destroy()`）。**想锁住输入就别调它。**
- **分选机的进度/状态用另一套 tag**，而且游戏自己的拼写不一致：常量叫 `DESEQUENCER_PROGRESS_TAG`、值却是 `"DESEQUQUENCER_PROGRESS_TAG"`（双 C），状态是 `"DESEQUENCER_STATE_TAG"`（单 C）。**读值时用双 C 的那个字符串**，别照常量名拼。

## 进度可见性的原版范式（照抄 MachineDesequencer）

```csharp
// 开工
StartProgressTypeMachine(machine, chipSlot.childItem);
ContinueProgressTypeMachine(machine);
inputSlot.childItem.SetSpriteAndShape("Items/items_misc", "blank_card_wip");
GeneralHelper.LockItem(inputSlot.childItem);                       // 锁定，不是消耗
inputSlot.childItem.shortDescription = "… " + cur + "/" + total;   // 悬停即可读进度
// 完成
GraphUtils.EmporiumTryAdd(outputSlot, DirectoryMaster.Item(targetId));
inputSlot.childItem.mayInventoryRemoveItemFunc = (_, _) => true;
inputSlot.childItem.Destroy();
```

**反例**：开工那一刻直接 `ConsumeRequiredAdditionalItems` → 机器里立刻空掉、鼠标没有东西可悬停，
玩家只看到「一台在动的机器」，两晚后突然冒出成品，完全不知道进度走到哪。

## GraphUtils.EmporiumTryAdd 会兜底，不能当「进了指定槽」的证据

`EmporiumTryAdd(node, item)`：先试 `node`，失败依次落 `afterhour → backInv → inv → showcase → frontInv`，全满才 `DestroyIfUnplaced`。
所以 `item.parentInventory != null` 完全可能只是**被背包吞了**。
要精确投放到某个容器，用 `GraphUtils.CanAccept(node, item)` + `GraphUtils.TryAccept(node, item)`（受 `mayInventoryAddItemFunc` 约束、不兜底）。

同理，`ItemSpawner.Spawn(id)` 造出来的是**游离幽灵实例**：`parentInventory` 永远空、`FindChildrenType` 数到的是它自己那几个空容器、
也永远不会被 `FindAllItem()` 扫到。要动**真实**那台机器，请走 `PlayerStore.Instance.FindAllItem()` 按 identifier 找。

## 机器动画：靠状态轮询，不要只靠事件

`MachineProgressHelper.StartProgressTypeMachine` 是**开机那一次**的事件。读档时机器早已 `STATE_WORKING`，
事件不会再来 —— 只在那里登记动画，八帧就永远不动。Vanilla Machine Animations 的做法是每 150ms 轮询
`GetMachineState(item) == "STATE_WORKING"`，并以 `GameItemElement`（UI 元素）为 key 只驱动屏幕上看得见的那些。

## 物品发放：三个入口语义完全不同

| 入口 | 做了什么 | 用途 |
| --- | --- | --- |
| `DirectoryMaster.Item(id, isOwned = true)` | `Create<T>` 新实例 → **强制剥掉所有子物品** → `SetItemOwned` → 补 `uniqueId` → `PermitHelper.OnNewItemCreated` | 真正发一件物品。给玩家 `true`，给 NPC `false` |
| `ItemSpawner.Spawn(id)` | 底层新建，不设 owned、不补 uniqueId、不通知许可证 | 造游离实例做只读测量 |
| `ItemDirectory.CreateEmptyItem(id)` | 空壳 | 自定义工厂内部造本体 |

- **第二参数是 `isOwned` 不是 clone**，默认 `true`，所以 `Item(id)` ≡ `Item(id, true)`。
- 剥子物品时会打 `contains child items ... Removing all child items as a fix`，所以**机器里的便签/芯片只能在发放那一刻塞**，不能写在工厂里。
- `DirectoryMaster.Item` **有两个同名重载**，patch 必须显式写参数类型。

## 电量：三个标签 + 五种电池实测值

```csharp
PowerHelper.InitPowerSourceItem(item, energy, bandwidth) 里做的事：
  item.SetGameItemType("ENERGY_CELL");                 // 这是"物品类型"，不是 tag
  item.EnableTag("power_source_item");
  item.ModifyTag("power_source_item_energy",     s => s.Enable().SetInt(energy));
  item.ModifyTag("power_source_item_max_energy", s => s.Enable().SetInt(energy));
  item.ModifyTag("power_source_item_bandwidth",  s => s.Enable().SetInt(bandwidth));
```

| 物品 | energy | bandwidth | 可充电 |
| --- | --- | --- | --- |
| `energy_credit` | 100 | 10 | 否 |
| `energy_credit_ext` | 250 | 10 | +4/晚 |
| `energy_credit_breeder` | 100 | 4 | +4/晚 |
| `energy_credit_dis` | 1000 | 10 | 否 |

判断"能不能当电池用"（照 `BatteryTools.Supports`）：
```csharp
item.IsTag("power_source_item")
 && !HypertechBatteryHelper.IsHypertechBattery(item)
 && !CurrentConverterHelper.IsCurrentConverter(item)
 && item.IsTag("power_source_item_energy")        // IsTag 判存在性
 && item.IsTag("power_source_item_max_energy")
 && item.GetTagReadonly("power_source_item_max_energy").GetInt() > 0
```
`GetTagReadonly` 对**不存在的标签返回默认 0**，所以"读出来是 0"不等于"标签不存在"，要判存在必须用 `IsTag`。

## 枚举目录：`DirectoryMaster.GetIdentifierList<T>`

```csharp
public static List<string> GetIdentifierList<T>(string dictionaryClassName = null) where T : DirectoryEntry
// 内部：directories[typeof(T)] → item is Directory<T> → list.AddRange(directory.factoryDictionary.Keys)
```

## 物品对物品交互（拖 A 到 B）的完整判定链

原版把"把一个物品拖到另一个物品上"拆成三条独立通道，**任一通过即可**（OR，不是 AND）：

```csharp
// 前置：拥有权
sourceOwned && (targetOwned || allowNonOwned)

// 通道 1：全局行为管理器
ItemBehaviourManager.current != null && ItemBehaviourManager.current.MayTarget(src, tgt)

// 通道 2：目标物品回调（委托链，OR 归约）
tgt.mayItemTargetThisFunc != null
    ? InvokeFuncExtensions.InvokeAllReduce<GameItem,GameItem,bool>(
          tgt.mayItemTargetThisFunc, src, tgt, InvokeFuncExtensions.BoolReduceOR) != false
    : (tgt.onItemTargetThisFunc != null)      // 只有回调没有判定时，视为通过

// 通道 3：源物品
src.MayTarget(tgt) && src.CanTarget(tgt)

// 全部失败 → 拒绝。三条 OR，所以任一为真就能交互。
```

执行侧：
```csharp
ItemBehaviourManager.current.TargetTooltip(src, tgt);   // 交互预览文本
ItemBehaviourManager.current.Target(src, tgt);          // ① 全局
tgt.onItemTargetThisFunc?.Invoke(src, tgt);             // ② 目标回调
src.Target(tgt);                                        // ③ 源物品回调
```

**为什么这件事重要**：通道 3 里的 `src.MayTarget(tgt)` 内部会看 `canUseOutsideCombat`，
非战斗场景对**材料类物品**经常返回 false。只看通道 3 就会误判"拖不上去"，
实际通道 1/2 已经放行。排查拖拽失败要把三条分开打出来看。

相关 API：
| API | 作用 |
| --- | --- |
| `ItemBehaviourManager.current.MayTarget(src, tgt)` | 全局判定 |
| `ItemBehaviourManager.current.Target(src, tgt)` | 全局执行 |
| `ItemBehaviourManager.current.TargetTooltip(src, tgt) → RichTextBuilder` | 交互预览 |
| `GameItem.mayItemTargetThisFunc` / `onItemTargetThisFunc` | 目标物品的判定/回调（多播委托） |
| `GameItem.MayTarget(other)` / `CanTarget(other)` / `Target(other)` | 源物品侧三件套 |
| `InvokeFuncExtensions.InvokeAllReduce<A,B,R>(del, a, b, reducer)` | **多播委托归约**（原版工具，处理 `Delegate.Combine` 出来的链） |
| `InvokeFuncExtensions.BoolReduceOR` | OR 归约器 |
| `GameMaster.current.InCombat()` | 是否战斗中 |

## Unity 假 null 的标准检测

```csharp
var u = obj as UnityEngine.Object;
if (u != null && u == null) return "null (destroyed)";
```
- `u != null` —— C# 引用还在
- `u == null` —— Unity 重载的 `==` 说底层 native 对象已经销毁
两个同时成立，就是**"引用还在但对象没了"**的假 null。

⚠ 对象句柄要跨轮持有（比如探针缓存一批 `GameItem`），必须用 `WeakReference<T>` + 版本号，
否则拿到的是已销毁对象，后续调用会抛或静默做错事。参考实现：`ObjectHandleRegistry`
（`Id` + `Version` + `WeakReference<object>` + 类型名 + 注册时间，注册时 `PurgeDeadReferences()`）。

## 造临时物品必须销毁，否则残留幽灵 UI

`DirectoryMaster.Create<GameItem>(id)`（以及任何造出实例的路径）会**创建 `TreeNodeRender` UI 对象**。
用完不 `Destroy()`，屏幕上会永久留下看不见但存在的 UI 节点。所以探针/测试里造实例一律 `try { … } finally { temp.Destroy(); }`。

## 游戏自带一张调试动作表，可以列也可以调（2026-11-26 查证）

游戏里有 `CustomUIDebugPanel`（全局命名空间，`public static class`），内部：

```csharp
private static readonly List<Entry> entries = new List<Entry>();   // private
private class Entry { public string category; public string name; public Action action; }  // 私有嵌套类，字段是 public
```

也就是说，**游戏自己维护一批带分类的调试动作，每条就是一个 `Action`**。分类常量一共 13 个：
`Store` / `Command` / `Spawn` / `Special` / `Modding` / `Scene` / `Kits` / `Items` / `Customers` / `Marketing` / `Butcher` / `Lou` / `Eleanor` / `Serpico`。

**对做验证的价值**：这些动作是游戏开发者自己写的，调它们等于"用户点调试面板"，比自己拼一串 API 稳得多。`entries` 和 `Entry` 都是 private，要反射读（`BindingFlags.Static | NonPublic` 拿字段，再按 `Instance|Public|NonPublic` 取 `category`/`name`/`action`）。桥的 `debug_actions` / `invoke_debug_action` 两个工具做的就是这件事。

**对做模组的价值（更好用的一条）**：这两个是 **`public static`**，不用反射：

```csharp
CustomUIDebugPanel.Add(category, name, action, tall, source, info);  // 往面板里挂自己的动作
CustomUIDebugPanel.Remove(source);                                    // 按 source 整组撤掉
```

所以要在模组里做调试入口，用 `source: "DeepSpaceArcade"` 挂一批、卸载时 `Remove("DeepSpaceArcade")` 一次全撤，
比自己搭调试 UI 省事，而且玩家能在原版面板里直接看到。⚠️ 这类入口**只能留在开发期**，正式候选里要去掉。

另外 `CustomUIDebugPanel.Toggle()` / `Open()` / `OpenModdingPanel()` / `OpenMarketingPanel()` / `OpenStoryPanel()` 也都是 public，可以直接开面板。

## 化学模拟：360 tick 与温度模型（蒸馏 SleepLagOptimizer）

- `ChemicalHelper.RunNightlyChemicalSimulation()` 遍历 `EmporiumEntry.Instance.GetAllItems()`，对每个有 `onOneSecondItemFunc` 的物品**跑 360 次**。
- `GameItemFunc.onOneSecondItemFunc` 是 `Action<GameItem, GameInventory, SlotMarker>` —— **原版给我们的现成每秒心跳**，做"实时机器"就用它，别自己起协程。
- 容器温度标签 `CONTAINER_TEMP_TAG`（double，℃），向 **26℃** 指数回归；速率 `0.05 / (sqrt(体积) + 11)`，每秒衰减 `exp(-k*125)`（后半段为作者拟合值）。
- 相关标签：`HEATING_TAG`（正在被加热）、`LIQUID_CONTAINER_TAG`（是液体容器）；液体含量在 `Liquid.currentPart` 标签里（int mL）。
- `Liquid.Liquids` 是全部液体表；每条有 `identifier` / `displayName`（**可变，别缓存**）/ `isEvaporative` / `boilingPoint`。
- 工具函数：`WaterHelper.IsEmpty(item)` / `WaterHelper.GetTotalVolume(item)`。
- **原版 bug**：`ChemicalHelper.HandleBoilingReaction(GameItem)` 什么都没煮沸也返回 1 → 每个非空液体容器每秒触发 `OnLiquidChanged` + UI 重绘。修复版逻辑：无蒸发液体或温度未超沸点 → 返回 0。

## 零 Harmony 接管交互：`GameItemFunc` 的 51 个委托属性（第二批，Pipeline Controller 蒸馏）

想把"把 A 拖到 B 上"这种交互做成自己的功能，**不需要 Patch 任何拖拽处理器**——物品自带的 `GameItemFunc` 上有六个可赋值委托：

| 委托（**已核对确切拼写**） | 语义 |
| --- | --- |
| `mayItemTargetItemFunc` / `canItemTargetItemFunc` / `onItemTargetItemFunc` | A 拖到 B（`Func<GameItem,GameItem,bool>` / `Action<GameItem,GameItem>`） |
| `mayThisTargetItemFunc` / `canThisTargetItemFunc` / `onThisTargetItemFunc` | 别的物品拖到**我**上 |
| `mayItemTargetThisFunc` / `canItemTargetThisFunc` / `onItemTargetThisFunc` | **我**被拖到别的物品上 |

> 之前写"六个"是错的，实际是**三组共九个**（已按 `GameItemFunc.cs` 核对）。Pipeline Controller 就是靠这九个实现"拖机器到控制器=加节点"及其反向，**机器周期零 Patch**（它只有 5 个 Harmony，全在外围）。

`GameItemFunc` 上**一共 51 个委托型 public 属性**，其余同样极有用的一批（全部已核对存在）：

| 领域 | 委托 | 用途 |
| --- | --- | --- |
| 容器准入 | `mayInventoryAddItemFunc` / `mayInventoryRemoveItemFunc` | 这件物品能否进/出某个 inventory |
| 堆叠 | `mayStackItemFunc` | 能否与另一件堆叠 |
| 槽位数量 | `maxSlotAddItemFunc` / `maxSlotRemoveItemFunc` / `maxSlotAmountItemFunc` / `minSlotAmountItemFunc` | 一次能进/出多少 |
| 槽位事件 | `onSlotAddItemFunc` / `onSlotRemoveItemFunc` / `onSlotChangeAmountItemFunc` / `onChangeAmountItemFunc` | 进/出/改量时通知 |
| 槽位调度 | `slotPriorityFunc` / `slotSearchPassthroughForItemFunc` | 优先落哪个槽 / 是否透传给子容器 |
| **父子修饰** | `parentItemShapeModifierForItemFunc` / `parentItemSpriteModifierForItemFunc` / `parentItemStateModifierForItemFunc` / `getItemSpriteModifierForItemFunc` | **子物品改变父物品的形状/贴图/状态**（"机器里装模组、机器外观随之变"的官方口子） |

## 模组启用状态与审核机制（第二批，五源互证，详见 `workshop-distill\模组列表管理五例.md`）

**不在** `Mods\` 目录、**不在**工坊目录、**不在** PlayerPrefs。真正的状态在 **Easy Save 3 的 `%persistentDataPath%\SaveFile.es3`**（扁平键 → `{__type, value}` 表，一行 JSON）。关键键：

| 键 | 类型 | 含义 |
| --- | --- | --- |
| `modOrder` | `List<string>` | **同时是"启用集"和"加载顺序"**；不在列表里 = 未启用 |
| `modTrust` | string（内嵌 JSON） | `{"records":[ModTrustRecord…],"stopped":[…]}` 审核记录 |
| `modTrustMac` | string | 上面那段 JSON 的 **HMAC-SHA256**，防手改 |
| `workshopOwners` | string | 工坊项 → 作者 SteamID 缓存 |
| `modUiWarningAcceptedVersion` | int | 玩家已接受的模组警告版本（当前 2） |

**两条硬事实**：
1. **只能重启生效**：`ModLoader.Awake()` 里 `_modOrder = ES3.Load<List<string>>("modOrder"); EnabledMods = new HashSet<string>(_modOrder);` —— 读完就不再回盘。
2. **读安全、写危险**：`modTrust` 带 `modTrustMac` 校验，直接改会被判篡改（工坊里"一键应用模组配置"的模组都是靠"引导玩家手点 + 只读比对"或"改写后同步重算 MAC"两条路，后者风险高）。

**对我们的用处**：
- 做自动化测试时，**读** `modOrder`/`modTrust` 判定"这台上装了哪些模组"是安全的；
- 想做"按预设切换模组组合"的工具，优先做"只读比对 + 引导玩家在游戏里点"，不要直接改 es3。
- 我们自己模组的"读档兼容性检查"可以反解**存档里记录的模组清单**（`Save Slot Mod Manager` 与 `Mod Changes` 都这么做），比读 es3 更稳。

## ⛔ 模组状态的三条硬红线（2026-11-27 五源互证 + 实测存档验证）

**① `[ModRestricted("loader-target")]` 是一票否决的禁区。**
原版 `ModTrust.Approve` / `ModLoader.SetModEnabled` / `ModLoader.ReorderMods` / `ModLoader.ApproveAndEnable` 全部带这个标记：**编译进 DLL 的调用点在 `ModScanner` 里直接命中 → 模组被判 `Refused`；运行期调用则抛 `UnauthorizedAccessException`。**
→ 我们的模组**任何时候都不许调用它们**，也不许"为了做模组管理器"去反射调。

**② 连 `ES3.Save("modOrder", …)` / `ES3.Save("modTrust", …)` 这种字面量键调用都会被 Hard 掉**（`ModScanner.cs:69,701-717`）。
分水岭很清楚：

| 做法 | 结果 |
| --- | --- |
| 用 `System.IO` 直接改 `SaveFile.es3` 文件 | 只被标 `files` 能力（可发但风险高） |
| 用 `ES3.Save("modOrder"/"modTrust", …)` | **被 ModScanner 硬拒（Refused）** |

**③ `modTrustMac` 是机器绑定的 HMAC，手改必被清空。**
密钥 = `SHA256("dse-mod-trust-1|" + deviceUniqueIdentifier + "|" + persistentDataPath + "|" + productName)`，再作 `HMACSHA256` 的 key；`modTrust` 校验不过 → **原版直接清空全部审核记录**（玩家要重新审所有模组）。字段包括 `id/source/workshopId/manifestHash/files/combinedHash/folderHash/declared/detected/gameVersion/approvedAt/updatedAt/developerMode/scannerVersion(=4)`。

**④ `modOrder` 的顺序只影响"模组菜单展示顺序"，不影响加载时序。** 真时序 = 本地 `Mods\` 目录枚举序 → 工坊项 → `Prerequisites` 拓扑。所以"靠排顺序改变加载先后"是无效操作。

**对我们的实际结论**：
- 我们自己的模组**永远只读**这些键（`ModLoader.Mods` / `IsModEnabled` / `LoadedMod.TrustState` / `RestartRequired` 都是零能力公开面）；
- 想做"开发期批量切模组"这类工具，**只能做成游戏进程外的独立小工具**去改文件（改 `modOrder` 无需重签、改 `modTrust` 必须重算 MAC），不能塞进游戏内模组；
- 别学 `Mod Preloader` 的伪造手法（它用 `new string(char[])` 拼键名规避扫描器）——那是"避检测"，踩线。
