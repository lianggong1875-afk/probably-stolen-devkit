### 0.1 2026-11-27 把对方的桥反编译读了一遍：结论不变，且多了一条硬理由

蒸馏档案：`workshop-distill\桥接器与开发框架两例.md`（MCP Bridge 3834799226，20 个 .cs / 7706 行）。

**它的问题（都是读码确认，不是猜）**：

| 项 | 它的实现 | 我们 |
| --- | --- | --- |
| 传输 | `HttpListener` 双前缀 `127.0.0.1` + `localhost`，端口 28910；失败降级裸 `TcpListener` 手写 HTTP | 只绑 loopback + 校验 `Origin` + 实例校验 |
| 鉴权/限流 | **零鉴权、零限流**，`Access-Control-Allow-Origin: *` 且**不看 Origin** → **本机任意网页都能驱动你的游戏** | 三重校验（loopback / Origin / 实例） |
| 工具契约 | 24 个工具，手写 `JObject` schema，`tools/call` **服务端不校验**（`required` 只是文字） | 声明式契约 + 递归 `Validate` + 结构化信封 |
| 主线程调度 | 自建 MonoBehaviour + ConcurrentQueue，**每帧只出队一件**；协程在跑时整队停摆；无 operationId、无幂等、无 world 绑定 | OperationQueue 状态机 + UUID 幂等 + world 绑定 |
| 超时/取消 | 15s/30s CTS，**取消只在执行前生效**（已启动的协程照跑完） | 「超时 ≠ 取消」显式语义 + partial result |
| 写安全 | 无白名单、无干跑，靠 6 道就地兜底 | 白名单 + 干跑 + 落点校验 |

> ⛔ **这一条要记住**：它的 `CORS: *` + 不看 `Origin` 等于**把整个游戏暴露给浏览器里的任意网页**（跨站请求就能读写你的存档物品）。我们的三重校验**不能退**，任何时候都不要为了"方便调试"把 `Origin` 校验关掉。

**可以白捡的三条（已记，尚未实施）**：
1. **热重载收尾自动跑一次 `ModScanner` 自证能力**（它在 `reload_mod_assets` 里就这么干）——我们 `reload_mod` 之后目前是人工去查能力。
2. **日志改用 `Application.logMessageReceivedThreaded`**（我们用非 threaded 版本，抓不到后台线程的异常）。
3. **失败信息按「通道 / 阶段」分条归因**（它在 `simulate_drag_target` 里做三通道诊断）——比一句 `isError: true` 有用得多。
4. 白捡两条小的：单次写操作自带 before/after diff；源物品快照指纹 + 重试上限。

## 3 四条核心契约

1. **世界绑定**：所有引用（`item_ref` / `customer_ref` / `target_ref`）都是 **world-bound**，跨 world 一律报 `belongs to a previous world`。桥重启、读档、换档都会换 world。引用有寿命（客户 ref 512 秒 / 5 分钟）。
2. **世界变了就停**：`run_test` 中途 world 变化 → `World changed during the test; no further steps were executed`。
3. **会话是单例**：`open_test_session` 只有一个。`testSlot` 如果显式传，**必须与已载入槽位一致**，否则 `Explicit testSlot must match the loaded save slot`。
4. **清理不是回滚**：`close_test_session` 只管它登记过的资源。原生 RNG、冷却计时器、延迟生成客、第三方钩子、自动存档都可能活过实验。

## 4 热重载开发循环（本桥最值钱的东西，📄 未实测）

### 4.1 模组要做的事：加两个方法

桥的完整契约原文（从 DLL 挖出来）：

> Switch an enabled MOD to an agent-compiled, uniquely named DLL staged in moduleDirectory. **Requires session/world and matching entry class plus `public void HotReloadPrepare()` / `public void HotReloadActivate()` on both versions.** Hooks declare support, not verified safety. Returns stages, actual loader references and patch-owner observations; gameplay effect remains `not_checked`. Compensation is limited. Session close retains replacement; assemblies remain until restart. **MOD callbacks/resources/assets are not automatically migrated.**

所以只要 `DeepSpaceArcade` 的 `IMod` 实现类上有这两个 public 方法，就能被 `reload_mod` 换掉：

```csharp
public void HotReloadPrepare()   { /* 解绑 Harmony patch、注销事件、销毁自建 UI、停掉自己的轮询 */ }
public void HotReloadActivate()  { /* 在新版本里重新绑好上面那些 */ }
```

**旧版本和新版本都要有**（"on both versions"）—— 换出前调旧的 `HotReloadPrepare`，换入后调新的 `HotReloadActivate`。

### 4.2 五个阶段与失败点

```
reload.preflight → reload.load → reload.construct → reload.switch → reload.observe
```

| 阶段 | 观测字段 | 失败含义 |
| --- | --- | --- |
| `preflight` | `hotReloadHooksPresent` | 缺钩子 → `Candidate is missing valid hot-reload hooks` / `reload_preflight_failed` |
| `load` | `candidateAssemblyLoaded` | 程序集标识已存在 → `Assembly name already loaded; rebuild with a unique assembly name`（**改文件名不算，得改程序集标识**） |
| `construct` | `candidateConstructed` | 候选类构造失败。⚠️ 到这一步**候选代码可能已经跑过了** |
| `switch` | `loaderReferencesMatchCandidate` | 换过去之后 loader 的引用要指向候选 |
| `observe` | `assetsReloaded`、`assembliesRemainLoaded` | 收尾观察 |

失败后一律 `reload_failed`，描述是 `Reload failed; inspect stage and compensation. Gameplay effects were not verified.`——**补偿能力有限，运行时状态不确定就重启游戏**。

### 4.3 三条硬限制

1. **程序集永久留在内存里**（`assemblies remain loaded`）。一轮开发里换 10 次就有 10 份程序集躺在进程里，改多少次名都没用。所以热重载只适合"一个功能反复调"，不适合整个下午都挂着。
2. **模组的回调/资源/资产不会自动迁移**。Unity 事件、Harmony patch、自建 GameObject、协程 —— 全靠 `HotReloadPrepare` 自己收拾干净。
3. **玩法效果一律 `not_checked`**。桥只证明"换过去了，loader 引用对上了"，**不证明行为正确**。真机可见行为还得自己验，这一点跟 [04](04-真机测试与探针.md) 的记账规矩一致。

### 4.4 用之前先空跑

`inspect_runtime kind=mods` 的返回里就有 `hotReloadHooksPresent` 和 `hotReloadVerification` 两个字段。**先看这两个字段**，确认钩子被识别了、没人真的 reload，再考虑动真格。

## 5 探针模块契约

### 5.1 最小形态

```csharp
using System;
using ModDevBridge;   // 引 sdkAssembly

public sealed class MyProbe : IStructuredDevModule
{
    public string Start() => "ready";                                  // 加载后立刻在主线程跑
    public object ExecuteStructured(string command) => new { ok = true, cmd = command };
    public string Execute(string command) => throw new InvalidOperationException("Use structured execution");
    public void Stop() { }
}
```

- 一个程序集里**恰好一个** public 无参构造的具体 `IDevModule` 实现（`Module must contain exactly one IDevModule implementation`）。
- `IStructuredDevModule` 返回 `JSON-serializable` 值，比 `string Execute` 好用。
- 资源用 `DevContext.Track(string name, Action cleanup)` 登记，**登记要在资源创建后立刻做**；`Stop`/cleanup 必须能重复调用。
- 编译引用：游戏 `Managed` 下的程序集 + `sdkAssembly`，**target 游戏的 Mono 框架，不要 net8/net10**。项目源码放桥目录外面。

### 5.2 加载的四个阶段

```
load.assembly → load.types → load.construct → load.start
```

失败有 `module_load_failed`。加载成功返回 `startResult`、`resources`、`cleanupStatus`、`assemblyStillLoaded`、`verification`。

### 5.3 ⚠️ 修正一条旧结论

[04](04-真机测试与探针.md) 里写过「**一个会话只能装一个探针**，`load_probe_module` 换第二个会失败」。这条**不准确**。桥的真实限制是：

- 「**Assembly name already loaded; rebuild with a unique name**」—— 是**程序集标识**不能重复，不是"只许一个探针"。
- 「Loaded assemblies **remain loaded**」—— 装进去就卸不掉，只能重启游戏。

所以正确做法是：**一个探针程序集里放所有命令**（我们现在就是这么干的，`ArcSummonProbe` 一个类几十条命令），需要换逻辑时编一个新**标识**的 DLL 再装一份。旧的那份还在内存里但不影响新的。

## 6 `run_test` 的步骤语言（📄 从 DLL 挖出，未实测）

```
session_id + world_id + steps[]，最多 100 步
```

已知的 step 类型与对应内部标记：

| step | 内部标记 / 失败码 | 说明 |
| --- | --- | --- |
| `wait_until` | `test.wait_until` / `wait_until condition not met` | 等条件成立 |
| `wait_frames` | — | 等 N 帧 |
| `assert` | `test.assert` / `assertion_failed` + `Assertion failed: …` | 断言，返回 `{ text, assertionVerified }` |
| `pointer_click` | `clickDispatched` | 派发点击 |
| `begin_drag` | `dragBegan` / `pointer_up_before_drag` | 开始拖 |
| `end_drag` | `dragEnded` / `ui_not_draggable` | 结束拖 |

未知步骤报 `Unknown test step`；`steps` 缺失报 `steps array required`；超限报 `At most 100 steps`。返回 `{ completedSteps, totalSteps, currentStep, currentStepIndex }`。

**价值**：这套语言能在游戏主线程里连续走"点击 → 等 → 断言 → 拖"，不受我们 Python 客户端「隔一步对象就假 null」的影响。**待实测一遍再写进工具**。

## 7 挖完整契约的方法（描述被截断时用）

`Tools/list` 的描述有长度上限，完整版埋在 DLL 里。掏法：

```powershell
python -c "
import re, io
p = r'D:\steam\steamapps\common\Probably Stolen\Mods\ModDevBridgeNext\ModDevBridgeNext.dll'
b = open(p, 'rb').read()
out = []
for m in re.finditer(rb'(?:[\x20-\x7e]\x00){40,}', b):
    out.append(m.group().decode('utf-16-le', 'replace'))
io.open('bridge-strings.txt', 'w', encoding='utf-8').write('\n'.join(dict.fromkeys(out)))
"
```

232 条长字符串里包含：**全部 30 个工具的完整描述**、所有错误码与提示语、`reload_mod` 五阶段、`run_test` 步骤名、进度/快照/配置的返回模板。想搞清楚某个工具到底做什么，比读截断描述快得多。

同样的手法可以用于任何 `.NET` 程序集的资源字符串。

## 8 坑（⚠️ 都踩过）

1. **`query_ui` 传 `limit` 返回空**，要用 `max_nodes`（1..10000）。`max_depth` 0..64。
2. **`operate_ui` 必须用 `query_ui` 当场给的 `targetRef`**，裸 `uiRef` 只能读不能点。拖拽目的地用 `observation.actionRef`（`view=nodes` 或 `get_ui_details` 里，支持只能放不能拿的节点）。内容变了会被拒 —— 重新观测，别硬点。
3. **`targetRef` / `instanceId` / sibling-index 路径会在虚拟列表重绑记录后继续存活** —— 路径顺序**不是**视觉列表顺序。`context.rootRef` 才标明来源容器。
4. **内容守卫不证明业务身份**，坐标输入根本没有守卫。
5. **`query_items` 必须给 `scope`**（`store`/`inspected`/`selected`），`root` 还要求 `store` 作用域 + 已知 root 别名。**空结果只代表"这些具名容器里没有"，不代表整个游戏里没有**。旧结论「`query_items` 在这台机器恒返回空」是用法错，见 [07](07-踩坑台账.md)。
6. **`get_inspection` 的 active 不是可见、不是渲染正确**。
7. **`operate_inspection` 换另一个物品要显式 `replace=true`**，否则 `Another item is open`。
8. **`close_test_session` 之后行为要对齐 `cleanupStatus`**，别假设干净了。
9. **`enqueue_customer` 只进队列**，客人进场还要摇铃（`StoreBell.OnClick`）。队列上限 2000。
10. **`csc` 编探针必须给唯一程序集标识**，改文件名不改标识。
11. **桥的 md 文档不在 Mods 目录**，在工坊包目录。
12. `not_observed_game_scanner_restricts_Process_API` —— 桥自己也记了：**加载器的合规扫描会限制 `Process` API**。探针里别去起外部进程。
