## 一、两家各自的架构，学什么

**SDJYBN Framework**（轻量依赖库，给别人引用）
```
Config / ConfigSection / ConfigValue<T>   类型安全配置
Module（常量）+ Framework.Boot/IsEnabled  模块开关，三级回退：配置 → 内存 → 默认 true
Log / LogHandle                           日志句柄
Interaction                               读游戏当前交互状态（只读）
Loc / LocHandle                           本地化句柄
Tooltip / TooltipScope + Patch            提示框作用域
Stack\SplitSpec / SplitMath / SplitDelivery / SplitQueue   堆叠拆分
```
学：**`_isHost` 区分本体/被引用**、**Boot 幂等**、**开关三级回退（异常一律当开启）**。

**Developer Tools**（功能型大模组）
```
<Feature>Tools     静态纯逻辑（BatteryTools / ContainerTools / CreditTools / DifficultyTools …）
<Feature>Record    数据载体（BatteryRecord / CreditRecord / DifficultyRecord …）
<Feature>Patch     Harmony 补丁，只做转发不含业务逻辑（ContainerLoadedPatch / CustomModuleUsePatch …）
WorkshopUI         集中式 UI
SpawnEngine        物品发放统一入口（就绪检查 + id 校验 + 参数校验 + 目标枚举）
```
学：**Tools / Record / Patch 三分**、**发放物品走单一入口**、**逐参数校验并给明确错误**。

**不学的**：它那套模块开关、它的 UI 体系、它的 `L.T(...)` 本地化封装。我们功能内聚在 `Arc*` 类里已经够用，硬套框架反而多一层。

## 二、就绪检查链（解决时序崩溃）

`SpawnEngine.Ready` 是整段最值得抄的东西：

```csharp
public static bool Ready
{
    get
    {
        if (PlayerStore.HasInstance
            && EmporiumEntry.Instance != null
            && EmporiumEntry.Instance.invElement != null
            && StoreUIManager.Instance != null
            && PlayerStore.Instance.playerLocation == 0)      // 0 = 在店里
        {
            if (MapUIManager.Instance != null) return !MapUIManager.Instance.IsOutside;
            return true;
        }
        return false;
    }
}
```

要点：**按依赖顺序逐层检查，任何一层缺失就返回 false，不抛异常**。

我们踩过的时序坑正对应这里：
- `ArcAssets.Own()` 在 `Init` 阶段失败 —— 那时 `ModLoader.Mods` 还是 `count=0`
- 46 个 sprite 在 Init 阶段 `not found`（`Sprite name 'x' in atlas 'y' was not found`）
- 结论：**凡是"要用游戏对象"的操作，先过一遍就绪链**，而不是靠某个单点 flag。

⚠️ `PlayerStore.HasInstance` 是必需的：`PlayerStore.Instance` 这个属性**会自动创建背包等对象**，直接判 `Instance != null` 等于自己制造了一个半初始化的 PlayerStore。

## 三、物品 id 校验：别再拿 Spawn 试

```csharp
public static void ValidateId(string id)
{
    if (string.IsNullOrWhiteSpace(id)
        || ItemSpawnerHiddenList.IsHidden(id)
        || !DirectoryMaster.Has<GameItem>(id))
        throw new ArgumentException("物品不存在或属于内部物品：" + id);
}
```

- **`DirectoryMaster.Has<T>(string identifier)`**：遍历 `directories[typeof(T)]` 逐个 `directory.Has(id)`。**这才是判断 id 有没有注册的正确方法。**
- **`ItemSpawnerHiddenList.IsHidden(id)`**：`save_bag` / `back_inv_save_bag` / `hidden_save_bag` / `showcase_save_bag` / `sold_save_bag` 这几个内部存档物品 + 前缀表，懒加载。
- ⚠ **反例**：我们之前用 `ItemSpawner.Spawn(id)` 判断 id 是否存在 —— 它对**无效 id 也返回一个空物品**（不报错），所以根本判断不出来，`battery` / `energy_cell` / `power_cell` 全都"存在"。改用 `DirectoryMaster.Has<GameItem>` 就一次就试准了。

## 四、物品发放：三个入口，语义完全不同

| 入口 | 做了什么 | 什么时候用 |
| --- | --- | --- |
| `DirectoryMaster.Item(id, isOwned = true)` | `Create<T>` 新实例 → **强制剥掉所有子物品** → `SetItemOwned` → 补 `uniqueId` → `PermitHelper.OnNewItemCreated` | **真正发一件物品给玩家/NPC**。发给玩家用默认 `true`，发给 NPC 用 `false` |
| `ItemSpawner.Spawn(id)` | 底层新建，不设 owned、不补 uniqueId、不通知许可证 | **造游离实例做只读测量**（探针判定收不收、看标签）。别拿它发放 |
| `ItemDirectory.CreateEmptyItem(id)` | 空壳，工厂自己填 | **自定义物品工厂内部**造本体（我们的 `ArcAssets.NewItem` 走这条） |

两条容易踩的：

1. **`isOwned` 是第二参数，不是"是否克隆"**。它默认 `true`，所以 `Item(id)` 与 `Item(id, true)` 完全等价；`Item(id, false)` 才是不标记拥有。
2. **`DirectoryMaster.Item` 会销毁工厂预装的所有子物品**，日志里会有一条 `contains child items ... Removing all child items as a fix`。所以**机器里的便签/芯片只能在真正发放那一刻塞**，不能写在工厂里 —— 我们 `ArcMachines.CreateInstructionNote` 的注释就是这么来的，现在从源码确认了。
3. `DirectoryMaster.Item` **有两个同名重载**，patch 时必须显式写参数类型，否则 `AmbiguousMatchException`（我们 `ArcRegistry` 里已经记过这条）。

## 五、投放与回滚：`SplitDelivery` 范式

```csharp
public static bool TryDeliverAll(List<GameItem> pieces, out string where)
{
    where = null;
    if (pieces == null || pieces.Count == 0) return false;
    if (EmporiumEntry.Instance == null) { DestroyAll(pieces); return false; }

    for (int i = 0; i < pieces.Count; i++)
    {
        GameItem val = pieces[i];
        if (val == null) { DestroyAll(pieces); return false; }

        try { GeneralHelper.SetItemOwned(val, true); } catch { }

        try { GraphUtils.EmporiumTryAdd(EmporiumEntry.Instance.backInvinvElement, val); }
        catch (Exception ex) { Debug.LogWarning("原版投放失败：" + ex.Message); DestroyAll(pieces); return false; }

        if (val.parentInventory == null) { DestroyAll(pieces); return false; }   // ← 投递后必验

        if (where == null) where = WhereOf(val);
    }
    return true;
}
```

**防 `EmporiumTryAdd` 兜底的三件事**（`EmporiumTryAdd` 本身会依次落到 afterhour → backInv → inv → showcase → frontInv，全满才 `DestroyIfUnplaced`）：

1. **先 `SetItemOwned(val, true)`** —— 没标记拥有的物品在后续逻辑里可能被当垃圾清掉
2. **指定确切的目标容器**（`backInvinvElement`），不是"随便给一个节点"
3. **投递后验证落点**，失败**整体 `DestroyAll` 回滚**，不留半成品

**关键：验证落点要用引用比较，不是判空**

```csharp
private static string WhereOf(GameItem piece)
{
    if (piece.parentInventory == EmporiumEntry.Instance.backInvinvElement) return "柜台";
    if (piece.parentInventory == EmporiumEntry.Instance.frontInvinvElement) return "前台";
    ...
}
```

我们 `feedlive` 里写的是 `if (it.parentInventory != null)` —— **这正是被兜底骗到的原因**：物品被背包吞掉时 `parentInventory` 一样非空。
正确写法是 `if (it.parentInventory == 目标容器)`。

同理，往机器槽里塞东西时，判定必须是 `it.parentInventory == 机器的那个 GameInventory`，
而且最好用 `GraphUtils.CanAccept(inv, item)` + `GraphUtils.TryAccept(inv, item)`
（受 `mayInventoryAddItemFunc` 约束、**不兜底**），而不是 `EmporiumTryAdd`。

## 六、异常策略：对外吞，对内抛

| 场景 | 做法 | 例子 |
| --- | --- | --- |
| **给别的模组调用的只读 API** | 整体 `try/catch`，返回**安全默认值**，绝不抛 | `Interaction.IsDraggingAnything` 每条都是 `try { … } catch { return false; }` |
| **自己内部的功能入口** | **抛异常 + 明确消息**，让调用方看见 | `SpawnEngine.ValidateId` 抛 `ArgumentException("物品不存在或属于内部物品：" + id)` |

我们现在的 `ArcAssets` / `ArcMachines` 大量 `try { } catch { }` 静默吞异常 —— 相当于"全按对外 API 处理"，
代价是**坏了不吭声**（46 个 sprite 缺失就是在日志里躺了两天才被翻出来）。以后区分：**内部流程该抛就抛，只有真正跨模组边界才吞**。

## 七、顺带挖到的原版交互 API

`Interaction` 里这几个我们之前不知道，做真机验证时有用：

| API | 拿到什么 |
| --- | --- |
| `ItemMouseDragHandler.current.IsDraggingItem` / `.GetCurrentItem()` | 玩家**正在拖**的物品 |
| `ItemMultiSelectHandler.current.IsGroupDraggingItem(item)` | 是否在**多选拖动** |
| `ItemSelectHandler.current.GetEquippedItem()` | 玩家**手上拿着**的物品 |
| `ItemSelectHandler.current` 的私有字段 `currentItem` | 选中的物品（反射，一次性解析后缓存） |

反射字段的写法值得学：`_selectedResolved` / `_selectedField` 静态缓存，**只解析一次**，失败也缓存，不每帧反射。

## 十一、第三个参考：MCP Bridge / Agent 开发桥接器（工坊 `3834799226`）

`ProbablyStolen_MCPBridge.dll` 245 KB，自带 `AGENT_GUIDE.md`（给 agent 的 24 工具手册，值得整份读）。
它和我们正在用的 `ModDevBridgeNext`（`3835953432`）是**两个不同实现**，端口也不同（它 28910 / 我们 18774）。

**架构**（26 类型）：
```
McpHttpServer + McpRouter + McpToolDefinition/Result/ContentBlock   协议层
MainThreadDispatcher + WorkItem/SyncWorkItem/CoroutineWorkItem       HTTP 线程 → Unity 主线程
ObjectHandleRegistry + ObjectHandleRecord + ReferenceEqualityComparer 跨轮对象句柄（代际版本 + 弱引用）
ReflectionTools / RegistryTools / StoreStateTools / MutationSandboxTools / DiagnosticTools / InteractionTools / VisualAssetTools  七组工具
LogRingBuffer + LogEntry                                             环形日志缓冲
```
**值得学的**：`MainThreadDispatcher` 把 HTTP 回调排队到主线程（Unity API 不能跨线程）；对象句柄用 `Id + Version + WeakReference` 防止拿到已销毁对象。

**它做到的、我们还没有的能力**（按价值排序）：
| 能力 | 说明 | 对我们的用处 |
| --- | --- | --- |
| `simulate_drag_target` | 三通道判定后执行物品对物品交互，能绕过 `canUseOutsideCombat` 误拦 | **真机验证"把芯片拖进机器"不用真鼠标**，已把 API 链记进 03 |
| `fast_forward_machines` | 语义化推进机器生产（`one_cycle` / `complete` + `auto_recharge`） | 我们为验证刻录等了两晚，这个能一步到位 |
| `reload_mod_assets` | 零重启热重载本地模组资源（本地化/贴图/音频/书籍/物品定义），并同步场景实例 + 跑 ModScanner 合规检查 | 我们换贴图重启了三四次 |
| `extract_sprites` | 用 GPU RenderTexture 从**不可读**图集（`Items/itematlas`）无损切出 PNG | 想要原版素材时用得上 |
| `export_visual_catalog` | 导出单文件 HTML 图鉴（内嵌 Base64 图标、可折叠网格、标签徽章、搜索排序） | 做物品图鉴/给用户看效果 |
| `query_registries` | 14 个静态注册表统一枚举（底层就是 `DirectoryMaster.GetIdentifierList<T>`） | 已记进 03，我们探针可以直接用 |
| `eval_member` | 点路径反射（读/写/调方法），支持 `dict[key]` 索引、`@handle` 参数注入、Unity 组件自动解包 | 比我们 `call_probe` 灵活得多 |

**要不要直接装它**：它能与我们的桥共存（端口不同），但同样带 `files`/`network`/`reflection-external` 能力，
装上要人工批准；而且两个桥都 patch 游戏，有重叠风险。**当前判断：先蒸馏 API 自用，不装**。
