# 19-各类模组制作规范

> 来源：工坊 15 个标杆模组的反编译蒸馏（见 `workshop-distill\`）+ 原版 `共享开发\reference\Assembly-CSharp\` 交叉核对 + 我们自己两个项目的实战踩坑。
> 用法：**开工先按类型对号入座，照着一节里的"必守项 / 禁忌 / 验收清单"做**，不要从零想架构。

---

## 0. 十一 条规定（跨所有类型，违反任意一条都可能在别人机器上出事）

1. **只写自己的键**。物品 Tag 用 `<模组短名>_<用途>`（如 `SCT_BOUND_STORAGES_JSON`、`DIGITAL_VAULT_DATA_STRING`），ModData 键用 `<modid>.<用途>`。绝不写别人模组的键，也不改原版已有键的语义。
2. **判物品是否已注册用 `DirectoryMaster.Has<GameItem>(id)`**，绝不用 `ItemSpawner.Spawn` 试探（无效 ID 也返回空壳）。注册前先查，冲突时不注册并 Warn，**先到者赢**。
3. **Patch 只 Postfix 追加，能不改返回值就不改**。要拦返回值必须有"为什么非拦不可"的一句话理由，并写进注释。
4. **Patch 命中重载方法必须写显式 `new Type[]{...}`**。工坊里 Args 写成 `(Type[])null` 的模组只有在自己核对过"目标无重载"后才安全（Mod Conflict Scanner 就是这么干的，它核对过）。
5. **不整段替换原版入口**（`RunNightlyChemicalSimulation`、`DecodeSaveItem` 这类）。整段替换 = 与所有同类模组互斥。要优化就优化内部热点，或挂官方 `ModHook`。
6. **强制顺序要显式声明**：`[HarmonyPriority]`、`[HarmonyBefore("mod.xxx")]`、`[HarmonyAfter("mod.xxx")]`。不声明就是"顺序随缘"，别人加了同类功能就会飘。
7. **能力（capabilities）最小化**：主体模组零能力，需要读写文件的切成 companion（参考 Probably Extend Framework 的拆法）。
8. **异常：对内暴露、边界捕获**。Harmony 入口 / Unity 帧回调可以做一层捕获，必须 `LogError` 带堆栈；内部逻辑禁止空 `catch {}`。
9. **静态状态三处成对重置**：`OnDisable`、读档（`OnGameLoadedNormal` / `OnGameLoadedLate`）、热重载（`HotReloadPrepare`/`HotReloadActivate`）。
10. **自检进日志**：涉及"引用别的数据"的功能（前置节点、配方、剧情 id、容器绑定），在 `OnGameLoadedLate` 跑一次完整性自检（存在性 + 环检测），把问题 Warn 出来，不要留给玩家踩空引用。
11. **开工前先翻原版口子，最后才写 Harmony**。原版现成的扩展面（都已核对 `reference\Assembly-CSharp\`）：    - `ModHelper` **144 个 public static 方法**（内容注册、ModData、掉落表、跨模组消息总线、协程调度…）；
    - `GameItemFunc` **51 个委托属性**（拖拽三组九个 target 委托、容器准入、堆叠、槽位数量与优先级、**父子形状/贴图/状态修饰**、自定义 tooltip 富文本、每秒 tick、读档回调）；
    - `ModHook` **37 个钩子**（成对的 Early/Late 给了"抢先/收尾"两种位置）。
    这三处都找不到口子，再考虑 Patch。工坊实证：Storage Control Terminal（零 Patch 做带 UI 的机器）、Zoh Framework（零 Patch 做剧本引擎）、Pipeline Controller（5 个 Patch 全在外围，靠委托接管交互）。
12. **⛔ 绝不碰模组加载器状态**（2026-11-27 五源互证，详见 `03` 的「模组状态的三条硬红线」）：
    - 不许调用 `ModLoader.SetModEnabled` / `ModLoader.ReorderMods` / `ModLoader.ApproveAndEnable` / `ModTrust.Approve` —— 它们带 `[ModRestricted("loader-target")]`，**编译进 DLL 就被 ModScanner 判 Refused，运行期调用直接抛 `UnauthorizedAccessException`**；
    - 连 `ES3.Save("modOrder", …)` / `ES3.Save("modTrust", …)` 这种**字面量键**调用都会被 ModScanner 硬拒；
    - 我们自己永远只**读**（`ModLoader.Mods` / `IsModEnabled` / `LoadedMod.TrustState` / `RestartRequired`，全是零能力公开面）；
    - 别学 `Mod Preloader` 用 `new string(char[])` 拼键名规避扫描器——那是避检测，踩线。

## 1. 内容扩展类（自定义物品 / 机器 / 配方 / 食物 / 饮料）

**代表模组**：Storage Control Terminal（机器+目录注册）、Digital Vault（数据化存储）、UltraPurifier、Pen's 系列。

**必守项**

| 关注点 | 规范 |
| --- | --- |
| 物品声明 | 用原版目录（`DirectoryMaster`）注册；自定义品类只 `EnableTag`，**绝不往 `SetGameItemType` 写非原版类型**（会刷 `[Translation Error]`） |
| 机器"能用"的本质 | 不需要 `contentWindow`。机器 = `SetGameItemType("MACHINE")`；点开界面 = `onActivateSlotItemFunc` 开自定义窗口（`CustomUIManager.CreateWindow(..., Style.Machinery)`） |
| 占格形状 | 别手写 3×3 数字。用 `SetSpriteAndShapeFromMod(modId, key)`，它会按贴图 `rect/gridSize` × 逐格 alpha 生成 GridShape；之后立刻 `ValidateShapeState()` |
| 发放 | 玩家：`DirectoryMaster.Item(id, true)`；NPC：`DirectoryMaster.Item(id, false)`；只读探针：`ItemSpawner.Spawn` + `finally { item.Destroy(); }` |
| 精确投放 | `GraphUtils.CanAccept(inv, item)` 预检 → `GraphUtils.TryAccept*(...)`；校验落点用引用比较 `item.parentInventory == targetInv` |
| 读档恢复 | 自定义私有数据必须挂 `item.onLoaded` 或照 `MachineHelper.LoadUpgrade` / `SpriteHelper.UpdateWaterContainerSprite` 的分工补数据（**数据走 MachineHelper，显示走 SpriteHelper**） |
| 铁律 | 真伪/成色判定只认 `ItemFeature.realCondition.identifier`，绝不读显示名或 `fakeCondition` |

**禁忌**

- 往别人的容器里硬塞物品（一定要先 `CanAccept`，否则会出现幽灵物品/丢件）。
- 自己的物品用 `SetSprite` 切到原版图集后忘记清 `useSpriteFromMod`（→ 白底问号，见 `3845751834-SpriteHeal.md`）。
- 在 `Init/OnEnable` 阶段读 `LocHelper.Get` 并缓存（→ `invalid operation handle`，见 `3845556624`）。

**验收清单**

- [ ] `DirectoryMaster.Has<GameItem>(id)` 为 false 时才注册，冲突有 Warn
- [ ] 读档后自定义字段全部恢复（真机：存档→退出→读档→检查）
- [ ] 物品图标在"读档后 / 换图集后"都不变问号
- [ ] 机器界面关掉再开不重复创建窗口（重入测试）
- [ ] 名字/描述在中文与英文下都不出 `[Translation Error]`

## 2. QoL / UI 增强类（高亮、提示框、面板、快捷键、窗口）

**代表模组**：Client Demand Highlight、Item Details、Better Sliders、Window Snapping、Toolbox Wheel、Container UI Resize、After-Hours Highlights、进度条。

**必守项**

| 关注点 | 规范 |
| --- | --- |
| 快捷键 | 用 `ModHelper.AddGameOptionKeyBind` 注册进游戏「选项 → 按键」，**不要自己轮询 `Input.GetKeyDown`**（会和别人抢键） |
| 自定义面板 | `CustomUIManager.CreateWindow(...)` + `CustomUIBuilder`，不要手搓 `PixelWindow`；`PixelWindow` 只在需要接管原版窗口时才碰 |
| 覆盖层 | 只在需要时创建，关掉要销毁；窗口/覆盖层引用在 `OnDisable` 与读档时清空 |
| 挂载点 | 优先 `ModHook.OnCreateTooltipLate`（提示框）、`OnShutterOpenedEarly/Late`、`OnGameLoadedLate` |
| 模态/输入 | 打开自己的模态面板时要屏蔽底层输入（参考 ProgressBar 的 `InputGate`） |

**禁忌**

- 全局拦截 `Input` / `EventSystem`（会让别人的 UI 也失效）。
- Patch 原版 UI 的 `Update` 做每帧昂贵计算（改用事件/节流）。
- 同一显示元素多个模组都改写（如 `GameItem.get_name`）——这是 Mod Conflict Scanner 判"红色冲突"的靶点之一。
- **改原版 getter 却不声明优先级**：改 getter（`GameGridInventory.get_widthPixels`、`GameItem.GetDisplayName`、`PixelWindow` 尺寸反推链）等于"接管语义"，装第二个同类模组必冲突。工坊实证见 `workshop-distill\UI深度扩展八例.md` §8。
- **用 `Update` 轮询代替事件**却不做节流（0.12~0.25s 是工坊模组的常用档位，不要每帧）。
- **全局屏蔽输入却不兜底**：Toolbox Wheel 一次异常退出就会永久失输入，必须配 `Clear()` 兜底。

**验收清单**

- [ ] 热键可改、可关闭，不与其他模组默认键冲突
- [ ] 面板打开时游戏不卡（单帧 < 4ms 新增开销）
- [ ] 关闭模组后 UI 无残留、无空引用
- [ ] 中文/英文切换后文字正常（含 CJK 不回退成空白）

## 3. 性能优化类

**代表模组**：Sleep Lag Optimizer、Value Cache、Appraisal Cache Optimization、Better Performance、Perf Monitor、Lag Inspector。

**必守项**

| 关注点 | 规范 |
| --- | --- |
| 先量后改 | 先上计时（`Stopwatch` + 分阶段日志），确认热点再动刀；改完必须给出前后数字 |
| 缓存三要素 | ①键必须包含**所有**影响结果的外部状态（事件、加价、纯度、日期）；②失效用**代际计数**（全局 epoch）而不是逐条删；③必须可一键关闭回原版 |
| 缓存容器 | 用 `ConditionalWeakTable<被缓存对象, 缓存体>`（对象被回收则缓存消失），加容量上限自愈 |
| 线程 | 缓存读写限定主线程（记 `Thread.CurrentThread.ManagedThreadId`），跨线程只读原始数据 |
| 批处理延迟 | 原版批量流程（过夜/读档）里要"延迟 + 去重"时，用 `Prefix 打开标志 / **Finalizer** 关闭标志`（Postfix 在异常路径不会执行），flush 时按依赖顺序做 |
| 只读优先 | 纯优化模组必须**零存档写入**、可随时开关，绝不改物品/标签语义 |

**禁忌**

- 整段替换原版入口方法（互斥风险，见 §0.5）。
- 在 `Update` 里做全场景扫描（用事件或缓存）。
- 缓存里存 `GameItem` 强引用（会阻止销毁 → 内存泄漏 + 幽灵对象）；要存就用弱表。

**验收清单**

- [ ] 有前后对比数字（毫秒/帧），不是"感觉快了"
- [ ] 关掉开关立刻回原版行为，无需重启
- [ ] 连续游玩 30 天无内存增长（缓存有上限）
- [ ] 与其它优化模组同开不冲突（都不整段替换入口）

## 4. 事件 / 剧情 / 顾客 / 对话类

**代表模组**：Station Events、Scavenging Events、Zoh Framework、Street Whispers、NightRegulars、神秘仰慕者/更多新闻、Proficiency System。

**必守项**

| 关注点 | 规范 |
| --- | --- |
| 事件注册 | 走原版事件系统（`StoreEventManager.Activate/QueueFuturEvent/GetActiveEvents`），不要自己造并行时间轴 |
| 过夜介入 | 用 `ModHook.OnHandlingNightlyServicesEarly/Late`，不要硬 Patch `HandlePower/Operation/...` 里的任意一个 |
| 顾客介入 | `ModHook.OnGenerateCustomerVeryEarly/VeryLate` + `ModHelper.SetClientSource` 声明归属；要给原版顾客加台词优先用"替换 `allDoneDialogue` + `ConditionalWeakTable`"这类安全注入（Zoh 的 `SmallTalkInjector`） |
| 对话 | 用 `DialogueScene` 的 `startAction` 惰性翻页（每页显示时才求下一步），不要一次性把整段文本塞进 UI |
| 剧情数据 | 数据用脚本/JSON 外置（Zoh 的 `.zoh` 是极端样本），**便于玩家和非程序员改**；C# 里只放解释器 |
| 自检 | 剧情/事件引用 id 必须在读档后自检存在性 + 无环（Wild's Network 的 `SelfCheck` 是范本） |

**禁忌**

- 在顾客生成流程里同步做重活（生成卡顿会表现为"顾客凭空消失"）。
- 直接 `PlayerStore.Instance` 而不判 `PlayerStore.HasInstance`。
- 把剧情文本硬编码在 C# 里（改一句话要重新编译 + 玩家要等更新）。

**验收清单**

- [ ] 事件在日历/报纸/卷帘门上显示与实际效果一致
- [ ] 存档里的事件状态跨读档正确恢复
- [ ] 剧情缺失/损坏时降级而不是崩（Zoh 的做法：坏脚本退化成普通顾客）
- [ ] 加的事件在"其它事件模组"同开时不重复/不覆盖

## 5. 框架 / 互操作类

**代表模组**：Wild's Network API、Zoh Framework、SDJYBN Framework、Probably Extend Framework（+ File Companion）、Stock Reroll: Better Merchants Compatibility。

**必守项**

| 关注点 | 规范 |
| --- | --- |
| 零硬依赖 | 跨模组协作**不要**引用别人的 dll。用"约定名字 + 消息总线"：`GameObject.Find("固定名")` + `BroadcastMessage("固定方法名", List<object>)`，数据用 `Dictionary<string, object>` 且**必须带协议版本号**，读到 `v < 当前版本` 就忽略 |
| 可选依赖 | 依赖别人时写"软前置"（`softPrereqs` 语义）：缺了只提示，不阻塞；能跑就继续 |
| 动态值 | 允许把 `Func<string>`/`Func<bool>` 之类闭包塞进协议数据（同进程传引用），实现多语言/条件可见，**但订阅方对象生命周期必须长于使用期** |
| 冲突策略 | 同名 id **保留先到者 + Warn**，永不"后到者覆盖"；tab label、图标、排序都遵守这个原则 |
| 对外 API | 对外暴露的入口越少越好：一个 `Register(...)`、一个 `Remove(...)`、一个 `IsRunning` 查询；其余私有 |
| 自检 | 框架必须自带 `SelfCheck`：孤立节点、缺失前置、循环前置（DFS 三色）、重复注册 |
| 拆分 | 需要 files/network 能力的部分切成 companion 模组，主体零能力 |

**禁忌**

- 框架里 `Assembly.Load` 别人的 dll（能力扫描会标 `dynamic-code`，正式版直接被拒）。
- 在别人的 UI 里用 Prefix 返回 false 抢执行（先到者赢 → 你的功能直接消失）。
- 对外 API 返回值里暴露内部可变集合。

**验收清单**

- [ ] 卸载框架后，依赖它的内容模组有明确降级而不是崩
- [ ] 协议版本升级后老订阅者不炸
- [ ] 两个模组声明同一 id 时只 Warn 不崩
- [ ] `SelfCheck` 能在读档后列出所有引用问题

## 6. 工具 / 调试类（开发者工具）

**代表模组**：Developer Tools、Debug Console Plus、Item Spawner、绮罗的编辑工具、Lag Inspector、Perf Monitor、Mod Audit、Mod Preloader、MCP Bridge。

**必守项**

| 关注点 | 规范 |
| --- | --- |
| 调试入口 | 用 `ModHelper.AddDebugFunction` 注册，`OnDisable` 用 `RemoveDebugFunctions` 清理 |
| 主线程 | 跨线程操作游戏对象一律 `ModHelper.RunOnMainThread` + `ModHelper.Delay`，并用 **generation 计数器**做过期抑制（防跨帧竞态重复弹窗） |
| 日志 | 写自己 ModData 目录（`GetModDataFolder`），日志带时间戳 + 触发条件；控制台日志用 `Debug.Log` 前缀标识模组 |
| 只在开发用 | 带 `files`/`process` 能力的开发工具**不要**混进正式发布候选（`-PublicRelease` 必须零能力） |
| 数据自解释 | 生成给玩家看的配置/数据目录时，自动写一份 `说明.txt`（Probably Extend Framework 的做法） |

**禁忌**

- 调试功能默认开启（会拖慢正式游玩）。
- 用 `Console.WriteLine` / 写死绝对路径。
- 在工具里 `Process.Start` 外部程序（`process` 能力，正式版红线）。

**验收清单**

- [ ] 所有调试入口可一键关闭、可清理
- [ ] 无文件/网络能力残留（跑 `Test-ArcadeLoaderScan.ps1` 验证）
- [ ] 日志不会无限增长（有轮转或上限）

## 7. 立绘 / 美术 / 音频资源类

**代表模组**：Portrait Studio（+ Author Kit）、Probably Extend Framework Files、NightRegulars、各类娘化/配音包、Vanilla Machine Animations、Better Newspapers。

**必守项**

| 关注点 | 规范 |
| --- | --- |
| 图片来源 | 支持"目录 + 命名约定"的外部素材来源（玩家丢图即生效），文件大小/修改时间变化即重画，**不要求改名** |
| 命名约定 | 短名 = 本体（`Clara.png`），同前缀更长名 = 差分（`Clara_ep1.png`）；每层文件夹名都成为标签；文件夹名是来客池时自动参与抽取 |
| 分辨率/预算 | 贴图遵循原版尺寸档位；大图要提供降采样兜底（回退链：`extreme → adult → serene`，永不空白） |
| 字体回退 | 有 CJK 文本的 UI 要保证字体回退链含 CJK 字体；加完 `TMP_Text.ForceMeshUpdate()` 刷新 |
| 音频 | 零依赖路线是自带 WAV 解码 + `AudioClip.Create`（见 `12-立绘引擎与音画资源架构.md`），不引入第三方音频库 |
| 权限 | 读文件 = `files` 能力 → 切到 companion |

**禁忌**

- 用 `Resources.Load` 加载模组目录外的资源（路径不同，必失败）。
- 直接把 4K 原图丢进游戏（显存 + 加载时间双爆）。
- 覆盖原版图集文件本身（更新游戏就丢）。

**验收清单**

- [ ] 立绘缺失时回退到下一个来源，不出现空白/问号
- [ ] 中文/日文文本正常渲染
- [ ] 素材替换不需要改档、不需要重启
- [ ] 包内没有超出白名单的扩展名

## 8. 存档 / 读档增强类（高风险）

**代表模组**：Progress Bar、Save Mod Check、Save Slot Mod Manager、Mod Changes、Save Recycle Bin、F6/F5 快速存档、Autosave Before Bed。

**必守项**

| 关注点 | 规范 |
| --- | --- |
| 只读优先 | 能不写存档就不写；只写模组私有键，不改原版存档结构（`17`/`09` 号经验的延续） |
| 读档钩子 | 自定义数据恢复用 `item.onLoaded`；批量后处理用 `OnGameLoadedLate` |
| 分帧加载 | 要接管读档必须实现"出错回退到原版"（Progress Bar 的 `Fallback(reason)`），宁可卡也不能坏档 |
| 校验 | 改写存档前先备份到 ModData，失败自动回滚（Save Mod Check 的做法） |
| 版本化 | 自己写的持久化结构必须带版本号 + 严格全量校验，字段不合规就当"没有数据"（Container Link 的做法） |

**禁忌**

- 直接改原版 ES3 里的原版键。
- **碰 `%persistentDataPath%\SaveFile.es3` 里的 `modOrder` / `modTrust` / `modTrustMac`**：那不是"游戏设置"，而是**模组启用状态与审核记录**（`modTrust` 还有 HMAC 校验）。改它 = 篡改玩家模组列表，会被判异常（详见 `03-原版接口速查` 的「模组启用状态与审核机制」）。
- 在存档写入路径上做非幂等操作（重试会写坏）。
- 用一次性的 `try/catch` 吞掉解码异常（坏档应该明确报错 + 只读锁死，参考 DigitalVault 的 `broken` 只读锁）。

**验收清单**

- [ ] 反复存/读 10 次数据一致
- [ ] 存档里删除模组后重载不崩（降级）
- [ ] 坏数据触发只读锁而不是覆盖
- [ ] Slot 0 主档永不触碰（开发期只用 Slot 1）

## 9. 联机 / 跨进程类

**代表模组**：Probably Multiplayer（3828909239）、双人联机 NextDoor（3845780921）、Steam Friend in Probably Stolen、Coop Adapter。
详见 `workshop-distill\3828909239-ProbablyMultiplayer.md` 与 `workshop-distill\补充两例-调试面板与双人联机.md`。

工坊里至少有**两条可行路线**，门槛差一个数量级：

| 维度 | Probably Multiplayer | NextDoor |
| --- | --- | --- |
| 传输 | 自写 WebSocket（手写 RFC6455 + permessage-deflate）+ HTTPS 发现 + **第三方中继服务器** | 局域网 TCP 直连 或 Steam 好友「加入游戏」 |
| 权威 | 服务端权威（会话整份覆盖 + Revision） | 会话同步 + **双轨存档**（host/guest 各一条轨） |
| 玩家店呈现 | 接管原版顾客流程（把真人变顾客） | **镜像视图**（把对方店画出来） |
| 成本 | 需要自建/租中继 + 版本兼容闸门 | 局域网内可用，无服务器依赖 |

**必守项（两条路线共同）**

1. **协议必须带版本号 + 至少一道闸门**：Probably Multiplayer 用 `Protocol.Version=35` 在"发现清单 / 握手 / 运行期 error"三处校验，不匹配就进"只能更新"终态。我们若做任何跨进程协议，版本号是第一个要写的字段。
2. **状态同步只走自己的通道**，绝不改原版存档结构做同步。
3. **所有跨端状态必须能单机降级**：连不上就按原版跑（Probably Multiplayer 断线后立刻 `ResumeNext()` 叫原版顾客，而不是让玩家卡在空店）。
4. **只挂 ModHook，不 Patch 过夜主流程**：两个联机模组都只挂 `OnGoingSleepLate` / `OnHandlingNightlyServicesLate` / `OnShutterOpenedLate` 这类钩子，没有一个去 Patch `EndNight`。
5. **转账/交易类要有手续费 + 幂等 + 显式流程**（NextDoor 用「拨电话 → 数字键输金额 → 回车」，手续费 1%）。
6. **高风险改动留退路**：NextDoor 用配置项 `v4=1/0` 让玩家能退回上一代存档方案。

**禁忌**

- 物品数据不过签名就往对方发（Probably Multiplayer 的 `WireItem.Data` 没有签名也没服务端校验，**别把它当反作弊样本**）；跨端给物品一律"对面本地 `DirectoryMaster.Item(id, true)` 生成"，不要让整段存档片段过线。
- 供应商锁定：把域名/裸 IP 硬编码进客户端（Probably Multiplayer 这么干了，主线挂了全服一起挂）。
- 在镜像视图里不屏蔽本地输入（NextDoor 为此 Patch 了 5 个输入方法）。

> 对我们的现实建议：**"可能是群友"不需要联机**。如果只是想让自定义顾客像真人一样走完整流程，抄"借壳"（`ModHelper.SetClientSource` + `ModHook.OnGenerateCustomerVeryLate`，不够再用 `StoreClientList.CreateInventor` + `CreateClientInstance`）就能白拿进店动画、头像位、对话框、名牌、离场动画。

## 11. 与「冲突检测」有关的硬情报（来自 Mod Conflict Scanner 蒸馏）

工坊里那个 2.5 万订阅的冲突检测器，**只认 3 类冲突**，其中"红色（硬冲突）"只有两类靶点：

| 类别 | 判据 | 我们要做什么 |
| --- | --- | --- |
| 物品显示层（itemname） | 多个模组同时 Patch `GameItem` 的 `get_name` / `get_shortDescription` / `GetDisplayName` 一类 | **我们不要碰全局物品显示层**；要做改名只在"自己的物品"上做 |
| 本地化层（loc） | 多个模组同时 Patch `LocHelper.SetLocale` / `FontLoader` / `TMP_Settings` | 做文案注入走"注册自己的表 + 只 Postfix 追加"，不改写全局 |
| 存档链（savewrite） | Patch `PlayerStore` 的存/读链 | 单个模组命中会被**放大自风险**（+itemname 或 loc 就变红）；我们若必须碰存读链，绝不能同时改显示层 |
| 同名 DLL | 同名但 size/SHA256 不同 | 我们的 DLL 名要唯一带项目前缀 |
| 声明冲突 | `manifest.xml` 里 `<Conflicts><Mod>id</Mod></Conflicts>` | 我们可以在 manifest 里**主动声明**已知互斥模组 |

**重要提醒**：这个检测器**不查** identifier 重复注册、语言 key 覆盖、atlas 同名、manifest ID 重复。也就是说"玩家没看到标红"不等于我们没问题——上面十条铁律仍然要自己守。
