## 1. 玩法闭环

### 1.1 销赃职业扩展：**关店以后的那半小时**

玩家开局必须是原版自带的「销赃人（fence）」剧本——`Bg.ScenarioIsFence()` 判定 `PlayerStore.startType == 4`，否则整条线直接不启用（`Bg.cs:126-206`；`ModEntry.cs:181-192` 在 `OnNewGameStarted` 时按 scenarioId 含 `fence` 再判一次）。是销赃人，才在**每个营业日**拿到上层区黑手套的委托：**开门时**看柜台上的纸条和货（`ModHook.OnShutterOpenedEarly` → `Aftermath.OnShutterOpened`，`Aftermath.cs:26-98`），**白天**等奴仆/中间人上门谈单（`ModHook.OnGenerateCustomerLate` → `ModEntry.OnGenerateCustomer`，`ModEntry.cs:126-179`），**关店那一刻**弹「夜间服务」入口（`OnShutterClosedEarly` → `NightService.OnShutterClosed`，`NightService.cs:65-73`），在证据板上挑一个执行者（雇佣兵/ Wilde / Sawyer / 屠夫 / 乞丐 / 疤刘）付定金派出去，判定掷骰（`Rules.SuccessRate` + D20 UI），**次日开门**纸条说明成败，战利品直接摆上柜台（`AddDirectSellingItemToTable` / `GraphUtils.TryAcceptAll`），最后按普通货卖出去，**下周一**奴仆上门结赏金、涨声望（`SettleDay`，`Rules.NextMonday`）。

挂载点：**营业日**（开门/来客/关店三段）+ **过夜清场**（`OnGoingSleepEarly`/`OnHandlingNightlyServicesEarly` 只做关面板）。它**没有**用原版夜出地点系统——夜间服务是自己开的模态面板，挂的是"卷帘门已关"这个事件，而不是"去哪个地点"。

### 1.2 夜间集装箱拍卖：**夜里出门去拍卖场**

拍卖走的是原版「打烊后夜出」地图：`ModHelper.AddAfterhourLocation("xiaowo_night_auction", …)`（`Core.cs:66-73`）往夜晚地图塞一个目的地。玩家夜出选它 → 选场次（新手/中级/高级，入场费 0/300/1500）→ 一场四箱、最多拍三箱 → 每箱暗标或公开、最多五轮，**前四轮都得领先第二名足够倍数才提前成交**（2.0×/1.6×/1.3×/1.1×，`AuctionEngine.cs:21-22`、`:371`）→ 赢了钱从现金扣、货记进 `pending_deliveries`，**回到店里**（`ModHook.OnReturningStoreLate`）才发一个名为「集装箱」的自定义物品，玩家拆箱取货再卖。它还有两条并行的日常线：拍卖行商人按周来店里（`AuctionMerchants.HandleDailyVisitors`）、拍卖行顾问服务走原版网络升级面板（`AddNetworkUpgrade`）。

挂载点：**夜出**为主，**营业日**（来客 + 顾问 + 寄存箱）为辅，**过夜/读档**只用于补状态。

### 1.3 災變日：**一场连着三天的地区灾难**

玩家满足前置（Eleanor 线 `eleanorDriveChoice==2`、开店满 7 天、`storeBoughtDay>=0`，`DisasterDayEvents.TryGetContext`，`DisasterDayEvents.cs:3789-3847`）后，从"武器需求"新闻开始滚雪球：武器需求 → 疫情爆发 → 隔离 → 物资短缺 → 二次隔离，每一环都是**原版 `StoreEvent`**，`duration = 3` 天（`CreateNewsEvent`，`DisasterDayEvents.cs:4461-4482`）。老存档不必重开：第一次进店会弹一张纸，让你**勾选"补齐前置"**（直接写 `storeClientData.eleanorDriveChoice`/`RunStats.OnGeorgioLoan`/`serpicoDocumentChoice`，`DisasterDaySetup.cs:222-271`）。灾难期间店内顾客池被改（隔离期把"下层区"顾客换成任意阵营，`DisasterDay_ComputeClientType_Patch.cs`）、贸易被锁（`IsTradeLocked`）、柜台放货触发没收/搜查、顾客会就"要不要卖管制药品"给你出选择题。夜里可以出门去「隔离检查站」——一个用**世界层 SpriteRenderer 舞台**演的过检小游戏（读屏幕数字、按三色按钮、敲门），过检对错记进灯塔声望（`lighthouse_rep`，−200~200，五个正档 20/40/60/80/100 分别解锁买家、富买家、卖家、额外馈赠、管制品收购）。整条线跑完是五章剧情 + 多结局。

挂载点：**当日事件/营业日**（`StoreEventManager.OnDayStart` 注入新闻 + 改顾客池 + 锁交易）+ **夜出**（检查站）+ **过夜**（`OnHandlingNightlyServicesLate`）。

## 2. 它怎么"发明一个新玩法"而不用改原版核心

### 2.1 扩展点账本（三模组实际使用情况）

| 扩展点 | 职业扩展 | 夜间拍卖 | 災變日 |
| --- | --- | --- | --- |
| `ModHelper.AddAfterhourLocation` | ✗ | ✅ 1 个（`Core.cs:66`） | ✅ 1 个（`DisasterDayStation.cs:126`，并 `usesAfterhourBag=false`） |
| `ModHelper.AddAfterhourEvent` | ✗ | ✅ 9 个（6 个夜市常态事件 + 3 个场次顾问，`AuctionNightMarket.cs:84-99`） | ✗ |
| `ModHelper.AddNetworkUpgrade` | ✗ | ✅ 1 个（加急清证，`WildeExpressEvidence.cs:43`） | ✗ |
| `ModHelper.AddAppraisalItem` | ✗ | ✗ | ✗ |
| 自定义物品（`OnModItemDirectoryInit`） | ✅ 8 个模块注册（`ModEntry.cs:73-80`） | ✅ `AuctionItemRegistration.Register` | ✅ `DisasterDayItems.OnItemDirectoryInit`（27 个 id，`DisasterDayItems.cs:123-160`） |
| 自定义 UI | `CustomUIManager.Window()` + 自绘 IMGUI 板 | `CustomUIManager.Instance.CreateWindow()` + 手摆 RectTransform | `CustomUIBuilder` 纸片 + 世界层 SpriteRenderer 舞台 |
| 原版 `StoreEvent` 数据注入 | 报纸/短缺（`RiotWeek.cs:805-854`、`OdinOps.cs:413-416`） | ✗ | ✅ 主力手段 |
| 原版声望阵营（`storeReputations`） | ✅ 新增一条 `FACTION_UPPER_BLACK_GLOVE` | ✗（自己写商人关系 LV） | ⚠ 不走数据，直接**替换**声望页内容 |
| 原版 `modData` 私有键 | ✅ | ✅ | ✅ |

结论：**三家都没用 `AddAppraisalItem`**——鉴定品类扩展跟玩法模块是两条正交的轴。真正撑起"新玩法"的是四件套：`AddAfterhourLocation`（新场景入口）+ 自定义物品（新道具载体）+ `modData`（新状态）+ 自己的 UI（新界面）。

### 2.2 各自不得不 Patch 的地方，和理由

- **职业**：因为要在**原版数值层面**起作用——暴动周军火加价 150%（`RiotPricePatch` 补 `GameItem.GetNegociatedValue`）、补给箱内无货时压价到 30（`SupplyBoxValuePatch` 补 `get_unitValue`）、雇人扣率（`StoreClient.SetBudget`）。这些东西原版没有"数值修正"扩展点，只能补 getter。
- **拍卖**：因为要**接管原版的物品交互语义**——"集装箱"是能双击打开、只能取不能存的容器，必须补 `ItemMouseDoubleClickHandler.OpenContentAction`、`GameGridInventory.Expel`/`MayHaveValidInventorySlot`、`GameItem.CanTarget/MayTarget/Target`。另外给 NPC 商人加"专收某类货"的独占行为，必须补 `StoreClient.IsClientBuyingThisItem`/`IsClientRefusingItem`。
- **災變日**：因为要**卡住原版流程的时机**——`PlayerStore.CanEndDay`（剧情访客没走完不许关门）、`PlayerStore.GetNextClient`（下一个客人来了要跑剧情）、`NegociationUIManager.IsTradeLocked`（选项没答完不许交易）。它把"数值/事件"全放在原版数据结构里改，只在**时序**上加钩子，这是一个很干净的取舍。

## 3. 数据与状态

### 3.1 拍卖：4 箱 × 3 竞拍者 × 5 轮

- 状态全在 `PlayerStore.modData`（`ModHelper.SetModData("xiaowo_night_auction", …)`），键前缀 `xiaowo_night_auction.`（`AuctionState.cs:39-74`）。
- 每箱序列化成**一行 40 字段的逗号分隔串**：`AuctionState.SaveLots`（`AuctionState.cs:312-330`），箱体字段含 `Slot/Category/Seed/ItemCount/EstimatedValue/CurrentBid/Round/PlayerLeading/Finished/Lost/Started/Sealed/HighestBidder/ActiveMask/IntelMask/Budgets/LastOffers/BidLog/…`，日志与货单用 Base64 包一层避免逗号冲突。
- 三个 NPC 各自的钱包**跨箱持久**：`AuctionRivalFunds`（`AuctionRivalFunds.cs`），`Encode()` 用 `|` 分层（版本号 `1`、场次、锚定现金、初始/剩余三连、结算过的箱 key、情报付款明细），`Decode()` **任何一条不变量破了就返回 null**（剩余 > 初始、初始 > 1.5×场次上限、情报付款 > 初始……）。
- 键名即模式版本：`lots_v2_<day>`；历史 `history` 字段长度 6/9/10 都能读（`AuctionState.History`，`AuctionState.cs:429-450`）。
- 防坏档三道：① `Decode` 的长度白名单（23/24/26/28/29/32/33/37/38/40 种合法字段数，`AuctionState.cs:573`），② 每个字段区间校验失败就整批丢弃重建，③ 购买 `CommitPurchase` 用 **modData 快照 + 现金回滚**（`AuctionState.cs:350-407`）。
- 版本迁移：`MigrateKeys()` 把旧的 `xiaowo_night_auction.<k>` 平铺键搬进官方 `modData`（`AuctionState.cs:76-100`），冲突时**保留官方值**并打警告——从不覆盖玩家现有进度。

### 3.2 职业：297 个键 + 一个派生量

- `Save.cs` 是一个 3714 行的纯属性包，全部落到 `ModHelper.GetModDataInt/SetModDataInt("upper.blackglove", key, fallback)`（`Save.cs:3577-3595`）。命名有前缀分组：`bg_riot_*`、`bg_hostile_*`、`bg_rent2_*`、`bg_odin_*`、`bg_dream_*`、`bg_wilde_*`。
- **等级不落盘**：只存 `bg_rep`（声望原始值），`Stage` 是 `Rules.StageOf(Reputation)` 现算（20/50/100 → 2/3/4 阶，`Rules.cs:431-446`，`Save.cs:18`）。这是最正确的一处设计。
- 防坏档：`Maintenance.cs` 是一整个"读档自检管线"，由 `Visits.OnGameLoaded()`（挂在 `ModHook.OnGameLoadedNormal`）调 `Maintenance.OnLoaded()`（`Visits.cs:51-64`），顺序是
  `LegacyFixes()` → `SaveVersion < 2 ? Migrate()` → `ReconcileHire()` → `ClearPhantomDispatch()` → `RepairOutcome()` → `RollbackWarning()` → `SelfCheck()`（`Maintenance.cs:258-286`）。
  其中 `ReconcileHire` 用 `HireNonce == Bg.SessionNonce` 判断"读的是不是同一次会话的档"，读到更早的日期就撤销那次派遣（`Maintenance.cs:318-339`）——**用一次性 nonce 防读档回溯刷派遣**，很值得抄。
- 版本迁移：`bg_save_version` 默认 0，`Migrate(0→2)` 修越界的 `TargetId/PendingTarget/NextTargetId`、清残留的刺客字段、把声望夹到 `[0,100]`（`Maintenance.cs:341-395`）。

### 3.3 災變日：全部 key + sentinel

- `DisasterDayState` 只有 24 行，读写 `ModHelper.Get/SetModDataInt("disaster_day", key, …)`，`slotId` 参数**收下但不用**（`DisasterDayState.cs:15-23`）——即"跟着当前档走"。
- 没有单一"当日事件"对象；日期一律用 `*_day` 键 + `GetInt(_, -1)` 表示"未排期"，`IsDue = day >= 值`、`IsWithinEvent = [值, 值+3)`（`DisasterDayEvents.cs:3716-3787`）。这就是**事件即数据**：不存"当前事件是什么"，只存"这件事哪天开始"。
- 没有版本号，也没有迁移；向前兼容靠"缺键就 -1"和每次 `TryGetContext` 顺手补齐排期（`DisasterDayEvents.cs:3809-3841`）。
- 一个额外状态：`DisasterDayState.SetInt(0, "fast_story", …)` ——剧情节奏是**全局开关**（不是存档内选择），Setup 纸片里选。

### 7.2 拍卖公平性：信息不对称 + 谁都不可能凭空出钱

`AuctionEngine.cs:515-543`（`PlanRound`）——三个 NPC 各自只看到"公开信息"：暗标时看不见别人本轮报价（`lot.Sealed` → 用玩家上一轮 `PlayerOffer`），公开竞拍时**只看见自己座位之前的人**本轮报价（`j < i` 才用 `bidPlan.Offers[j]`，否则用上一轮 `LastOffers[j]`）。这一条保证了"按座位顺序出价"的物理真实性。

```csharp
	private static BidPlan PlanRound(AuctionLot lot, int round, int playerOffer)
	{
		BidPlan bidPlan = new BidPlan();
		round = Math.Clamp(round, 1, 5);
		int num = ((!lot.Withdrawn) ? (lot.Sealed ? lot.PlayerOffer : playerOffer) : 0);
		for (int i = 0; i < 3; i++)
		{
			if ((lot.ActiveMask & (1 << i)) == 0)
			{
				bidPlan.Exits[i] = ((lot.RivalExitReasons[i] != 0) ? lot.RivalExitReasons[i] : 2);
				continue;
			}
			int num2 = num;
			for (int j = 0; j < 3; j++)
			{
				if (j != i && (lot.ActiveMask & (1 << j)) != 0)
				{
					int val = ((!lot.Sealed && j < i) ? bidPlan.Offers[j] : lot.LastOffers[j]);
					num2 = Math.Max(num2, val);
				}
			}
			int limit = SpendingLimit(lot, i, i == 2);
			int appraisal = Appraisal(lot, i);
			int previous = lot.LastOffers[i];
			int available = Math.Max(0, lot.Budgets[i] - lot.RivalIntelSpent[i]);
			AuctionRivalDecision auctionRivalDecision = new AuctionRivalAgent(lot.Seed, i).Decide(new AuctionRivalObservation(round, previous, num2, appraisal, limit, available, lot.MemoryModifiers[i], !lot.Sealed));
			bidPlan.Offers[i] = auctionRivalDecision.Offer;
			bidPlan.Exits[i] = (int)auctionRivalDecision.Exit;
			bidPlan.Actions[i] = auctionRivalDecision.Action;
		}
		return bidPlan;
	}
```
钱的三重约束在 `SpendingLimit`（`AuctionEngine.cs:479-511`）：取三者的最小值——`(钱包 − 情报花费) × 85~95%`、`参考价 × 110~145%`（买过情报则取 `情报估值 × 110%`）与 `评估价 × (心理率 + 记忆修正)/100` 里更小的那个；而 `AuctionRivalFunds.Settle`（`AuctionRivalFunds.cs:97-137`）在每次 `SaveLots` 时把花费和成交价扣进 `Remaining`，跨箱延续。任何一处出现"钱包不够"就抛 `InvalidOperationException("Rival intelligence exceeds wallet.")`（`:116`）——**宁可炸也不静默纠正**。

## 8. 对我们的可用点

### 8.1 从职业借：**先写 `Maintenance.cs`，再写玩法**

它的 3714 行 `Save.cs` 不值得抄，但 `Maintenance.cs` 的 258-286 行那套"读档自检管线"是全三例里最硬的工程资产：读档时按固定顺序跑 `LegacyFixes → 版本迁移 → 撤销回溯的派遣 → 清幽灵状态 → 修判定 → 自检精灵`，每一步只做一件事、每步都打日志、整段外层 `try/catch` 只包住"迁移"这一小段。反面教材也在里面：`Save.Stage >= 50` 这种"派生量 vs 原始量"混用（`Visits.cs:590` 等 7 处），提醒我们**等级只算不存，比较一律用原始量**。

### 8.2 从拍卖借：**两阶段交付 + 事务快照**

`CommitPurchase`（`AuctionState.cs:350-407`）是"花玩家的钱换货"唯一正确的写法：先记 `pending_deliveries`（真正的货）→ 再改箱状态 → 再记账 → 最后才 `store.ModCash(-bid)`；`catch` 里用进门前拍的 `modData` 快照逐个还原、把现金差额补回、把内存状态回滚，然后**重新抛**。配合"回店才发货"（`OnReturningStoreLate` → `TryDeliverPendingFromHook`），任何一步崩了都不会出现"钱扣了货没了"。

### 8.3 从灾难借：**要影响数值，就先找原版的数据结构**

我们要做"某天全城缺某类货"，最省事也最不容易和别的模组打架的路是造一个 `StoreEvent` + `NegociationData(tag, demand, …)`，而不是 patch `GameItem.GetNegociatedValue`。职业模组自己就是**两种手法都用**的活证据：暴动周军火 ×1.5 走补 getter（`RiotPricePatch`），而"前线道路断了 → 食物/医疗/武器严重短缺"走 `StoreEvent` + `NegociationData(text, 90, …)` + `ActivateEvent`（`OdinOps.cs:405-419`）；后者十二行搞定、可被报纸读出、能和别的模组叠加，前者一旦撞车就互相覆盖。判断标准很简单：**能通过原版数据表达的，绝不 patch getter**。

### 8.4 三处明确不要照抄

1. **单文件巨兽**：`Save.cs` 3714 行 / `AuctionController.cs` 2715 行 / `DisasterDayEvents.cs` 6298 行。三家都在这里付出了可维护性代价（灾难那 6298 行里 83 个 `CreateXxxClient` 造客户方法全在同一个类里）。我们按"状态 / 规则 / 表现 / 补丁"四层分文件，每个文件控制在 400 行内。
2. **入口 if 瀑布**：`ModEntry.OnGenerateCustomer`（`ModEntry.cs:126-179`）让 20 多个模块顺序调用、每个自己判"我今天来不来"，加第 21 个时没人知道顺序为什么是这样。改成"每个模块注册一个 `(priority, predicate, action)`，入口只排序遍历"。
3. **破坏式 UI 替换**：`DisasterDay_LighthouseReputation_Patch` 清空 `ReputationUIManager.layout` 的子物体。这在只装它一个模组时很漂亮，装第二个也改声望页的模组时就会互相吃掉。要做声望展示，用 `Faction.cs` 那种"往 `storeReputations` 里加一行"的路子。
