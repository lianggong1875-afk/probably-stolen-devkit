## 1. 模块化架构

### 1.1 目录：一个平坦功能层 + 两个"内嵌子模组"

`DangpuPlus\` 是内核（入口、`Core` 启动序列、`ConfigFile`/`ConfigEntry`、`OptionsPage`、`FeatureHost`/`FeaturePack`、`Hud`、`L`、`Safe`、`SelfTest`）；`DangpuPlus.Features\` 是 **371 个功能文件全裸平铺**，文件名 = 类名 = 功能名，无二级目录；`ExchangePreview` / `CollectAllWater` 是内嵌子模组（各带 `Hook.cs`、`XxxMod` 入口）；`ProbablyStolenWindowTabs` 是整份移植进来的第三方（dbfoxtw 的 Window Tabs），独立命名空间、由 `Core` 单独调（`Core.cs:100-106`）。

**371 个文件不建子目录**，靠"文件名即类名"导航，`FeaturePack` 那张表就是唯一的地图。这是它能塞 103 个功能的前提。

### 1.2 入口约定是硬约定，不是惯例

`DangpuPlus.Features` 下每个功能必须是 `public static class`，且**同时**提供三个静态方法：

```csharp
public static void Init(ConfigFile cfg, ManualLogSource log, Harmony harmony)
public static void Update()
public static void OnGUI()
```

因为 `FeaturePack` 用**方法组**直接绑委托（`FeaturePack.cs:30-33`），少一个方法编译就过不了。用不上的写空实现——`FillFromTarget.cs:24-30` 就是两个空方法。`Init` 里的第二层约定（几乎 100% 遵守）：**先 Bind 开关，开关关掉立刻 `return`，一行 Harmony 都不打**（`BayPages.cs:406-412`、`Core.cs:87`）。

### 1.3 三个注册表，呈"分形"

1. 顶层 `FeatureHost`（`FeatureHost.cs:26-44`）只登记 4 个门面：`AugInfo`、`DashboardBar`、`FeaturePack`、`UpdateNotice`。
2. `FeaturePack`（`FeaturePack.cs:26-749`）是 103 项大表。
3. 子命名空间自带门面：`CollectAllWaterFeature` / `ExchangePreviewFeature` 对外只暴露 `Init/Update/OnGUI`，父表登记 1 项（`FeaturePack.cs:133-146`），内部再拆 `XxxMod.Init` + `Hook.Patch`（`CollectAllWaterMod.cs:9`、`ExchangePreviewMod.cs:25`）。

收益：**加一个子模组 = 父表加 1 行 + 建一个门面**，不碰那 371 个文件里的任何一个。

### 1.4 开关体系：不用裸 `ModConfig`，自造 `ConfigFile` 门面

这是整份源码最值得抄的设计（`DangpuPlus\ConfigFile.cs`，221 行）：

- 构造两行拿两个配置（`:29-33`）：`GetConfig(modId)` 给**玩家可见**的，`GetConfig(modId + ".state")` 给**内部状态**的。
- `Bind<T>` 只支持 `bool/int/float/string/KeyCode`，其余抛 `NotSupportedException`（`:46-112`）。**故意不支持数组/枚举**，逼着把多选做成 `int` 索引 + `Choices`（`OptionsPage.cs:169` 的堆叠上限）。
- **分流**：在 `OptionsPage` 声明过（有 label/tip）的进正式配置；没声明的悄悄进 `.state`，并从旧位置 `Adopt` 迁移一次（`:58-64, 114-124`）。内部状态因此不污染玩家可见配置。
- **默认值迁移**（`:135-166`）：每次把见到的默认值记进 `defaults.json`；下次启动若"记录的旧默认 ≠ 现在默认"且"用户当前值 = 旧默认"，就跟随新默认，用户改过则不动。巨量设置模组版本演进刚需。
- **退休键** `RetiredKeys`（`OptionsPage.cs:211-217`，37 个键）+ 强制回默认（`ConfigFile.cs:98-104`）。

### 1.5 四级开关级联

```
Core.Enabled（总闸）
 └ Sections.Trade / Storage / Machine / Water / Misc（5 个分区闸）
    └ Features.EnableXxx（单功能闸，253 个 Bind 的大头）
       └ OptionsPage 子项（靠 interactable 谓词置灰）
```

`Sections` 是启动时**快照**（`Core.cs:66-70` 一次性读进 5 个 `static bool`），所以分区开关全部标注"重启游戏后生效"——有意取舍，见 §7.2。

## 2. 生命周期与性能

### 2.1 唯一驱动器

`Core.Start` 无论启用与否都 `CreateHud()`（`Core.cs:61` 与 `112`），挂一个 `DontDestroyOnLoad` + `hideFlags = (HideFlags)61` 的空对象（`:117-127`）。**整个模组只有一个 `MonoBehaviour`**，连内嵌 WindowTabs 的 `PollScene`/`LateUpdate` 也是从这里被调用的（`Hud.cs:87-90, 183-189`）。

### 2.2 固定跑批顺序（`Hud.cs:77-181`）

`GuiBlocker.Sync` → `SelfTest.Tick` → `L.LogOnce` → （**总闸短路**：未启用只跑 `OptionsPage.Tick` 就 return，`:82`）→ `WindowTabs.PollScene` → `OptionsPage.Tick` → （**场景短路**：`!Active` 就 return，`:92`，`Active` = `GameMaster.current != null && EmporiumEntry.Instance != null`）→ `BatterySwap` → 鉴定热键/自动鉴定（0.5s）→ `ModuleAutofill`（Detect 0.25s + Tick 每帧）→ `Hud.Clicks` → `StorageLabels`（0.5s + 每帧拖拽）→ `FeatureHost.Update()`（4 个子系统 → `FeaturePack` 的 103 项）→ `AutofillBoard.Tick`。

### 2.3 三道短路 + 时间片节流

短路：总闸、场景、「单项 `Init` 里的 `if (!enabled) return`」。节流：功能内部一律 `_nextRefresh`，且**面板不可见时时间片翻倍**——`RatAdvisor.cs:304-322` 是模板（`_nextRefresh = Time.unscaledTime + (flag ? 1f : 2f);`）。实测间隔：`SelectionCount` 0.1s、`TradeInfo` 0.2s、`ModuleAutofill.Detect` 0.25s、`GunOrderHelper` 0.4s、`RatAdvisor`/`FishAdvisor`/`PowerPanel`/`PharmaBoard`/`BrewAdvisor` 1s（不可见 2s）。

### 2.4 有没有分帧/预算？——几乎没有

全库 `Time.frameCount` 只有 16 行 / 6 个文件，**全部是"同帧去重"**（双击、快捷键录入、Esc 只吃一次），不是分帧调度。唯一真正的**毫秒预算**在 `BoxTags.PumpProbe`（`BoxTags.cs:850-902`）：每帧泵最多 6ms 就 `break`，剩下的留给下一帧（`_job.Pending` 队列）。另一个"预算"是求解器自己的评估上限 `EvalBudget = 6000000L`（`SolverInput.cs:23`；`ModuleSolver.cs:1229-1366` 的 LNS + 局部搜索），**是算法预算不是帧预算**。

结论：**靠"阈值 + 时间片 + 可见性"控制开销，没做帧预算调度器**。103 个功能里真正每帧干活的只有十几个，其余 1-2s 一拍，所以扛得住。

### 2.5 缓存与失效：三种手法

1. **时间片**（主流，§2.3）。
2. **全局版本纪元**：`InventorySignal` 补 3 个原版方法（`GameItem.AddParent`/`RemoveParent`、`GeneralHelper.SetItemOwned`）+ 2 个 ModHook，只干一件事——`Version++`（`InventorySignal.cs:32-48`）。消费者比对一个 long 决定要不要重扫，`AssetMonitor.cs:134` 是标准用法：`if (_dirty || _language != L.Lang || (_seenVersion != InventorySignal.Version && Time.unscaledTime >= _nextScan))`。**一个 int 代替一堆事件订阅**。
3. **显式置零**：动作后 `_nextRefresh = 0f`（`BrewAdvisor.cs:137,159`、`PharmaBoard.cs:621,765,840`、`RatAdvisor.cs:288` 等 30+ 处）。把计时器清零当"置脏"，比 dirty 标志位少一半代码。

### 2.6 失败熔断与错误去重

`FeaturePack` 的 catch 调 `Trip`：连续 120 次失败 → `Failed = true`，本会话不再调它（`FeaturePack.cs:859-866`）。配 `Safe.Err` 的 `HashSet<string> Seen` 去重（`Safe.cs:40-49`，同一"位置+异常类型+消息"只打一次），否则 103 个功能会刷屏。

### 3.2 高危区一：全局显示层 —— 碰了，四道护栏

它**没有**"整段替换绘制"，全是"进上下文/出上下文"成对：

1. **全局 IMGUI 矩阵**：`Hud.OnGUI` 拷出 `GUI.matrix`，按 UI 比例缩放，`try/finally` 强制还原（`Hud.cs:220-264`）。任何一帧抛异常矩阵也会还原——否则整个游戏 UI 会被缩放到报废。
2. **原版弹窗缩放**：`PopupScale` 不改预制体，只写 `localScale` 并把原值记进 `Dictionary<IntPtr, Vector3> Original`（`PopupScale.cs:13`）以便还原；补丁用**方法名反射批量命中重载**（`:32-39` 遍历 `typeof(OverlayHandler).GetMethods()`，名字是 `ShowTooltip`/`ShowTooltip2` 就挂 Postfix），绕开重载签名歧义。
3. **排版上下文**：`TooltipLayout` 对 `GetTooltip`/`GetTooltipAdvanced` 挂 Prefix `Enter` + **Finalizer** `Leave`（`TooltipLayout.cs:28-34`）。用 Finalizer 而非 Postfix 是必须的：原方法抛异常也要退出上下文。
4. **Dashboard 不自己画**：`NativeBoard` 拼装的是**游戏原生** `PixelWindow` + `GridPixelElement` + `TagElement` + `AdvButtonElement`（`NativeBoard.cs:39-119` 字段表），只补 `PixelWindow.FixBounds` 一个方法让窗口能夹进屏幕（`:228-231`）。原生窗口天生跟随 UI 缩放/层级/拖拽。

### 3.3 高危区二：本地化层 —— **完全没碰**

`L.cs` 333 行只**读** `LocalizationSettings.SelectedLocale`（`:228-255`），从不注册表项、不注入翻译：

- 译文来自**编译进 DLL 的内嵌 TSV**（`:298-327` 读 `DangpuPlus.Lang.<lang>.tsv` 资源流；csproj 里 6 个 `EmbeddedResource`）。
- **中文原文当 key**：`L.K(zh)` 直接 `return zh`（`:116-119`），写代码时就写中文，渲染时 `L.T(zh)` 查表（`:121-141`，缺失回退 en → 中文）。7 语言（zh/en/de/es/fr/ja/ru）零侵入。
- 语言切换靠 **1 秒轮询**（`:21-41` 的 `Lang` getter）+ `OptionsPage.Tick` 比对 `_sectionLang` 后 `RefreshSections` 重刷分区名（`OptionsPage.cs:500-513`）。

**这是对"本地化高危区"最好的答案：不 patch、不注册、只消费。** 代价是轮询 + 内嵌资源体积。

### 3.4 高危区三：存档链 —— 碰了 1 个方法，只读不写

### 5.2 声明式 `Row` + 单字符 `kind`


### 5.6 三套 UI 框架按场景分用

- 要"像游戏自带窗口"的（Dashboard/帮助/列表）→ **原生 `PixelWindow`**（`NativeBoard` 1943 行，支持标签页/分页/排序/双击）。
- 设置项 → **游戏原生选项系统**（玩家在熟悉的地方找开关，天然支持待提交值/变灰/多语言回调）。

### 5.7 帮助文档用 DSL

两份 523 行内嵌 md（`DangpuPlus.Help.zh.md` / `.en.md`），靠 `@how`/`@setting`/`@see` 三个标记做结构化，`HelpTab` 解析后填进原生窗口（`HelpTab.cs:63-110`：三列 + 标签页 + 历史回退栈 `History`）。**文档与代码同仓、同编译、同版本**，不靠外部 wiki。

## 7. 反面教材：为了"大"付出的代价

### 7.1 共享静态枢纽 = 隐式硬依赖，"可选"是假的

实测 **85 个文件、492 处**引用 8 个枢纽静态类：`Hud.*` 238 处、`BoxTags.*` 138 处、`Recommend.*` 37、`ModTheme.*` 34。`Hud` 当基础设施可以接受；**但 `BoxTags` 是"可选功能"**——它的 `IsContainer`/`AddUsableGrids`/分类表被洗白分拣、台面分拣、多页找回、售货机补货等十几个功能直接调用（`LegacyRescue.cs:105-108` 即活例）。结果：玩家关掉"箱子分类"，其余功能失效或行为诡异，作者只能靠**选项文案**（"需开启箱子分类"）打补丁。**教训：库就该是库（不可关），功能才可关。**

### 7.2 开关不能热切换

`Sections.*` 是启动快照（`Core.cs:66-70`），分区/功能开关几乎全标"重启游戏后生效"，也没有 setter 触发重注册。换来的是**不用"运行时拆 Harmony 补丁"**（那本来就脆）。建议拆成"能热切的纯 UI/纯算法开关"与"要重注册的补丁类开关"并系统化——它其实已经这么干了（`AutoAppraise`、`PopupScale` 立即生效），只是没系统化。

### 7.3 零跨模组排序，靠运行时"怪别人"兜底

0 个 `HarmonyPriority`/`HarmonyBefore`/`HarmonyAfter`，3 个 Harmony 实例都用本地 id（`local.dangpuplus*`，不是原版约定的 `"mod." + manifest.ID`）。作者显然知道排序问题，于是写了 `ModConflict`：功能抛异常时用 `Harmony.GetPatchInfo(method)` 反查**同一原版方法上所有别人的补丁**，经 `ModLoader.ModIdOfAssembly` 查出 mod 名写进日志"可能是这几个害的"（`ModConflict.cs:18-45, 93-108`）。**诊断聪明，但替代不了排序**：`HarmonyAfter` 一行解决的确定性，靠异常归因是补救不是预防。

### 7.4 一处最脆的 patch：给编译器闭包命名

```csharp
			MethodInfo target = AccessTools.Method("WaterHelper+<>c__DisplayClass10_0:<InitLiquidContainerItem>b__9", (Type[])null, (Type[])null);
```

（`FillFromTarget.cs:15`）`<>c__DisplayClass10_0` 是编译器自动编号，游戏重编译必然变，此功能静默失效（只 `Log.Warn`）。且用字符串重载、不给参数类型表，同名重载也命中不了。**宁可放弃该功能，也不要 patch 闭包名。**

### 7.5 语义风险靠文案声明，不靠代码保证

`OptionsPage.cs:42` 写："多页升级也不加载：第 2-5 页里的物品可能在存档时丢失，关闭前先把物品移到第 1 页"。**关掉一个开关可能导致存档丢物品**，防线是"在 tip 里写明白"。它确实补了 `LegacyRescue` 找回（§3.4），但那是**事后补救**；正确做法是关功能前主动搬数据，或干脆不允许"有数据时"关。

### 7.6 空 `catch` —— 与我们的规范直接冲突

至少两处完全吞掉：`ConfigFile.cs:182-185`（读 `defaults.json` 失败静默返回空表）、`ModConflict.cs:42-44`（`catch { }`）；`L.Lang` getter 把 `Time.unscaledTime` 包 try/catch（`L.cs:26-33`）、`L.Game` catch 后静默回退（`:210-226`）。这是"保持游戏不崩"的现实妥协，但按我们"内部暴露、边界捕获 + `LogError` 带堆栈"的规范不该这么写。

### 7.7 巨型文件 + 三处同改

`NativeBoard.cs` 1943 行、`BoxTags.cs` 1791、`ModuleAutofill.cs` 1693、`FeaturePack.cs` 867。加一个带设置的功能要改**三个文件**：功能文件 + `FeaturePack` 一条表项 + `OptionsPage` 一行 Row。两处都是手写无校验——键名拼错不会编译报错，只会变成 `.state` 里的影子项，玩家看不到。

### 7.8 其他：目录平坦、约定不一、自测靠文件 IPC

371 个功能平铺一个目录（靠文件名导航，分组信息只存在于 `FeaturePack`/`OptionsPage` 的表顺序里，是隐式的）；同一文件里 `Pages` 用前缀约定、`Live` 用显式 `"h"` 标题行，两套层级表达法混用；`SelfTest` 靠 `ModData\selftest.request` 触发、结果写 `selftest.json`（`SelfTest.cs:44-46, 144-148`），还有"补丁数 < 10 判失败"的断言（`:192`）——对工坊用户自查有用，**但我们已有游戏内桥接器，不需要这套文件 IPC**。

## 8. 对我们的可用点

**直接抄（低成本低风险）**

1. **`ConfigFile` 门面**（221 行全抄）：BepInEx 风格 API + 正式/`.state` 双配置分流 + `defaults.json` 默认值迁移 + 退休键。任何"设置会长期演进"的模组都该有。
2. **功能注册表 + 熔断**（范式 A）：表 + 4 个委托 + 每项独立 try/catch + 连续失败停用。文件少、无反射、启动顺序确定。
3. **全局版本纪元**（`InventorySignal`）：3 个原版方法 + 2 个 ModHook 换一个 `int`，代替一堆失效事件。我们的估价缓存、容器索引都能用。
4. **`SafePatch` 单点补丁器**：唯一入口 + `Missing` 清单 + 失败不抛，并自动给每个被补方法挂一个 `Guard` finalizer（`SafePatch.cs:19-38, 108-111`：用栈帧判断异常是否出自本模组，是才吞）。这个 `Guard` 值得单独复用。
5. **`IPendingValues` 级联置灰**（`OptionsPage.cs:462-465`）：一行谓词实现三级依赖，不点应用就变灰。
6. **帮助 DSL**（`@how/@setting/@see` + 内嵌 md + 原生窗口）：文档与代码同版本，避免 wiki 漂移。
7. **Esc 统一拦截点**（`Panel.cs:106-144`）：`StoreUIManager.ResolveEscape` Prefix + 同帧去重，一个口子管所有面板。

**抄思路，改实现**

8. **§3.3 本地化策略**：中文原文当 key + 内嵌 TSV + 只读 `SelectedLocale`。我们单语言用不上多语言，但"**不 patch 本地化层**"要变成纪律。
9. **§3.4 存档链纪律**：`DecodeNodes` 只观察、落位推迟到 `Update`、模组数据走私有 JSON（`saves/slot<N>.json` + `.bad` 备份）。这是"持久化只写模组私有键"的现成范例。
10. **§3.2 显示层四道护栏**：`GUI.matrix` try/finally、缩放记原值、排版上下文 Prefix+**Finalizer**、Dashboard 复用原生 `PixelWindow` 而非自绘。**最后一条尤其重要**：做 Dashboard 先看能不能拼原生窗口，别急着上 IMGUI。

**明确避开**

11. **不要**把可关功能当库用（§7.1）：要么做成不可关的库，要么依赖注入（拿接口，不拿别人家的静态类）。
12. **不要** patch 编译器生成的闭包名（§7.4）。
13. **不要**在内部逻辑里空 catch（§7.6）；熔断必须留 `LogError` + 名称。
14. **不要**让一个开关的关闭导致存档数据丢失（§7.5）——关之前主动搬数据。
15. **要**写 `HarmonyAfter`/`HarmonyPriority`（§7.3），别指望事后归因。
16. **要**把"能热切"与"要重启"分成两类并系统化（§7.2），别散落成文案。

**规模参考线**：103 功能 / 8.3 万行 ≈ 每功能 800 行；而核心基础设施（`DangpuPlus\` 命名空间）只占 **8,100 行 / 9.7%**，其余 90% 是功能实现。**一个能装 100 个功能的内核，本身只要 8 千行。**
