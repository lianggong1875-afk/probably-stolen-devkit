### 2. 它是不是又一个好感度系统？——不是，一个数字都没有

全仓搜 `affection / trust / favor / score`，**只命中两个台词键名**（`RomanceDialogue.cs:1078` 的 `r13t_trust`、`:1235` 的 `r17_trust`），没有任何计分器、没有任何 ±1/+2 权重。真状态是三样：`relationship`（`"none"`/`"dating"`/`"married"`，`RomanceSave.cs:25`，被 `Scheduler.cs:100`、`CareRules.cs:11`、`ScavengingRules.cs:9` 读）、`completed`（`List<string>` 事件 id，`:31`，`Has/MarkDone` 在 `:231/:236`，被 `Scheduler.NextEligible` 逐条查）、`decisions` / `rewards`（分支 token / 已发奖 token，`:33-35`，`TryDecide/TryReward` 在 `:249/:259`，只做幂等）。外加两个总开关：`optOut`（玩家可整支线退出，`Scheduler.cs:46`）与 `weddingCommitted`（婚礼已落地，`:62`）。

> **所以它没犯 Eleanor 那个错（算了一堆数却没人读），因为根本没有可算的数。** 代价换到了另一头，见 §5.1：同一个语义存了两份（`weddingCommitted` + `relationship=="married"`），两份就要配一套自愈代码。

**推进的唯一闸门链**（`Scheduler.cs:85-105`）：事件必须按 `Events.MainLine`（11 条，`Events.cs:37-41`）顺序完成；`07a` 及之后额外要求 `relationship == "dating"`；`09_wedding` 还要求"已闭店 + 求婚被接受"（`Scheduler.cs:75`）。间隔由 `Events.DelayFor`（`:43-60`）给 0-7 天，`nextEligibleDay` 一条字段统管。

**入场前置读的是原版卢线**（`RomanceGate.cs:15-29`）：反射取 `StoreClientData` 的私有字段 `louCapturedDay / louShotDay / louRevealDay / louTrapDay / isLouTrapWon / louLockerPaidDay` 与 `GetLouDemandMinimum/Remaining()`，据此判定原版卢主线走到哪个结局（`Scheduler.cs:28-34` 的 `Delivery/Locker/Warehouse`）——**恋爱线只在原版主线通关后开门**（`RomanceGate.cs:104-114`）。这是全模组最关键的设计：不去猜玩家进度，直接读原版账。

**结婚后落到游戏里的东西只有三样**：① 她按 `VisitIntervalDays = 3` 来店（`MarriedRules.cs:7,22-33`），每次 `CanVisit` 还要过 `weddingCommitted && relationship=="married" && !optOut`；② 六件**实体纪念物**进背包——`lou_romance_orders_copy / flowers / rings / home_key / ring_player / ring_lou`（`RomanceItems.cs:25-27`，戒指两枚＝你一枚她一枚），其中三件可"补领"（`:33` `Reissuable`，带去重计数防刷）；③ 一座**新地点**（她家，见 §6.5）。没有共同财产、没有合并钱包、没有新顾客形态——**婚后不新增系统，只新增挂点**。

### 3. 关系推进的挂点：对话选项，不是送礼也不是交易

一个事件 = 一个顾客实例 + 一串 `Dialogue` + 若干选项，四步：

1. **造客**：`RomanceFlow.BuildClient`（`:229-258`）`new StoreClient{ identifier = "loyce_lou_romance."+eventId, spriteName = RomancePortrait.ForEvent(eventId), clientFaction = "FACTION_BLACK_MARKET", clientIntent = 5, dismissable = true, arrestable = false, nonShootable = true }` + `ModHelper.SetClientSource`；
2. **插队**：`manager.AddNextClient(client)` + `TryCallNextClient()`，随后**核对是否真的上台**（`RomanceFlow.cs:100-106`：`GetClientBlueprint() != client` 就把自己从 `clientStack` 摘掉并清 `activeEvent`）——这一步很多人不写，结果是"事件没触发、存档却已标记完成"；
3. **选项**：`Dialogue.AddChoice(ItemDirectory.CreateEmptyItem("lou_romance_choice"), Loc(key), …)`（`RomanceDialogue.cs:77`）——**用一个专门注册的空物品当选项图标**；落点进 `Scheduler.Resolve`，写 `decisions` 与 `completed`；
4. **收尾**：`OnDismiss` → `RomanceFlow.OnLeft`（`:278-292`），没走完就把 `nextEligibleDay` 推到明天并保留 `pendingEvent`——**关窗即弃也能续**。

交易不是按钮，是婚后**她在对话里提供服务**：护理（`ShopCare.Theft/Cleaning`，7 天一期，`CareRules.cs:7,36-48`）走原版 `StoreService.UpdateCost`（`LouShopCareCleaningPatch.cs:5-14`）与 `PlayerStore.HandleInsurance`（`LouShopCareInsurancePatch.cs:8-16`）；拾荒是"她邀你一起去"（`ScavengingRules.cs:25-64`）。送礼是**她给你**（`MarriedRules.PickGift`，`:123-150`：`cup_noodle/nudka/nutrifruit/cat_bar/li_eat_snackbar/energy_drink`），不是玩家讨好她。

**面板是"补漏"而不是"主菜"**：`Ctrl+Shift+L`（`RomanceInput.cs:13`，`KeyCode 108` + 左右 Ctrl/Shift 都认）开一个 `CustomUIManager.Window("loyce_lou_romance.conversation", …, "paper").SetSize(490,350)` 的纸面窗口，按钮只有"状态 / 补领纪念物 / 补领每日 / 继续剧情 / 告白 / 求婚 / 聊天 / 关闭"（`RomanceUi.cs:101-213`）——**全部是"把卡住的事件接回来"，剧情本体永远发生在柜台对话里**。这是关系类模组该有的分工：UI 负责救济，对话负责内容。

### 5. 踩坑与红线

**5.1 同一语义存两份 → 必须自带修复器。** `weddingCommitted` 与 `relationship=="married"` 是两个字段，代码到处写 `s.weddingCommitted && s.relationship == "married"`（`CareRules.cs:11`、`ScavengingRules.cs:9`、`MarriedRules.cs:24`）。为此它带了两套自愈：`SaveDateRepair`（109 行）把"未来日期"逐字段夹回今天（`SaveDateRepair.cs:23-45`），`RescueRules.ClearStaleProtection`（`:22-40`）在未婚档上清掉残留的婚姻保护状态，注释明写 "routine inspections return to vanilla"（`ModEntry.cs:141-147`）。**代价：`SaveDateRepair` 109 行 + `Migrate` 的 16 级迁移（`RomanceStore.cs:57-194`）合计 247 行，占存档类 582 行的 42%——这四成代码全在回答"旧档怎么办"。**

**5.2 把原版对白的节点数写死。** `AttachArrest` 要顺 `mainDialogue.nextDialogue` 走 **4 个**节点（晨间 3 个，`RomanceRescue.cs:136`），走不到就 `throw new InvalidOperationException("Original security sentence announcement changed; R11 cannot attach.")`（`:166`）。游戏改一版保安台词必炸——**但它是显式炸（有日志），不是静默降级**，这点值得学。

**5.3 反射拿私有字段 = 版本脆弱面。** 整个前置判定压在 `StoreClientData` 的 6 个私有 `lou*` 字段和 2 个私有方法上（`RomanceGate.cs:15-29`）。字段改名不会有编译错误，只会让 `VanillaResolved` 永假（恋爱线再也不触发）。

**5.4 `activeEvent` 是内存态，读档必须成对清。** `OnLoading`（`ModEntry.cs:232-243`）与 `ResetRuntimeForRestart`（`:245-254`）各清一遍 8 个静态子系统——少清一个就变成"客人在，但那不是我的事件"。

### 6. 对我们的可用点

**6.1 "关系等级"用 `completed` 事件链 + 一个 `relationship` 枚举，不要整数。** 我们 `FreyaState` 现在是 `met_story` / `story_step=3` 这种竖线键值，可直接扩成 `done=lou_romance_01|05|07a` + `rel=dating` 两段；`Scheduler.NextEligible` 那 40 余行（`Scheduler.cs:36-83`）就是"下一个该来谁"的全部逻辑，可整段照抄。

**6.2 客人"插队"必须回读是否真的上台。** `AddNextClient` + `GetClientBlueprint() != client` 就回滚（`RomanceFlow.cs:100-106`）。我们两款模组都有"自家 NPC 该来却没来"的场景，这一句能省掉整类幽灵事件。

**6.3 关系到位后应该给玩法，不是给台词。** 三处最便宜的：`ScavHelper.GetMaxScavAttempts` Postfix +1（`ScavengingRules.cs:81-88` 就 8 行）、两处受伤率 Postfix ×0.75、`StoreService.UpdateCost` Postfix 打折。深空当铺要"老主顾照顾生意"，这是现成的三个数值挂点，每个都只有 Postfix 一行。

**6.4 用"她替你把案子摆平"表达关系，比加好感条更有戏。** 落点是 `secData.evidenceLevel / state` 直接清零（`RomanceRescue.cs:222-223`），做法是把营救对白**接在**原版宣布之后而不是替换原版——顺便绕开跨模组冲突：我们只往链尾加内容，不动原版文本。

**6.5 新地点：`ModHelper.AddAfterhourLocation` 的 11 参签名已核对。** `AddAfterhourLocation(modId, "lou_romance_home", 名称, null, null, null, atlasKey, spriteKey, null, 可见条件, 可进条件)`（`RomanceHome.cs:143`），配 `home.usesAfterhourBag = false` + `onArrive/onLeave` 建自家面板；进门前置是**持有 `lou_romance_home_key` 这个物品**（`:214`）——"关系给钥匙、钥匙开新地点"比"解锁一张地图"省一半脚本。

### 1. 它给哪个"箱"加演出：所有被上锁的补给箱

挂点是 **`LockHelper.UnlockContainer`**，不是"打开容器"、也不是"生成战利品"：

```csharp

    && item.IsTag("LOCKED_CONTAINER_TAG") && item.GetTagReadonly("LOCK_STATUS").GetBool())
```

`SUPPLY_CRATE` 是 `LockHelper.InitLockedContainerItem` 给**任何**上锁容器打的类型（`LockHelper.cs:37`），解锁时被移除（`:89`）。所以覆盖的是"凡是被锁住的箱子"，五个 `loot_crate_*` 只是主要来源（`PreBuiltItemHelper.cs:91-95`）。**挂点选得对，是因为原版解锁时还会重摇内容**：`UnlockContainer` 末尾调 `TryRefillForBetterLuck`（`LockHelper.cs:98`），而它会把箱内物品**全部销毁重抽**（`PreBuiltItemHelper.cs:303-328`，条件：玩家当前幸运 > 箱子生成时的幸运）。挂在 Prefix、或挂在"打开容器"，显示的都会是旧内容。

演出内容全部来自 **Postfix 后重读箱内实况**：`CrateData.ReadRewards(contentWindow.child.childItems, …, CrateOdds.ForCrate(item))` → `Enqueue`（`CrateUnlockPatch.cs:58-59`）。

### 2. 演出怎么做的：自建 Canvas + 关掉所有别的 Canvas

- **不用 `CustomUIManager.Window`**：`RevealView` 自己 `AddComponent<Canvas>() + CanvasScaler + CanvasGroup`（`RevealView.cs:234-241`），面板尺寸/坐标硬编（323/-124 这类常数）；
- **模态靠"把别人的 Canvas 全关掉"**：`ModalCanvasGuard.Enter()` 挂 `Canvas.willRenderCanvases`，每帧把自己 `sortingOrder` 设 32000，并把场景里所有其它 Canvas 的 `enabled = false`（`ModalCanvasGuard.cs:38-56`），退出时逐个恢复（`:64-82`）；
- **输入靠两个补丁**：`EventSystem.Update` Prefix 返回 `!BlockInput()`（`RevealEventPatch.cs:10-13`）、`InputActionManager.Update` Prefix 重置所有 `InputActionHandler` 并锁 `lastMousePosition`（`RevealInputPatch.cs:18-45`）；

### 4. 关键代码摘录

**① 一次开锁只花一张：把"用掉的"换成拆分出来的那一个**（`OpenLockPatch.cs:10-23`）——它同时校验 `IsCurrentlyLocked` 与 `CanOpenLock`，**只在"真能开"时才拆**，否则一张错卡会把叠白白拆散（原版开不了时只播一声 negative beep、不销毁卡）。

```csharp
[HarmonyPatch(typeof(LockHelper), "TryOpenLock")]
static void Prefix(ref GameItem key, GameItem box, string keyLockId)
{
    try
    {
        if (Stack.IsStack(key) && LockHelper.IsCurrentlyLocked(box) && LockHelper.CanOpenLock(box, keyLockId))
            key = key.GetSplitItem(1);      // ← 原方法里 key.Destroy() 只毁这 1 张，叠剩 4 张
    }
    catch (Exception ex) { Debug.LogError("[KeycardStack] open lock: " + ex); }
}
```

**② 解序器：先捕获三个槽位，再在"每夜服务/加速时"补弹卡**（`DeseqCapturePatch.cs:8-16` + `Deseq.cs:154-166`）

```csharp
// 捕获：CreateMachineInventoryWindow 返回 6 元组，取第 4/5/6 项（chip/input/output）
static void Postfix((PixelWindow, GameSlotInventory, GameGridInventory, GameSlotInventory, GameSlotInventory, GameSlotInventory) __result)
    => Deseq.pending = new DeseqSlots { chip = __result.Item4, input = __result.Item5, output = __result.Item6 };

static GameItem Copy(GameItem card)                               // Deseq.cs:154
{
    GameItem val = DirectoryMaster.Item(card.identifier, true);   // 新建（原版 GetSplitItem 也这样，不搬 state）
    Stack.CopyState(card, val);                                   // ← 所以这里手写深拷贝
    val.unitCount = card.unitCount; val.name = card.name; val.unitValue = card.unitValue;
    return val;
}
```

### 5. 踩坑与红线

**5.1 用 `unitCount` 换"零序列化"，代价是"每处都得想起它"。** 这是全节最值钱的取舍：不新增字段 → 不写存档、不写迁移、不写读档修复；但**任何读 `unitValue`、`GetCurrentValue`、数量上限的地方都会算错一倍**，它一共补了 7 处（见上表）。做堆叠前先 `grep` 一遍 `unitValue` / `GetCurrentValue` / `unitCount == 1`。

**5.2 拆分会丢 `state`——这是原版 `GetSplitItem` 的硬行为。** `GameItem.cs:1313-1332` 里新对象由 `DirectoryMaster.Item(identifier)` 造，**`state` / `modifiedState` 一个字都没搬**。门禁卡没状态所以侥幸无事；**换成"写了序列号的钥匙卡 / 有耐久的工具 / 已鉴定过的货"，照这套堆叠就是静默数据丢失**。要用就先 `Stack.CopyState`（照 `Stack.cs:40-62` 的深拷贝），或者干脆别用 `unitCount`。

**5.3 只覆盖了 6 种卡，漏了 2 种。** 原版有 7 种钥匙卡工厂（`MiscItemDirectory.cs:59-66`：`cmd/sec/sci/med/eng/sup/ser` + `blank`），`Ids` 只含 `cmd/sec/med/eng/ser/blank`，**`sci_keycard`（`LOCK_ID_SCI`）与 `sup_keycard`（`LOCK_ID_SUP`）既不堆也不显示张数**。两者结构与其它卡完全一致（`MiscItemDirectory.cs:1096-1115`、`:1198-1217`）——**大概率是漏了（推测）**；补上只需再加两个 10 行 Postfix + 往 `Ids` 加两个字符串。

**5.4 机器槽位必须禁堆，按物品存记忆一律用弱引用。** `maxSlotAmountItemFunc` 写 `(!IsCard(it) || inv is GameSlotInventory) ? 1 : 5`（`Stack.cs:104`），否则解序器的 input/chip/output 会把 5 张当 1 张吃掉；解序器注册用 `ConditionalWeakTable<GameItem, DeseqSlots>`（`Deseq.cs:14`）+ `List<WeakReference<GameItem>>`（`:16`），`ServiceAll` 顺手清死引用（`:62-87`），驱动是 `ModHook.OnHandlingNightlyServicesLate`（`KeycardStackMod.cs:20`）而不是 `Update()` 轮询——**能挂 nightly 就不挂帧。**

### 6. 对我们的可用点

**6.1 想给物品加堆叠，先问一句"每件有没有私有数据"。** 没有 → 两个委托（`mayStackItemFunc` + `maxSlotAmountItemFunc`，`Stack.cs:99-106` 共 8 行）+ 一张 id 白名单，再 grep 完 `unitValue/GetCurrentValue/数量` 补乘张数；有 → 走 ③ 的"定长字符串队列"，或直接放弃堆叠。**这是本档案最省事的一条判据。**
**6.2 "用掉一张"的正确姿势是 `key.GetSplitItem(1)` 后把参数换掉**（`OpenLockPatch.cs:16`），而不是自己 `unitCount -= 1`。前者让原版的 `Destroy()`/计数/回调全部照常跑，后者要自己补一整串副作用。
**6.3 运行时生成叠图，零美术。** `StackSprite` 173 行就能给任意方形物品画"一叠"（底黑化 + 每层 2px 偏移 + 满叠红封条），按 `atlas/path/张数` 缓存。深空当铺要给"一叠刮刮乐 / 一沓钞票 / 一包药"做图标，直接抄这份。
**6.4 "机器自动补料"整套可整块搬**：`CreateMachineInventoryWindow` 的 6 元组 Postfix 抓槽位 → `ConditionalWeakTable` 按机器存 → 夜间/加速时 `Service` 弹成品并从"机器所在容器 → 前柜 → 后仓"找下一件原料（`Deseq.cs:104-184`）。养鼠工厂、全自动制药都缺这一块。
**6.5 让"张数"参与交易要一次改三处**：价值（`GetCurrentValue`/`GetNegociatedValue`）、黑市交换（`ExchangeBarter`）、顾客订单（`StoreRequest`）。③④ 不约而同都在这三处各写一份，说明这是原版的固定三叉口。
