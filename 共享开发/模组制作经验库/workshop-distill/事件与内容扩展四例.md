## 0. 先给结论：四件事、四种姿势

| 要干的事 | 谁做得最干净 | 手段 | 关键原版入口 |
| --- | --- | --- | --- |
| **只读事件池做展示** | Shutter Events | 纯 `ModHook` 定时 + 直接读 `GetActiveEvents()`，**零 Harmony** | `StoreEventManager.GetActiveEvents()`、`StoreEvent.duration/isPermanent/GetEventPriceEffect()` |
| **往随机流程注入事件** | Scavenging Events（做法有争议） | 自建 `EventDefinition` 注册表 + 权重轮盘 + `Prefix` 返 `false` 抢整个拾荒入口 | `ScavHelper.ScavengeDumpingGrounds()`、`ModHelper.GetModData/SetModData` |
| **内容外置 + 一次性标记** | 仰慕者与新闻 | C# 常量表 + 本地化 key 拼装 + ModData 三种"已发过"记法 | `PreBuiltItemHelper.CreateHandnote`、`StoreEventManager.cosmeticEventBlueprints` |

一句话教训：原版把"事件"和"掉落"都做成了可扩展的表（`StoreEventBlueprint` / `LootRegistry` / `ModHook.OnLootRolled`），四个模组里**只有 Scavenging Events 放弃这些口子去整段替换方法**——换来自由度，也换来"和同类模组互斥"。

## 2. 往随机流程注入事件：Scavenging Events（3844993390）

### 2.1 靶点只有一个：`ScavHelper.ScavengeDumpingGrounds`（Prefix 返 false）

```csharp

	{
		if (!ScavHelper.CanScavenge())

			return true;
		}

	}
}
```

- **不是** `ModHelper.RegisterLootTable`，**也不是** `ModHook.OnLootRolled`（全目录 grep：只调 `LootRegistry.Roll(...)` 读原版表，见 §2.5）。它自己 `new Harmony("scavenging_events")` + `PatchAll(typeof(ScavengeDumpingGroundsPatch).Assembly)`（`core/ModInitializer.cs:101-102`）——`CanScavengePatch` 也靠这次整程序集扫描打上。
- 命中事件时**整个原版拾荒被跳过**：伤口判定、`HealthData.RollLuck()`、坏运气空手、音效、`RunStats.OnScavengedItems` 全不发生；为不丢账，模组手工复制了原版尾段（`EventManager.cs:131-148` vs `ScavHelper.cs:121-130`）：递减 `dumpingGroundMinor/MajorWoundImmunitySearchesLeft`、`scavengingAttempts++`、`RunStats.OnScavengeAttempt()`。
- 事件**不消耗**原版掉落表（自己发奖），所以 25% 的拾荒日玩家拿的是事件收益而非 `dumpingGroundTG` 掉落。概率硬编码：`EventManager.cs:90` `int num = 25;`。

### 2.3 抽签：先事件链，再权重轮盘


`core/RunData.cs`：`[Serializable] class RunData { int dataVersion = 1; List<string> triggeredEvents; }`。存：`ModHelper.SetModData("scavenging_events", "run_data", JsonUtility.ToJson(Current))`（`core/RunDataManager.cs:53-63`）；读：`JsonUtility.FromJson<RunData>`，异常则重建并立回写（`:22-51`）。命中即记账，只对 `!Repeatable` 生效（`EventManager.cs:70-84`）。`AccessCardEvent.Execute` 里又手动 `Add/Save` 一次（`Events/AccessCardEvent.cs:10-18`）——注册时已记过，属重复保险。生命周期：`OnNewGameStarted → CreateNew()`、`OnGameLoadedLate → Load()`（`ModInitializer.cs:112-122`）。

### 2.5 奖励落地：读原版表 + 塞夜间拾荒容器

所有 Reward 同一骨架（`UnexpectedFortuneReward.cs:8-38`）：`LootRegistry.Roll("materialTable")` → `ItemSpawner.Spawn(id)` → `GraphUtils.TryAcceptAll(EmporiumEntry.Instance.afterhourInventory, item, -1)`（返回 > 0 表示还有装不下的）。表 id 全是 `TableMaster` 常量（`TableMaster.cs:6-26`）：`materialTable / accessCardTable / householdTable / allModuleTable / toolTable / makeshiftWeaponTable`（另有 `dumpingGroundTG` 是原版拾荒**表组**，`ScavHelper.SpawnDumpingGroundLoot` 用 `LootRegistry.RollGroup` 消费）——**没有一处把物品 id 硬编码成随机结果**（`satchel`、`rat` 这类定死的是剧情道具）。奖励池交给原版数据、模组只决定"抽几次"，这是全套代码最值得抄的一处。

### 3.2 "只收到一次"三种记法，模组三种都用了

| 记法 | key | 语义 | 位置 |
| --- | --- | --- | --- |
| 集合字符串 | `notes_t{tier:00}_used` = `"1,3,7"` | 该档已抽过的 index，抽完清空重来 | `AdmirerNotes.cs:60-104` |
| 布尔+日期、单次布尔 | `npc_seen_{id}=day`、`npc_rep_{id}=rep`、`npc_done_{id}=bool`（见过→隔日投递→永不重复）；`intro_letter_given`、`injury_gift_pending`/`_tier`、`note_box_granted`（只发一次的开关） | `NpcNotes.cs:100-104,239-270`、`Patch_SecretAdmirerIntro.cs`、`InjuryNotes.cs`、`NoteBox.cs:13` |

去重 + 耗尽重置的核心（`AdmirerNotes.cs:85-104`）：先数"该档还有几个可用"，若为 0 就把 `1..num` 全从 set 移除（**清空重来，内容不枯竭**）；再把可用下标收进 `List`、`Random.Range` 取一个、写回 `string.Join(",", ...)`。

### 3.3 13 位特殊人物：identifier 前缀表 + 隔日投递

`NpcNotes.cs:18-98` 是一张 `NpcDef { Id, Name, Prefixes }` 表，13 位：`georgio / eleanor / serpico / lou(wanted5) / joe(insurance) / sawyer(janitor) / jackson(inventor) / butcher(wanted2) / bailey(wanted1) / arthur(wanted3) / li(wanted6) / juan(wanted7) / john(wanted8)`。匹配靠**顾客 identifier 前缀**（`:223-237`），并显式排除伪装同名：`if (identifier == "eleanorUncle") return false;`。

三段式，全部靠补丁落在原版时序上：① `StoreClientManager.AddClient`/`AddNextClient` 的 **Prefix** → 记 `npc_seen_{id}=当天`、`npc_rep_{id}=当前声望`；② 次日 `StoreShutterButton.OnShutterDoorOpenMorning` 的 **Postfix** → `DeliverPending()`：`dayCounter > seenDay && !npc_done_` → 按记录时声望定档（`<30 → t1`、`<100 → t2`、否则 `t3`）取 `psm_npc_{id}_t{n}`，上柜台 + `npc_done_=true`；③ 全体被 `StartingPerk.IsSecretAdmirer()`（开局特性）门控——**内容型模组最省事的收窄手段**。

`OnShutterDoorOpenMorning`（`StoreShutterButton.cs:108-192`）是原版"开店总闸"：开头 `FireOnShutterOpenedEarly()`、结尾 `FireOnShutterOpenedLate()`，中间是报纸/许可/导师纸条/`HandleSecretAdmirerOnOpenShutter()` 等一长串发放。**挂它的 Postfix = 排在所有原版早晨发放之后**，纸条不会盖掉原版纸条。

- 每个专精 = 20 行以内补丁类 + 一次 `SpecGate.On(cat, slot)` 判定；111 个补丁靠同一行门禁，"未选中 = 完全不生效"是结构性保证。
- 数值全在 `Core` 静态字段 + `ModConfig`，补丁里只剩结构、没有魔法数字。
- 照抄要改两处：① 空 `catch` 换边界捕获 + `LogError`（工作区硬规范）；② 写标签类（如 `SpecModuleTemp`）必须配 `ResetAllTempStat` 式还原 + 幂等标记，否则玩家重置专精后加成永久留在物品上。

## 7. 坑

### 7.1 "作者明说的"——只有代码层面的等价约束（工坊简介未取证）

1. **事件链要求"从早期存档开始玩"**：Stage 1 门槛 `dayCounter > 14 && GetScavTimeLeft() > 2`，Stage 4 还要求 `storeClientData.isButcherHuntOver`（屠夫剧情已完，推测）。中途加入且已过 14 天、剧情状态不匹配的存档会永久卡在 Stage 1 前——这就是"不建议中途加入"这类提示的技术原因（简介未取证）。
2. **内容被开局特性门控**：纸条/NPC 纸条/收纳盒都要求 `StartingPerk.IsSecretAdmirer()`；老存档没这个 perk = 装了什么都看不见（`AdmirerNotes.cs:42-47` 直接 `return null`）。
3. **热禁用不彻底**：熟练度 `OnDisable` 明写"补丁由加载器管理"；Scavenging 的 `Initialize()` 在 `Init()` 里就跑完 PatchAll + 注册事件 + 绑钩子，`OnDisable` 只打日志（`core/ModEntry.cs:19-22`）。运行时关掉模组，事件/加成仍生效。
4. **单次事件不可回滚**：`RefuseStage → EndQuestChain()` 写 `isEnded = true` 进档，没有"重开链"接口。

### 7.2 代码里能看出来的坏档 / 冲突风险
**A. 会污染存档状态**

1. **把显示文本写进物品标签**：`CreateHandnote` 把本地化结果写进 `HANDNOTE_BODY`。纸条一旦发出，换语言/改文案都不更新（100 条内容 = 100 份"发出即冻结"的文本）。新闻有 `RefreshActiveNews` 兜底，纸条没有。
2. **幂等标记让加成变永久 + `lvl.{cat}` 只增不减**：`PROF_FILTER_SCALED_TAG` 把滤芯耐久永久 ×2、`PROF_VINTAGE_APPLIED_TAG` 同理，重置专精不回收；等级缓存则让"永远回不到真实经验对应等级"（`:264-275`）。两者都是可接受的设计取舍，但我们要做"可重置"系统就必须自己写回收与重算。

**B. 抢原版入口 / 补丁面失控**

3. **Prefix 返 false 的连锁损失**：事件日跳过原版全部分支（含别人的 `OnLootRolled` 钩子，§5.2）；`ConsumeScavengeAttempt` 是手工复制的原版尾段，原版一改就漂移且不报错。
4. **111 个补丁 = 111 个冲突点**：覆盖 76 个方法、19 个方法被自己重复补 2~6 次；同模组内多个 Prefix/Postfix 的相对顺序靠 Harmony 默认规则，全项目只有一处 `[HarmonyPriority(0)]`（`OnItemTradedFinalizer`）。
5. **同一方法拆成 3 个补丁类**：仰慕者把 `Patch_SecretAdmirerGate`(Prefix) + `Patch_SecretAdmirerChance`(Prefix/Postfix) + `Patch_SecretAdmirerIntro`(Postfix) 全打在 `HandleSecretAdmirerOnOpenShutter` 上——"门关了就什么都不该发生"只能靠每个回调里再查一次 `NoteGate.Paused()`（代码确实这么写了），别指望"Prefix 返 false 会顺带跳过 Postfix"（取决于 Harmony 版本，推测）。
6. **不写参数类型表**：仰慕者 9 个补丁全部省略 `new Type[]{...}`。查过原版 `AddClient(StoreClient)`、`CreateSecretAdmirerNote()`、`HandleSecretAdmirerOnOpenShutter()`、`OnShutterDoorOpenMorning()`、`ReceiveMajorWound()` **当前都无重载**，今天安全；一旦游戏加重载，整批 `PatchAll` 会一起挂（`AmbiguousMatchException`，见 [`07-踩坑台账.md`](../../07-踩坑台账.md) 同类前科）。

**C. 状态机 / 空引用**

7. **裸读 `PlayerStore.Instance`**：`Board.Build()` 直接 `PlayerStore.Instance`（`Board.cs:551`，无 `HasInstance` 判定）；仰慕者、Scavenging 的奖励函数同样直接读——隐式创建半初始化对象是这类写法的经典代价。
8. **UI 锁泄漏**：`EventUIState.Lock()` 后窗口若被非正常路径清掉，`CanScavenge()` 会一直 false（拾荒彻底失灵）；它靠 `OnLeavingStoreEarly/OnReturningStoreEarly` 兜底（§2.7），没这个兜底就是存档级软锁。
9. **蓝图残留**：`cosmeticEventBlueprints` 是 `static`，加进去的 60 条永不撤；模组禁用后原版仍会抽到 `psm_news_*`，`storeEventFunc` 里 `GetLocalized` 只返回 key → 报纸出现 `psm_news_07_title` 这种原文。热禁用场景要自己写"移除蓝图"。
10. **`AccessCardUI`/`RobberyUI` 不判 `CustomUIManager.Instance`**（`AccessCardUI.cs:9-11` 直接 `Lock()` 后建窗），只有 `LonelyRatUI`/`UnexpectedFortuneUI` 判了——UI 管理器缺失时锁不会释放。

**D. 死代码 / 编码**

11. **双份真相**：`EventSettings` 那 20 个权重常量**整份没人引用**（实际权重写在 `ModInitializer.RegisterEvents` 字面量里，grep 只命中定义行）；`EventManager.TryTriggerEvent(chancePercent)` 同样无人调用。改数值的人一定会改错地方。
12. **反编译中文日志是乱码**：熟练度多个文件（`SpecClinicRulePatch`、`LegalShieldPatch`、`OnItemTradedFinalizer`…）的字符串是 GBK 被当 UTF-8 解的乱码（例 `"娉曞姟鎶ょ浘锛?`），不影响逻辑，但引用时要避开这些行。
