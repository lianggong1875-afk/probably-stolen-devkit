## 1. `3829353625` 鉴定单自动丢弃 Appraisal Slip to Trash

**id**：`3829353625`（`<ID>appraisal_trash</ID>`，v1.0.0，游戏 0.46D，`<Capabilities />` 自闭合，根节点 `<Manifest>`）
**反编译目录**：`缓存文件夹\decomp_ws\3829353625\`
**为什么值得读**：全库性价比最高的一例——**109 行、24.9 万订阅**。不新增物品、UI、配置、存档字段，只把原版
刚生出来的那张鉴定单挪进垃圾桶。要学的不是功能，是**"最小可用模组"的完整形状**。

### 1.2 它怎么做到"只丢这次新生成的那张"

**扫描比对，不是生成回调。** 原版没有"鉴定单生成完毕"这种事件可挂：

1. `Prefix` 把 `EmporiumEntry.Instance.frontInvinvElement.childItems`（前台 18×4 货台，原版 `EmporiumEntry.cs:212`）
   **按引用**塞进 `HashSet<GameItem>`——"这一秒之前桌上有什么"。
2. `Postfix` 再枚举同一清单，凡**不在快照里**、`identifier == "slip"`、带 `SLIP_TITLE` 的，就是本次新生成的。
3. 桌上的威胁信/情报为什么幸免：它们同样是 `slip` + `SLIP_TITLE`（都由 `PreBuiltItemHelper.CreatePaperWithText` 造，
   原版 `PreBuiltItemHelper.cs:104-117`），但**早就存在**，已被快照收走，`!__state.Contains(item)` 直接排除。
4. 引用比较成立的前提：`GameItem` 没有重写 `Equals/GetHashCode`（原版 `GameItem.cs` 全文无 `override bool Equals`），
   所以 `HashSet<GameItem>` 是**对象身份**比较，不会被同名同 id 的纸骗过去。

**容量判定**：没有单独判容量。`GraphUtils.TryAcceptAll(inv, item, -1)`（原版 `GraphUtils.cs:166-204`）返回值是
**"没塞进去的剩余量"**：内部 `TryFindOneValidInventorySlot` 拿不到槽就 `break`，返回 `amount - num`。
作者**连返回值都不接**（`_ = item.unitCount;` 是反编译残留死代码）——垃圾桶满了自然一个都塞不进，物品原封不动
留在货台，所以"满了就留桌上"是**白送的**，不需要写 if。

**为什么费与评级照常**：`GiveAppraisalFee` 是整条链的**最后一步**，自己先把钱加了、单据字符串拼好，最后一行才
`AddDirectSellingItemToTable(...)` 造单（原版 `AppraisalServiceHelper.cs:37-47`）；评级 `precision` 更上游就定了
（`GetAcceptEstimateDialog` 先算 `correctBaseValue`/`estimatePrecision` 再调用，`:61-68`）。补丁挂 `Postfix`，
等于挂在"钱进账、单已生成"之后，不改流程也不改数值，只挪产物。

### 1.4 踩坑与红线

- **`SLIP_TITLE` 不是鉴定单专属 tag**：原版 `PlayerStore.cs:2359`、`StoreEvent.cs:229`、`PreBuiltItemHelper.cs:108`
  都在写它，所有"带标题的纸"都是 `slip` + `SLIP_TITLE`。真正起作用的是**补丁点的时间窗**（只在
  `GiveAppraisalFee` 执行期间），不是 tag 过滤。挪到别处抄这套差分，就会把玩家桌上的情报一起扫走。
- **`FrontItems()` 被调两次**（Prefix/Postfix 各一），每次新建 `List`。18×4 量级无所谓，但说明作者接受
  O(n) 重复扫描换代码短。
- **两处 `catch` 只 `Log.Error`、不 rethrow**：与本工作区"边界捕获"规矩方向一致，但塞垃圾桶失败时玩家
  只会看到单子还在桌上，无任何提示。
- **无热重载处理**：`OnEnable/OnDisable` 空实现。本例无跨帧状态（`__state` 由 Harmony 逐调用传递）才安全。
- **manifest 用 `<Manifest>` 根**（本批仅它如此），另两例是 `<Mod>`。两种 ModLoader 都认，但我们统一 `<Mod>`。
- `AppraisalServiceHelper.GiveAppraisalFee(int,int,int)` 无重载，不用写参数类型表；有重载的类必须写 `new Type[]{...}`。

### 1.5 对我们的可用点

1. **模板就取这一份**：`ModEntry`（22 行，只留 `Log`）+ 一个 `[HarmonyPatch]` 静态类 + 一处日志 = 可发布形状。
   "单据自动归档""鉴定提示音"这类单点需求不该超过 150 行。
2. **差分 > 找事件**：没有完成回调时，Prefix 快照 + Postfix 求差（按引用，不按 id），天然兼容其他模组在同一
   方法上的前后插入。
3. **容量判定交给 `TryAcceptAll` 的返回值**（剩余量），不要自己数 `childItems.Count`。
4. **"挂最后一步"**：改产物不改流程，就把补丁挂在整条链的收尾方法上，定价/评级/声望全部原样保留。
5. **反例警示**：它的过滤器（`identifier=="slip"` + `SLIP_TITLE`）单看是错的，靠补丁点时间窗兜住，抄过滤条件不抄挂点就是事故。

**全从 `item.modifiedState.dict`（`Dictionary<string,TagState>`）读，不碰私有字段。** 判定顺序在

**滤芯/香水靠 tag，水箱靠"分格液体求和"，电量靠单独一条 15 上限**——三者表达完全不同，作者没硬统一成百分比，
而是统一成 `(Current, Maximum)` 只读 struct（`:6-18`），`Fraction` 只是派生。**灌装类（药片/试纸/种子）
连 tag 都不读值**，去数 `contentWindow.childElement` 里子物品的 `unitCount`（`:117-147`），
且排除已用过的试纸（`IS_SPENT`）和装土的容器（`CONTAINER_TAG`）。

**防剧透那一刀值得单独记**：耐久是 `ItemFeature`，没验过可能是假的。`TryReadDurability`（`:68-92`）先看
`IsExposed() || IsFeatureDiscovered()`；没暴露就查 `isDisabled / IsInitiallyShown / GetPublicHidden / IsFeatureMatch`，
仍不成立时**改读 `DURABILITY_FAKE_TAG`**——"没验过就显示假值"，读不到假值才整体不显示。这是显示类功能的正解：
**能看见的必须和玩家已知的一致**，宁可不显示，也不能露出 `realCondition` 那一侧的真值。

### 2.3 "用掉的部分显示灰色"：换 Sprite，不是叠图

`DurabilityAppearance.Initialize` 抓住 `GameItemElement.background.image` 与 `fakeBackground.image` 两个 `Image`
（预览态各一份，`:91-96`），绘制时**直接给 `image.sprite` 换一张新 sprite**（`:55-65`），`Restore()` 再换回。
没有额外 GameObject、没有遮罩层、没有 Image 叠加——不增 draw call、不改层级、无需处理射线穿透。

新 sprite 由 `SpriteWearCache` 现造：按 `(WearDirection, 步数, 亮度)` 缓存变体，每张源 sprite 只读一次像素。
灰度是 `Luminance * 3 / 5`（`WearPixels.cs:162`，60% 灰），亮度滑块 `-100..100` 再作用其上（`:163`，负值乘、
正值向 255 插值）。三个白名单区域除外：`PreservedArea`（增压器那颗 3×3 指示灯，26,22）、`WearArea`（血清只取
上半 16×16）、`ProgressArea`（血清液面窗口 4,6,8,10）——**有独立指示灯的精灵不会被灰化污染**。

**空槽 vs 耗尽**（最容易搞混，判定完全不同）：
- **空槽**：`GameSlotInventory.backgroundImage` 上挂的是原版"幽灵图"——
  `SetBackgroundFadeSprite("Items/items_amenities","water_filter")`（原版 `AmenitiesItemDirectory.cs:560`、
  `MachineRAS.cs:127`），半透明彩色。模组把它**重画成纯白描边**（`FilterSlotArtwork.BuildOutline:77`：
  只保留 alpha≥16 且四邻有透明的边缘像素，RGB 拉满 255），于是空槽看起来是**空心轮廓**。
  补丁点在 `GameSlotInventory.Validate` 的 Postfix（`FilterSlotValidatedPatch.cs:5-12`）。
- **耗尽**：槽里**真的有** `childItem`，由 `DurabilityAppearance` 正常灰化 → 一块实心灰滤芯。
- 水壶本体另有一套：`PitcherFilterAlert` 在水壶图标上画 0~100 百分比徽标，状态值 `-1`=空槽（无 childItem）、
  `-2`=装了但耐久读不出、`0..100`=百分比（`PitcherFilterAlert.cs:127-154`）；槽类型是 `GameSlotInventory`
  （`contentWindow.childElement is GameSlotInventory`），两套判定互补不重叠。

**配置**：原版 `ModConfig`，不是自绘设置窗——`ModHelper.GetConfig("item_durability_bars")` 后
`config.Define("show.<id>", true, "Item display", label)` 与 `config.Define("brightness.<id>", 0, "Item display", label, -100, 100)`
各 21 条（21 物品 × 2）+ 1 条 `"alert.spent_filter"`（`DisplaySettings.cs:31-105`）。
**右键重置是自己补的**：`SettingsPreviewHover` 实现 `IPointerClickHandler`，右键（`button == 1`）把滑条
`value = 0f`（`:166-176`）——原版 `ModConfigWindow` 没有这个能力。设置窗打开后还要补一处：`ModConfig` 的分区名
只收字面量，所以 `DisplaySettings.LocalizeSection` 事后 `window.Get("section_Item display").SetText(...)`（`:161-187`）。

**性能**：**不是每帧重算**。`DurabilityAppearance` 常驻但 `enabled=false`；`Refresh(readData)` 只做
`readPending |= readData; enabled = true;`（`:98-102`），`LateUpdate` 第一行就自禁（`:106`），每次变更只跑一帧；

### 2.5 踩坑与红线

- **必须走 RenderTexture 读像素**：物品图在**图集**里，`source.texture` 是整张图集，直接 `GetPixels32()`
  会拿到几百 KB 的整图。`ReadPixels`（`:240-330`）用 `RenderTexture.GetTemporary` + `Graphics.Blit` 按
  `textureRect` 抠子区域，还要按 `packingRotation`（0~3）翻转像素序。自己写会踩图集旋转、`textureRectOffset`
  负偏移、`border` 九宫格三处坑。
- **变体爆炸**：key 含 `brightness`（-100..100），每张 sprite 最多 201 × 步数 × 4 方向个 `Texture2D`，
  所以必须有 `ClearVariants()` 在改设置时全清（`OverlayManager.ApplySettings:124`）。这是自建缓存的税。
- **两个 `Image` 要一起画**：`background` 与 `fakeBackground`（预览假底），漏一个会在拖动预览里露原图。
- **`FindObjectsOfType` 只有一次机会**：`AttachExisting` 挂在 `OnGameLoadedNormal` 与 `OnEnable`，
  但**无热重载钩子**（透视报告：`HotReloadPrepare/Activate` = 否）。热重载后旧组件被销毁、新的没挂上，
  是已知薄弱点（推测：作者靠"重开游戏"兜）。
- **`MAX_DURABILITY_TAG` 为 0 会除零**：`Fraction` 无保护（`DurabilityData.cs:12`），保护在调用方的 `maximum <= 0` 判空里。

### 2.6 对我们的可用点

1. **"改外观"的正确粒度是换 Sprite**：做磨损/污渍/贴纸这类图标级效果，先考虑缓存一张变体 sprite 去替
   `Image.sprite`，而不是往物品节点上叠子物体——零层级风险、零射线问题。
2. **`modifiedState.dict` 就是我们的数据库**：原版在写的 tag 都能零侵入读出来，写方向同理
   （`ModifyTag` + `TagState.Enable().SetInt/SetString`），比反射私有字段稳。
3. **防剧透读法三段式**：`IsExposed || IsFeatureDiscovered` 不成立 → 读 `*_FAKE_*` → 都没有就不画。
   我们做任何揭示类扣子（成色、鉴定结果、隐藏属性）都照抄。
4. **设置项照抄**：`ModConfig.Define` 逐项 bool + 一个 -100..100 int 滑条 + `IPointerClickHandler` 右键归零，
   比自绘设置窗省一个数量级（对比：545 行 `SettingsPreview` 只为在设置窗里**预览效果**，可选）。
5. **脏标记 + 自禁用模式**：需要"变更后重画一次"的常驻组件，用 `Refresh(){ enabled = true; }` +
   `LateUpdate` 首行自禁，比每帧判 dirty 便宜。

## 3. `3830874694` 更合理的广告牌 / 灯牌 Proper Signboards

**id**：`3830874694`（`<ID>PawnshopBillboards</ID>`，v1.0.48，游戏 0.46D，`<Capabilities />` 自闭合）
**反编译目录**：`缓存文件夹\decomp_ws\3830874694\`
**为什么值得读**：把"摆在货架上的招牌"变成"挂在柜台上方的招牌"，而且**没有重写任何展示判定**——靠 Transpiler
把原版读 `childItems` 的地方换成"展示柜 ∪ 挂区"。这是本工作区最缺的范式：**换输入，不换算法**。

### 3.2 招牌挂上去之后，展示加成还生效吗

**生效，而且原版加成公式一行都没抄。** 手法是"换输入"：把原版**读展示柜内容**的地方，在 IL 层换成读
"展示柜 ∪ 挂区"。原版 `ShowcaseHelper` 的所有判定都基于 `EmporiumEntry.Instance.showcaseElement.childItems`
（`ShowcaseHelper.cs:75-85`、`:92-99`），所以这个"读"被替换后，分类/价值/证书/黑灯/预测全部自动跟着走。

被替换的 `childItems` 读点（`HangingDisplayEffectsHook.cs:11-26`、`HangingPhysicalDisplayHook.cs:11-18`）：

| 分组 | 方法 |
| --- | --- |
| 展示效果 | `ShowcaseHelper.HasMerchandise` / `GetTypeCount` / `GetTypeTotalValue` / `GetDisplayCaseType` |
| 证书/黑灯 | `AppraisalRankHelper.GetDisplayedCertificate`；`BlackLampHelper.GetLampCountForTarget` / `GetActiveInvitations` / `IsInDisplayCase` |
| 库存统计 | `PlayerStore.CheckMostStockType` / `CheckMostStockTypeShowcase` |
| 物理检查 | `ShowcaseHelper.IsShowCaseContainSeriousContraband` / `…SeriousStolen`；`ContrabandHelper.StartInspection` / `SecurityCheckDisplayCase`；`PlayerStore.GetTotalEstimatedValue` |

**两套替换结果是分开的，这是最讲究的一刀**：`DisplayItems(inv)`（`HangingAdvertising.cs:130-145`）**过滤
`Visible`**——关灯的悬挂物不算广告、不算预测客流；`PhysicalItems(inv)`（`:147-154`）**不过滤**——关灯的仍是实体，
照样过违禁/赃物检查、照样计入估值。另有两处是**整方法 Prefix 顶掉**：`ShowcaseHelper.HasShowcaseSpecialItem`
→ `HangingAdvertising.HasSpecial()`（`HangingSpecialHook.cs`）；`GetShowCaseContainItemCount(id)` →
`HangingAdvertising.Count(id)`（`HangingSignCountHook.cs`）。

`GetDisplayCasePrediction`（原版 `ShowcaseHelper.cs:223-…`，14 个 `IsShowcaseContainItemById("sign_*")` 加
`GetShowCaseContainItemCount("scav_token")`）走第二个 Transpiler：**只换操作数**，把 `IsShowcaseContainItemById`
的调用指令改成 `HangingAdvertising.Contains`、`GetShowCaseContainItemCount` 改成 `Count`
（`HangingPredictionHook.cs:11-29`）——不增删指令、不动分支，比 `CodeMatcher` 重排安全得多。

**`InitShowcaseSpecialItem` 它一次都没调用**：原版那方法只是给物品打 `SHOWCASE_SPECIAL_ITEM_TAG`
（`ShowcaseHelper.cs:55-61`）。本模组只在两处**读**这 tag：`BillboardManager.IsSign:438`（判定"这是招牌，
允许双击挂起"）与 `HangingAdvertising.HasSpecial:122`（喂给上面那个 Prefix 替换）。

### 3.3 挂点在哪：自建容器 + 网格坐标 + 视觉镜像

**挂点是自建容器，不是原版任何容器。** `HangingStorage.Create()`（`HangingStorage.cs:134-146`）建
`new GameGridInventory(36, 20){ identifier = "billboards.hanging.inventory" }`，`SetParent(null)` +
`DontDestroyOnLoad` + `SetActive(false)`（整个容器不显示）。物品是**真搬进去**的
（`MoveWhole(item, HangingStorage.Inventory, placement)`，`BillboardManager.cs:1375`），所以"不占展示柜格子"
是真的不占；屏幕上看到的是 `BillboardMirror`——`TreeNodeRender.Instantiate((PixelElement)item, …)` 复制源物品的
渲染节点，自己再叠灯管/光晕/挂线（`BillboardMirror.cs:43-60`），并挂 `BillboardHitFilter` 接点击。

**屏幕挂区**是纯数学，不依赖原版布局（`SlotLayout.cs`）：房间 960×540、格 16px、挂区 **18 列 × 10 行**、
`Top = 52 + HeightOffset`、两个 region（主区 `OriginX=336`、左区 `OriginX=2`；`Fits` 检查
`x+width<=18 && y+height<=10` 且矩形不相交，`:53-60`）。高度滑条把 `Top` 在 `-100..-12` 之间挪（`:74`）。

**双击挂起 / 拖拽取下（也能拖拽挂上）**：
- 双击：`ItemMouseDoubleClickHandler.DoubleClickAction` 的 Prefix，`return !BillboardManager.TryToggle(...)`
  （`DoubleClickHook.cs:14-19`）——**返回 false 就是吃掉原版双击**。`TryToggle`（`BillboardManager.cs:1287-1373`）
  入场条件很严：`IsSign(item) && GeneralHelper.IsItemOwned(item)` + `InStore` + `MayRemove()` + `!IsDisplayOnly`
  + `ValidArt`；已在挂区则"取回"（目标 `EmporiumEntry.Instance.invElement`，仓库满则报 `StorageFull` 留在挂区）。
- 拖拽挂上：`ItemMouseDragHandler.EndDrag` 的 Prefix，`DropOnWall`（`:1656-1718`）**不检查 `IsSign`**——任何可拖
  动物品都能挂（这就是 manifest 里"只要 18×10 格放得下都能挂"的来路）。命中靠 `RectTransformUtility` 把鼠标转到
  挂区局部坐标 + `RegionAt` + `WallInFront`（射线栈顶必须是挂区同一 Canvas）。
- 拖拽取下：`DragEndHook` 在 `DropOnWall` 成功时把 `___lastInventory/___lastItem` 置 null、把 `args[0]` 改成 true
  （告诉原版"已处理"），避免原版再把它塞回原容器。

**白名单怎么维护**（`BillboardManager.IsSign:434-453`）：三路并集——`SHOWCASE_SPECIAL_ITEM_TAG` ∪ 硬编码 14 个 id
（`sign_water/food/material/ruined_machine/medical/household/firearm/firearm_heavy/berry/expedition/luxury`、
`ce_electronics_sign`、`be_brewery_sign`、`ce_sia_blade`）∪ 名字匹配（含"灯牌"，或英文
`\b(?:sign|signboard|billboard)s?\b`）。`ce_sia_blade` 是唯一被单独排除的例外（`TryToggle` 里直接 return false）——
它虽然是 `SHOWCASE_SPECIAL_ITEM_TAG`，但属于展柜内特殊物品，不该被挂走。

**存档**：`owner.modData["billboards.hanging.layout.v1"]`（原版 `PlayerStore.modData` 字典，只写私有键，
`BillboardManager.cs:716` 与迁移路径 `:1468` 两处写），内容是 `"billboards:1\n"` 版本头 + `LayoutCodec.Write(...)`
（挂位表）+ 每个悬挂物整棵 `StoredBillboard`（`SaveItemNode` 镜像：`uuid/itemState/itemShape/itemModifiedShape/
itemType/name/uniqueId/unitValue/spriteAtlasPath/childItems/childItemInventoryNode`…），`ItemFeature` 列表另外
Base64 序列化（`HangingStorage.cs:129-132`）。另有**旁路**：`SaveManager.EncodeNodes` 的 Postfix 把挂位节点塞进

### 3.4 关键代码摘录

```csharp
// PawnshopBillboards/HangingAdvertising.cs:130-154 —— 换输入的两个出口
internal static List<GameItem> DisplayItems(GameInventory inventory)
{
    if (!Core.Enabled || (object)inventory != EmporiumEntry.Instance.showcaseElement)
        return inventory.childItems;                       // 非展示柜：原样返回，一行不改原版
    List<GameItem> list = new List<GameItem>();
    foreach (GameItem item in Items())                     // Items() = 展示柜 ∪ 挂区快照（带缓存）
        if (Visible(item)) list.Add(item);                 // 关灯的悬挂物不算"广告"
    return list;
}
internal static List<GameItem> PhysicalItems(GameInventory inventory)
{
    if (Core.Enabled && (object)inventory == EmporiumEntry.Instance.showcaseElement)
        return new List<GameItem>(Items());                // 不过滤 → 关灯也照样过违禁检查
    return inventory.childItems;
}

// PawnshopBillboards/HangingPredictionHook.cs:11-29 —— 只换两个被调用者，不重写方法体
private static IEnumerable<CodeInstruction> Transpiler(IEnumerable<CodeInstruction> instructions)
{
    MethodInfo source = AccessTools.Method(typeof(ShowcaseHelper), "IsShowcaseContainItemById");
    MethodInfo target = AccessTools.Method(typeof(HangingAdvertising), "Contains");
    MethodInfo countSource = AccessTools.Method(typeof(ShowcaseHelper), "GetShowCaseContainItemCount");
    MethodInfo countTarget = AccessTools.Method(typeof(HangingAdvertising), "Count");
    foreach (CodeInstruction instruction in instructions)
    {
        if (instruction.Calls(source))            instruction.operand = target;    // 换操作数
        else if (instruction.Calls(countSource))  instruction.operand = countTarget;
        yield return instruction;
    }
}
```

### 3.5 踩坑与红线

- **`Items()` 有缓存，但键是"展示柜对象 + changeDepth==0"**（`:48-73`）：`BeginChange/EndChange` 期间
  （`changeDepth > 0`）**不落缓存**，避免搬物品中途把半成品列表冻住。抄"外部列表喂原版"必须一并抄这个深度标记。
- **`Contains/Count` 上标了 `[MethodImpl(NoInlining)]`**：它们是被塞进十几个原版方法的替换目标，保持独立
  调用点（推测：防 Mono 内联后让替换/回溯失效）。
- **`GetMostCommonWaterTypeInDisplay` 是运行期手动 `new Harmony(...)` 装/卸的**（`HangingWaterDisplayHook.Install/
  Uninstall`，`Core.cs:59-66` 按 `PlayerStore.runID` 决定装不装），与 ModLoader 统一打的那批补丁**不是一条时间线**。
- **它动了原版存档流两处**：`PlayerStore.SaveGame` 的 Prefix（只警告）+ `SaveManager.EncodeNodes` 的 Postfix（真塞
  节点）。后者是绕过 ES3 结构限制的通行做法，也最易随原版存档格式变更而坏，所以它另配 `ValidateSnapshots` 与
  `unavailable/unresolved` 两张保留表。
- **`DropOnWall` 与 `TryToggle` 准入不一致**（前者不管 `IsSign`）：两条入口条件集合不同，是无主物品被拖上墙的常见来路。
- **38 补丁 / 19 Transpiler 是硬耦合**：原版任何一次重命名（`GetShowCaseContainItemCount` 这种不规范命名尤其易被"顺手修正"）都会让 `AccessTools.Method` 返回 null，整批静默失效。抄它必须补启动自检。

### 3.6 对我们的可用点

1. **"展示加成还生效"不必重写公式**：要让我们自己的展示物参与原版分类/证书/黑灯/预测，两条路——(a) 让物品
   **真的**待在 `showcaseElement` 里（最省事）；(b) 像它一样把读点换成"柜 ∪ 挂区"，代价 19 个 Transpiler，
   只在"物品必须离开展示柜"时才值得。
2. **`SHOWCASE_SPECIAL_ITEM_TAG` 是与其他模组的公共接缝**：我们的灯牌用 `InitShowcaseSpecialItem` 打这 tag 后，
   Proper Signboards 会**自动**把它纳入双击挂起白名单（`IsSign:438`）并计入 `HasSpecial`——两模组展示判定**互补**。
3. **绝不能靠"容器成员关系"记状态**：它一挂起就把物品搬进隐藏 36×20 容器。任何"读
   `showcaseElement.childItems` 判断灯牌在不在/算数量"的代码，同装时会看到空。我们的开关/亮度/挂起状态必须存在
   **物品自己身上**（tag / `modData` / 自己容器里的 Placement）。
4. **双击与拖拽的接管姿势**：`DoubleClickAction` 的 Prefix `return !handled`（吃掉）比 Postfix 事后补救干净；
   拖拽要同时处理 `EndDrag` 的 `args[0]` 与私有字段 `___lastInventory/___lastItem`，否则原版二次落位。
5. **存档写自己的键 + 旁路注入原版流**：私有键 `modData["<mod>.<topic>.v1"]` 存布局（带版本头），物品本体靠
   `EncodeNodes` 旁路进 `back_inv_save_bag`，校验失败抛异常保留原记录——这正是"只写模组私有键、不改原版存档
   结构"的落地写法。
