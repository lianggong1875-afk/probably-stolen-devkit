## 三、它怎么做这件事

### 3.1 新地点接入：四档阶梯里的 **③′**（子类，但免反射）

`14` 的 §9.4 是四档：① 开局特性 ② 蹭原版地点 ②′ `ModHelper.AddAfterhourLocation` 11 参委托 + 自建舞台 ③ 子类 + `ModReflect.Set(map,"Current",…)`。它属于**第③档的变体**，但把"伪造 `Current`"换成了**官方公开注册**：

```csharp
// ModEntry.cs:36-37
AfterhourLocation.Register((AfterhourLocation)(object)new PawnshopLocation());
ModHook.OnModItemDirectoryInit += MercuryMallBasket.Register;
// ModEntry.cs:56（OnDisable）
AfterhourLocation.RemoveSource("deep_space_pawnshop");
```

原版 `AfterhourLocation.Register(AfterhourLocation)` 是 **public static**（`共享开发\reference\Assembly-CSharp\AfterhourLocation.cs:166`），内部只做"同 Id 替换 / 否则 Add"，原版三地点由 `EnsureVanilla()`（同文件 `:191`）先 `Insert(0..2)`。所以**不必反射、不必抢 `Current`**：只要进了 `all`，原版交通图自己 `GetDiscovered()` 就会列出来，点出发自己 `Travel`。

配套的三个"空壳"技巧（这是本档的精髓）：

1. `PanelObject` 返回一个**空 GameObject**（`PawnshopLocation.cs:40-52`）→ 原版 `OpenLocationPanel` 打开的是空面板，屏面全留给模组自己的 `OnGUI`；
2. `BackgroundKey = "deep_space_pawnshop:mall_bg"`（`PawnshopLocation.cs:18-20`）→ 原版 `ShowStage` 用 `SpriteRenderer` 铺 1600×900 背景图，`BackgroundSortingOrder = 20`；
3. `Arrive()` 里直接 `PawnshopWindow.Instance.OpenFullscreen()`（`PawnshopLocation.cs:110-117`），`Leave()` 里成对清理（`:119-138`）。

另有两条省事决定：`IsDiscovered() => true`、`IsAvailable() => true`（`:82-90`）—— 不进原版"探明/事件封锁"流程，开局就在交通图里；不覆盖 `StageObject`、全库 `ModHelper.AddAfterhourLocation` 出现 **0 次**。

**"交通图目的地"与"打烊后去处"是同一套**：`MapUIManager.Travel(AfterhourLocation)`（`MapUIManager.cs:171`）就是出门入口，`Current` 由它自己写。

要点：

- **没有"每家店一个类"**。一家店 = 一行 `new UpperShopDefinition(index, 店名, 职衔, 品类, 招呼语, string[] 货单, 柜台四角坐标, 每件库存)`；只有"一个区"才配一个会话类。
- **表里重复的 id 就是件数**（`node_medium` 写 4 次 = 4 件库存），另有 `CountFor(id)` 做按店覆写（`UpperShopDefinition.cs:50-96`：index 3 高端材料 ×8、index 5 净水 ×6、磁带类强制 ×1）。
- **下层是"生成式"而不是手写 30 家**：6 个品类 × 5 个名字占位，`LowerShopBusiness.Name/Role/Greeting` 用 `switch(slot)` 只改营业的那几个槽，其余保留占位名（`LowerShopCatalog.cs:21-29`）；货单由 `LowerShopPersonality.Pools[index]` 这条逗号字符串 `Split` 后 `Repeat` 生成（`:24-52`），`IsReserved` 划出 13 个"预留铺位"（`:53-62`）—— 这样简介只说"5 家"也成立，扩店不用改架构。
- 自检：`RegisteredIds/MissingIds` 拿 `DirectoryMaster.GetIdentifierList<GameItem>(null)` 反查，把"表里写了但物品没注册"的 id 集合报成 `商品目录缺项：{店名} / {ids}`（`LogisticsShopCatalog.cs:175-193`、`SecurityShopSession.cs:333-338`）。

### 3.3 收购 vs 出售：**同一个字段**

两者共用完全相同的"假客户 + 原版柜台 + 原版议价"骨架，唯一差别是 `StoreClient.clientIntent`：

| 意图 | 值 | 区 | 源码 |
| --- | --- | --- | --- |
| `ClientIntent.BUY`（客户买你的货 = 收购） | 1 | 物流区 9 家用，第 10 家（当铺）全品类收 | `LogisticsShopSession.cs:304` |
| `ClientIntent.SELL`（客户卖货给你 = 出售） | 2 | 上层 6／下层／安保 3／科技 4／酒吧／夜宵 | `SecurityShopSession.cs:236`、`UpperShopSession.cs:187`、`NightPotSession.cs:170`、`TechnologyMachineSession.cs:293`、`BarTradeSession.cs:199` |

"只卖货/不收"因此是天然结果：`SELL` 会话根本不设收购白名单，而 `BUY` 会话不摆货架。**不需要第二个开关**。

### 3.4 许可证机制：判定只挂在一处，而且被短路

- 证 = **原版许可证**，不是声望也不是自建资历：`PermitHelper.HavePermit("FIREARM", level)` 查的是 `PlayerStore.Instance.ActivePermits` 里的 `(itemType, contrabandLevel)` 元组表（`共享开发\reference\Assembly-CSharp\PermitHelper.cs:119-124`）；来源是原版许可证物品（`PERMIT_ITEM_TAG` / `PERMIT_ITEM_LEVEL` / `PERMIT_ITEM_TAG{i}`），由 `GrantedFromPermit` 发放。
- 级别来自物品本身：`ContrabandHelper.GetContrabandLevel(item)`（1/2/3 ↔ `RESTRICTED_1/2/3`）。
- **唯一判定点**：伪造客户的 `willAcceptItem`（`SecurityShopSession.cs:242`）——
  `willAcceptItem = item => stock.Contains(item) || MallPricePolicy.CheckSecurityPermit(item) == null;`
- 问题在于 `stock.Contains(item)` **短路**：货架上的枪械全部先进了 `stock`（`:407-415`），所以自家柜台的枪/弹**永远放行**；`CheckSecurityPermit` 只对"不在货架上的枪"（玩家自己塞进柜台的）生效。
- 更硬的证据：`CheckSecurityPermit` 返回的中文提示"这个要 N 级枪械许可证才能买。"（`MallPricePolicy.cs:213`）**全库没有第二个调用方**（`grep 许可|Permit` 仅 6 处命中），也没有任何 UI 显示它。
- 结论：**许可证装上了但基本空转**（作者意图"买枪要持证"是推测）。抄的时候不要抄这个闸门位置——见 §5 第 3 条。

### 3.5 交易流程：伪造 `StoreClient`，把原版柜台当多店铺引擎

1. **造客户**：`new StoreClient { identifier, displayName, clientFaction, clientIntent, nonShootable=true, arrestable=false, isIntroduced=true, isBargainAvailable=false, isMultiBuyDisabled=false, willAcceptItem=… }` → `PlayerStore.Instance.currentClientInstance = StoreClientInstance.CreateClientInstance(val)`（`LogisticsShopSession.cs:298-327`、`SecurityShopSession.cs:231-244`）。**议价直接关掉**（`isBargainAvailable=false`），纯标价。
2. **占柜台**：把 `EmporiumEntry.backInvinvElement` 上原有的自家货搬进 `backInvinvElementCounter` 暂存（`MoveExact`），改形状 `SetShape(18,4)`（物流）／`(32,4)`（当铺）／正面 `(11,21)`／`(16,9)`（枪械右柜），关掉动态背景、透明度拉满、隐藏正面窗口、`MapUIManager.ActivateClientOutsideStore()`（`LogisticsShopSession.cs:280-296`、`SecurityShopSession.cs:203-230`）。
3. **伪装站位**：`PlayerStore.Instance.playerLocation = (PlayerLocation)1`（店内）。
4. **摆货**：`Supply(index)` 自己扫格找位（`TryInventorySlot` → `GeneralHelper.SetItemOwned(item,false)` → `TryAcceptOnce(-1)`），摆完挂 `MallPricePolicy.ApplyMarkup` 加价标记（`SecurityShopSession.cs:321-410`）。**全库 0 次 `GraphUtils.EmporiumTryAdd`**。
5. **结算**：`NegociationUIManager.Instance.OpenUI()`（`LogisticsShopSession.cs:471-478`）—— 之后全是原版：议价面板、`BuyItem() → PlayerStore.OnItemBought` 扣钱入包、`StoreReputation.OnItemTraded` 结声望、`clientFaction` 影响倍率。
6. **关店还原**：非原货用 `GraphUtils.TryAcceptAll(afterhourInventory, item, -1)` 落地；**落不下就拒绝关店**并保留会话（`LogisticsShopSession.cs:392-405`）；再按 `WindowSnapshot`/`ItemSnapshot` 逐项还原窗口矩形、透明度、形状字符串、客户、站位。
7. **第二条交易路（例外）**：`PawnshopWindow` 自家「集市/回收」页直接改钱 —— 买 `PlayerStore.Instance.playerCash -= UnitPrice`、卖 `playerCash += GetValue()/2`（`PawnshopWindow.cs:6703`、`:6775`），**完全绕过原版议价、声望、客户预算**；电话订货反而规范，用 `store.ModCash(-order.paid, false)`（`MercuryOrderWindow.cs:105`）。

## 五、踩坑与红线

1. **柜台被全局改形，异常路径会留下"半改"状态**。`Open()` 里 `SetShape(18,4)`、关动态背景、隐藏正面窗口、`playerLocation=1`、换客户 —— 任一步抛异常都会走 `catch → Close()`；`Close()` 自己也可能因为"场外地面没就绪"抛 `InvalidOperationException("场外地面尚未就绪，保留柜台与会话")`（`LogisticsShopSession.cs:387-390`）。**后果**：玩家的原版柜台形状/透明度/客户停留在临时态，只能再开一次店或出门再回来修。抄的时候必须像它一样把"形状字符串 + 宽度"存成快照（`:264-273`），并且**先采样再改**。
2. **摆货失败直接销毁商品**。`Supply` 里 `TryPlaceIn` 失败 → `val.Destroy()`（`SecurityShopSession.cs:417-423`）。它没走 `GraphUtils.EmporiumTryAdd`（这点是对的：那个 API 六级兜底、全满静默销毁、还不告诉你成没成，见 `03` §"EmporiumTryAdd 六级兜底"），但自己重写后**同样**把"放不下"处理成销毁，只是多打了一条 `容量不足` 警告。要抄就抄 ⑦ 的做法（落不了地就拒绝推进），别抄 ⑥ 的销毁。
3. **许可证闸门被 `stock.Contains` 短路**（§3.4）。货架枪械无条件放行、提示文案无人显示，等于"看起来做了、实际没做"。**正确做法**：把持证判定放在"选中商品→加入议价篮"的动作位上（`NegociationUIManager` 的点击入口或自建 UI 的按钮），而不是放在 `willAcceptItem` 这种"客户愿不愿意收"的判定位上。
4. **一条动线两套交易系统**。原版议价（有 `clientFaction` 声望、有客户预算、有 `ScalperMarkup` 真实价）与自家「集市/回收」页（`playerCash -=` 裸改、卖价一律 `GetValue()/2`、无声望无预算）并存（`PawnshopWindow.cs:6654-6786`）。同一件物品在两个页签里价格/后果不同，玩家必然拿来套利（推测）。**要么全走原版会话，要么别在原版会话旁边摆一套更划算的。**
5. **裸改 `playerCash` 绕过原版记账**。`BuyOffer` 用 `DirectoryMaster.Create<GameItem>` 造物品、`UncheckedAccept` 塞背包、直接减现金（`PawnshopWindow.cs:6691-6704`）：既没走 `PlayerStore.OnItemBought`（→ 丢 `TrackBuyPrice`、丢 `RunStats`、丢声望），也没用 `ModCash`（同模组 `MercuryOrderWindow.cs:105` 就用了）。我们的铁律是 `DirectoryMaster.Item(id, true)` + `ModCash`。
6. **手测坐标表是硬耦合**。`LogisticsBubbleAnchor` 623 行 + `UpperBubbleAnchor` 620 行 = 45 个场景的 (名字 X/Y、柜台 Y) 手工数值；`LogisticsCounterArtTop` 再存一份柜台顶。**换一张场景图 = 重测一行坐标**。这是"自绘场景图 + 原版窗口钉上去"路线的固定成本，做同款必须预算进去（或者改用九宫格锚点/可配置 JSON）。
7. **`VanillaStorageRules` 把原版容器放宽成"任意自有物品都能塞"**。它包装 `mayInventoryAddItemFunc`（`VanillaStorageRules.cs:43-86`），对"非模组物品 + 双方都是自有 + 非锁定"直接 `return true`，并用 `GetInvocationList()` 逐个沿用原有链（这点很专业：别的模组先包过也不会被它吃掉）。但副作用是**原版冷藏/展示/收纳类容器的品类限制被整体解除**，等于给玩家一个免费扩容后门（推测为作者为解决"买到的容器装不进东西"而做的粗暴放行）。**这是平衡性红线，我们不要抄"放宽"，只抄"用 `ConditionalWeakTable` 记住原委托 + 逐链沿用 + 0.25s 重挂"的机制**。
8. **工程收尾卫生**：`AssemblyVersion 0.0.0.0`、7 张 `检查_*.png` 自查截图留在发布包里（`Textures\` 根目录）、`LogisticsShopSession.SyncBuyingList()` 是空方法（`:480-482`）、`MallPricePolicy` 里 6 个 `UpperMarkup/LowerMarkup/...` 方法全部返回常量却占着 30 行。发布前应清。
9. **`Leave()` 无法取消退出**：原版 `Leave()` 返回 void，清理失败只能 `LogError` 然后放任（`PawnshopLocation.cs:122-131` 注释亲口承认）。要在"离开"这一步拦人，得去 patch `MapUIManager.Return` 之前的那一步，而不是 `Leave`。
10. **纯中文硬编码文案遍布 UI**（`DrawFooter`、`DistrictDesc`、`GetGreeting` 等），无 `LocHelper` 走查；简介也全是中文，订阅 121 与这一点互为因果（推测）。

## 六、对我们的可用点

### 对《深空当铺：可能是群友》（`DeepSpacePawn.dll`）

1. **"多店铺"不用多类**：如果以后要开分店/连锁/夜市摊，照抄 §3.2 —— 一张 `(Index, Id, 店名, 职衔, 招呼语, string[] 货单, 台面四角)` 静态表 + **按区一个会话类**，把"收购/出售"收敛成一个 `ClientIntent` 字段。我们现在的 `PawnshopWindow` 已经有柜台逻辑，缺的正是这张表。
2. **场外柜台（`EmporiumEntry.backInvinvElement`）可以直接当"摊位"用**：`SetShape` + 暂存柜 + `Snapshot/Restore` 这套（§3.5 第 2、6 步）能让我们在**不新建任何 UI**的前提下多出 N 个交易点。注意配套的两条纪律：改形前存形状字符串、关店时落地失败就拒绝关店（⑦）。
3. **用 `ItemFeatureList.ScalperMarkup(percent)` 做"高档店贵一点"**：原版黄牛特征自带 tooltip 与价值计算，比自己乘价格安全（`MallPricePolicy.cs:51-70`）。我们的「成色/真伪」定价可以叠在它之上而不是替代它。
4. **`PermitHelper` 直接复用**：持证判定取 `PermitHelper.HavePermit("FIREARM", ContrabandHelper.GetContrabandLevel(item))`，但**闸门放在点击动作位**（§5 第 3 条），别再放 `willAcceptItem`。
5. **客人注入用 `ModHook.OnGenerateCustomerVeryLate`**（`MercuryVisitor.cs:45`）：我们做"群友来访/熟客回访"时可照此把自家客人追加进原版队列，而不是替换 `GenerateCustomer`。
6. **`VanillaStorageRules` 的包装机制**值得移植（不是它的放行策略）：`ConditionalWeakTable<GameGridInventory, Rule>` + 逐链 `GetInvocationList()` + 定时重挂 —— 这是"我们的物品要进原版背包/容器"最稳的写法。

### 对《深空电玩》（`DeepSpaceArcade.dll`）

7. **"一个 OnGUI 画整个场所"是可维护的**（`PawnshopWindow` 10,436 行也跑得动，10k 行里 22 个 `Draw*Catalog` 是纯模板复用）；但它同时是**最大负债**：没有分区文件、没有组件化。我们要做电玩城分区（街机厅/抓娃娃/兑奖台）时，**照它的做法做数据（表）+ 会话（每区一类），但把绘制按区拆文件**，别长成一个 10k 行类。
8. **`TechnologyMachineSession` 的"右柜 + 展开正面柜台"**（`ExpandFrontCounterGrid` + 自建 `rightCaseGrid`）是"小店面摆大件"的现成解法 —— 电玩城的**大型机台**（占地 2×3 以上）正好用得上：正面货架放大件、右柜放配件。
9. **`MercuryOrderLedger` 的持久化范式可以直接抄**：把整份订单数据 `Encode` 成**带版本前缀的单字符串**（`"v2|day|used|unlocked|pending"`）塞进**一个** `ModHelper.SetModData` 键，读时 `array[0] != "v2"` 就抛"版本无法识别"（`MercuryOrderLedger.cs:57-64,153,300`）。零 ES3、零新存档键、版本可辨 —— 电玩城的**兑奖券/机台记录/排行榜**正需要这个。
10. **软依赖的正确姿势**：`AppDomain` 按程序集名找 `EntertainmentTtr`，找到就反射 `ttr.TtrBoot.Open()`，找不到就用自己的实现（`PawnshopWindow.cs:4762-4791`）。电玩城若要和别的"小游戏模组"共存，照这个写，别 `Assembly.Load` 也别硬引用。
