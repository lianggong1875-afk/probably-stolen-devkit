## 一、PortraitRuntime · 深空核心库（工坊 `3831627217`）

> **id**：`player.portraitruntime`｜`PortraitRuntime.Core.dll` + `PortraitRuntime.Unity.dll`｜v2.5.0｜1.4 万订阅
> **反编译目录**：`缓存文件夹\decomp_ws\3831627217`（**只有 Core 那 47 个 .cs，Unity 程序集没反编译出来**）

### 2. 它怎么做这件事

#### 2.1 它和 PEF（`3841909877`）、NightRegulars（`3845197390`）的边界

| 维度 | **PortraitRuntime**（本档） | **Probably Extend Framework** | **NightRegulars（yg_regulars）** |
| --- | --- | --- | --- |
| 主打 | **运行时 + 数据契约**：人物/剧情/物品/访客/存档/调试六类 | **贴图覆盖层 + QoL 全家桶**（F9 工坊、60 个 public 成员） | **只做立绘**：按需读图、套装回退、高清去像素 |
| 谁管素材 | 内容包（独立模组或 `packs/` 下的目录），核心库**一张图都不带** | 主框架自己扫每个模组目录里的 `TextureExtend.json/.csv` | 三个纯美术订阅项（serene/adult/extreme） |
| 谁管运行时 | Core 库（纯逻辑）+ Unity 程序集（反射挂载） | 框架本体（16 处手动 Patch） | 框架本体（含 `WantedElement.OnEnable` 等少数 Patch） |
| 谁管 API | **C# 静态门面 + 版本化通道**（`lookup/1`、`inspect/1`、`lifecycle/1`…）+ JSON 信封 `{ok,error,data}` | C# API 一律 `modId` 打头 + 文件契约 + `sig` 字符串签名 | 基本没有对外 API，只有配置项 |
| 内容包要写代码吗 | **可以完全不写**（放目录）／也可写一行 `ContentSources.Register` | 不用写（放文件） | 不用写（放 png） |
| 冲突面 | 反射挂原生方法，声明 `reflection-external` | 16 处 Harmony | 立绘替换 + 通缉令/场景/菜单 |
| 独有能力 | **对话/剧情引擎、自定义访客、按单件状态换图标、F3 巡检** | 高清立绘、立绘池、昼夜差分、F3/F9 工坊 UI | 套装回退 + 关 `PixelPerfectCamera` 去像素 |
| 取舍 | 想当"内容平台"，代价是自带两套契约（JSON + API 版本号）、非零能力 | 想当"美术总入口"，代价是补丁多、什么都吃 | 想当"最干净的立绘壳"，代价是只有立绘 |

**一句话边界**：PEF 管"**图从哪来、怎么盖上去**"，NightRegulars 管"**立绘怎么高清、缺套怎么办**"，
PortraitRuntime 管"**人物背后是一套可存档的剧情状态机**"。三者不是同一层的竞品：前者是渲染层，后者是内容层。

#### 2.2 对外接口到底长什么样（编译期引用 还是 零编译依赖？）

**两条都给了，而且分工明确：**

1. **编译期 C#**：`PortraitRuntime.Core` 是一堆 `public static` 门面 —— `ContentSources.Register(modId, packsDirectory)`、`PackReader.LoadSources(...)`、`Catalog.Character/Item/Story/Text`、`StoryEngine.TryApply/Matches`、`ItemIcons.Resolve`、`PortraitFit.Calculate`、`SpriteLookup.Resolve`。内容模组只要引一个 netstandard2.1 的 DLL。
2. **零编译依赖的 JSON 契约**：`portrait-pack/1`（`Pack.cs:9`）。一个内容包 = 一个目录 + `pack.json` + 图。核心库自己带 `packs/内容包说明.txt` 明说"**也可在此添加社区包目录**"。

"核心库与内容包独立维护"就是靠这两件事同时成立：**核心库只认目录**（`ContentSources` 维护 `modId → 目录` 的字典，`ContentSources.cs:9-31`），
人物美化包是**另一个模组**（字符串证据：`PortraitRuntime.Unity.dll` 里按名字探 `LaunchGiftPortraits.Content.BeautyContentMod`），它把自己的 `packs/` 目录注册进来。
所以：**内容包可以是纯资源 + JSON，也可以是薄 DLL；但"人物美化"这一层是独立模组，不在核心库里。**

内容包的加载有硬校验（`PackReader.Validate`），几个必须知道的：
- `format` 必须 `portrait-pack/1`；`id` 匹配 `^[A-Za-z0-9_.-]+$`；`priority` 0..1000000（`:152-160`）
- `gameBuild` 支持 `">=26337366"` 前缀写法，否则必须精确等于（`:162-164`）
- 全目录配额：≤1000 目录 / 深度 ≤32 / ≤10000 文件 / ≤4 GiB；**任何 reparse point（符号链接/junction）直接拒**（`:14-16,361-376`，资产路径同样查越界与链接，`:26-48`）
- `pack.json` ≤8 MiB，重复 JSON 键直接抛（`:65-72`）
- 立绘必须**像素尺寸恰好等于** `portraitCanvas`（默认 1152×844，`:25,343`）；物品图标必须 32 的倍数且**宽高比等于 grid**（`:238,343`）
- 新物品 ID / 新访客 ID **必须带 `<packId>.` 前缀**（`:204,293`）

#### 2.3 六类能力：内容包最小要写什么

一个 `pack.json` 就能同时声明六类（字段来自 `Pack.cs:31-41`）：

```jsonc
{
  "format": "portrait-pack/1", "id": "mypack", "priority": 100,
  "portraitCanvas": [1152, 844],
  "characters": { }, "items": { }, "actors": { }, "stories": { },
  "special": { }, "texts": { }
}
```

| 能力 | 键 | 最小例子 | 落点（原版） |
| --- | --- | --- | --- |
| ① 人物立绘 | `characters` | `"spy": {"identifiers":["spacerFood"], "factories":["StoreClientList.CreateSpacerClientFood"], "base":"img/spy.png", "variants":{"angry":"img/spy_angry.png"}, "story":{"dialog_spacer_food_1":"img/spy2.png"}}` | 访客 `identity`/工厂方法 → 立绘；`story` 是**按原版台词键**换表情，键必须在 `dialogue_keys.json` 白名单内（`PackReader.cs:195`） |
| ② 对话剧情 | `stories` + `actors.story` | `"s1": {"start":"n0","nodes":{"n0":{"text":"…","next":"n1"},"n1":{"text":"…","choices":[{"text":"收下","next":"n2","actions":[{"op":"cash","amount":120}]}],"end":false},"n2":{"text":"…","end":true}}}` | 自绘对话（不走原版 `DialogUIManager`），节点强制"end / next / choices 三选一"（`:274`） |
| ③ 物品与图标 | `items` | `"mypack.disc": {"create":true,"name":"盘","icon":"img/d.png","grid":[2,2],"value":40,"tags":["ARC_GAME_GOODS"],"filter":"point","iconRules":[{"id":"worn","icon":"img/d_worn.png","when":{"hasTags":["DURABILITY_TAG"],"numbers":{"DURABILITY_TAG":{"valueType":"double","max":20}}}}]}` | `DirectoryMaster` + 图标；**按单件 tag 状态选图标**是本框架最独特的一条（`ItemIcons.cs:18-116`） |
| ④ 自定义访客 | `actors` | `"mypack.spy": {"name":"探子","character":"spy","story":"s1","intent":"BUY","buyItems":["mypack.disc"],"cash":300,"once":true,"when":{"minDay":5,"equals":{"met":"yes"}}}` | `StoreClientManager` 造客；`intent ∈ DIALOGUE/SELL/BUY/SELLNBUY`（`:295`），`vanillaSprite:"default"` 可直接借原版立绘（`ActorDef.cs:11`） |
| ⑤ 状态与存档 | `IStoryHost` | 内容包**不用写**；效果里 `{"op":"set","key":"met","value":"yes"}` 即写入 `mypack/met`，走原版存档（`IStoryHost.Get/Set`，`IStoryHost.cs:9-11`） | 键一律私有命名空间 `packId/…`，`_` 开头被保留（`:305`） |
| ⑥ 调试 | `catalogs/debug_visits.json` | 见 2.6；内容包把 `packId`/`characterId` 填进 `DebugCase` 就能被 F3 巡检点名（`DebugCase.cs:25-27`） | F3 控制台 + F11 诊断 |

> ⑥ 的最小可用写法：给自己包的访客补一条 `{"id":"visit/mypack.spy","label":"探子","identity":"mypack.spy","packId":"mypack","characterId":"spy"}`（字段见 `DebugCase.cs:7-27`），F3 巡检就会点名它并落报告。核心库自带的那份 `catalogs/debug_visits.json` 只覆盖原版 276 个工厂；**内容包目录里的 `debug_visits.json` 会不会被一起读，属「推测」**（Core 里没有对应读取代码，只能靠字符串 `catalogs`/`debug_visits.json` 推断在 Unity 侧）。

#### 2.4 "单独启用核心库时人物外观保持原版"是怎么做到的

**三层降级，从硬到软：**

1. **整机关（最硬）**：装了旧立绘模组就直接不挂任何钩子。字符串证据：
   `"Legacy portrait mod enabled; disable it before enabling PortraitRuntime. No hooks installed."`
   配套方法名 `<HasLegacyConflict>b__82_0`。→ 也就是说它**不是"补丁挂着但早退"，而是"压根不装"**（推测量级：至少立绘那条链不装）。
2. **数据层（空目录也是合法状态）**：0 个包 → `Catalog` 空对象（**不是 null**，`PackReader.LoadSources:445-461`）。
   于是 `SpriteLookup.Resolve` 全部走 `Reason="no-mapping"`（`SpriteLookup.cs:53-59`），`Resolve(null,…)` 走 `"runtime-absent"`（`:33-39`）。
   日志只说一句 `Loaded 0 packs; 0 characters, 0 items, 0 actors`。
3. **单张图层（软回退）**：`SpriteResolver.TryPick` 先试原版 key，再试候选，最后 `status="native-key-missing"` 返回 false（`SpriteResolver.cs:23-40`）→ 调用方保留原版 sprite。
   字符串证据里还有 `debug.sprite.fallback` / `native-key-missing` / `unresolved` 三个可观测状态，说明**每张图回退都留痕**。

结论：**"保持原版"不是靠一句 if，而是靠"空目录天然无事可做 + 解析失败必留痕 + 冲突旧模组直接不装钩子"三层叠出来的。**

#### 2.5 它是怎么被别的模组依赖的（manifest 里那句 `Prerequisites` 是空的）

- `manifest.xml` 的 `<Prerequisites />` 是**空的** —— 工坊层面不声明依赖，靠运行时自己探。
- 探测手段（字符串证据）：反射扫 `Assembly-CSharp`（`Assembly-CSharp`、`GetTypes/GetMethods/BindingFlags/GetMethod` 都在字符串表里），**没有 `ModReflect` 类型的符号**——它直接用裸反射，不走我们工作区惯用的 `ModReflect.FindType`。
- 内容侧：按类型全名探 `LaunchGiftPortraits.Content.BeautyContentMod`；另有 `portrait-content.marker` 这种"我是内容包"的标记名，以及 `{{ version, ready, registered, owners }}` 的 API 状态快照（`owners` = 已注册内容源）。
- 消费侧容错：`api.subscriber.failed` / `api.sync.failed` / `runtime-absent` —— 订阅方崩了不拖垮运行时。

> 对我们：**"不声明 Prerequisites、运行时探类型"是工坊通用做法**（我们两个项目也都这么干）。
> 但要注意它的代价：探不到就静默降级，玩家只会觉得"立绘没换"，所以它才必须有 F3 巡检（见下）。

#### 2.6 F3 调试台：自绘 IMGUI + 可回放的巡检

- **不是游戏内 `CustomUI`，是 Unity `OnGUI` + `GUILayout`**（字符串表里 `OnGUI/GUILayout/GUIContent/GUILayoutOption` 齐备，`CustomUI` 只做"别在打字时抢键"的判定）。
- 有**命令行求值器**：`DebugConsole+<Evaluate>d__55`，以及版本化请求串 `conditions/1`、`lookup/1`、`inspect/1`、`refresh/1`，响应信封 `{{ ok = {0}, error = {1}, data = {2} }}`。
- 子窗口：`ItemDebugPanel`（物品调试）、`VisitorQueueWindow`（访客队列）、`PixelWindow`、`DragWindow`；打开调试台时挂 `PortraitRuntime.DebugHudBlocker` 挡原版 HUD。
- **开关默认关**：字符串 `"Enabled; F11 diagnostics. F3 debug console is off (enable it in the Mod settings)"`、`"Mod settings unavailable; F3 debug console stays disabled: "`；配置项就是 `debugConsole` / `detailedLogging`（走游戏 `ModConfig`）。
- **人物巡检（本档最值钱的一件）**：`catalogs/debug_visits.json` 把**原版 276 个访客工厂**列成清单：

```json
{"id":"visit/spacerFood","label":"星际客","registrationId":"spacerFood",
 "identity":"spacerFood","factory":"StoreClientList.CreateSpacerClientFood",
 "spriteKey":null,"spriteExpressions":["SpriteDict.GetRandomScavSpriteName()"]}
```

`DebugTourPlan.Start(...)` 去重后要求 1..5000 条，`Next()/Seek()/Stop()` 逐个点名（`DebugTourPlan.cs:27-68`）；
`spriteExpressions` 是**运行期求值的表达式**（所以随机立绘每次点到都是真实随机结果，`GetRandomScavSpriteName` 也在字符串表里）。
结果落 `tour-report-<时间戳>.json`（`debug.report.export` / `debug.case.result` / `debug.case.failed`），另有 `layout capture` 工具把立绘在屏幕上的矩形记下来（`layout.capture.saved`、`portrait-layout/1`、`uniform-bottom-anchored`）。
- **物品调试**：`inspect/1` 返回 `{{ context, faction, intent, budget, arrestable, dismissable, survivesShot }}` 这一整包上下文；图标解析失败有 `invalid-item` / `item.inspect.failed` / `texture_unreadable_or_missing` / `empty_alpha` 细分原因。
- **日志诊断**：`TraceLog` 是 JSONL、4 MiB 滚 32 个文件、每行带 `utc/session/seq/level/event/data`（`TraceLog.cs:47-90`）；F11 落一份大盘 `{{ gameHashes, runtime, sources, debug, packs, conflicts, client, itemRuntime, cacheBytes … }}`（字符串证据 `diagnostics-` / `"Diagnostics written to "`）。

### 3. 关键代码摘录

**① 冲突仲裁：优先级 + 包 id 字典序（`Catalog.cs:60-71`）**

```csharp
private void Put<T>(Dictionary<string, Entry<T>> table, string key, Entry<T> entry)
{
    if (table.TryGetValue(key, out var value))
    {
        Conflicts.Add(key + ": " + value.Pack.Id + " / " + entry.Pack.Id);   // 覆盖必留痕
        if (value.Pack.Priority > entry.Pack.Priority
            || (value.Pack.Priority == entry.Pack.Priority && StringComparer.Ordinal.Compare(value.Pack.Id, entry.Pack.Id) > 0))
            return;                                                          // 高优先级留；同优先级 id 大的留
    }

}
```

### 4. 踩坑与红线

1. **它不是零能力模组**：`files + reflection-external` 两条都声明了。想把它当发布依赖，等于把这两条能力也拉进玩家环境。
2. **内容包格式是它的私产**：`portrait-pack/1` 只对它自己生效，PEF 不认、NightRegulars 不认。选它 = 内容一次编写只能在这个框架里跑。
3. **立绘尺寸零容忍**：png 必须恰好等于 `portraitCanvas`，多一像素就整包被拒（`PackReader.cs:343`）。`AssetDimensions` 可给个别资产开豁免（`:331-336`）。
4. **台词键必须存在**：`characters.*.story` 的键要能在 `dialogue_keys.json` 里查到，否则整包拒（`:195`）—— 换表情时打错一个键，整个内容包不上架。
5. **HJP 分层资产有半边支持**：立绘/特殊图认 `容器路径/表达式` + 同名 `.bundle` 与 `assetDimensions` 尺寸声明（细分层号格式「推测」），**物品图明确不支持**（`PackReader.cs:312-319`）。
6. **`_` 前缀是保留命名空间**，内容包用它做状态键会被拒（`:305,380`）。
7. **两个程序集缺一不可**：只装 Core 等于装了个没人调用的库。反过来，Unity 程序集在、内容包不在 → 就是 2.4 的第二/三层。

## 三、自动换电池 AutoBatterySwap（工坊 `3828963396`）

> **id**：`local.autobattery`｜单程序集 `AutoBatterySwap.dll`｜v1.0.21｜6.2 万订阅｜916 行
> **反编译目录**：`缓存文件夹\decomp_ws\3828963396`（10 .cs，全量）
> **为什么值得读**：**它把"换电池"当成一次带守恒校验的事务来做。** `GraphUtils.SwapItemsInPlace` 原地对调 + 换完立刻验"能量总和与件数不变"，不符就撤回 —— 这是本档最该学的部分，几乎所有"过夜自动整理"类模组都缺这一层。

### 1. 规模与结构

`AutoBatteryMod`(61，`IMod`+4 个 `ConfigEntry`) → `NightOrder`(213，过夜时机 + 充电器预结算) → `BatterySwap`(359，扫描/建模/执行/校验) → `SwapPlanner`(186，**纯数据**的工作量分配) + `Cell`/`Batt`/`SwapMove`(30，纯 DTO) + `SwapHotkey`(37，手动 F8) + `Lang`(26，双语)。
`SwapPlanner` 完全不认识 `GameItem`（计划层与游戏对象层分离），这是"先算后验"的前提。

### 2. 它怎么做这件事

- **挂在哪个过夜钩子**：`ModHook.OnHandlingNightlyServicesLate`（`AutoBatteryMod.cs:31-32` → `NightOrder.BeforeMachinesDraw`）。**不 Patch `PlayerStore.EndNight`**。
  为什么要"Late"还要"早于机器吃电"？—— 按经验库 `03-原版接口速查.md:481-499` 的 `EndNight` 管线，Late 钩子在 `HandlePower/HandleOperation` 等一串 `Handle*` 服务**都跑完之后**；而机器真正结算耗电是在随后的**逐件 `onCycleEndSlotItemFunc` 过夜结算**里（`03:138`：`PlayerStore:1757` 逐件 Invoke，"服务/事件全都处理完之后"）。所以"Late"指**服务阶段末尾**，仍早于机器吃电 —— 这正是它选这个点的原因：**别家模组的 Early 处理器都跑完了，库存是稳定的**。
- **它自己还改了序**：`NightOrder.Charge()` 把 `recharger`（自充电器）的 cycle-end 结算**提前跑掉**，标记进 `Charged` 列表；随后把该物品的 `onCycleEndSlotItemFunc` 换成 `CycleHook.Call` 包装，包装里发现"本轮已充过"就跳过原委托（`NightOrder.cs:13-19,192-211`）。
  目的：**选"最满的电池"之前，必须先让充电器把电充满**，否则会挑错；同时防重复充（多充一晚=白送电）。
- **怎么判断"电量不够"**：不是百分比，是**今晚要花多少**。`Usage = MachineryHelper.GetMachinePowerUsage(machine)`，`Energy = tag "power_source_item_energy"`，判据 `Energy(battery) < Usage(machine)` 才换（`BatterySwap.cs:70-92,324-348`）。
- **怎么找"最满的电池"**：扫 `PlayerStore.Instance.FindAllItem(true)` 全量（含背包），只要 `IsTag("power_source_item")`（`:35-44`）；候选人必须 `unitCount == 1`、`!Blocked`、不在别的机器里、`Energy >= Usage` 且 `Energy > 旧电池`（`SwapPlanner.cs:60-72`）；同分优先**充电器里的**，仍同分按 id 小的来（`:68`）—— 全序，结果可复现。
- **三个选项**（`AutoBatteryMod.cs:20-22`）：
  - `SkipSelfCharging`（默认开）→ `LeaveAlone`：`BREEDER_POWER_SOURCE_ITEM_TAG` 或 `power_source_item_recharge` 的电池既不拿来换、也不从机器里换走（`BatterySwap.cs:298-313`）
  - `SkipPinned`（默认开）→ `ItemPinHelper.IsPinned(item)` 直接跳过（同上）
  - `ChargerOnly`（默认关）→ 只有"父物品是 `recharger`"的电池才算候选（`:118,164`）
  另有两条**写死不可关**：`HypertechBatteryHelper.IsHypertechBattery` / `CurrentConverterHelper.IsCurrentConverter`（`:118,164`）。
- **物品归属安全（本档重点）**：
  1. 移动原语只有一条：`GraphUtils.SwapItemsInPlace(donor, previous)`（`BatterySwap.cs:211`）—— **原位对调**，不 Create/Destroy，所以**旧电池天然落在供体原来那个格子上，不存在"放不下"这个分支**。
  2. 对调后立刻用**引用比较**验落点：`donor.parentInventory == machineSlot`，不成立就 `Undo`（再换回来）并返回 false（`:215-221`）。
  3. 每次换完都做**全局守恒校验** `SamePower`：重新扫全部 `power_source_item`，件数与能量总和必须与换前一致，且换前的每一件都还在（`:223-238`）。不符 → `Undo` + `LogError` + **立刻 break 停止今晚剩余换电**（`:179-184`）。
  4. 执行前对每条 move **再校验一遍**（plan 之后世界可能变了）：`val6.childItem != val7`、`unitCount != 1`、能量不如价……任何一条不成立就 `continue`（`:164`）。
  5. 防重入双闸：`busy`（`BatterySwap.cs:13-22`）+ `pass`/`frame` 同帧窗口（`NightOrder.cs:113-120`）+ `SwapPlanner.ClaimPass` 保证一晚只跑一次（`:28-36`）。

### 3. 关键代码摘录

```csharp
// ① 过夜入口与"预充电"（NightOrder.cs:56-111 摘要；End() 挂在 OnGoingSleepLate/OnWakingUpEarly/OnGameLoadedLate 上，只置 open=false 把包装器关掉）
public static void BeforeMachinesDraw()
{
    if (busy) return;   busy = true;
    try
    {
        pass++;  open = true;  frame = Time.frameCount;  Charged.Clear();   // 同帧窗口 + 本轮已结算集合
        PlayerStore instance = PlayerStore.Instance;   if (instance == null) return;
        List<GameItem> list = instance.FindAllItem(true);
        Prune(list);
        for (int i = 0; i < list.Count; i++) Arm(list[i]);   // 给每件包一层 cycle-end 包装
        Charge();                                            // 提前结算 recharger，避免挑错"最满的"
        BatterySwap.Run(night: true, verbose: false);
    }
    finally { busy = false; }
}

// ② 对调 + 验落点 + 撤回（BatterySwap.cs:201-221）
private static bool Trade(GameItem donor, GameItem previous, GameSlotInventory machineSlot)
{
    if (donor == null || previous == null || machineSlot == null) return false;
    if (donor.parentInventory == null || (object)previous.parentInventory != machineSlot) return false;   // 旧电池必须真在机器槽里
    if (!GraphUtils.SwapItemsInPlace(donor, previous)) return false;                                      // 唯一移动原语
    if ((object)donor.parentInventory == machineSlot && previous.parentInventory != null) return true;    // 引用比较验落点
    Undo(donor, previous);   return false;
}

// ③ 守恒校验（BatterySwap.cs:223-238）
private static bool SamePower(List<GameItem> before, int beforeSum, int beforeCount)
{
    List<GameItem> list = CurrentSources();                                  // 重扫全部电源
    if (list.Count != beforeCount || Sum(list) != beforeSum) return false;    // 件数 + 总能量
    for (int i = 0; i < before.Count; i++) if (IndexOf(list, before[i]) < 0) return false;   // 每件都还在（引用）
    return true;
}
```

### 4. 踩坑与红线

1. **阈值是"今晚用量"不是百分比**：`Energy < Usage` 才换，`==` 算够用。设成 50% 会让"今晚只要 8 点电、电池有 9 点"的机器被换走。
2. **必须排除"堆叠"电池**（`unitCount != 1` 一律跳过），否则拆堆会丢件。
3. **plan 与 apply 之间世界会变**：它在执行循环里把守卫条件**重算一遍**（`:164` 那一长串），不是只信 plan。我们写"自动整理"必须照做。
4. **`SamePower` 是最后一道防线，不是装饰**：`FindAllItem(true)` 含背包（经验库 `07:94`），任何一步把物品挪丢了，只有全局守恒能发现。
5. **两段死代码别误读**：`SwapPlanner.ModulePower`（`:86-98`）无人调用，`SwapPlanner.Apply` 也没被用（真实执行走 `BatterySwap.Trade`，计划层只输出 `SwapMove`）—— 看这类小模组要分清"设计稿"与"实际路径"。
6. **`OnHandlingNightlyServicesLate` 的位置容易被误读**：经验库的 `EndNight` 图把 Late 画在 `HandlePower` 之后，看上去"太晚了"；真正的关键在它之后还有**逐件 `onCycleEndSlotItemFunc`**。这段建议真机断点确认一次（未验证），但 AutoBatterySwap 6.2 万订阅的实测间接支持这个顺序。

### 5. 对我们的可用点

1. **`深空电玩` 刻录机（功能 3：装电池即播）**：现在拔插电池是玩家手动。照这里写"过夜前给刻录机换满电电池"——判据用 `MachineryHelper.GetMachinePowerUsage`，执行用 `SwapItemsInPlace` + `SamePower`，一晚只跑一次（`pass`+`ClaimPass`）。
2. **`深空电玩`**：`ARC_BURN_FAULT`/概率维修那条链上若要"自动补料"，把"料"换成电池/硬件件也是同一套模型：`Cell`/`Batt` 抽象成 `Slot`/`Stock`，先 plan 后逐条校验再执行。
3. **`深空当铺：可能是群友`**：清仓箱/展柜自动补货属于同类"过夜整理"，直接抄本节 §4 第 3–4 条（执行前重算守卫 + 换完守恒校验 + 不符就撤回并停止），比现在的"逐件 try"稳。
4. **两个项目通用**：**一次移动原语 + 一条守恒不变量**，比写十个 `if` 分支更安全；我们的"整备/换盘/搬货"都该有这么一条 `SamePower` 式的断言。
5. **两个项目通用**：`ModConfig.For(id).Define(...)` 的四个选项都带**中英双语标题+长说明+默认值**（`AutoBatteryMod.cs:20-23`），配置文案规范与我们经验库那条"做什么/为什么/生效时机/副作用"完全一致，可直接当模板。

## 附：三个立绘框架怎么选（一句话）

**要"我们的内容跑在别人的运行时上"选 PortraitRuntime（数据契约最硬、还自带 F3 巡检），要"别人的美术包塞进我们的模组"选 Probably Extend Framework（文件契约最宽、60 个 public 入口），只要"纯立绘 + 高清去像素"选 NightRegulars；但《深空电玩》《深空当铺》的立绘都已经长在自己身上，三个都别当编译依赖 —— 只抄 PortraitRuntime 的**数据契约与自检**、PEF 的**文件发现**、NightRegulars 的**按需加载与回退**。**
