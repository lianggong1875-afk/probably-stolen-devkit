# 估价缓存优化 / Value Cache（代际失效缓存）｜工坊 3843892181

> 蒸馏自反编译源码 `缓存文件夹\decomp_ws\3843892181`（73 个 .cs / 1482 行，零能力模组，44 个 Patch + 28 个使缓存失效的钩子）。
> 价值：**"缓存一个原版计算很贵的结果，又要保证永不过期"的教科书实现**。作者用"代际（epoch）+ 弱表"两招把"精准失效"做成了 O(1)。

## 1. 问题

容器里塞满物品时，每次查看容器总估价，游戏都要把箱内所有物品重新走一遍 `GameItem.GetCurrentValue()`（内部还要算特性、事件加成、市场加价、水源纯度、铸锭纯度…）。物品一多就卡。

## 2. 核心设计：ConditionalWeakTable + 全局 epoch

```csharp
static ConditionalWeakTable<GameItem, ItemCache> table = new();   // 键弱引用：物品被 GC，缓存项自动消失
static long epoch = 1;                                            // 全局代际
static int trackedItems, mainThreadId;
const int MaxTrackedItems = 50000;      // 超过就整体 Reset
const int MaxEntriesPerItem = 32;       // 单物品最多 32 个键变体

public static void Bump() { Interlocked.Increment(ref epoch); }    // 任何"影响估价"的改动都调它
```

**为什么用 epoch 而不是逐条删除**：
- 每个缓存项记录自己写入时的 `Entry.Epoch`；读取时若 `Entry.Epoch != 当前 epoch`，直接认为整条失效（清空该物品的 entries 并返回 miss）。
- 于是"让所有缓存失效"= 一个 `Interlocked.Increment`，成本 O(1)，不需要遍历任何集合，也不需要知道到底哪件物品受影响了。
- 代价是**粗略失效**：改一次店铺加价会让所有物品的缓存全灭。作者认为可接受（估价是读取，不是每帧调用）。

```csharp
public static bool TryGet(GameItem item, CacheKey key, out long value)
{
    value = 0;
    if (!enabled || item == null) return false;
    if (!table.TryGetValue(item, out var cache)) { NoteNoCache(); return false; }
    long now = Interlocked.Read(ref epoch);
    if (cache.Epoch != now) { cache.Entries.Clear(); cache.Epoch = now; NoteEpochMiss(); return false; }
    if (cache.Entries.TryGetValue(key, out value)) { NoteHit(); return true; }
    NoteKeyMiss(); return false;
}
```

## 3. 缓存键：把所有影响估价的因子塞进 value type

```csharp
// CacheKey.cs（struct，值语义 → 可直接做 Dictionary 键）
struct CacheKey {
    bool a1, a2, a3, a4;      // 四个布尔开关（对应 GetCurrentValue 的四个重载参数）
    long marketMod;           // 市场加价/加成
    int  retailMarkup;        // 店铺加价
    bool applyMarkUp;         // 该物品是否适用店铺加价（item.IsApplyMarkUp()）
    string events;            // 当前生效的店铺事件签名
}
```

事件签名的构造（**这是最容易被忽略的一环**：事件会改价，所以事件变了缓存必须变）：

```csharp
static string BuildEventSignature(StoreEventManager mgr)
{
    var active = mgr.GetActiveEvents();
    if (active == null || active.Count == 0) return string.Empty;
    var sb = new StringBuilder(64);
    foreach (var ev in active)
    {
        if (ev == null) { sb.Append('|'); continue; }
        sb.Append(ev.identifier).Append('\u001f');
        foreach (var neg in ev.negociationDatas ?? Enumerable.Empty<NegociationData>())
            if (neg != null) sb.Append(neg.itemType).Append('\u001e').Append(neg.value).Append('\u001f');
        sb.Append('\u001d');
    }
    return sb.ToString();
}
```

> 注意它用不可见控制符分隔，避免 identifier 里出现分隔符时产生歧义——**我们自己拼签名时应照抄这个习惯**。

## 4. 键的构建被包成"要么完整要么放弃"

```csharp
public static bool TryBuildKey(GameItem item, bool a1, bool a2, bool a3, bool a4,
                               long marketMod, out CacheKey key)
{
    key = default;
    if (!enabled) return false;
    if (item == null) return false;
    if (Thread.CurrentThread.ManagedThreadId != mainThreadId) return false;  // 只在主线程用缓存
    var store = PlayerStore.Instance;
    var station = StoreStation.Instance;
    if (store == null || station == null || station.storeEventManager == null) return false;
    key = new CacheKey(a1, a2, a3, a4, marketMod, store.retailMarkup,
                       item.IsApplyMarkUp(), BuildEventSignature(station.storeEventManager));
    return true;
}
```

`TryBuildKey` 返回 false 时的语义是"**这次不走缓存，老老实实算**"，绝不返回半成品键。这是缓存能安全的基础。

## 5. 失效钩子：44 个 Patch 全部是"信号源"

它 Patch 了几乎所有会改动物品价值/特性/品类的成员，Postfix 里只做一件事——`ValueCache.Bump()`：

- 物品侧：`AddItemFeature`、`RemoveItemFeature`、`RemoveItemFeatureByID`、`RemoveFeatureByCategory`、`RemoveAllFeature`、`SetGameItemType`、`RemoveGameItemType`、`AddFeatureRelatedToBuyer/Event`、`RemoveFeatureRelatedToBuyer/Event`、`ApplyContrabandFeatureToChildren`、`RemoveContrabandFeature*`、`RemoveTemporaryClientFeature`、`SyncModifiedState`；
- 价格/状态侧：`set_unitValue`、`set_unitBaseValue`、`set_lateUnitValue`、`set_backupUnitValue`、`set_unitCount`、`set_state`、`set_modifiedState`、`set_uniqueId`、`set_identifier`、`set_contentWindow`、`set_parentInventory`；
- 特性侧（`ItemFeature`）：`StartExposing`、`SetExposed`、`SetExposedValueMod`、`SetPreExposedValueMod`、`SetValueModifier`、`SetValueStage`、`SetActualDisplay`、`SetPublicDisplay`、`SetPublicHidden`、`SetTool`、`SetConditions`、`SetFeatureDiscovered`、`DiscoverFeature`、`ExposeFeature`、`SetCategory`、`set_identifier`、`set_isFeatureMatch`；
- 外部系统侧：`Tag.EnableTag/DisableTag/ModifyTag/SetEnableDisableTag`、`Water.SetPresumedPurity/InitWaterFeature/UpdateWaterFeature/UpdateWaterFeatureFake/OnLiquidChanged/OnLiquidContainerPourInto`、`IngotPurityHelper.SetPurity/FeaturePurity`、`VendingFountainHelper.SimulateWaterSale`、`LabelerUIManager.Repeat`、`LabelerElement.OnDropdownValueChanged`、`Dialogue.AddChoice`、`GameItem.GetDonationCreditValue`。

**这 44 个方法名本身就是"哪些操作会改变物品价值"的权威清单**，我们做任何"价格/估价相关缓存"都该照这张表挂失效钩子。

## 6. 安全阀

| 阀门 | 实现 |
| --- | --- |
| 主线程约束 | 键构建与 `TryGetBase/StoreBase` 都校验 `Thread.CurrentThread.ManagedThreadId == mainThreadId` |
| 容量上限 | `trackedItems >= 50000` → `Reset("item cap")` 整体重来（内存优先） |
| 单物品条目上限 | 每物品最多 32 个键变体，满了只打日志不存 |
| 开关 | `ModConfig` 一个"启用容器估价缓存"开关，关掉即刻回原版逻辑 |
| 读档/热重载 | `Initialize()` 重建表 + `Interlocked.Increment(epoch)`；`Shutdown()` 关开关+Reset |
| 统计埋点 | calls/hits/misses/epochMisses/keyMisses/buildSkips 全都有 Interlocked 计数（反编译后计数体被优化成空，但字段保留，说明原版有埋点） |

## 7. 我们的用法

1. **任何"贵且幂等"的原版计算都可以这样缓存**：比如我们能想到的：容器总估价、物品真伪判定汇总、机器加成汇总、事件影响汇总。模板：`ConditionalWeakTable<被缓存对象, 缓存体>` + 全局 epoch + `TryBuildKey` 完整键。
2. **失效策略分两级**：局部（同物品键变化）+ 全局（epoch bump）。不要做"精确逐条失效"，那需要维护反向索引，成本高且易漏。
3. 缓存键里**必须包含外部系统状态**（事件、加价、纯度），否则会返回过期值——这是这类模组最常见的 bug 来源。
4. 我们自己的模组如果需要缓存，先照抄它的 `mainThreadId` 约束与容量自愈，别裸用 Dictionary。

## 8. 踩坑与风险

- **44 个 Patch 本身是冲突面**：如果别的模组也 Patch 这些 setter，Harmony 的执行顺序会影响 epoch 何时 bump。作者没写 `HarmonyPriority`，属默认优先级。
- epoch bump 后的"粗粒度全灭"在极端场景（每秒改一次加价）会让缓存命中率为 0，退化成纯开销。作者没有做自适应关闭，只给了手动开关。
- 反编译后可见大量空 `catch {}`（原版可能写了日志但被优化/或本来就吞），**这点与我们的编程规范冲突**，抄结构不要抄异常处理。
