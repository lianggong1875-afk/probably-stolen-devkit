### 1.2 它怎么做：**不复制 AgeWell，复制 Projector**

题意说"照着 AgeWell 做的"。**源码里不是**：`MachineFactory.Build` 的第一行是

```csharp
GameItem val = MachineProjector.Projector();   // PenSelfLearning\MachineFactory.cs:16
```

`MachineProjector.Projector()` 是原版**投影仪**的公开工厂（`MachineProjector.cs:7-71`），它一次性给你：`contentWindow`（电池面板+模组盘+备注槽三件套）、`SetupBatterySlot`、`MACHINE_PERFORMANCE/QUALITY_RATIO_INT`、`MODULE_TYPE_UNIVERSAL` 模组盘准入、`onCycleEndSlotItemFunc` 的耗电范式。模组随后**逐项覆盖身份**：`identifier / name / shortDescription / flavorText / 贴图 / 形状 / InitMachinery / 三个 cycle 委托`（`MachineFactory.cs:22-38`）。

AgeWell 在这里是**逻辑范式**的参照物，不是代码来源：`MachineWineRack.AgeWell()` 用质量加成换"额外陈化天数"（`MachineWineRack.cs:93-97`：`1 + max(0,qualityBonus)/125`），本模组换成"质量加成换额外推进次数"（`NightService.cs:741-764`：`planned = gainPerUse + baseAdvances + trunc(quality/qualityPerAdvance)`，`qualityPerAdvance` 默认 50，`ModSettings.cs:79-89`）。

**三个属性各管一件事，全部读原版字段，零自存**：

| 属性 | 数据源（原版 tag） | 本模组怎么用 |
|---|---|---|
| 质量 → 进度加速 | 模组 `BONUS_PERCENTAGE_QUALITY_INT`（或 `TEMP_*`） | `SettleMachine` 里 `SumPercent(machine,"QUALITY")` → 额外推进次数（`NightService.cs:184,229-234`） |
| 效率 → 省电 | 同上，`..._EFFICIENCY_INT` | 写回 `machinery_drawn_power`（`NightService.cs:1271-1310`） |
| 性能 → 获得算法概率 | 同上，`..._PERFORMANCE_INT` | 夹到 0–100 当百分比骰点（`NightService.cs:339-350`） |

"算法/自学习"本身也是**原版词条**：`ModuleEffectHelper` 早就定义了 `MODULE_EFFECT_LEARNING_ALGORITHM`，上限存在 `LEARNING_ALGO_MAX_{PERFORMANCE,EFFICIENCY,QUALITY}_INT`（`ModuleEffectHelper.cs:41-45,239-262`）。模组干的事只有两件：`ModuleEffectHelper.AddEffectToModule(mod,"MODULE_EFFECT_LEARNING_ALGORITHM")` 给词条，然后把 `BONUS_PERCENTAGE_*` 往上限推（`NightService.cs:404-421,1222-1264`）。**它一行自定义存档都没写**——进度就是原版 tag 的值。

**零 Harmony 靠什么触发**：靠原版的两个多播委托槽 + 三个 ModHook。

| 触发点 | 原版派发位置 | 本模组接法 |
|---|---|---|
| 过夜 | `PlayerStore.EndNight()` 先置 `CurrentConverterHelper.isNightCycle = true`，再 `FindAllItem().ForEach(onCycleEndEarly)` → … → `RunWindow(2)` → `onCycleEndSlotItemFunc` → `RunWindow(3)` → `onCycleEndLateSlotItemFunc` → 置 false（`PlayerStore.cs:1694-1770`） | `onCycleEndSlotItemFunc = NightService.Cycle`、`onCycleEndLateSlotItemFunc = NightService.NightCycle`（`MachineFactory.cs:37-38`） |
| 上架 | `ModHook.OnPlaceInventorInventoryItemEarly/Late`（双重保险，见 `PenMod.cs:75-93`） | 概率把机器塞进 DrJackson 售货台 |
| 读档 | `ModHook.OnGameLoadedNormal` | 重扫 `PlayerStore.FindAllItem` 重挂灯点/效果（`PenMod.cs:185-245`） |

**SaveManager 的关键事实**：读档不是"反序列化原对象"，而是 `DirectoryMaster.Item(savedItem.identifier)` **重新跑一遍工厂**（`SaveManager.cs:155-170`），于是 `Build()` 里的三个委托、窗口、模组盘回调**自动重建**。这就是零 Patch 加机器能活过读档的根本原因；也意味着**工厂方法会被读档路径再次执行**，里面任何"发物品/写世界"的动作都必须判 `SaveManager.IsDecoding`（本模组在 `MachineFactory.cs:81-84` 就这么干的）。

### 1.3 新增一台机器的 checklist（可直接照抄）

### 1.5 踩坑与红线

1. **电池被机器 tag 污染**：`PowerHelper.DrawPowerSource` 会把机器的 `machinery_drawn_power` 写到电池上，模组用 `PowerTagCleaner.Clean` 每次用完就 `dict.Remove` 两个 key（`PowerTagCleaner.cs:9-45`）。做耗电机器，这条几乎必踩。
2. **`DrawPowerSource` 返回值不等于"真的扣电"**：本模组用"换电池 / 电量下降 / `CanDrawPowerSource`"三重兜底判定（`NightService.cs:194-226`）。做"没电就不干活"的逻辑要照抄这个判定，不要只信返回值。
3. **读档会重跑工厂**：`SaveManager.DecodeNodesInternal` → `DirectoryMaster.Item(identifier)`（`SaveManager.cs:155-170`）。工厂里发物品 = 每次读档都发一份。
4. **贴图路径会随存档回灌**：`DecodeNodesInternal` 用存档里的 `spriteAtlasPath/spritePath` 调 `SetSprite`（`SaveManager.cs:178`），旧版本存档会把 sprite 指回旧路径，所以要有 `EnsureMachineSprite` 这类"发现不对就改回来"的修复函数（`MachineFactory.cs:106-134`）。
5. **`MACHINE_PERFORMANCE_RATIO_INT` 是原版投影仪留给自己的字段**：模组直接把它从字典里删掉、把效率/质量 ratio 钉成 1（`SelfLearnWindow.cs:294-332`），否则原版 `GetCurrentQualityBonus()/ratio` 会把加成二次缩小。
6. **不要指望"自己算出来的加成"和原版机器 tag 一致**：模组从不读 `TOTAL_PERCENTAGE_*`，而是自己遍历模组求和（`SumPercent`，`NightService.cs:1125-1166`）+ 靠 `ModuleHelper.ApplyBasicModuleEffect` 让原版重算（`:1280`）。读 `TOTAL_*` 只有在原版刚跑过动作时才新鲜。
7. **反向修原版机器耗电是"帮别人擦屁股"**：`RepairForeignMachine` 会改**别的机器**的 `MACHINERY_DRAWN_POWER_BASE`（`SelfLearnWindow.cs:134-188`）——除非确有必要，别在自己的模组里写这种跨模组写操作。
8. **异常处理风格不可照抄**：本模组通篇 `try{…}catch{}`（甚至有空的 `catch { }`，如 `MachineFactory.cs:69-71`）。按本工作区规范，边界处必须 `LogError` 带堆栈。
9. **它是 night 驱动的**：`Cycle` 里 `if (!CurrentConverterHelper.isNightCycle) { TurboCycle(...); return; }`（`NightService.cs:144-148`）——白天只吃涡轮，不推进。做"长周期生产"要明确"白天干不干活"。

### 1.6 对我们的可用点

- **零 Patch 加机器这条路已实证可行**，而且**读档安全**：只要在 `OnModItemDirectoryInit` 里注册工厂，原版读档会自动重建整台机器。这条比"Patch 原版机器的 Create"干净一个数量级。
- `MachineProjector.Projector()` 是**最快的机器骨架**（窗口+电池+模组盘+备注槽一次给全）；我们做"当铺鉴定台/翻新台"这类 3×3 单机，直接拿它当壳再改身份，省 200 行面板代码。
- "属性→行为"的正确接法是**读原版 `BONUS_PERCENTAGE_*` 模组 tag + 写原版 `machinery_drawn_power`**，不要自建一套百分比系统——玩家会同时装模组升级，两套系统必然打架。
- 长周期推进挂 `onCycleEndSlotItemFunc`（过夜），实时推进挂 `onOneSecondItemFunc`（每秒），这是原版唯一两个稳定节拍；`EndNight` 的顺序（early → 主 → hopper(2) → late → hopper(3)）决定了"先产再运"，要做物流就挂 late。
- 说明书/纸条这类"槽内文档"必须走 `UncheckedAccept` + 引用校验 + 失败回滚（`NoteInstaller.cs:129-172`），否则读档会掉物品。

### 2.2 它怎么做：重算原版工艺，且**不写自己的化学**

**它没有复刻化学公式，也没有转调"原版机器"**，而是转调**原版化学静态库**，跑在自己克隆的假物品上：

```csharp
internal sealed class SimulationItem : GameItem            // DreamDustAutomation.Planning\SimulationItem.cs:5-30
{
    public SimulationItem(GameItem source = null) : base("dda_simulation", (PixelWindow)null) {
        if (source != null) { identifier = source.identifier;
            foreach (KeyValuePair<string, TagState> item in source.modifiedState.dict)
                ((GameItem)this).state.dict.Add(item.Key, item.Value.Clone()); }
        else { /* LIQUID_CONTAINER_TAG + CHEM_ITEM_TAG + 容量 1e7 + 26℃ + 全液体清零 */ }

    public override void Destroy() { }        // 假物品不回收到任何池
```

有了它，`ChemistryOperations` 就是一层**双实现适配器**：真实物品走原版静态函数，假物品走状态拷贝（两边语义必须一致，这是它最大的正确性风险，也是它 468 行里一半代码在干的事）：


### 2.5 白天计时 / 过夜完成：两个节拍并存

### 2.7 踩坑与红线

1. **`SimulationItem` 是双刃剑**：它继承 `GameItem` 并覆写 `Destroy/Validate`，任何原版函数里若有 `is GameItemElement` 分支就会走不同路径（`ChemistryOperations.Amount` 就专门判 `is SimulationItem`）。给原版函数喂假物品前，必须逐条核对"它有没有判真实类型"。
2. **必须"先算后做"且"做了再验"**：`FormOne` 在成型前重算纯度 `Amount(sim, Active)*100 < actualGrade*UnitVolume` 就抛 `runtime_purity_changed`（`MachineController.cs:4417-4420`）；输出槽放不下就 `Destroy` 并保留罐内液体（`:4425-4439`）。
3. **失败一律用 key 不用文案**：`throw new MachineFault("runtime_xxx")`，文案在 `Localization` 里查。这样 85 个文件的中英双语才没有硬编码。
4. **计划/执行状态序列化进机器 tag**：`DDA_RUNNING_V1`（JSON 字符串）、`DDA_INCOMPLETE_BATCH_V1`、`DDA_RECOVERY_REASON_V1`（`BatchPersistence.cs:13-17,264-311`）。读档时反序列化失败要能降级到"半成品待回收"，而不是坏档。
5. **窗口关掉也要跑**：`Tick`/`Cycle` 是挂在自己的机器委托上的，不依赖 UI 打开；协程宿主借的是 `EmporiumEntry.Instance` 的 MonoBehaviour（`MachineController.cs:3516`）。
6. **3 ms 预算 + 每帧记录**：`ModPerformance` 只在单帧模组总耗时 >16 ms 时打一条 `[DDA_PERF]`（`ModPerformance.cs:46-61`）——做重计算模组必须留这条可观测线。
7. **一档一台也是"检查已拥有"而不是"计数器"**：`ContainsMachine(owned)` + 售货台前后仓扫描（`ModEntry.cs:61-75`），没有写"已售出"标志位，因此删档/卖机后能重新刷出。

### 2.8 对我们的可用点

- **"接管原版机器"= 把原版核心的 `onCycleEnd/onOneSecond` 摘下来自己调**（`HardwareBinding.cs:115-121`）。这条比复刻机器便宜得多：原版核心的槽位、升级、涡轮、耗电、音效全保留，我们只负责"什么时候推进"。
- **`SimulationItem` 这个"状态克隆体"是重算一切原版工艺的通用钥匙**：拿到它的 `state.dict` 深拷贝语义，就能在不动世界的情况下把原版反应跑 900 次。
- **降档搜索 + 早停 + 硬上限**是廉价而稳的规划骨架：六档纯度 × 若干投料方案，每方案 ≤900 tick，再加 3 ms 时间片，就能在 4,541 行 UI 里做到不卡帧。
- **贴标只写 `fakeCondition` 并 `SetExposed(false)`**，`realCondition` 不动——这正是本工作区"真伪/成色只认真实字段"铁律的**反向应用**（我们做伪造/贴标系统时，改的就是这个字段）。
- **"过夜一次算完整段"** 给了长周期生产一个通用解：把 `Step()` 写成幂等多步函数，白天每帧 +1、夜间 while 到不能再推，两条路径天然一致。

### 3.8 踩坑与红线

1. **46 个补丁不是炫技，是"原版没有的接缝"**：喂食/繁殖/屠宰/笼位槽/物流/售卖全都只有 private 或内联逻辑，只能补丁。但每个补丁都极薄（Prefix 返回 bool 或 Postfix 计数），业务仍在 `RanchRuntime`。**我们写自动化，补丁要薄到"只做路由"**。
2. **`SaveManager.DecodeNodes` 上做迁移是必要的恶**：它改了结构就要升 `CurrentVersion`（现 10），并保留 `ToMigrationIndex` 之类的旧索引映射（`RanchSaveMigration.cs:103-144`）。一旦做过一次，以后每次改布局都要付这笔账——**能不改布局就别改**。
3. **实例表用 `ConditionalWeakTable<GameItem, RanchRuntime>`**（`RanchRuntime.cs:915`）——物品被销毁时实例自动回收，避免静态字典泄漏。这是"每物品一个运行时"的标配。
4. **反射只用在两处**：`GenericConfirmationUIManager.onConfirm`（私有字段，`RanchRuntime.cs:224`）与 `StoreStation.instance`（`:823`）。都是"原版没暴露 API 又必须拿"，属于可接受的兜底，但要在注释里写清为什么。
5. **规则与能力分离**：`AutoSlaughter = Bool("SLAUGHTER") && HasButcher`。UI 上勾了但机器没装屠宰机 → 不执行，且要给"缺设备"的原因（`RanchPlanner` 的 `Reasons` 会写"自动屠宰未启用或缺少屠宰机"，`:88-92`）。
6. **别照抄它的文件数**：5,811 行 `RanchRuntime` 里超过一半是 UI 刷新与文字。真要学，学 `Core` 那 6 个纯函数文件（`RanchPolicy`/`RanchPlan`/`RatSnapshot`/`RanchPlanner`/`PredictiveBreeding`/`EnvironmentCalculator`）。

### 3.9 对我们的可用点

- **"规则=数据（物品 tag）+ 决策=纯函数 + 执行=薄补丁路由"** 是三段式自动化的标准形。我们要做的"当铺自动定价/自动上架/自动翻新"完全套得进这个骨架，且 Core 层能离线单测。
- **一档限一台**用 `ModHelper.SetModDataBool(modId, "xxx_acquired", true)` + "已拥有扫描"双保险，比全局配置正确（每个存档独立），也比写存档结构安全。
- **消耗品自动续的三元组**（库存 tag / 每瓶点数 / 上限）+ 空瓶送垃圾页，可直接搬到"鉴定液/清洗剂/显影液"。
- **夜间记录只挂三个计数补丁**（生/死/吃），不新建日志物品——我们做"一夜经营报表"可以照这个最小侵入法。
