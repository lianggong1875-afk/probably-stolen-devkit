# A. MCP Bridge（3834799226）

## A1 传输：`HttpListener` + `TcpListener` 兜底，端口 28910，**零鉴权、零限流**

```csharp
// 缓存文件夹/decomp_ws/3834799226/ProbablyStolen_MCPBridge.Core/McpHttpServer.cs:40-46

			_isRunning = true;
			Debug.Log((object)$"[MCP Bridge] HttpListener started successfully on port {_port}");
			Task.Run(() => ListenHttpListenerAsync(_httpListener, _cts.Token));
```

- **端口**：`ModConfig.For(manifest.ID).Define("port", 28910, "server", …)`（`McpBridgeMod.cs:31`），`OnEnable` 里再做一次区间裁剪 `<1024 || >65535 → 28910`（`McpBridgeMod.cs:55-59`）。还有 `autostart` 开关（默认 `true`）。
- **协议**：JSON-RPC 2.0 over POST，**一条路径都没有**——`ProcessHttpListenerRequestAsync` 完全不看 `RawUrl`，`/`、`/mcp`、`/随便什么` 都进同一个处理分支（`McpHttpServer.cs:149-151`，那里甚至留了个空的 `if (request.RawUrl == null) { }`）。`GET` 返回健康探针 JSON（`status/name/version/inStore/time`）。
- **批量**：请求体是 `JArray` 时逐条串行处理再回数组（`McpHttpServer.cs:191-205`）。
- **SSE**：只有「单响应 SSE」——`Accept` 里有 `text/event-stream` 就把整条响应包成 `event: message\ndata: …\n\n`（`McpHttpServer.cs:233-243`）。**没有**独立 SSE 流，也没有 `Mcp-Session-Id` 会话。
- **兜底传输**：`HttpListener` 起不来（例如 http.sys 预留被占）就降级成裸 `TcpListener(IPAddress.Loopback, port)`，自己解析请求行/`Content-Length`/`Accept`，手写 HTTP 响应头（`McpHttpServer.cs:48-75` 与 `:271-414`）。这是全套代码里最「硬核」的一段：约 140 行手写 HTTP。
- **能力**：manifest 实打实声明了三项 —— `files`（热重载要读 mod 目录、写截图）、`network`（`HttpListener`/`TcpListener` 调用点）、`reflection-external`（`reload_mod_assets` 直接反射改游戏私有字段）。⚠️ 也就是说**它不可能做成零能力模组**，玩家必须信任它。
- **鉴权 / 限流：两者都不存在。**
  - 无反 CSRF：`Access-Control-Allow-Origin: *`（`McpHttpServer.cs:140`），且**从不检查 `Origin` 请求头**。任何网页里的 JS 都能 POST 到 `127.0.0.1:28910` 驱动游戏（浏览器允许跨站「简单请求」打本机回环）。这是它最大的安全缺口，对我们这种同样监听回环的桥是反面教材。
  - 无 token / 无 instance 校验：客户端连的是哪个游戏进程，靠运气。
  - 无请求体上限：`request.InputStream` 一路 `ReadToEndAsync()`（`McpHttpServer.cs:176-179`）。
  - 无并发上限：每个 POST 都 `Task.Run(...)`，线程池想开多少开多少（`McpHttpServer.cs:119`），最后全部挤进**同一个**主线程队列 → 后到的必然超时。

## A3 主线程执行：自建 `MonoBehaviour` + `ConcurrentQueue`，**每帧只取一件**；超时用 CTS，取消只在「执行前」生效

它**没有用** `ModHelper.RunOnMainThread`，也没用 `RunInBackground`（全仓 grep 零命中）。做法是挂一个自己的 `McpMainThreadRunner`：

```csharp
// 缓存文件夹/decomp_ws/3834799226/ProbablyStolen_MCPBridge.Core/MainThreadDispatcher.cs:146-176
	private void Update()
	{
		if (!_isCoroutineRunning && Queue.TryDequeue(out WorkItem result))
		{
			result.Execute(this);
		}
	}

	public static async Task<T> EnqueueAsync<T>(Func<T> func, int timeoutMs = 15000, CancellationToken cancellationToken = default(CancellationToken))
	{
		EnsureInitialized();
		TaskCompletionSource<T> tcs = new TaskCompletionSource<T>(TaskCreationOptions.RunContinuationsAsynchronously);
		SyncWorkItem<T> workItem = new SyncWorkItem<T>(func, tcs);
		using CancellationTokenSource cts = CancellationTokenSource.CreateLinkedTokenSource(cancellationToken);
		cts.CancelAfter(timeoutMs);
		using (cts.Token.Register(() =>
		{
			tcs.TrySetCanceled();
		}))
		{
			Queue.Enqueue(workItem);
			try
			{
				return await tcs.Task;
			}
			catch (TaskCanceledException)
			{
				throw new TimeoutException($"Main thread task timed out after {timeoutMs}ms or was cancelled.");
			}
		}
	}
```

要点：

1. **两种载荷**：`SyncWorkItem<T>`（同步 `Func<T>`）与 `CoroutineWorkItem<T>`（`Func<TaskCompletionSource<T>, IEnumerator>`，用来跑 `yield return new WaitForEndOfFrame()` 这种帧末逻辑，截图/图集导出全靠它）。
2. **回传**：`TaskCompletionSource<T>` 在主线程 `TrySetResult/TrySetException`，HTTP 线程 `await` → 同一调用栈上直接组 `McpToolResult`。协程版更绕：`RunCoroutine` 手动 `MoveNext`，捕获异常塞 `TrySetException`，结束前把 `dispatcher._isCoroutineRunning` 复位（`MainThreadDispatcher.cs:74-100`）。
3. **节流副作用**：`Update` 一帧只出队一件，且 `_isCoroutineRunning` 为真时**整条队列停摆**。加上 HTTP 侧无并发限制（A1），多客户端并发时后到的请求几乎必然吃 15 s 超时。
4. **超时**：`EnqueueAsync` 默认 15 000 ms、`EnqueueCoroutineAsync` 默认 30 000 ms；超时 → `TaskCanceledException` 被翻译成 `TimeoutException`。
5. **取消**：`WorkItem` 抽象了 `Cancel(string reason)`，但两个实现都只是 `_tcs.TrySetCanceled()`。**真正生效的取消点是执行前**——`SyncWorkItem.Execute` 第一行 `if (_tcs.Task.IsCanceled) return;`（`:33-36`）。所以：超时后没轮到的那一件会被静默跳过（不执行，安全）；**已经开始执行的同步工作无法打断**；**已启动的协程即使超时也会一路跑完**（`RunCoroutine` 不看 token）。
6. **MCP 层没有取消通道**：不处理 `notifications/cancelled`，没有 `progress` 通知，没有 `logging` capability。
7. **失败面**：工具里抛异常由 `McpRouter.cs:101-106` 兜住，`Debug.LogError` + 返回 `isError` 文本（含 `StackTrace`）；外层再兜一次给 `-32603`。也就是说**异常永不冒泡到游戏循环**，这一点是合格的。

1. **懒绑定（`ConfigValue<T>`）**：构造时不碰原生 API，只存一个 `Func<ConfigEntry<T>>`；`Value` getter 里「没绑定就先 `TryBind()`，还绑不上就用 `_default`」（`ConfigValue.cs:20-34`）。`OnChanged` 在**绑定之前**注册也会排队，`TryBind` 成功后统一 `Attach`（`:62-99`）。`Config.EnsureAll` 挂在 `ModHook.OnGameLoadedLate`，读档后再补一遍绑定（`Config.cs:28-43`）。⇒ 这让「配置类字段初始化时机早于游戏就绪」这个坑彻底消失。
2. **宿主角色的自识别**：`Framework.Boot` 里 `_isHost = manifest.ID == "sdjybn.framework"`，只有真身才去注册 `ConfigSection`（`Framework.cs:33-46`、`:59-75`）。也就是说**源码可以整段拷进别人的 DLL**（内嵌），拷进去时 `_isHost=false`，不会在两个 modId 下重复注册同一批配置项。这是「源码级框架」而非「DLL 依赖式框架」的写法。
3. **fail-open 的开关语义**：`IsEnabled` 对**未知模块名返回 `true`**（`Framework.cs:77-92`）；`Tooltip.Fire` 同时用 `IsEnabled("tooltip")` 与 `IsEnabled(entry.ModId)` 两道闸（`Tooltip.cs:47`、`:54`）。⇒ 少配一个模块名不会把别人的功能关掉。

### 模式二：主线程调度队列 —— `TaskCompletionSource` 把帧循环变成可 `await` 的 API

```csharp
// 缓存文件夹/decomp_ws/3834799226/ProbablyStolen_MCPBridge.Core/MainThreadDispatcher.cs:146-176

	{
		if (!_isCoroutineRunning && Queue.TryDequeue(out WorkItem result))

	public static async Task<T> EnqueueAsync<T>(Func<T> func, int timeoutMs = 15000, CancellationToken cancellationToken = default(CancellationToken))
	{
		EnsureInitialized();
		TaskCompletionSource<T> tcs = new TaskCompletionSource<T>(TaskCreationOptions.RunContinuationsAsynchronously);
		SyncWorkItem<T> workItem = new SyncWorkItem<T>(func, tcs);
		using CancellationTokenSource cts = CancellationTokenSource.CreateLinkedTokenSource(cancellationToken);
		cts.CancelAfter(timeoutMs);
		using (cts.Token.Register(() =>
		{
			tcs.TrySetCanceled();
		}))
		{
			Queue.Enqueue(workItem);
			try
			{
				return await tcs.Task;
			}
			catch (TaskCanceledException)
			{
				throw new TimeoutException($"Main thread task timed out after {timeoutMs}ms or was cancelled.");
			}
		}
	}
```

**为什么可复用**：任何「必须在 Unity 主线程做、但 HTTP/IO 线程要拿结果」的场景，都是这 20 行。三个要点值得单独记住：① `TaskCreationOptions.RunContinuationsAsynchronously` —— 否则 `TrySetResult` 会在主线程上同步跑完续体，等于把 HTTP 逻辑搬进帧回调；② `CreateLinkedTokenSource` 让外部 token 与内部超时合并；③ **执行前的 `IsCanceled` 检查**（`SyncWorkItem.Execute` 第一行）让「超时后才轮到的任务」自动作废，而不是白跑一遍。我们自己的 `OperationQueue.Tick()` 是同一思想的进阶版（多了状态机与幂等），新写工具时应当调用它而不是自起 `MonoBehaviour`。

# D 对我们的可用点

按「投入产出比」排序，只列能落到 `深空桥接器/` 里的：

1. **热重载收尾加一次 `ModScanner` 自检**（借 `reload_mod_assets:1080-1085`）。我们 `reload_mod` 的 `observe` 阶段现在只报 `patch owners` 与 `assembliesRemainLoaded`；补上 `scannerHardFlags` / `detectedCapabilities`，就能在**同一次调用里**回答「这个新 DLL 会不会被扫描器拦」。对我们「正式版必须零能力」的硬约束，这是直接的验收自动化。
