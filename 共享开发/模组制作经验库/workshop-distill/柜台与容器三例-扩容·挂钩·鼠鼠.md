### 1.3 它怎么做：形状、触发点、底部起排、屏幕位置、安全缩回
**改的是形状，不是容量字段。** `GameGridInventory` 没有 capacity：容量就是 `inventoryShape` 的格数（`GameGridInventory.cs:196-201` 的 `SetShape` 重建整张 `GridShape` 并 `Validate()`）。所以 18×4→8→12→16 是 72/144/216/288 格，`SetShape` 一改，容量、窗口 `heightPixels`、摆放合法性同时变。

**"放得下就停止扩容"靠的是"每轮都真的去探一次格"**（`CounterHelper.cs:93-124`）：

| 环节 | 代码事实 |
| --- | --- |
| 门的形状先验 | 只接管 `width==18 && IsCustomerCounterHeight(h)`（h∈{4,8,12,16}）的柜台，其余原样返回（`:110-113`） |
| 循环条件 | `while (h < 目标 && (!CanTakeAnything() ∨ 该物品找不到格))`（`:114`）——`CanTakeAnything()`＝还有空格∨能堆叠∨有透传（原版 `GameGridInventory.cs:131-151`），第二个条件才是"这件放不下" |
| 每轮只加一档 | `ExpandCustomerCounter`（`:156-183`）算 `NextCustomerHeight(h, 目标/4)`＝+4 行；**高度没变就 break**（`:119-122`），防止死循环 |
| 触发时机 | 原则：**在"决定分流/决定销毁"之前**。原版 `GraphUtils.EmporiumTryAdd`（原版 `:12-18`）是一条 if 链：前柜在链尾，前面全失败就 `DestroyIfUnplaced`；而 `TryAddInto` 先问 `CanAccept`（原版 `:20-38`、`:111-118`）。0.1.7 特意补了 `GraphUtils.CanAccept` 前缀（`GraphUtils_CanAccept_Patch.cs:14-25`），因为旧版挂在更晚的 `TryAcceptAll` 上时，预检失败根本走不到（见其 `validation.md` 的 0.1.7 记录） |
| 堆叠余量 | `TryAcceptAll` 有 40 次上限且"找不到格就 break"（原版 `GraphUtils.cs:185`），返回**剩余量**；`RetryCustomerRemainder`（`:126-149`）只在"本次真长高了"时用新高度重投剩余量，不递归 |

**"从底部起排、大件跨区"是 Postfix 整体换掉原版选格结果。** 原版按 y 从小到大扫（原版 `GameGridInventory.cs:888`），也就是**永远从最上面一行开始塞**；模组在 `TryFindOneValidInventorySlot` / `..._TopMiddle` 的 Postfix 里用自己算的形状顺序重试（`CustomerSlotOrder_Patch.cs:13-17`、`CustomerMiddleSlotOrder_Patch.cs:13-17`）：
- `CustomerPlacements`（`:347-368`）把高度切成 4 行一条的**带**，`for (bottomRow = h-1; bottomRow >= 3; bottomRow -= 4)` → **自下而上逐带**；带内 `BottomPlacements`（`:316-345`）从"物品底边贴带底"开始往上扫；四条带都放不下时最后再扫 `0..h-1` 的完整高度（`:364`）——大件就是这样跨区的；
- 只在"已扩容（h≠4）∧原版确实找到了位置∧不是堆叠目标"时才替换（`:372-380`），否则原样返回；替换失败也返回原版结果（`:390`）。

**"扩缩时保持屏幕位置"不是重排坐标，是让物品跟着格子走。** 两处位移精确相消：

| 谁在动 | 怎么动 | 出处 |
| --- | --- | --- |
| 窗口 | `SetShape` → `Validate()` 重算 `heightPixels` → 重跑原版 `GetFrontInvPosition`；普通店面走兜底分支 `frontInv = (backInv.x, backInv.y + frontInvWindow.heightPixels)`，**位置与自身高度线性相关** | 原版 `EmporiumEntry.cs:1645-1653`（`:1652`）；调用点 `CounterHelper.cs:172-176`、`:423-431` |
| 物品 | `anchoredPosition = (minX*gridSize, -minY*gridSize)`，y 向下、`minY` 越小越靠上 | 原版 `GameItemElement.cs:199` |
| 补偿 | 加 4 行 ⇒ 每件物品 `new GridShapeBuilder(modifiedShape).SetPosition(minX, minY+4)`；缩 4 行 ⇒ `minY-4`。位移量与行数**恰好相等**，窗口与物品的位移互相抵消 ⇒ 屏幕上不动 | `CounterHelper.cs:286-314`、调用点 `:169`、`:256` |

这也解释了为什么我方柜台只需要 `SetShape(18,5)` 就完事：后柜位置 `y = -(canvasH/100)*52.2` **只跟画布有关**（原版 `EmporiumEntry.cs:1662`），顶边固定 ⇒ 多出来的一行是**向下长**，物品一个都不用动（`CounterHelper.cs:53-91`）。

**"安全缩回"是三段式否决，失败就挂起。** `TryShrinkCustomerCounter`（`:239-268`）：① 目标行数必须合法且 `h > 目标`；② `HasItemsInUpperRows(items, h-目标)` —— 只要有物品 `minY < h-目标`（即待删的那几行）就 **return false 不缩**；③ `ShiftCustomerItems(..., -(h-目标))`，任一物品 `minY-n < 0` 也 false；④ 全绿才 `SetShape` + 重摆窗口。失败不是重试到底：`TryResetCustomerCounter`（`:216-237`）把柜台记进静态 `pendingReset`，靠三处再试——顾客换人（`StoreUIManager_OnNextClientArrived_Patch.cs:8-12`）、顾客把东西拿走（`PlayerStore_RemoveNotOwned_Patch.cs:8-12`）、以及 **1 Hz 心跳** `EmporiumEntry.OneSecPrefixFunction` 的 Postfix（`EmporiumEntry_Refresh_Patch.cs:8-12` → `RefreshCounters` `:196-214`）。我方柜台的第 5 行用同一套路，只是判定换成 `HasItemsInExtendedRows(inv, 4)`＝任一物品 `maxY >= 4` 就不缩（`:393-421`）。

**和 batch-9 `3832768562` 拾荒扩地的差别（同一道题，两种解法）**

| 维度 | `3832768562` 拾荒扩地（12×9→12×15） | `3835887557` 柜台扩容（18×4→18×16） |
| --- | --- | --- |
| 形状校验 | 极严：宽高 + `minX/minY==0` + `orientation==0` + `!flipped` + 越界哨兵 + 逐格可用（`PlainShape`）；**被别人改过就永久让位** | 只查 `width==18 && h∈{4,8,12,16}`（`:35-42`），**不查旋转/翻转/原点/洞**；别人改过也会被 `SetShape` 一把抹平 |
| 物品 | **一格都不搬**：地面非空就不动手 | **主动搬**：全员 `minY±n`，两段式先算后写 |
| 触发 | 一次性接管，之后不再碰 | 每次"要放东西"都探一次，按需 +4 行，双向（含缩回） |
| 失败姿态 | 放弃 + 一行日志，不重试 | `pendingReset` 挂起，三处时机 + 1 Hz 重试，成功前保持现状 |
| 窗口适配 | 改 `localScale/localPosition`，必须成对 Prefix 还原/Postfix 重算 | 只重跑原版 `GetFrontInvPosition`，不碰 scale ⇒ **16 行在 720p 会不会出屏没人管** |

两例的**共同前提**：都是"改原版结构的租约"——先确认形状主权，再改；差别只在"要不要连物品一起搬"，而一旦搬了就必须连窗口几何一起管。

// CounterHelper.cs:286-314 —— 不是重排，是把每格行号整体平移；两段式：先全算，再全写
public static bool ShiftCustomerItems(IList<GameItem> items, int rows) {
    if (items == null) return true;
    GridShape[] array = new GridShape[items.Count];
    for (int i = 0; i < items.Count; i++) {
        if (items[i] != null) {
            GridShape modifiedShape = items[i].modifiedShape;
            if (modifiedShape == null || modifiedShape.minY + rows < 0) return false;     // 任一越界就整体放弃
            array[i] = new GridShapeBuilder(modifiedShape).SetPosition(modifiedShape.minX, modifiedShape.minY + rows).Build();
        }
    }
    for (int j = 0; j < items.Count; j++) if (items[j] != null) items[j].modifiedShape = array[j];
    return true;
}

private static bool TryShrinkCustomerCounter(EmporiumEntry emporium, int height) {
    GameGridInventory frontInvinvElement = emporium.frontInvinvElement;
    if (frontInvinvElement == null || frontInvinvElement.inventoryShape == null) return false;

    if (inventoryShape.width != 18 || !IsCustomerCounterHeight(inventoryShape.height) || inventoryShape.height <= height) return false;

### 1.6 踩坑与红线
1. **`SetShape` 是无情重建**：`SetDataFill(0)` 造一张满格新图（原版 `GameGridInventory.cs:196-201`），越界物品不会被搬也不会被报错——`ResetFrontCounterGrid`（原版 `:420-424` 硬 `SetShape(18,4)`）就是现成的屠刀，必须 Prefix 拦（patch #14）。任何"改原版网格"的模组都得先问：谁还会调 `SetShape`？
2. **改形状必须同时管几何**：窗口位置与自身 `heightPixels` 线性相关（前柜），与画布相关（后柜）。前柜要平移物品、后柜不要——照抄一半就会看到物品整体跟着跳 4 行的高度。16 行在 720p 的可见性本包**没做**（batch-9 做了 `Fit` 缩放），是我们接手时的第一件事。
3. **禁用/卸载的收尾**：后柜第 5 行有物品时关配置，`HasItemsInExtendedRows` 会让它**一直保持 5 行**；README 明确要求"先清空第五行并保存再停用"。同理前缀只负责扩、不负责善后，卸载后第 5 行物品会留在越界坐标。
4. **`OneSecPrefixFunction` 是个幌子方法**：原版全文只有一句 `isGeneScannerScanning = false`（原版 `EmporiumEntry.cs:562-565`），被 1 秒 tick 调用；模组拿它当心跳（patch #13）。这是**热点靶点**，别人也挂就排队——别把它当稳定 API。
5. **`GraphUtils.CanAccept` 是最热的共享点**（batch-9、本包、任何"扩地/扩容"模组都要挂）。它的语义是"这个容器现在能不能收"——在里面**改形状**属于副作用写在判定里，多个模组同时这么做会互相把形状改来改去。本包用 `IsCustomerCounterHeight` 圈住自己，等于宣称"18×N 归我"；我们若要共存，先读形状再决定，别无条件 `SetShape`。
6. **零能力不等于零风险**：`manifest` 空 `<Capabilities/>`、无反射无 IL，但 15 个 patch 里 3 个在 `GraphUtils`、3 个在 `PlayerStore` 的落桌链上——冲突扫描要按"方法"而不是按"标签"看。

### 1.7 对我们的可用点
- **"改动前先把形状当租约验一遍"**：抄 batch-9 的 `PlainShape` 五连（宽高 + 原点 + 朝向 + flipped + 越界哨兵），别抄本包的"只看宽高"——它那是自家独占场景才敢这么省。
- **"两段式提交"可复用**：所有"改坐标 / 改形状"的动作都先算进数组、全绿再写回（`:293-312`）。比 try/catch 回滚简单，而且天然没有半成品状态。
- **"心跳借道"**：要一个 1 Hz 的廉价时机，`EmporiumEntry.OneSecPrefixFunction` Postfix 最省；要"事件时机"，`OnNextClientArrived` / `RemoveNotOwnedItemFromTable` 比轮询准。
- **"屏幕位置不变"的通用判据**：`容器位置是否随尺寸变` × `物品坐标原点是否在容器边缘` 两个问题决定要不要补偿物品坐标。我们做"更大的展台/更大的外出后仓"时，先回答这两问，再决定搬不搬物品。
- **拦"预检"而不是拦"接受"**：原版凡是 `CanAccept → 失败就换目标/销毁` 的链路（`EmporiumTryAdd`、`TryAddInto`、`TryAddDirectSellingItemToTable`），扩容必须挂在预检上，挂晚了等于没挂。

### 2.3 它怎么做：坐标、容器、让路
**① 坐标：本包根本没有坐标。** 33 个 `.cs` 里 `RectTransform`/`anchoredPosition`/`transform`/`canvas` 一次都没出现（`Vector2` 只出现在一个 Harmony 参数表和 `Sprite.Create` 的 pivot 上）；`WallHook.dll` 里也搜不到 `mount`/`anchor`/`canvas` 字样。挂钩就是个**普通网格物品**：
- 形状 `new GridShapeBuilder(1, level + 1)`＝1×2 / 1×3 / 1×4 的竖条（`WallHookItems.cs:165`），`SetGameItemType("STORAGE")`、`EnableTag("DOREMI_WALLHOOK")`、`useSpriteFromMod=true`（`:163-171`）；
- 精灵 32×64 / 32×96 / 32×128（`EmbeddedWallHookSprites.cs:27-32`），从程序集资源解出、**校验尺寸与 PPU 后才替换**（`:60-67`、`:78-110`）；
- 所谓"挂在墙上"＝玩家把它摆到墙边 + 一格宽的竖条形状 + 美术。**没有墙面锚点、没有相对墙面运算、没有 960×540 设计空间换算**——那是 `3832013611` 的做法（硬坐标 `(128,355)` / `ArtRuntime.CenterX/TopY`）。
- 注意 README v2.3 有一条"可把挂钩拖到水龙头下方固定壁挂点、本体留在主仓只把精灵画到墙上"——**本包代码里找不到任何实现**（无 transform、无 mount 字符串）。取证实测：`grep -rn "RectTransform|anchoredPosition|transform|canvas"` 0 命中、DLL 二进制搜 `mount/anchor/canvasWidth` 0 命中。结论：README 超前于本包 DLL（推测：该功能在后续版本或作者忘了提交），**照它做会踩空**。

**② 真容器，不是挂件。** `Create(level)` 建的是 `GridPixelElement(level, 1).SetSpacing(4,4)`，里面横排 `level` 个 `GameSlotInventory(4,4)`，每个都可收 1 件（`WallHookItems.cs:99-110`），再套 `MachineHelper.CreateMachineryWindow(true, panels)` 当 `contentWindow`（`:116-120`），最后 `WallHookSlots.Register`（`:123`）把每个 slot 记进三张静态表并统一改名 `identifier = "doremi_wallhook.slot.{i}"`（`WallHookSlots.cs:56-84`）。所以背包是**真 childItem**，存档走原版 `SaveItemNode` 子树，不需要自定义序列化——代价是读档后**必须重绑**：`CollectSlots` 递归认五种节点（`GameSlotInventory`/`GridPixelElement`/`MachineryPanelRow`/`MachineryPanel`/`MachineryIntake`，`:169-243`），`RebindAllLoadedItems` 在 `OnGameLoadedLate` 里扫 `EmporiumEntry.GetAllItems()`（`:245-269`、`Core.cs:35`）；`DecodeSaveItem` 之后还有一层兜底：拿存档 JSON 里挂钩节点的 `childItems` 子树比一遍，缺了就用 `SaveManager.DecodeNodes` 重建并替换（`WallHookLoadRecoveryPatch.cs:12-85`）。
**谁能上钩**：**10 个硬编码 id 白名单**（`WallHookSlots.cs:9-11`：7 个原版背包 + 2 个 kids + 自家奶龙），不是 tag 判定；外加 `WouldCreateContainmentCycle` 沿 `GetParentItem()` 上溯防"背包套自己"（`:29-54`）。三处一致性靠同一个谓词 `CanAcceptBackpack` 卡在 `TryInventorySlot`/`UncheckedAccept`/`SlotMarker.TryAcceptOnce`/`MayHaveValidInventorySlot`/`CheckInventorySlotStillValid` 五个入口（对应 5 个 patch）。

**共存结论**：两个挂钩模组各自只对"自己记录的 uid"动手，容器互不共享，所以能并存；真正的冲突面只有一个——**同一个背包被两边同时宣称**。那时 `3832013611` 主动退出（它读本包的键），本包照旧按自己的记录归位 ⇒ 结果确定。反方向（本包读到对方的键）**不存在**，所以**不存在互读**，是单向让路。

**其他值得抄的机制**：离店携带是 `Prefix` 接管原版 `EmporiumEntry.TransferBackpackToInv`（原版 `:1876-1883` 只有 `TryAcceptAll` 一句，**不查结果**就把 `selectedBackpack` 清掉——背包没进携带槽也当带上了）；本包改成 `Expel → UncheckedAccept → 引用比对`，失败按 挂钩→物品区→后仓 三级回滚（`BackpackCarry.cs:8-62`）。存盘窗口期（原版**不序列化**离店携带槽）用 `PlayerStore.SaveGame` 的 `Prefix` 把背包临时塞回挂钩、`Finalizer` 再塞回携带槽（`WallHookSavePatch.cs:9-18` + `BackpackReturn.cs:185-255`）。归位是"回店确认后才做"，且每 15 帧才试一次（`:154-183`），`readyAttempts < 120` 才放弃（`:283`、`:321`）。

### 2.6 踩坑与红线
1. **`PerSaveState.MarkDirty` 没有实体**（`:76-81` 反编译体只剩 `if (store == null) {}`）：所有 `MarkDirty` 调用都不产生可观察效果，README 说的"延后到游戏自动存档周期"实际是"完全不管存档时机"。写协议键后玩家直接退游戏，`return_state` 就丢（物品还在，只是不归位）。是源码本就空还是反编译丢了调用（推测：本就空，因为同文件 `SetString` 已经直接写 `ModHelper`）。
2. **`slotIndex <= 2` 写死在解析里**（`:480`）：将来加四级挂钩，旧记录会被判非法 → `Clear()`。要扩就得同时改 `TryParse` 与 `TryGetPendingState`（`:498-504`）。
3. **白名单是 id 数组，不是 tag**（`:9-11`）：第三方背包**一律上不去**；反过来原版加新背包 id 也要改码。这与 `3832013611` 的 `BACKPACK_TAG || backpack` 宽判定正好相反——两者装一起时，同一件模组背包在 A 模组能挂、在 B 模组不能挂，玩家会当成 bug。
4. **`readyAttempts < 120` 是硬上限**（`:283`、`:321`）：回店后 120 次 tick 内场景/物品没准备好就 `FailSafely` 清状态（背包留在原地，不丢但不归位）。慢存档 + 大量模组时会命中。
5. **无热重载**（透视 4 项全否）：`WallHookSlots.Clear()` 只在 `OnDisable` 与 `Core` 卸载时调（`Core.cs:66`），静态三表 + `ByOwnerUniqueId` 是纯内存态；热重载后旧 item 引用会悬挂。
6. **升级合并必须等拖拽结束**：`WallHookUpgrade.Tick` 在 `ItemMouseDragHandler.current.IsDraggingItem` 时把处理帧往后推（`:60-64`），且 `TryMerge` 的回滚顺序是"先把新钩接进目标格 → 再 Expel 源钩"（`:102-123`），任何人改这段都要保住这个顺序，否则一次失败会同时丢两件。

### 2.7 对我们的可用点
- **"自建窗口里挂真 `GameSlotInventory`"这条路已验证可行且能存档**：关键是 `contentWindow` + `MachineHelper.CreateMachineryWindow` + 每格 `GameSlotInventory`，读档靠"重扫 `childElement` 树 + 按 uid 重绑"，而不是自定义序列化。我们的"多功能货架/展示柜"可以直接照抄这套骨架（`WallHookItems.cs:99-123` + `WallHookSlots.cs:169-269`）。
- **对外只暴露一个标量键**：`v1|a|b|c` 这种"版本 + 定长段 + 严格解析"，比塞 JSON 或建二级结构更抗别人读。我们若要做"被让路"的一方，就照这个格式写，并在 README 里点名键名。
- **让路协议的正确姿势是"读方让、写方不管"**：本包完全不感知 `3832013611` 的存在，成本全在读方。我们要跟别人共存时，优先选择"读别人的键"，而不是要求别人读我们的。
- **存盘窗口期借调**（`PrepareForSave`/`RestoreAfterSave`）：凡是"临时把物品搬到一个原版不序列化的容器"的功能（带出门、临时工作台、快递箱），都要在 `SaveGame` 的 Prefix/Finalizer 里做"存前搬回、存后搬走"，且 `Finalizer` 必须拿到 `Exception` 再原样返回（`WallHookSavePatch.cs:14-18`）。
- **卸货要"只卸新拿的"**：`return_existing_contents` 记离店时的 uid 快照，回店用差集决定卸哪些（`WallHookBackpackUnload.cs:9-44`），并且 `ShouldKeepInside` 放行 pin/生长中/上锁/`MODULE_STUCK_TAG`（`:243-246`）。这套"快照 + 差集 + 例外表"比"全卸"友好得多。

### 3.5 踩坑与红线
1. **`alpha=1` 不是美术疏忽**：原版给物品背景图设了 `alphaHitTestMinimumThreshold = 1E-05f`（原版 `GameItemElement.cs:106`），alpha=0 的格子**点不到、拖不动**；填成 1/255 既看不见又保住整块矩形可点。我们换任何物品图都要问这一句。
2. **`ShapeDepth` 必须是 `[ThreadStatic]`**（`PigArt.cs:9-10`）：`BuildShapeFromSprite` 可能被嵌套调用（物品创建 → 换图 → 再算形状），单例计数器会把别人的嵌套也吃掉。配 `Finalizer` 保证异常路径也还原。
3. **缓存键含 `original.GetInstanceID()`**（`PigArt.cs:186`）：同一套图会被每件物品合成一次，包里 40 张猪全在场时内存是 `件数 × 96×64×4B`。量大时要加"按 (key,state,mark) 共享 + 只造必要变体"。
4. **`IsRat` 要求 `!item.useSpriteFromMod`**（`PigStates.cs:36`）：别的模组给老鼠换了 mod 贴图，本模组就**静默不生效**。它靠 `[HarmonyPriority(0)] + [HarmonyAfter("mod.rat_skincare")]`（`RatAtlas.cs:9-10`、`ItemArt.cs:9-10`）抢在对方之后覆盖，并在 `OnModAssetsLoaded` 里检测到 `rat_skincare` 就警告（`Core.cs:161-167`）。
5. **`"mod." + id` 是加载器注入的 Harmony 实例名，不是魔法串**：原版 `ModLoader.cs:1611-1612` `new Harmony("mod." + manifest.ID)`。所以 `[HarmonyAfter("mod.xxx")]` 是**通用的跨模组排序协议**，我们也能用（要排在谁后面就写谁的 id）。
6. **纯外观也要防"顺手改数据"**：`MarkAppearance` 只做 `Prefix false`（把两个 overlay 渲染节点 `enabled=false`），不改 `AnimalMarkHelper` 的任何状态；`Labels` 只在 `GetDisplayName` 上加后缀 `[老鼠]`。一旦在这些 Postfix 里写 tag，就不再是"纯外观"了。

### 3.6 对我们的可用点
- **"换图不动占格"的三件套**：`[ThreadStatic] 深度计数器` + 原图 rect 等比校验 + `Sprite.Create` 保 pivot/PPU/border。我们的"改外观类"模组（换皮、显示器贴图、货架涂装）直接抄。
- **`alpha=1` 填充**：换任何可点物品的图都要做，否则透明角落点不到（原版 `alphaHitTestMinimumThreshold`）。
- **"状态叠图在内存里合成"**：不新增物品、不加 tag，只按 `modifiedState` 现算现画（`Compose` + `Blit` + 墨水染色）。比"每种状态一张完整图"省几十张图，也比"多层 GameObject"省一套 UI。
- **`[HarmonyAfter("mod.<id>")]` + 启用检测**：跨模组抢显示优先级时，这是唯一不需要对方配合的手段；但要接受"对方的 `useSpriteFromMod` 会让我们的判定直接失效"这个事实。
- **中英双串硬编码 + `LocHelper.GetCurrentLocaleCode()`**：小模组不建 `.trans` 的合法规避（`Labels.cs:7-15`），代价是每种语言都要写在源码里——超过 3 种语言就别这么干。
