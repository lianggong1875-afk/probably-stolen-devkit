# 机器改造与流体操作四例｜工坊 3845287659 + 3842333957 + 3844978771 + 3846097337

> 蒸馏自 `缓存文件夹\decomp_ws\` 下四个模组的反编译源码：
> **Machine Fusion**（3845287659）、**probably real-time**（3842333957）、**Machine Link**（3844978771）、**Liquid Pipe Hub**（3846097337）。
> 价值：这四个模组把**原版机器系统的槽位布局、加工判定、数值标签、液体搬运**全都摸清了，等于给我们一张"机器怎么改"的完整地图。

## 0. 先给结论：改机器数值的正确姿势

工坊里两种流派，优劣分明：

| 流派 | 做法 | 代表 | 代价 |
| --- | --- | --- | --- |
| **临时改数值 → 调原版 → 还原**（推荐） | Prefix 里把原版标签改成放大值，让原版方法照常执行，Postfix/**Finalizer** 还原 | Machine Fusion | 原版逻辑不动，与其它模组不互斥；缺点是每次调用都要写两次标签 |
| **整段替换原版入口** | Prefix 返回 false，自己重写 | SleepLagOptimizer 换掉 `RunNightlyChemicalSimulation` | 与所有同类模组互斥（工坊实证：3 个模组这么干） |

Machine Fusion 的完整写法（**Prefix 暂存原值 / Postfix 还原 / Finalizer 兜底**）：

```csharp
[HarmonyPatch(typeof(MachineProgressHelper), "ContinueProgressTypeMachine")]
internal static class ProgressSpeedPatch
{
    [HarmonyPrefix]
    private static void Prefix(GameItem machine, out BoostState __state)
    {
        __state = null;
        if (machine == null || SaveManager.IsDecoding || !FusionRegistry.IsSupported(machine.identifier)) return;
        int level = FusionCore.GetLevel(machine);
        if (level <= 1) return;                                   // 战时不影响原版机器
        int speed;
        try { speed = machine.GetTagReadonly("CURRENT_PROCESSING_SPEED_TAG").GetInt(); }
        catch { return; }                                          // 没这个标签 = 不是进度型机器
        if (speed == 0) return;
        __state = new BoostState { Original = speed };
        int boosted = FusionRegistry.ScaleInt(speed, FusionRegistry.OutputFactor(level));
        machine.ModifyTag("CURRENT_PROCESSING_SPEED_TAG", ts => ts.Enable().SetInt(boosted), true);
        machine.SyncModifiedState();
    }

    [HarmonyPostfix] private static void Postfix(GameItem machine, BoostState s) => Restore(machine, s);
    [HarmonyFinalizer] private static Exception Finalizer(GameItem machine, BoostState s, Exception e)
    { Restore(machine, s); return e; }                            // 原版抛异常也必须还原，否则速度永久被放大

    private static void Restore(GameItem machine, BoostState s)
    {
        if (machine == null || s == null) return;
        machine.ModifyTag("CURRENT_PROCESSING_SPEED_TAG", ts => ts.Enable().SetInt(s.Original), true);
        machine.SyncModifiedState();
    }
}
```

三个关键细节：
1. **`SaveManager.IsDecoding` 时直接跳过**——读档过程中改标签会被写进存档。
2. **`__state` 传 class 而不是 struct**，这样 `null` 就能表示"这次没改过"，还原时天然幂等。
3. **`SyncModifiedState()`** 必须调，否则标签改了但 `modifiedState` 不同步，原版读存档时可能拿到旧值。

## 2. Machine Fusion：等级即标签 + 合并事务

- **等级存在物品标签**：`MACHINE_FUSION_LEVEL_INT`（int），用 `ModifyTag(tag, ts => ts.Enable().SetInt(v), true)` + `SyncModifiedState()` 写；读档后 `EnsureLevel(item)` 补默认 1 并刷新名字。
- **名字带等级但可回退**：`UpdateName` 会先 `StripLevelSuffix`（去掉末尾 ` Lv.N`）再加，避免 `Lv.2 Lv.3` 叠罗汉。
- **合并事务顺序**：校验 → 保便签 → 写新等级 → `ApplyLevel`（含 `item.Validate()`）→ 销毁源机；**销毁失败则把等级回滚到原值**。这个"先改目标、后销毁源、失败回滚"的顺序是安全的。
- **合并前置校验清单**（值得照抄到我们任何"合体/转化"功能）：
  1. 两件都不是 null、不是同一件；
  2. identifier 相同（同型号）；
  3. 双方都 `GeneralHelper.IsItemOwned`；
  4. 都不带 `BROKEN_MACHINE_TAG`；
  5. 材料机**没有内容物**（`FindAllChildItems` 里除便签/说明书外为空）；
  6. 当前不在框选拖拽中（`ItemMultiSelectHandler.current?.IsGroupDragging == false`）。

## 3. real-time：把"过夜结算"改造成"每秒推进"的思路

它的整体骨架是：`WorkshopTime`（把真实时间折算成游戏 tick）+ `MachineJobs`（判定每种机器这一 tick 能不能推进）+ `WorkshopMachine`（真正执行并刷新 UI）。

它 Patch 的入口（可作为"机器相关可介入点"清单）：

```
MachineHelper.OnMachineActioned          机器被操作后
MachineProgressHelper.ContinueProgress*  进度推进
HydroponicHelper.ContinueGrowing         水培生长
ModuleEffectHelper.ActivateOnUseAction   模组效果触发
GameItem.ModifyTag (显式 Type[])         拦截标签写入
MachineryHelper.CreateMachineryTooltip   机器提示框
EmporiumEntry.OnDestroy                  场景销毁时清理
```

**它改的是"什么时候跑"，而不是"跑什么"**——`CanAdvance` 全部复用原版判定（见 1.3）。这是最不容易与其它模组打架的改造方式，值得学。

## 4. Machine Link：多台机器共用一个窗口

- 它的反编译目录里命名空间仍是 `ContainerLink\`，并新增 `FurnaceLink\`——说明作者是在自己前作 **Container Link（3844123767）**的代码基上扩展的，共用同一套"连接/拆离/持久化"基础设施。**这本身是个架构决策样本：同作者的系列模组共享内核**。
- 支持的机型：熔炉（2~4 台横竖排，共用原料与成品区，但每台用自己的电池与模组，只有通电台才加工）、3D 打印机（共用材料与成品，各自保留蓝图芯片/电池/模组/进度，可同时打不同配方）、循环水养殖（养殖区连通、水量水质共用，各自保留电池/滤芯/喂食器/屠宰机）、冰箱（同扩容等级拼成矩形，冷藏与冷冻分别扩大，电池槽按位置排列，**每台只给自己区域供电**）。
- 与其他模组的关系：**若「容器连接」或别的模组已接管冰箱，本模组会静默让位**——这是"先到者赢 + 主动让位"的实践（具体判断靠"目标是否已被接管"的状态标志，不是模组存在性扫描）。

它 Patch 的机器侧方法（与容器版重叠的就不列了）：

```
MachineFridge.UpgradeStorage / CanUpgradeStorage / ApplyStorageSize   冰箱扩容与尺寸
MachineryIntake.Validate                                             机器取料校验
ChemicalHelper.RunNightlyChemicalSimulation                          过夜化学（与另两个模组重叠！）
PixelWindow.Destroy / Hide                                           窗口生命周期
```

> ⚠️ 它和 SleepLagOptimizer、ProgressBar 都 Patch 了 `RunNightlyChemicalSimulation` —— 装两个就打架。我们若做冰箱/机器合并类功能，**不要碰这个方法**。

## 5. Liquid Pipe Hub：液体搬运的原子操作

### 5.1 原版液体 API 全貌（从这里补齐）

```csharp
WaterHelper.GetTotalVolume(item)      // 当前总容积（mL）
WaterHelper.GetFreeCapacity(item)     // 还能装多少
WaterHelper.GetTotalCapacity(item)    // 总容量
WaterHelper.GetCurrentCapacityML(item)// 特定容器当前量（水培水槽等）
WaterHelper.GetWaterPurity(item)      // 纯度（用于净水判定）
WaterHelper.AddWater(item, amount, freeCapacity, useRange, low, high, notify)
WaterHelper.EmptyContainer(item)
WaterHelper.TransferLiquid(mother, child)     // 整容器转移

Liquid.GetCurrentPartFromId(id)              // 取该液体在容器里的 Tag key
Liquid.Liquids                               // 全部液体
liquid.canBeRemovedByPurifier / isEvaporative / boilingPoint

ChemicalHelper.SetChemContentUL(item, part, value)   // 原子设值（管道模组的核心）
ChemicalHelper.AddChemContentUL(item, part, delta)
ChemicalHelper.DissolveInto(...)
```

### 5.2 搬运的两种写法

```csharp
// A. 一步到位（原版已封装好）：整容器倒进另一个容器
WaterHelper.TransferLiquid(mother, child);

// B. 定量转移（管道模组用的）：先算容量，再双端原子增减
int free  = WaterHelper.GetFreeCapacity(child);
int total = WaterHelper.GetTotalVolume(mother);
int moved = Math.Min(free, total);
if (moved > 0)
{
    ChemicalHelper.SetChemContentUL(child,  currentPart, currentChild + moved);
    ChemicalHelper.SetChemContentUL(mother, currentPart, currentMother - moved);
}
```

**B 的注意点**：液体是"按 part 分开存"的（水、酒精、酸各自一个 Tag），所谓"转移液体"其实是**逐个 part 搬**；只要有一个 part 搬错就会丢液或造液。管道模组为此对 `AddChemContentUL` / `SetChemContentUL` / `DissolveInto` 都做了 Patch 来做一致性保护——我们自己做液体搬运时应只在**原版容器之间**搬，不自己造 part。

### 5.3 它的其他手法

- **把机器登记进家具目录**：Patch `FurnitureItemDirectory.InitDirectory` 把自己的 3×3 机器注册进去（另一种注册路径）。
- **Patch ModHook 自己的触发方法**：`[HarmonyPatch(typeof(ModHook), "FireOnPlaceInventorInventoryItemEarly")]` —— 用来捕捉"发明家货架放货"的时机给机器定价/上架。**这招很有意思：ModHook 的 Fire\* 方法本身也是可 Patch 点**，可以在别的模组挂的钩子触发前后插自己的逻辑而不必去抢原版方法。
- **给容器打视觉角标**：`GameItemElement.UpdatePinOverlay` Patch + 自绘 `PipeBadgeOverlay`，在同一容器上标记"母/子"颜色。做"容器关系可视化"可以照抄。

## 6. 对我们的可用点

1. **改机器产出/速度/耗电**：照 Machine Fusion 的"临时改标签 + Finalizer 还原"，靶点是 `CURRENT_PROCESSING_SPEED_TAG` 与 `MachineryHelper.GetMachinePowerUsage` / `MachineMoistureFarm.GetOutputVolume` / `MachinePurifier.PurifyContainer` / `HydroponicHelper.ContinueGrowing` / `MachineProgressHelper.ContinueProgressTypeMachine`。
2. **做"多台机器合体/升级"**：照它的前置校验清单 + 事务顺序（先改目标、后销源、失败回滚）+ 等级存物品标签（随物品走，不写 ModData）。
3. **做液体自动化**：优先用 `WaterHelper.TransferLiquid` / `EmptyContainer`；要定量就用 `SetChemContentUL` 双端原子增减，并且**只在原版容器之间搬**。
4. **想吃"机器开工"的时机**：`MachineHelper.OnMachineActioned` + `MachineProgressHelper.ContinueProgress*` 比 Patch 每个机器类安全。
5. **别碰** `ChemicalHelper.RunNightlyChemicalSimulation`（三个工坊模组已在抢）。
6. "改什么时候跑，不改跑什么"是 real-time 模组最值得学的思想。
