### 1.2 原版机制：柜台满了到底在哪一行销毁

链条自下而上，全部核实过：

1. **销毁本体** `GraphUtils.DestroyIfUnplaced(item, context)`（`GraphUtils.cs:41-61`）：只有 `item.parentInventory == null`（即**一格都没放进去**）才继续；若 `unitCount > 0` 先 `ReportUnplaced(...)`（`:57`）；然后 `item.Destroy()`（`:59`）。
2. **"提示"只有日志** `GraphUtils.ReportUnplaced`（`GraphUtils.cs:63-72`）把 `(identifier, context)` 累加进静态字典，`LetterboxManager.RunNextUpdate(FlushUnplaced)` 排一次，`FlushUnplaced`（`:74-94`）拼一行 `Destroyed unplaced items: 'xxx' xN (front counter full)` 走 `Debug.LogWarning`（`:93`）。**只进 Player.log，不进游戏任何 UI** —— 这就是简介里"没有任何提示"的准确含义（不是完全没有痕迹，是玩家看不见）。
3. **组合器** `GraphUtils.TryAcceptAllOrDestroy`（`GraphUtils.cs:96-104`）：`TryAcceptAll(...)` 后 `return DestroyIfUnplaced(...)`。注意 `DestroyIfUnplaced` 的返回值语义是**"放下去了就 true"**（`parentInventory != null`），所以 `TryAddDirectSellingItemToTable` 的 bool 是"是否成功上柜"。
4. **柜台直上** `PlayerStore.TryAddDirectSellingItemToTable(GameItem, ...)`（`PlayerStore.cs:2545-2573`）：两个阵营不信任校验（`:2552` / `:2557`，判 `LLDISTRUSTED` / `BM_DISTRUSTED` + 违禁品，**这两条也会 `DestroyIfUnplaced`**）→ `GeneralHelper.SetItemOwned`（`:2562`）→ `StolenHelper.InitStolenItem`（`:2565`）→ `GraphUtils.TryAcceptAllOrDestroy(EmporiumEntry.Instance.frontInvinvElement, gameItem, "front counter full")`（`:2567`）。
5. **字符串重载多一层预检** `PlayerStore.cs:2530-2538`：`frontInvinvElement.CanTakeAnything() == false` 时连物品都不生成，只 `ReportUnplaced(identifier, 1, "front counter full, offer skipped")` 然后返回 false。**所以"按 id 上货"和"按实例上货"丢东西的方式不同**：前者连实例都没有，后者实例被 Destroy。
6. **柜台容器与落位算法**：`EmporiumEntry.cs:212` `frontInvinvElement = new GameGridInventory(18, 4)`（**72 格**）；`GameGridInventory.TryFindOneValidInventorySlot`（`GameGridInventory.cs:824-905`）先排序已有物品（`:831-838`），再按 `4 朝向 × 2 翻转`、每种朝向下 `height × width` 双层循环返回**第一个**放得下的位置（`:884-903`）。这是**贪心左上优先、无装箱优化**：1×1 小货会把 72 格填成棋盘，之后任何需要连续块的大件都失败。

### 1.3 为什么"箱子最先死"，以及声望越高越惨

- **体积**：箱子不是独立物品，是用大件模板套 tag 造出来的 —— `PreBuiltItemHelper.CreateLootCrate(crateId, boxId)`（`PreBuiltItemHelper.cs:264-276`）拿 `evidence_box` / `med_box` / `sec_box` / `eng_box` / `service_box` 其中一个当底，再 `ModifyTag("LOOT_CRATE_ID_STRING", ...)`（所以它的 `identifier` 仍是 `evidence_box`）。占格数由 sprite 像素 ÷ `gridSize` 推出（`GameItem.SetSpriteAndShape` → `BuildShapeFromSprite`，`GameItem.cs:339-353`），而箱子内部容量就有 7×5（`ContainerItemDirectory.cs:288-290`）——**它要的是一块连续区域，不是 1×1**，而门禁卡/模块全是 1×1。
- **顺序**：`StoreClientList.CreateThief()`（`StoreClientList.cs:2053`）的 endAction 里先掷 **20 种**独立货（`:2066-2144`，逐项 `RNG.Roll(阈值 × bMRepStockMult)`）：高级瓶装水 5、护肤霜 5、神经香水 6、信息素香水 4、涡轮增压 5、指挥/安保/医疗/工程/服务门禁卡各 5/10/15/15/20、刮刮卡 15、六种随机模块各 8~12、便携净水器 12、高级滤芯 12、真注射器 20。**箱子在这 20 项之后**（`:2146-2193`），箱子后面还有 5 个 `crypto_module_*`（`:2194-2212`）和一组白食（`:2214-2228`）。
- **概率乘数** `StoreClientList.GetBMRepStockMult()`（`StoreClientList.cs:2031-2051`）：黑市声望 ≥40/60/80/100 → 1.25/1.5/1.75/**2.5**。`RNG.Roll(float)` 是百分比（`RNG.cs:18-21`：`Random.Range(0f,100f) < chance`），所以声望 100 时那 20 项的单项命中率是 10%（阈值 4）~50%（阈值 20），**期望约 5~6 件**，再加必出的箱子与 ~1 件 crypto 模块，一趟 7~8 件——其中大半是 1×1 钥匙卡/模块。
- **箱子其实是"必出"**：解锁 `BM_RELIABLE` 后箱子走 100% 分支（`:2146-2169`，`RNG.GetRandomInt(0,100)` 只是决定哪一类箱子）；未解锁才 `RNG.Roll(30 × mult)`（`:2170`）。所以"高声望看不见箱子"不是掷不到，是**掷到了摆不上**——正好呼应简介"声望刚过 40 每趟都有箱子，过 100 基本看不见"。
- **柜台不是每趟清空的**（这条最容易被忽略）：`ClearFrontInv()` 只在**离店**（`EmporiumEntry.cs:854`）和**过夜**（`PlayerStore.cs:1752`）时调，两处都是 `item.Destroy()` 全清（`EmporiumEntry.cs:1015-1025`）。所以一个营业日里，前面每位卖家留下的未售货、玩家自己买下又占位的货，全都堆在同一块 18×4 上，**小偷往往是当天第 N 位来访者**——他一趟的 7~8 件只是压垮骆驼的最后一把。
- 结论一句话：**柜台跨来访累积 + 声望越高每趟越多 1×1 杂货 → 贪心左上把连续格切碎 → 排在最后的大件 `parentInventory` 仍为 null → 被 `DestroyIfUnplaced` 销毁。**

### 1.4 它怎么改顺序：不重排列表，拦"上柜台"再重放

- **拦截点** `TryAddPatch.cs:6-13` 显式写参数类型表锁死五参重载；Prefix（`:16-32`）在 `Buffer.active` 时把 5 个参数塞进 `Buffer.Pending`，然后 `__result = true; return false;` 吞掉调用。
- **窗口**：`Dialogue.ExecuteEndAction()`（`Dialogue.cs:291-298`，先 `isEndActionExecuted = true` 再 `endAction()`）。`EndActionPatch.Prefix`（`:12-35`）读 `PlayerStore.currentClientInstance.GetClientBlueprint().identifier`，命中 `"thief"` 或 `"retired_chemist"`（后者受 `Settings.RestrictedChemFirst` 控）就 `Buffer.Begin()`；**`Finalizer`**（`:37-47`）里 `Buffer.Flush(...)`。用 Finalizer 而不是 Postfix 的理由很硬：endAction 抛异常也会 flush，货不会永久卡在缓冲区里。
- **重放** `Buffer.Flush`（`Buffer.cs:36-60`）：`items.OrderBy(p => priority(p.item)).ToList()` 后逐件真调 `PlayerStore.Instance.TryAddDirectSellingItemToTable(...)`，并统计 `placed`。`OrderBy` 是稳定排序，**同优先级内保持原版掷序**。
- **小偷的排序键** `EndActionPatch.cs:41`：`(!Buffer.crates.Contains(item)) ? 1 : 0` —— 箱子 0，其余 1。
- **箱子身份怎么认** `CrateMarkPatch.cs:11-25`：`TargetMethods()` 一次挂 `LootCrateEvidence/Medical/Engineering/Security/Service` 五个无参静态方法（`AccessTools.Method(typeof(PreBuiltItemHelper), name, null, null)`），Postfix 把 `__result` 收进 `Buffer.crates`。**不能按 id 判**（箱子 id 是 `evidence_box`），只能按"谁造出来的"。

### 1.5 磁带与管制化学品：同一机制的另外两个受害者

- **补给运输员** `StoreClientList.PlaceSupplierInventory()`（`StoreClientList.cs:2433-2493`）：约 30 件杂货之后才是磁带（`:2484` 必给 `cassetteN d`，`:2487` 概率给 `l`，`:2491` 概率给裸 `cassetteN`）。它被 `CreateSupplier`（`:2506-2509`）和 `CreateSupplierIntro`（`:2528-2531`）**两个 client 共用**，所以模组直接补 `PlaceSupplierInventory` 本身（`SupplierPatch.cs:6`），一次覆盖两条来访路径——比自己 hook 两个 endAction 聪明。
- **磁带排序键** `SupplierPatch.Priority`（`:11-28`）：正则 `^cassette\d+([ld]?)$`，捕获组空 → **0**，`"l"` → 1，`"d"` → 2，非磁带 → 3。也就是说"裸 `cassetteN` 最前、`l` 次之、`d` 再次、杂货最后"（推测：`l`/`d` 是同一盘磁带的两档规格，简介把这层写作"完好的排最前"）。**它没有去识别体积**，只是把"玩家最想要的那一类"提到最前——这正是绕开装箱问题的正确抽象。
- **退休化学家** `StoreClientListSpec.CreateRetiredChemist()`（`StoreClientListSpec.cs:673-770`）：先摆 4 台大件（blender / heating_plate / evaporator / chem_finisher），`restricted_chemical` 在 `:701`，后面还有十几个小件。排序键 `item.identifier == "restricted_chemical" ? 0 : 1`（`EndActionPatch.cs:45`）。注意这条的竞争者是**大件**，不是小件：两台机器就吃掉大半连续格，管制化学品排在第四个大件之后，失败率极高。

### 1.7 踩坑与红线

1. **`__result = true` 是谎报**：窗口期内所有调用者都拿到"成功"，但东西还在缓冲里。原版绝大多数调用者是 void 重载；唯一的 bool 调用者是 `StoreClientListMinor.cs:871`（收核废料：`TryAddDirectSellingItemToTable("nuclear_waste", isOwend: true)` 每成功一次付 100 块，`:876-879`）——它走**字符串重载**（本模组没打）且不在三个缓冲窗口内，所以目前无害；但这就是谎报返回值的后果形状：**付了钱、没上货**。
2. **缓冲期间柜台真的是空的**，而原版有 3 处拿"柜台空不空"当条件：`EmporiumEntry.IsFrontCounterEmptyNonOwned()`（`EmporiumEntry.cs:1547-1561`：无物品，或全是玩家所有的，就算空）被小偷用（`StoreClientList.cs:2214`，送 3 件 common_chemical/common_medical）、被另外两个 client 用（`:1861` / `:2016`，送 nutrifruit）。闸误开 → 白食被塞进缓冲区、排箱子后面一起抢格。所以"延迟放置"**必须**配套一道"假装还没结束"的补丁。这是本档案最值得记的一条耦合。
3. **它只覆盖 3 个来源，不是通用修复**：`AddDirectToWeightedTable`（`PlayerStore.cs:2582-2586`，走 `backInvinvElement`）与 `AddDirectSellingItemToTableMiddle`（`:2575-2580`，`TryAcceptAllMid` + `DestroyIfUnplaced`）同样会销毁物品，本模组完全没管。
4. **flush 里再入风险**：`Buffer.active` 在 `Flush` 第一行就置 false，所以 flush 期间若有回调再次上货，会直接走原版（可能嵌套销毁），没有重入栈，只有 `Buffer.active` 一个布尔。
5. **同批多个箱子之间不排序**：键只分"箱子/非箱子"，两个箱子抢一个大格时仍可能丢一个（概率低）。
6. **别抄 `Delegate.Combine` 前置的老解**（upstream `04-踩坑清单.md:464-471` 的 #52）：把上货前置只能保证"我先摆"，排在后面的原版货照样死，而且改变了原版的掷序语义。缓冲 + 排序严格更好。

### 1.8 对我们的可用点

- **直接命中的风险点**：`深空电玩/src/ArcDelivery.cs:121-153` —— 银狼整包货逐件 `store.TryAddDirectSellingItemToTable(item, false)`，放不下时原版**直接销毁**，我们只 `ArcLog.Warn` + `skippedCount++`，然后 `continue`；循环结束还把 `VarPendingPackDone` 抹掉（`:152-160`）→ **整包丢件不可恢复**。这是我们唯一的"批量上柜"路径，危险等级等同小偷箱子。
- **第二处**：`深空电玩/src/ArcClients.cs:534-551` —— 上门卖家一次带 `count` 件，用的是 **void 重载** `store.AddDirectSellingItemToTable(identifier, isOwend: false)`（`:549`），连返回值都没有；柜台塞不进时物品凭空消失，日志里只剩原版那一行。
- **正面样例已在库里**：`深空当铺：可能是群友/src/FreyaStock.cs:38-104` 的 `DspStock.Place`（`SetItemOwned` → `TryAcceptAll` + `parentInventory` 引用比较 → 溢出到后仓 → 计数 `Lost`），`:9-19` 的注释把背景写清了。**新代码一律走它**，别再直调 `TryAddDirectSellingItemToTable`。
- **可复用的新招**：真要一次上多件且分主次，抄 `Buffer` 的"拦截 → 排序 → 重放"，但排序键用**面积降序**（大件先占连续格）而不是"是不是某个 id"，并且**不要**在 flush 期间谎报成功。
- **验证手法**：这条 bug 游戏里没有 UI 提示，唯一可观测信号是 Player.log 里的 `Destroyed unplaced items:`（`GraphUtils.cs:93`）。回归时可以把它当断言源：**跑完一次上货，grep 该行必须为空**。

1. **配置与补丁不一致**：`AllowStartingPerks` 不看 `Enabled`、不看 `IgnoreIncompatibility`。`free_selection = false` 时 `UsedPoints()` 返回真值，但 `CanStart` 仍被强制 true → 玩家可以带着负点数开局，面板上 `pointsCounter` 标红显示 `-27` 之类。**"关掉开关"只关掉了一半**。

### 4.4 踩坑与红线

1. **"绝对 Y 覆写"是通用坑**：任何原版每次 `SetMode` 都写死坐标的 UI，只在 `Start` 改一次必失效。判断办法：grep 目标 transform 的所有 `localPosition =` 赋值点，逐个挂。
2. **间距必须乘 `localScale`**：写死 35 在缩放变化后必错位；治安官那条就是 `35f * (scale.y / 2f)`（`:130`）。
3. **持枪模式的名字框间距用的是普通模式的差值**（`scaledGap` 只算一次，`:113`）：原版两个模式的间距分别是 `defaultModeYName - defaultModeY` 与 `shootingModeYName - shootingModeY = 16`，两者不等时持枪下名字框会偏（推测，取决于运行时基线值，未真机验证）。
4. **缩放后重排可能被守卫吃掉**：`Apply` 要求 `名字 == 气泡 + 当前缩放间距`（`:36`）才施加，缩放一变这条就不成立，于是不会按新缩放重排（推测：表现为缩放切换后名字框滞后一次）。
5. **红线（内容层）**：`WorkshopNotice.cs:8` 硬编码 `3845291920`，扫描 `ModLoader.Mods` 的 `WorkshopId`/`ShadowedWorkshopId`（`:41-48`）并订阅 `ModWorkshop.OnItemInstalled`（`:18`），命中就在主菜单弹全屏红色警告、点名该条目与作者（`NoticeWindow.cs:52-57`）。技术上是"安装事件 + 模组列表扫描"，内容上是对第三方条目的指控。**我们不做这类指控**；技术模式可以借，文案和对象不行。
6. **自建 Canvas 而不是用原版窗口**：`NoticeWindow` 手搓 `Canvas` + `sortingOrder = 32000` 全屏遮罩（`NoticeWindow.cs:32-49`），与原版 `ConfirmPanelUIManager`/`PixelWindow` 风格脱节。我们要弹窗就用原版窗口组件。
7. **无热重载钩子**（无 `HotReloadPrepare`/`Activate`）：重载后 `Enabled` 静态字段与已施加的位移都不会自动复位（推测：取决于 ModLoader 重载前是否调 `OnDisable`；`Restore()` 只在 `OnDisable` 里被调）。

### 4.5 对我们的可用点

- **UI 位移模板**：`3 个写绝对值的方法 + 1 个缩放方法` 全挂 + `PositionPair` 幂等。重点不是 40px，而是**幂等**（同一帧被多处调用不会叠加），以及"当前 Y 是否等于基线"这套模式推断法——比自己维护一个 mode 枚举可靠。
- **多分辨率适配不要学它**：227/262 是写死的像素基线。正确做法是从 `rectTransform` 读一次基线存进字典（key 用 transform 实例），缩放变化时重算。
- **判断"该挂哪几刀"的流程可以固定下来**：找原版给 `localPosition` 赋绝对值的所有方法 → 全部挂 → 加 `[HarmonyPrepare]` 探针抗小版本。这条流程适用于我们所有 UI 微调补丁。
- **一个 427 行的教训**：小功能+额外功能混在一个程序集里，会让后来者误判复杂度。我们要加"顺手做的提醒/警告"就另开模组，别塞进位移补丁。
