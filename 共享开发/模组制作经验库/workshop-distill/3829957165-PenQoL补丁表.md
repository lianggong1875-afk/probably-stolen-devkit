## 1. 特性化补丁表的完整设计（本文核心）

### 1.1 `featurePatch` 是什么

它是 `Patches` 的**私有嵌套类** `FeaturePatch`（`PascalCase`；反编译把局部变量降级成 `featurePatch`）。这里的 "feature" **不是 C# 特性**，是"这条补丁属于哪个功能开关"的键。

```csharp
// Patches.cs:12-25（空行省略）
private sealed class FeaturePatch
{
    public string Feature;         // :14  开关键，如 "chem_batch"、"filter_automation"
    public MethodBase Target;      // :16  ← 已解析的原版方法（不是 Func<MethodBase>，见 §8.2）
    public HarmonyMethod Prefix;   // :18
    public HarmonyMethod Postfix;  // :20
    public HarmonyMethod Finalizer; //:22  ← 全库没有一处真正传入（见 §8.5）
    public bool Applied;           // :24  自记账的运行态，与 Harmony 真实状态无校验
}
```

配套全局态（`Patches.cs:27-43`）共 8 个字段：`HarmonyId`（`:27`）、`_harmony`、三个"只装一次"闸 `_coreApplied`/`_configResetApplied`/`_dropdownApplied`(+`_dropdownFailed`)、两个计数器 `_ok`/`_failed`、以及 `List<FeaturePatch> FeaturePatches`。
**关键取舍：`Target` 是 `MethodBase` 而非 `Func<MethodBase>`** —— 这决定了它所有失败模式的形状（对比 §6 的 (b)）。条目只在**挂载成功**后才入表（`Patches.cs:126-142`），所以表里每一项都是"确实装着"的。

### 1.2 挂载：唯一的 2 个 `Patch` 调用点之一

```csharp
// Patches.cs:595-615（原文）—— 单条挂载 + 逐条 try/catch
private static bool Add(string label, MethodBase target, HarmonyMethod prefix, HarmonyMethod postfix, HarmonyMethod finalizer)
{
    try
    {
        if (target == null)                               // :599
        {
            _failed++;
            Log.Warn("[patch " + label + "] target not found - skipped");
            return false;                                 // :603  ← 只丢这一条
        }
        _harmony.Patch(target, prefix, postfix, (HarmonyMethod)null, finalizer);  // :605
        _ok++;
        return true;
    }
    catch (Exception ex)                                  // :609
    {
        _failed++;
        Log.Warn("[patch " + label + "] failed: " + ex.Message);
        return false;
    }
}
```

`AddFeature` 在 `Add` 成功后入表（`Patches.cs:126-142`）：`:128` 先 `Add(...)`，`:131` 若成功则 `FeaturePatches.Add(new FeaturePatch{... Applied = true})`（`:138` 初始即"已应用"）。
于是"加一个功能"就是**一行一条补丁**，标签里写序号 + 靶点 + 用途：

```csharp
// Patches.cs:509-510（原文）
AddFeature("tab_drag_chooser", "68 ItemMouseDragHandler.Drag tab chooser", AccessTools.Method(typeof(ItemMouseDragHandler), "Drag", new Type[1] { typeof(Vector3) }, (Type[])null), null, new HarmonyMethod(AccessTools.Method(typeof(PatchTabDropChooser), "DragPostfix", (Type[])null, (Type[])null)));
AddFeature("tab_drag_chooser", "69 ItemMouseDragHandler.EndDrag tab chooser cleanup", AccessTools.Method(typeof(ItemMouseDragHandler), "EndDrag", new Type[1] { typeof(bool) }, (Type[])null), null, new HarmonyMethod(AccessTools.Method(typeof(PatchTabDropChooser), "EndDragPostfix", (Type[])null, (Type[])null)));
```

> 注意**每个 `AccessTools.Method` 都显式写了参数类型表**（`new Type[]{...}` 或 `Type.EmptyTypes`）——17k 行里最值得学的一条纪律：重载一律不靠猜。（这也正是 §8.1 风险概率低的原因。）

### 1.3 按开关单独禁用：`SetFeatureEnabled`（最该抄的 30 行）

```csharp
// Patches.cs:45-78（原文）
internal static void SetFeatureEnabled(string feature, bool enabled)
{
    if (_harmony == null || string.IsNullOrEmpty(feature)) { return; }
    for (int i = 0; i < FeaturePatches.Count; i++)
    {
        FeaturePatch featurePatch = FeaturePatches[i];
        if (featurePatch == null || featurePatch.Feature != feature || featurePatch.Applied == enabled)
        {
            continue;                                        // :54 已是目标态就跳过（幂等）
        }
        try
        {
            if (enabled)
            {
                _harmony.Patch(featurePatch.Target, featurePatch.Prefix, featurePatch.Postfix, (HarmonyMethod)null, featurePatch.Finalizer); // :62
            }
            else
            {
                Unpatch(featurePatch.Target, featurePatch.Prefix);     // :66
                Unpatch(featurePatch.Target, featurePatch.Postfix);    // :67
                Unpatch(featurePatch.Target, featurePatch.Finalizer);  // :68
            }
            featurePatch.Applied = enabled;                            // :70
            Log.Debug("[patch feature] " + feature + " applied=" + enabled);
        }
        catch (Exception ex)
        {
            Log.Warn("[patch feature " + feature + "] toggle failed: " + ex.Message);  // :75
        }
    }
}
```

"单独摘掉一条"靠**方法级摘除**（`Patches.cs:80-93`）：`if (target == null || patch == null || patch.method == null) return;` 然后 `_harmony.Unpatch(target, patch.method);`（`:88`），整个调用套在**空 `catch { }`** 里（`:90-92`，风险见 §8.4）。

> 这是全表最关键的技术选择。`UnpatchAll(id)` 只能整批摘，`Unpatch(target, method)` 才能**在同一条原版方法上只摘我这一条**。因此"一个靶点挂多个功能"不会互相误伤——`ItemMultiSelectHandler.OnEventPress` 同时有 `alt_box_select`(#35) 和 `multi_select_toggle`(#42) 两个 Prefix，关掉前者，后者的 Prefix 仍挂着。

### 1.4 唯一对账入口：`SyncFeaturePatches`

`Patches.cs:95-119` 就是**全部可开关功能的清单**（22 行，每行 `SetFeatureEnabled(键, ModSettings.X)`）。其中 4 行是精髓（原文）：

即：**N 个开关共用一条补丁时，补丁闸门 = N 个开关的 OR**。这让 22 个功能键和 49 个配置项不必一一对应。调用点 4 处、全幂等：`ApplyCore` 末尾（`:540`）、`ModHook.OnModConfigApplied`（`ModConfigResetCompat.cs:86`）、各 `ConfigEntry.OnChanged`（`ModSettings.cs:728, 746, 757, 783, 852, 1022`）。

## 4. 它怎么做到"多个功能之间不互相干扰"

结论：**没有通用冲突检测、没有优先级、没有仲裁器**，靠四层局部纪律。

**① 物理隔离**：88 个文件里 83 处 `static class`，命名三分——`Xxx.cs`(22) 功能本体+私有状态、`PatchXxx.cs`(44) 补丁入口**只做转发**、`XxxCompat.cs` 跨功能只读门面。`Patch*` 平均 22 行，全是这个形状（`PatchTabDropChooser.cs:8-21`）：

```csharp
public static void DragPostfix()
{
    try
    {
        if (TabDropChooser.Enabled) { TabDropChooser.OnDragFrame(); }   // :12 补丁里的第二道闸
    }
    catch (Exception ex) { Log.Debug("tab chooser drag hook failed: " + ex.Message); }
}
```

补丁入口层不含业务逻辑，所以功能之间不通过补丁互相踩。

**② 双闸门**：`SyncFeaturePatches` 摘补丁（第一道）+ 功能内部再读一次 `ModSettings`（第二道）。`ChemBatch.cs:748` 是 `if (!ModSettings.ChemBatch) { Disable(value); return; }`，`DragSlotReplace.cs:53` 是 `if (!ModSettings.DragSlotReplace) return false;`。**这是刻意的安全网**：即使 `SyncFeaturePatches` 静默失败，功能仍是死的。

**③ OR 合并**：见 §1.4 的 4 处 `A || B`——这是唯一"会真正互相影响"的地方，且是设计而非 bug。

**④ 三个手工共享协议**（没有抽象，全靠点名）：框选带归属用 `Assist` 的**帧戳所有权标记**（`_armedTool`/`_armedFrame`/`_qolSelectionOwned`/`_bandTransparentFrame` 与 `Time.frameCount` 比较，`Assist.cs:331-397`）；吸附 vs 框选抢同一修饰键靠 `QoLKeyBindings.SnapConflictsWithBoxSelect()`（`:261-289`）主动让路；加选 vs 原版快速转移靠 `MultiSelectCompat.IsQuickTransferConflict(key)`（`:51-69`）。

**共享状态其实在游戏身上**：多选集合不自己维护，反射读原版私有字段（`Selection.cs:170-174`）：


## 6. 三种"大合集"组织方式对比

**(a) `DangpuPlus`(3828893950) · 静态委托表**：抽象单位是**"一段常驻逻辑"**——103 项 `(Name, Init, Update, OnGUI)` 登在 `FeaturePack`，一个 `Hud : MonoBehaviour` 顺序跑完全部 `Update`/`OnGUI`，每项外套"连续失败 120 次即本会话停用"的熔断；开关在 `Init` 里 `Bind` 后立即 `return`（**关掉=根本不打补丁，因此改开关需重启**）。

**(b) `Probably Extend Framework`(3841909877) · 自描述 Patch 注册表**（已复核 `decomp_ws\3841909877\...\Ports.cs:11-32`）：

```csharp
private sealed class Port
{
    internal string name;               // "PlayerStore.SellItem"
    internal string feature;            // "卖出时按 sold 标签换来客差分"  ← 中文说明
    internal string status;             // "not installed" / "ok" / 异常摘要
    internal Func<MethodBase> target;   // ← 延迟解析（与 (c) 的根本差别）
    internal HarmonyMethod prefix;
    internal HarmonyMethod postfix;
    internal Func<string> probe;        // ← Read 型健康探针，null 表示健康
    internal bool ok;
}
```

`Patch(name, feature, target, prefix, postfix)` 只登记去重**不解析**；`InstallAll()` 才逐条 `try { port.target() } catch`，失败只废一条；`Report()` 输出 `√/× + 中文说明`；`UninstallAll()` 走 `UnpatchAll(id)` **全量**摘。

**(c) 本模组 · 特性化补丁对象表**：抽象单位是**"一条可独立摘挂的补丁 + 它属于哪个开关"**——`FeaturePatch{Feature, Target(已解析), Prefix, Postfix, Applied}` 入 `List`，`Add` 单挂、`SetFeatureEnabled` 方法级单摘，`SyncFeaturePatches` 把 49 个配置项映射到 22 个键（含 `A||B`）。

| 维度 | (a) 委托表 | (b) Patch 注册表 | (c) 特性化补丁对象 |
| --- | --- | --- | --- |
| 装载方式 | `Hud` 每帧顺序调 | `InstallAll()` 一次 | `ApplyCore()` 一次（3 入口幂等） |
| 失败粒度 | 每项熔断（累计式） | 每条 try/catch，**只废一条** | 每条 `Add` try/catch，**但靶点解析在 try 外**（§8.1） |
| **热禁用一个功能** | ✗ 需重启（`Init` 只跑一次） | ✗ 只能全量卸载重装 | **✓ 方法级单摘单挂，即时生效** |
| 自带可诊断性 | 熔断计数 | **`√/×` + 中文说明，最强** | 只有 `_ok/_failed` 两整数 + 日志 |
| 适合"大量小补丁" | 一般 | **最好** | 好（一行一条，写得最短） |
| 适合"大量常驻逻辑" | **最好**（有 Update/OnGUI 槽位） | 差（无槽位） | 差（无槽位） |
| 加一个功能成本 | 1 行表 + 3 方法 | 1 行 `Patch(...)` + 补丁体 | 1 行 `AddFeature(...)` + 补丁体 + 1 行 `SetFeatureEnabled(...)` |

**四条结论**：① **"大量小补丁"选 (b) 或 (c)**，(a) 的槽位是"每帧/每 GUI"，补一个原版方法要额外绕一圈；② **"大量常驻逻辑"只有 (a) 顺手**，(b)(c) 连一个"每帧跑一遍"的槽位都没有（本模组为此自造了 `InstallOnOneSecond`，`ChemBatch.cs:1204`，完全在表外）；③ **"热禁用一个功能"只有 (c) 做到**——`Unpatch(target, method)` 能只摘自己那一条，而 (b) 的 `UnpatchAll(id)` 会连带摘掉别的功能；**需求里有"边玩边关功能"就必须照 (c) 改 (b)**；④ **"更新后查哪条失效" (b) 最强**（延迟解析 + 逐条 catch + `Report()`），(c) 最弱。

**失败模式对照**：(a) 某 `Update` 抛异常 → 熔断涨 → 第 120 次本会话静默停用该功能（其余 102 项照跑），重启恢复但**无 UI 告知**；(b) 签名变了 → 那一条 `MissingMethodException` → 日志一行 + `Report()` 里一个 ×，**其余全装**；(c) 签名变了 → 只丢一条（好），但若变成**重载歧义**则 `AmbiguousMatchException` 逃出 `ApplyCore`，**剩余几十条一条不装且永不重试**。

## 7. 可复用模式（4 条）

**模式一：补丁描述对象 + 方法级摘挂** —— 见 §1.3 全码。要点三条：`Feature` 字段让补丁与开关解耦（N:1）；`Applied` 让重复调用幂等；用 `Unpatch(target, method)` 而非 `UnpatchAll(id)` 才能单摘。

**模式二：N 个开关 OR 合并到一条补丁** —— 见 §1.4 的 4 处原文。配一个"或"派生属性即可（`ModSettings.cs:177-187` 的 `AnyAutoDiscardEnabled`：4 个子开关全关且 `DiscardExpeditionLog` 为假时才返回 `false`）。
**抄法**：把"补丁条数"和"玩家可见开关数"当两个独立量，用一张 22 行映射函数连起来；**不要**为了"一一对应"把一条补丁拆成两条。

**模式三：巨量设置的 section 变量 + OnChanged 扇出** —— 见 §3。分组名做成局部变量复用，避免 49 处字符串不一致；"配置变了通知谁"写死在 `OnChanged`（补丁闸门/功能态/UI 可见性/缓存清理四路）。

**模式四：跨功能只读门面**（`MultiSelectCompat.cs:7-49` 节选）—— 当 A 需要知道"B 现在是否起作用"时，不读 B 的私有字段，而是建门面把 B 的开关也判进来、查询全包 try/catch 给安全默认值：

```csharp
public static bool IsToggleDown()
{
    if (!ModSettings.MultiSelectToggle) { return false; }          // 门面自带开关判断
    return QoLKeyBindings.IsMultiSelectToggleDown();
}
public static bool HasSelection()
{
    try { return Selection.HasAnySelected(); } catch { return false; }
}
public static bool ShouldToggleItem()
{
    if (IsToggleDown() && HasSelection()) { return ItemUnderPointer() != null; }
    return false;
}
```

这样 B 关掉时门面自动返回 `false`，A 无需知道自己依赖了谁。

## 8. 风险清单

### 8.1 ★最严重：`AccessTools.Method` 在 `Add` 的 try/catch 之外

`Add(label, AccessTools.Method(...), ...)` —— 靶点解析是**实参求值**，发生在 `Add` 方法体之前，`Add` 的 try/catch（`:597-614`）**保护不到它**。

| 情况 | 结果 |
| --- | --- |
| 返回 `null`（方法不存在/签名变了） | `if (target == null)` 拦住 → `_failed++` + `Log.Warn("[patch <label>] target not found - skipped")` → **只丢这一条** ✔ |
| **抛异常**（典型：不写参数类型时的 `AmbiguousMatchException`） | 异常从实参位置逃出 `ApplyCore`；而 `_coreApplied = true` **在 `:345` 就已置位**（早于 77 条登记）→ **剩余全部登记一条不跑，且永不重试** ✘ |

两个调用点处理都不理想：`OnEnable` 那层是**空 `catch { }`**（`PenLabelerAssistMod.cs:76-78`，三层嵌套最内层），静默；`OnGameLoadedLate` 有 `Log.Error("deferred patch apply failed: …")`（`:332`），看得见但无法恢复。**玩家感受是"模组只生效一半"，日志只有一行。**
缓解（公平地说）：作者对**每个** `AccessTools.Method` 都写了参数类型表（§1.2 注），正常版本歧义概率很低；触发条件是"游戏更新新增同名重载"。

### 8.2 中：`Target` 已解析，无延迟解析能力

对比 (b) 的 `Func<MethodBase>`：某条登记失败就**永无重试可能**（表里根本没这项，`AddFeature` 在 `Add` 返回 false 时不入表，`:129`）。唯一补救是 `OnGameLoadedLate`/`OnDifficultyApplied` 再调 `ApplyCore`，但被 `_coreApplied` 挡住 = 空转。

### 8.3 中：`Applied` 记账可能与真实 Harmony 状态永久失同步

另一个模组若调用 `harmony.UnpatchAll()`（无 id 重载会摘**全进程所有**补丁），本模组 `Applied` 仍是 `true`；玩家再"关→开"时，`:54` 因 `Applied == enabled` 直接 `continue`，**永远不重挂**。没有任何代码校验 Harmony 真实状态。

### 8.4 轻但普遍：三处静默失败

- `Unpatch` 内部空 `catch { }`（`:90-92`）：**它永不抛异常，所以 `:70` 的 `Applied = enabled` 一定执行** → "摘失败了，但账上记成已摘"，之后开关"关→开"被 `:54` 跳过，补丁再也回不来。
- `SyncFeaturePatches` 每个调用点都被 `try { … } catch { }` 包住（`ModSettings.cs:728, 746, 757, 852, 1022`；`ModConfigResetCompat.cs:88`）→ **开关切了补丁没变，玩家只看到"开关没反应"，日志空白**。
- `OnDisable` 里 21 个连续 `try { X.Reset(); } catch { }`（`PenLabelerAssistMod.cs:89-236`）。

> 三条正撞我们工作区硬规范第 2 条（严禁空 catch 吞异常）。**这是本模组最不该抄的部分。**

### 8.5 轻：`Finalizer` 是从未启用的死字段

`FeaturePatch.Finalizer`（`:22`）在 `Add`/`AddFeature`/`SetFeatureEnabled`/`Remove` 全链路都传，但**全库没有一处 call site 提供非 null finalizer**（80 处登记全是 4 参重载；6 参重载唯一的 finalizer 实参是 `:123` 的 `null`）。影响：这张表**没有任何"必须不抛异常"的兜底**，兜底被放到了 `Patch*` 类里逐个 try/catch 与 §8.4 那些空 catch。（推测：为已移除的功能预留，或作者本想用未用起来。）

### 8.6 中：Harmony 实例 ID 不是 `mod.<manifest.ID>`，且零优先级

- 实例 ID 硬编码 `"Pen_mod_QoL_Tweaks.patches"`（`:27`/`:350`/`:576`）。按 ModLoader 惯例别人以 `"mod." + manifest.ID` 为比较基准，**用这个自定义 ID 做 `[HarmonyBefore/After]` 目标会对不上**。
- **`HarmonyPriority`/`Before`/`After` 全库 0 处**（已 grep）。配合 §2.3——它覆盖 `StoreUIManager.Update`、`Item*Handler.OnEvent*`、`PixelWindow.*` 这些 QoL/UI 模组必抢的热点却零顺序声明——**同时装两个 UI 模组时谁先谁后未定义**。它靠"Prefix 里 `return false` 跳过原版"抢语义（`PatchTabDropChooser.cs:45`），这种写法对顺序极度敏感。

### 8.7 轻：`chem_batch` 分组错位

见 §3 缺陷 1（`:1000` 声明 `text7`，`:1001` 用 `text2`）。只影响 UI 里找不到设置，不影响功能。

## 9. 对我们的可用点

**结论：要引入，但只引入"表"的一半，并补上 (b) 的两个零件。** 我们两个模组（`深空电玩`/`深空当铺：可能是群友`）目前规模用不上 22 个开关的补丁表；但一旦出现"一个模组里十几个独立小补丁"（例如给 UI 加十个 hover 提示），**三个范式各取一样**是最优解：
1. **取 (c) 的"开关归属 + 方法级摘挂"** —— (c) 独有，别人抄不到；
2. **取 (b) 的"`Func<MethodBase>` 延迟解析 + 逐条 catch + `Report()` 打 √/×"** —— 正好修掉 §8.1 全表停摆、§8.2 无法重试、以及 (c) 最弱的可诊断性；
3. **取 (a) 的熔断** —— 只给带 `Update`/每帧逻辑的功能用，纯 Prefix/Postfix 不需要。

即：**把 `Target` 换成 `Func<MethodBase>`，其余照抄 (c)，再加一个 `Report()`**，代码量约 130 行。

```csharp
// 建议形态（按 §7 模式一 + (b) 的延迟解析 + Report 合成，非本模组原文）
internal sealed class PatchRow
{
    internal string Key;                 // 功能键（N 条补丁可共用 1 个 Key）
    internal string Why;                 // ← 抄 (b)：一句话说"为什么非拦不可"
    internal Func<MethodBase> Target;    // ← 抄 (b)：延迟解析
    internal HarmonyMethod Prefix, Postfix;
    internal bool Applied;               // ← 抄 (c)：运行态
    internal string Status = "not installed";
}
// 四个接口：Register(Key, Why, target, prefix, postfix) / InstallAll() / SetEnabled(Key, bool) / Report()
```

**明确不抄的五条**：

| 不抄 | 原因 | 替代 |
| --- | --- | --- |
| 21 个连续 `try { } catch { }` | 违反硬规范第 2 条 | 各 `Reset()` 吞可恢复项，不可恢复的 `LogError` 带堆栈 |
