### ①-5 踩坑与红线

1. **单点依赖，全有或全无**：整套架构压在 `RichTextBuilder.slices` 与 `RichTextBuilder+TextSlice` 的 11 个私有字段上（`SliceAccess.cs:38-56`）。任一个改名/移除 → `Init()` 返回 false → 模组整体沉默（`SectionedTooltipsMod.cs:35-44`）。这比"改一半崩一半"好，但**它把自己绑死在原版内部结构上**，游戏一改文本系统就整份失效（本档案不评估其未来可用性）。
2. **94 个补丁是懒装的**：`EnsureHelpers()` 在第一次 tooltip 的 Prefix 里才 `Helpers.Apply(new Harmony(Id + ".helpers"))`（`TooltipBasicPatch.cs:24`、`SectionedTooltipsMod.cs:47-60`），装完打印 `patched n/94 tooltip helpers`。94 个全在一个 Harmony 实例下——**卸载/热重载时它没有成对 `UnpatchAll`**（无 `HotReloadPrepare/Activate`，透视报告同结论），我们若学这套必须补热重载对称性。
3. **`HasTooltip.__result = false` 是"关掉别人工具提示"的口子**（`HasTooltipPatch.cs:14-17`）：折叠态下第三方读 `HasTooltip` 会得到 false。这与"只在 `__result == false` 时动手"的经典坑同型——**任何依赖 `HasTooltip` 做判断的模组会被它悄悄改变分支**。
4. **它会重排别人的 tooltip 行，并允许玩家一键关掉**：第三方用 `ModInternal.CreateTooltipEarly/Late` 塞的行被归到 `mods` 节（`Helpers.cs:78-79,176-177`），而 `Settings.ShowModInfo` 可以整节隐藏。**结论：不能把关键信息只放在 tooltip 行里**——玩家或另一个模组都能让它消失。
5. **重排后仍要"看起来一样"**：`Swap` 里 `b.Clear(); b.Add(output)` 之外还硬把 `b.maxCharWidth` 抬到 1000（`Layout.cs:547-555`）——原版用 `maxCharWidth` 决定换行宽度，重写文本时必须把它一起接管，否则宽度会在两套逻辑间打架。
6. **性能**：布局结果按 `(item, slices 文本 hash, Settings.Version)` 缓存 32 条（`Layout.cs:220-232,318-336`）；`Stats` 自己把"单条 >3 ms / 均值 >12 ms"记为慢并打日志（`Stats.cs:8-9`）。**首次**渲染每条 tooltip 都是全量分词 + 两遍测量（`TextUnits.Wrap` + `TMP.preferredWidth`），这是 16.5k 行里最贵的一段。
7. **`Fuse` 熔断是局部降级**：连续 3 次异常只停"排版"或"估价单"这一路（`Fuse.cs:31-44`），原版文本照出。对比我们红线"内部禁止静默 `catch`"：它**不是静默**——`Fuse.Fail` 会 `LogError` 带堆栈，且降级目标明确（回到原版）。这个用法合规。

### ①-6 对我们的可用点

1. **抄"节界标记"，别抄"94 个补丁"**：它为了知道"这一行来自哪一节"付出了 103 个补丁面。我们的检视/估价窗只有 3~5 个数据来源（原版鉴定、我们的判定、价格、成色），**自己按行序排版即可**，一个 `CreateXxxTooltip` 都不用碰。
2. **抄跨模组协议**：`AppDomain.SetData("item_details.tooltip_layout.v1", 委托)`（`ItemDetailsBridge.cs:40-51`）——零程序集引用、零反射、版本号写进键名、注册/反注册成对。我们若要让第三方模组往我们的估价单里加一行、或把"这一行是真相还是标签"标出来，这条路比互相引 DLL 稳。
3. **抄"三道闸"做不泄密的容器清单**：`LockHelper.IsCurrentlyLocked` + `contentWindow == null` + `contentWindow.isLocked` + `ITEM_BEHIND_LOCK_TAG`（`①-4 ⑤`）。我们的鉴定系统若要显示"箱子里有什么"，这四道判断是基线。
4. **"借原版画布"这一招值得记**：它给原版工具提示窗口挂 `CanvasGroup`、`alpha = 0`（`Ticket.cs:866-879`），**保留原版算好的尺寸与缩放**，自己的卡片按同尺寸铺在窗口父级上。等于白拿原版的自适应宽高、避让与缩放，只换掉墨迹——比我们自己算弹窗尺寸省事得多。
5. **抄"失败即回原版"的降级方向**：`Fuse` 的三振 + 明确降级目标，比"画一半"安全得多。
6. **别抄**：9 种纸色 + 点线引导符 + 单据号 + 自绘设置预览这一整套（占 66% 行数）。我们的信息层不需要把 tooltip 变成一张卡。

### ①-7 关键判断：**它会不会泄露真伪 / 成色真相？**

**不会——它没有那条数据通路。** 证据链（全部可复核）：

| 判据 | 结果 |
| --- | --- |
| 读 `ItemFeature` / `realCondition` / `fakeCondition` / `modifiedState` | **0 次命中**（16,531 行逐文件 `grep -rc`） |
| 自己算价值 / 成色 | **没有**：全库 0 处 `GetNegociatedValue` / `GetCurrentValue` / `GetRealDurability`；`Ticket.Price` 只摆位原版文本（`Ticket.cs:4207`） |
| 碰原版鉴定输出 | 只挂 Postfix **原样收编**：`AppraisalHelper.CreateAppraisalTooltip`、`AppraisalRankHelper.CreateCertificateTooltip`、`InspectableHelper.CreateInspectableTooltip`、`BlackLampHelper.CreateBlackLampTooltip` 全归到 `appraisal` 节（`Helpers.cs:88-92,166`），**一个字不改、一个数不加** |
| 唯一"新增"的信息 | **容器/机器内容物清单**（`ContentsInfo`）。原版 `ContainerHelper.CreateContainerTooltip` 只印一行"容器"提示（`ContainerHelper.cs:342-348`），它却列出子物品名/数量/液量/电量——但有锁即不画（`①-4 ⑤`） |
| 会不会放大真相 | 不会：它把"本来要开窗才看得到的内容"搬到 tooltip 上（便利性），不把"本来被伪装层盖住的条件"翻出来（真相） |

**真正要防的是另一件事**：它是**渲染层**，会重排并可能折叠/隐藏我们 tooltip 里已经写下的内容（`mods` 节可关、`HasTooltip` 可翻、`Expand.Concealed` 会把 tooltip 收起）。所以：**能装，但不能把"唯一告诉你这是赝品"的提示放在 tooltip 文本里**——要放在检视窗/估价单这种由我们自己画、且我们自己控制显隐的面板上。

```csharp
}
```

**② 设置窗只加"当前值"显示，不碰控件结构（`LuckyPerkSettingsValuePatch.cs:14-39`）**

### ④-5 踩坑与红线

1. **`GetLuck` 是静态全局闸门，副作用会外溢**：`RollBadLuck` 里 `if (num >= 0) return false;`——加了 +35 后"坏运气"判定**永远不触发**；`LotteryHelper.StampSpawnLuck` 会把加成后的值**写进物品 tag `LOTTERY_SPAWN_LUCK_INT`**（`LotteryHelper.cs:143-148`），而物品 tag 随存档序列化，所以**卸载模组后已盖章的彩票仍带高幸运**（推测：同 ③ 的角标 tag，需真机核对）。
2. **没有判 `PlayerStore.HasInstance`**，只靠 `instance?.healthData == null` 兜 null——不是我们该抄的写法（本工作区规范要求访问前先判 `HasInstance`）。
3. **配置项用硬编码 id**：`ModConfig.For("lucky_perk_plus")`（`LuckyPerkPlus.cs:15`）、设置补丁里 `mod?.Manifest?.ID != "lucky_perk_plus"`（`LuckyPerkSettingsValuePatch.cs:10`）。作者 id 恰好一致，换成带命名空间的 id 就静默失配。
4. **数值全靠读取侧兜**：`luck_bonus` 有 0–100 滑块区间，`extra_luck` 靠 `Mathf.Clamp(..., 0, 99999)`；>100 时 `Random.Range(0,100) < chance` 恒真——它对 `extra_luck` 做对了。**零热重载钩子、零状态**：纯函数式 Postfix，卸载即恢复（除 §1 的存档残留），无状态补丁是最安全的补丁。

### ④-6 对我们的可用点

1. **找"总闸"而不是"分支"**：改数值优先找"纯聚合 + 全游戏都过"的函数（`GetLuck`、`GetCurrentValue`、`GetCorrectBaseValue`）。一处 Postfix 覆盖彩票/刮刮乐/预制掉落。**但总闸也是别人的指纹热点**：`GetCorrectBaseValue` 在鉴定助手的指纹表里（`3828921912` §8.3），动它会被判"环境被改过"。所以总闸要分类：**纯展示类可动，判定/定价类别动**。
2. **给玩家开数值滑块，必须在读取侧夹取**（`Mathf.Clamp`），不要只靠 UI 范围；设置窗加"当前值"就用 `__result.Get("key")` + `OnSlider` 回调 + `label.SetText`，不重建控件、不替换原版窗口——对 `ModConfigWindow` 最轻的增强方式。
3. **数值增强类模组要顺手写"残留说明"**：哪些值会被写进物品 tag/存档（本例是彩票 `LOTTERY_SPAWN_LUCK_INT`），卸载后如何，写进简介——发布前检查项。
4. **别抄**：硬编码自己的 mod id 去 `ModConfig.For(...)`。
