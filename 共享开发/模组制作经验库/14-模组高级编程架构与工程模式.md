## 一、三类模组的架构选型矩阵

不要把简单玩法模组写成五层抽象，也不要把大型工具写成一锅粥：

| 模组形态 | 代表参考 | 推荐分层 | 核心要点 |
| --- | --- | --- | --- |
| **内容/玩法模组**（如深空电玩、Appraiser+） | `Appraiser+`、`StationEvents` | 入口 `IMod` + 按业务自然聚合的静态类（内容表/注册/运行态）+ 微型 Harmony Patch | 数据与代码分离（声明式内容表）；优先 `ModHook`/`ModHelper`/`ModReflect`；目标**正式版零能力** |
| **轻量公共依赖库** | `SDJYBNFramework` | `Framework` 宿主判别 + 扁平子服务（`Config`/`Log`/`Loc`/`Tooltip`/`Interaction`/`Stack`） | 用 `_isHost = manifest.ID == ModId` 区分单独运行与被引用；`Boot` 幂等；模块开关三级回退（配置 → 内存 → 默认开） |
| **大型工具/沙盒模组** | `DeveloperTools`（249 `.cs`） | `Runner`（单帧驱动）→ `*Tools`（无状态纯逻辑）→ `*Record`（不可变快照）→ `*Patch`（单行转发）→ `*Api`（扩展点） | 写操作一律遵循 `Read() → ValidateRecord() → ApplyCore()`，快照过期拒绝写入；分帧预算防掉帧 |

## 二、ES3 存档无污染防坏档范式（StationEvents 教科书级实现）

**痛点**：如果往 `StoreEventManager`（或其他会被 Easy Save 3 序列化的原版管理器）里塞了自定义 `StoreEvent` / 冷却键 / 动作 ID，一旦玩家卸载模组，原版读档时会反序列化出孤儿对象或找不到动作字典键，直接坏档或空引用崩溃。

**解法（完全零能力！）**：在 ES3 写盘的瞬间做**浅克隆投影剥离**，同时把模组数据写进 `ModHelper.SetModData`：

```csharp
// 1. 保存前把自己的状态抓出来写进 ModData，保存结束清理临时标记
[HarmonyPatch(typeof(PlayerStore), "SaveGame", new Type[] { })]
internal static class SavePreparationPatch
{
    [HarmonyPrefix]    static bool Prefix()   => MyPersistence.PrepareSave(); // Capture 进 ModHelper.SetModData
    [HarmonyFinalizer] static void Finalizer() => MyPersistence.FinishSave();
}

// 2. 拦截 ES3 写属性入口：碰到目标原版管理器时，克隆一份干净副本替换 __0！
[HarmonyPatch(typeof(ES3Type), "WriteProperties")]
internal static class SerializationProjectionPatch
{
    [HarmonyPrefix]
    static void Prefix(ref object __0)
    {
        if (__0 is StoreEventManager mgr)
            __0 = MyPersistence.CloneWithoutModEntries(mgr); // MemberwiseClone + 过滤掉本模组前缀条目
    }
}
```
- **读档还原**：在 `ModHook.OnGameLoadedEarly` 从 `ModHelper.GetModData` 读回记录，用工厂重建实例塞回 `StoreEventManager`。
- **结果**：磁盘上的 `save_N.es3` 永远 100% 纯净原版；装模组时状态完整延续，卸载模组后旧档丝滑可玩。可复用的最小骨架见 `工具库/templates/mod-patterns/Es3SafePersistence.cs`。

## 三、游戏内大型模态窗口的输入隔离体系（DeveloperTools）

当模组弹出带搜索框、滚动条、下拉框的 `CustomUIWindow` 时，原版游戏仍会继续响应鼠标滚轮缩放、快捷键、柜台点击，甚至点关闭按钮那一帧鼠标抬起会直接误点背后的物品。

`DeveloperTools` 用四件套彻底根治：

1. **`InputCaptureGate` 状态机**（`工具库/templates/mod-patterns/ModalInputGate.cs`）：
   - 窗口打开或任意鼠标键按住时保持 `captured = true`，并把 `releaseThrough` 推到 `frame + 1`；
   - 关闭窗口调用 `Closing(Time.frameCount)`，确保**关窗后至少多吃 1 帧 + 等全部鼠标键抬起**才交还输入，杜绝「点关闭穿透点到后面柜台」。
2. **全屏半透明遮罩 Backdrop**：
   - 在窗口父节点下建一个带 `Image (raycastTarget = true, alpha = 0.12)` 的全屏节点，每帧确保它的 `SiblingIndex == window.root.GetSiblingIndex() - 1`（紧贴窗口正下方）。
3. **打开窗口瞬间清焦点与游戏输入态**：
   - `EventSystem.current?.SetSelectedGameObject(null)`
   - `CustomEventHandler.ClearDoubleClickTarget()`
   - `InputActionManager.current.Reset(); InputActionManager.current.ResetExcept(null);`
4. **六个精准拦截点**（仅当 `Blocked` 且目标不在本窗口内时拦截）：
   - `InputActionManager.Update`（屏蔽游戏操作输入）
   - `KeyBindHelper.GetKeyDown` / `GetBackDown`（屏蔽热键与返回键）
   - `EventSystem.RaycastAll`（过滤掉窗口下层的游戏 UI 命中）
   - `CustomUIManager.HandleEscape`（优先关搜索框/选择器/自建窗口，不弹游戏主菜单）
   - `ScrollRect.OnScroll` / `TMP_InputField.OnScroll`（防止滚轮冒泡到镜头缩放）

## 四、防卡顿与防丢物两大运行时模式

### 1. 分帧预算制目录索引（`WorkshopRunner.IndexCatalog`）
遍历 `DirectoryMaster.GetIdentifierList<GameItem>()` 逐一创建临时实例采属性时，单帧全量创建会卡顿数秒且易留幽灵 UI：
- 过滤 `ItemSpawnerHiddenList.IsHidden(id)`；
- `Update()` 中每次最多扫 2 个，且加时间熔断 `Time.realtimeSinceStartup - start > 0.002f`（每帧预算 ≤2ms）；
- 每次创建严格包裹 `try { ... } finally { item?.Destroy(); }`；
- 监测 `scene != EmporiumEntry.Instance` 与 `OnGameLoadedInit`，切场景/读档立即中止并清空缓存。

### 2. 持久化待交付队列与落点回滚（`SDJYBN.SplitQueue`）
当需要把一件物品拆解/转换为多件产出物，而柜台或背包可能暂时没空位时：
- **先产出 → 全部尝试投放 → 任一失败则 `DestroyAll` 整体回滚 → 原物品完好无损并按 `uniqueId` 入队持久化到 `ModHelper.SetModData(modId, "split:" + uniqueId, snapshot)`**；
- 重试时机跳过玩家正在拖拽期间（`ItemMouseDragHandler.current.IsDraggingItem`）；
- 重试前比对 `Snapshot(item)`（防物品期间已被玩家改造/消耗），连续找不到 30 次或持续阻塞 120 次自动放弃清理；
- 校验落点一律用引用比较 `piece.parentInventory == targetInv`，不用 `!= null`。

## 五、Tooltip 多模组防冲突与安全扩展

原版提供了两个层次的 Tooltip 扩展点：

1. **推荐首选（零 Harmony）**：订阅 `ModHook.OnCreateTooltipLate += (RichTextBuilder builder, GameItem item) => ...`；若可能同帧触发多次，用 `ConditionalWeakTable<RichTextBuilder, object>` 防重复追加。
2. **需要临时改写原版上下文再恢复时**（`SDJYBN.TooltipPatch` 范式）：Patch `GameItemElement.GetTooltipBasic()`，在 `Prefix` 里通过 `out List<Action> __state` 记录回滚闭包，在 `Postfix` **与 `Finalizer` 两处都执行 `Restore(__state)`**——确保即使原版中途抛异常也不会把物品状态弄脏。

## 六、开发桥接器与后台服务的工程骨架（ModDevBridgeNext & MCPBridge）

扩展 `深空桥接器` 或编写开发辅助工具时，直接复用这两家已验证的底层工程模式：

| 机制 | 最佳实践实现 | 来源 |
| --- | --- | --- |
| **内嵌 HTTP 监听安全底线** | 强制 `IPAddress.IsLoopback && req.Url.Host == "127.0.0.1" && req.Headers["Origin"] == null`（防 DNS rebinding 与浏览器 CSRF）；后台线程走 `ModHelper.RunInBackground(token => ...)`，用 `token.Register` 统一关闭 `HttpListener` 与所有挂起连接 | `ModDevBridgeNext.HttpTransport` |
| **跨线程主线程调度** | 区分单帧 `EnqueueAsync<T>` 与多帧 `EnqueueCoroutineAsync<T>`（用 `_isCoroutineRunning` 互斥序列化，保护 `WaitForEndOfFrame` 截图与多帧拖拽）；用 `CancellationTokenSource.CreateLinkedTokenSource` + `CancelAfter` 控超时 | `MCPBridge.MainThreadDispatcher` |
| **世界代际守卫** | 每帧比对 `PlayerStore.Instance` 与 `NewGameData.Instance.isInMainMenu`，变动立刻刷新 `WorldId = Guid.NewGuid()`，旧句柄/旧测试会话自动作废 | `ModDevBridgeNext.BridgeRuntime` |
| **弱引用防假 null 句柄池** | `ObjectHandleRegistry` 存 `WeakReference<object>` + 版本号 + 类型名，读取时同时检查 `UnityEngine.Object` 假 null（`u != null && u == null`） | `MCPBridge.ObjectHandleRegistry` |
| **五阶段补偿热重载** | 严格按 `old.prepare → old.disable → old.unpatch → next.patch → next.init → next.enable → next.activate → commit` 执行，每步置 `Started/Completed` 标记，失败按精确逆序恢复旧版；`Commit` 直接替换 `LoadedMod` 的 `Instance`/`Assembly`/`HarmonyInstance` | `ModDevBridgeNext.HotReloadTransaction` |
| **资产热重载（不重启游戏）** | 贴图：`loadedMod.Sprites[key].texture.LoadImage(bytes)` 原地覆写 + 清 `RenderHandler.atlasCache`；书籍：`PaperBookRegistry.RemoveMod` + `LoadMod`；战利品：清 `LootRegistry.journal` + 置 `dirty = true` + `ModLootFile.Load`；在场物品：重造原型同步字段后调 `(item as GameItemElement)?.Validate()`；最后顺手跑一遍 `ModScanner.Scan` 核验能力 | `MCPBridge.MutationSandboxTools` |
| **不可读纹理 GPU 导出 PNG** | `RenderTexture.GetTemporary` → `Graphics.Blit` → `Texture2D.ReadPixels(sprite.textureRect)` → `EncodeToPNG` → 立刻 `Destroy` + `ReleaseTemporary` | `MCPBridge.VisualAssetTools` |
| **双版本条件编译** | `#if BRIDGE_FULL` 把高权限工具（`reload_mod`/`load_probe_module`）与工坊兼容版在编译期彻底切开，扫描器不报多余能力 | `ModDevBridgeNext.Distribution` |

## 八、一个模组塞几十个功能时的三种组织方式（2026-11 三模组实测对比）

工坊里"一个模组塞几十个功能"至少有三种成熟解法，照抄前先看这张表：

| | (a) 静态委托表 | (b) 自描述 Patch 注册表 | (c) 特性化补丁对象表 |
| --- | --- | --- | --- |
| 代表 | DangpuPlus（`FeaturePack` 103 项 `(Name, Init, Update, OnGUI)` + 熔断） | Probably Extend Framework（`.Patch(方法名, 中文说明, Func<MethodBase>)` + `Report()` 打 √/×） | Pen's QoL（`FeaturePatch{Feature, Target, Prefix, Postfix, Finalizer, Applied}` 表，22 键 / 49 配置项 / 80 处登记） |
| 适合 | **大量常驻逻辑**（每帧 / 每 GUI 有槽位） | **大量小补丁**，且要"更新后一眼看出哪条失效" | **大量小补丁**，且要"运行中单独关一个功能" |
| 热禁用一个功能 | ❌ 要重启 | ❌ `UnpatchAll(id)` 会连带摘掉同实例下别的补丁 | ✅ **唯一做到**：`Unpatch(target, patch.method)` 方法级摘除 |
| 排查"哪条补丁失效" | 弱 | ✅ **最强**：`Func<MethodBase>` 延迟解析 + 逐条 catch + `Report()` | 弱 |
| 补丁条数 vs 玩家开关数 | — | 1 : 1 | ✅ 可 **N 个开关 OR 合并成一条补丁** |

**选型建议**：
- 功能以"常驻逻辑"为主 → 用 (a)，别硬套补丁表（(b)(c) 连"每帧跑一遍"的槽位都没有）。
- 功能以"补丁"为主、且会随游戏更新频繁失效 → 用 (b)（延迟解析 + 逐条 catch + 自检报告能省大量排查时间）。
- 要"玩家边玩边开关单个功能" → 必须有 (c) 的**方法级摘挂**。
- 现实做法：**(b) 的骨架 + (c) 的摘挂粒度**——表里每条存 `Target`（延迟解析）与 `Applied` 标记，刷新时逐条 `Patch` / `Unpatch(target, method)`，并保留 `Report()`。

**⚠️ 照抄 (c) 必须避开的两个坑**（Pen's QoL 实测踩过）：
1. `AccessTools.Method(...)` 是**实参求值**。若把它写在 `ApplyCore` 的大 `try` 之外，某个目标抛 `AmbiguousMatchException` 就会逃出整个循环；而"已应用"标志早就置位 → **剩下几十条一条都不装，且永不重试**，外层还是空 `catch {}` 静默。
   正确写法：**每条补丁的目标解析 + 安装各自包一层 try/catch**，单条失败只跳过那一条。
2. `Applied` 标记要**校验 Harmony 真实状态**（`Harmony.GetPatchInfo(target)` 里有没有我方 method）。否则别的模组调 `UnpatchAll()` 之后，开关"关→开"会被"已 Applied"跳过，补丁永不回挂。
