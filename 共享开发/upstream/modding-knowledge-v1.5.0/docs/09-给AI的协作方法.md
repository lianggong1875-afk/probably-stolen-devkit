# 09 · 给 AI 的协作方法

> 这一节写给「被要求改这个游戏的模组」的 AI，也写给给 AI 下指令的人。
> 目标：让 AI 少做无效功、少把推测写成事实、少一件事改三遍。

---

## 1. AI 在这个项目里最容易犯的 7 个错

1. **虚构 API。** 凭「常见 Unity 游戏都这么写」编出一个不存在的方法。→ 每个非平凡 API 都要在 `Assembly-CSharp` 反编译里搜到，或在本知识库的 API 地图里找到。
2. **忽略版本。** 拿旧版结论套新版游戏。→ 结论必须带日期；改代码前先确认当前 `Assembly-CSharp` 的方法签名。
3. **一次改一大片。** 同时改 UI、存档、数值，出问题无法定位。→ 一次只改一件事，每步都能编译+加载。
4. **没验证就说完成。** 编译通过 ≠ 游戏里生效。→ 必须给出日志/行为证据；否则明确说「未验证」。
5. **动存档结构。** 觉得「加个字段很方便」。→ 先读坑 #23、#24、#30；默认不改存档。
6. **通读反编译。** 把上下文浪费在读几千行 `num`/`flag` 上。→ 先 grep 类名/方法名，只读声明和调用点。
7. **把临时文件留在模组目录。** → 直接导致模组不加载（坑 #16）。

---

## 2. 标准工作流（7 步）

### 第 0 步：读交接材料
如果项目有自己的 `DEV_NOTES.md` / `HANDOFF.md`，**先读**。没有就按本知识库的 `AI_GUIDE.md` 的阅读顺序走。

### 第 1 步：把需求拆成「可验证的一句话」
- ❌「做一个更好的机器系统」
- ✅「把搅拌机的输入区从 6×6 改成 9×9，不改变配方逻辑；验证：放进 81 个原料不报错，产出正常」

### 第 2 步：查官方入口
`docs/03` 的「按功能查表」→ 有钩子用钩子；没有就找到原版实现，照抄流程而不是改它的数据。

### 第 3 步：写最小改动
- 新文件优先，不改原文件的无关部分；
- 补丁写在单独的类里，带 `// 坑：` 注释说明为什么需要补丁；
- 所有每帧/每次点击的入口 try/catch。

### 第 4 步：编译
写清楚引用了哪些 DLL；报 `CS0012` 就补对应 `UnityEngine.*Module.dll`；报 `CS1504/CS2001` 检查 csc 调用方式（坑：参数数组）。

### 第 5 步：部署到游戏
先在 Mods 菜单启用+信任+重启；确认 `Player.log` 里有 Init 日志；再测功能。

### 第 6 步：验证并留证据
- 新档 + 旧档各测一次（涉及存档时）；
- 记录日志片段和数值；
- 失败也要记录「现象 + 已排除的可能」，不要静默重试。

### 第 7 步：回写笔记
把新结论追加到项目笔记，带日期和证据等级。**这是下一轮省时间的唯一办法。**

## 3. 该向用户要什么信息

AI 最容易在信息不足时硬猜。缺以下任何一项，先问：

| 缺什么 | 为什么要 |
|---|---|
| 游戏版本 / 是否刚更新 | 决定 API 是否还成立 |
| 是「新档」还是「旧档出问题」 | 决定排查方向（兼容 vs 逻辑） |
| 完整 `Player.log` 片段 | 区分「没加载」「补丁没中」「逻辑错」 |
| 复现步骤（第几天、哪个界面、点了什么） | 没有它无法定位 |
| 期望行为 vs 实际行为 | 避免修错方向 |
| 是否允许改存档结构 | 决定方案（默认不允许） |

问问题要具体，一次问 1~3 个，别列 10 条。

## 4. 交付时的写法

```markdown
## 改了什么
- 文件：`mod\xxx\src\Xxx.cs`（新增补丁 `Patch_Yyy`）
- 行为：……

## 为什么这样做
- 官方入口：`ModHook.OnZzz`（03 第 2.x 节）覆盖不了「……」，所以补丁目标是 `A.B()`。
- 证据：[静态] 反编译 `A.B` 在第 N 行做了 X。

## 怎么验证
1. 新档 → …… → 预期日志 `[Xxx] ...`
2. 旧档 → …… → 预期不丢物品

## 没验证的部分
- [待验] `...` 场景尚未实测。
```

**「没验证的部分」这一栏不能省。** 它比「已完成」更能建立信任。

## 5. 代码审查清单（提交前自己过一遍）

- [ ] 没有给重载方法打补丁（`DirectoryMaster.Item` 这类）。
- [ ] 每个每帧/每次点击的补丁入口都有 try/catch。
- [ ] 静态 UI 引用在 `OnGameLoadedInit` 里重置。
- [ ] 没有 `(object)node != null` 这种判空。
- [ ] 没有在 `Init` 里访问 `PlayerStore.Instance`。
- [ ] 没有在 `IsDecoding` 期间创建/移动物品。
- [ ] 没有改面板顺序 / 存档结构。
- [ ] 补回物品带 `IS_OWNED_TAG`，且期望/实际口径一致。
- [ ] 没有 `Process` / `Steamworks` / 网络 / 文件读写。
- [ ] 模组目录里没有临时文件。
- [ ] `manifest` 版本号已 bump，`<Capabilities>` 存在。
- [ ] 日志前缀统一，高频路径不打日志。

```markdown
**当前状态**：<已发布 vX.Y.Z / 本地已编译未发布 / 代码已改未编译>

- ……

**关键结论（带证据等级）**
- [实测] ……
- [静态] ……

**已知问题 / 待验**
- ……

**下一步**
1. ……

**文件索引**
- 源码：……
- 部署目录：……

```

## 7. 给用户的提示词模板

把下面这段和你的需求一起发给 AI，能省掉一半来回：

```text
你在给《深空当铺 / Probably Stolen》（Unity 2021.3.45f2, Mono, .NET 4.x）写模组。
先读模组目录里的 AI_GUIDE.md，再按它指的顺序读 docs/。
规则：
1. 先查官方 ModHook 有没有入口，再考虑 Harmony；用补丁要说明官方缺哪项语义。
2. 不改存档结构；涉及旧档时先说明兼容方案。
3. 一次只改一件事，每步都能编译+加载。
4. 结论标 [实测]/[静态]/[待验]；没验证就直说。
5. 不要往模组目录写临时文件。

我的需求：<一句话需求>
验收标准：<可观察的行为/日志>
```

## 8. 最后一条

**这个游戏的模组开发，难点不在写代码，而在「知道哪条路是活的」。**

官方钩子覆盖了大部分常规需求；剩下的坑集中在 UI 树、机器面板顺序、存档索引、扫描器规则这四类。这四类本知识库都写了。遇到新问题，先把它归类到这四类之一，再动手。
