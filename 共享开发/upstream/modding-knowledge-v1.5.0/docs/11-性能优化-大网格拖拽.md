# 性能优化：大网格拖拽为什么卡死，以及怎么救

> 来源：2026-11 修复「模组集成器」15×15 网格框选拖动卡死（实测有效）。适用于任何「大网格 + 槽变化触发全量重算」的容器 UI。
> 证据等级：现象与结果 `[实测]`，调用链与开销 `[静态 · 反编译]`。

---

## 1. 现象

一个自定义容器把网格扩到 15×15、里面放了 30～50 个可交互物品时：

- **框选多个物品拖动**，帧率骤降到个位数，严重时直接卡死/未响应；
- 单个物品拖动、开关窗口还算正常；
- 物品越多越慢，像是「每次移动都把整个网格算了一遍」。

---

## 2. 根因：每放一个物品，原版重算整个网格

以模组舱（`GameGridInventory`）为例，物品放入/取出的回调里，原版会调用：

```csharp
// MachineHelper / ModuleEffectHelper 的既有逻辑
ModuleEffectHelper.OnAddedModuleToGrid(item, machine, grid.childItems);
ModuleEffectHelper.OnRemovedModuleFromGrid(item, machine, grid.childItems);
```

两者内部都会执行：

```csharp
ModuleEffectHelper.ComputeAllModuleTempStat(moduleList);
```

而这个函数对**每个**模组做 3 次 `ModifyTag`（性能/效率/质量），`ModifyTag` 默认 `skipValidate = false`：

```csharp
foreach (var m in moduleList) ResetAllTempStat(m);      // 3 × ModifyTag → 3 × ValidateShapeState
foreach (var m in moduleList) ComputeTemporaryStat(m);  // 词条 onAnyAction，内部还会再改标签
```

`ValidateShapeState()` 不是「只校验自己」：

```csharp
modifiedState = ComputeModifiedShapeState(...);  // 重算形状/标签
Validate();                                      // 自身校验
parentInventory.Validate();                      // 整个父网格校验
foreach (var p in FindParentsType<GameItem>(parentInventory))
    p.ValidateShapeState();                      // 沿父链继续向上
```

于是**一次拖入 N 件**的代价是：

```
N × M（网格内模组数）× 3 × O(网格校验 + 父链)
```

`N ≈ M` 时就是平方级。15×15、40 个模组时，一次拖动会产生上万次网格/父链校验 —— 卡死。

> 同一个坑的另一种表现：`HubTotal()` 之类的「读总数」函数每次调用都 `RecomputeHubTotals()`（内含全仓库扫描 + 全量重算），放在按钮回调里，点一下「+5」就卡一次。

---

## 3. 四条改动（按收益排序）

### 3.1 把「每次事件重算」合并成「帧末算一次」

在自定义网格的槽回调里，临时抑制原版的全量重算，只做脏标记；由 `Update` 统一结算：

```csharp
// Harmony 前缀：批量期间直接跳过
[HarmonyPatch(typeof(ModuleEffectHelper), "ComputeAllModuleTempStat",
    new Type[] { typeof(List<GameItem>) })]
static class Patch_ComputeAllModuleTempStat
{
    static bool Prefix()
    {
        return !ModuleBatteryIntegrationMod.SuppressTempRecalc; // true 表示继续执行原版
    }
}

// 网格回调
grid.onSlotAddItemEndFunc = (item, inv, slot) =>
{
    BeginHubBatch();                       // SuppressTempRecalc = depth > 0
    try { ModuleEffectHelper.OnAddedModuleToGrid(item, hub, grid.childItems); }
    finally { EndHubBatch(); }
    MarkHubTempDirty();                    // 帧末统一算
};
```

```csharp
// KeyListener.Update
FlushHubTemp();   // 若 dirty，对每个容器 ComputeAllModuleTempStat + ComputeModuleEffect 一次
```

**要点**：抑制的是「原版调用的那个函数」，不是把原版逻辑删掉；帧末仍调用原版（或等价实现），语义不变。

### 3.2 拖动/框选期间不结算，松手才算

```csharp
public static void FlushHubTemp()
{
    if (!hubTempDirty) return;
    if (Input.GetMouseButton(0)) return;   // 左键按住（拖拽中）先不结算
    hubTempDirty = false;
    // …统一重算…
}
```

拖拽过程中玩家看不到「模组数值」的变化，晚几十毫秒结算没有副作用；松手那帧一次性算完。

### 3.3 大列表走批量版：批量写 + 每件只 sync 一次

原版每个模组要 3 次 `ValidateShapeState`。批量版把 TEMP 用 `skipValidate` 写进去，再每件 `SyncModifiedState()` 一次（只重算自身 modifiedState，不校验父网格、不递归父链）：

```csharp
// 1) 批量写（skipValidate = true）
foreach (var m in list)
{
    int p = m.GetTagReadonly("BONUS_PERCENTAGE_PERFORMANCE_INT").GetInt();
    int e = m.GetTagReadonly("BONUS_PERCENTAGE_EFFICIENCY_INT").GetInt();
    int q = m.GetTagReadonly("BONUS_PERCENTAGE_QUALITY_INT").GetInt();
    m.ModifyTag("TEMP_PERCENTAGE_PERFORMANCE_INT", st => st.SetInt(p), true);
    m.ModifyTag("TEMP_PERCENTAGE_EFFICIENCY_INT",  st => st.SetInt(e), true);
    m.ModifyTag("TEMP_PERCENTAGE_QUALITY_INT",     st => st.SetInt(q), true);
}

// 2) 每件 sync 一次（让 modifiedState 生效，onAnyAction 读的是它）
foreach (var m in list) m.SyncModifiedState();

// 3) 原版 onAnyAction（接收器/负反馈/节点等），内部会再改 TEMP
foreach (var m in list) ModuleEffectHelper.ComputeTemporaryStat(m);

// 4) 再 sync 一次，收敛 onAnyAction 的写入
foreach (var m in list) m.SyncModifiedState();
```

**顺序很重要**：`GetTagReadonly` 读的是 `modifiedState`，所以第 3 步之前必须先 sync，否则 onAnyAction 读到旧 TEMP，叠加结果会错。
**阈值分流**：只在 `moduleList.Count >= 12` 时走快版；小网格（原版机器模组舱）保持原版，减少行为差异面。

### 3.4 缓存「全图扫描」结果

```csharp
private static List<GameItem> hubListCache;

private static List<GameItem> GetHubs()
{
    if (hubListCache != null && hubListCache.All(h => h != null)) return hubListCache;
    hubListCache = FindHubs();      // GetAllOwnedItems + 飞船 + 任务现场，很贵
    return hubListCache;
}
```

- 失效点放在**低频**事件：读档、生成物品、打开面板；不要放在拖动/点击路径。
- 「读总数」只读缓存的标签值，不再每次调用重算。
- Unity 对象销毁后 `h == null` 为 true（Unity 重载），正好用来检测缓存失效；不要写 `(object)h == null`。

## 4. 结果与边界

- 改动后，15×15、40+ 模组的集成器框选拖动恢复流畅（作者实机确认「相当好」）`[实测]`。
- **剩余成本**：游戏自身在拖拽时仍会对网格做 `Validate`（物品跟随鼠标需要它），物品极多时这部分还在。若仍卡，下一步只能对「自定义网格的 Validate」做节流/合并（风险更高，需实机回归）。

### 4.1 批量生产的另一面：同步 vs 分帧（2026-11-19 实测）

- 批量输出 71 件时，**同步一次做完 + 结束只刷一次**比「分帧（每帧 8 个）+ 每帧 `Validate`」快得多。后者每帧都把已放好的成品全部重验，71 件累计约 360 次重复验证，连续掉 9 帧 `[实测]`。
- 分帧只在「必须保持界面响应」时值得用，且**每帧不要 `Validate`**——全部结束或每 N 帧刷一次。
- 同理：`CountFreeCells` 只算一次、逐件扣减；逐件的 `GraphUtils.CanAccept` 可以去掉（与 `TryAcceptAll` 重复落位搜索），用 `leftover` 兜底。

## 5. 通用排查清单（任何容器 UI 卡顿）

1. 在槽变化回调里下 `Stopwatch`/日志，确认是不是「每放一个物品就全量重算」。
2. 看被调用的原版函数是否对**整张网格**循环（名字里带 `All`、`Compute`、`Refresh` 的要警惕）。
3. 看它内部是否 `ModifyTag` → `ValidateShapeState`（默认会 `parentInventory.Validate()` + 父链递归）。
4. 有「读总数」的函数被按钮/每帧调用吗？→ 缓存。
5. 有「全仓库扫描」在热路径吗？→ 缓存 + 低频失效。
6. 批量化时：`skipValidate` 写入后，**先 sync 再跑依赖 modifiedState 的逻辑**。
7. 批量结束、鼠标松开时统一 `Validate()` 一次，保证 UI/网格状态收敛。
8. 分帧批量时**不要每帧 `Validate`**（见 4.1、`docs/04` 坑 #51）。
