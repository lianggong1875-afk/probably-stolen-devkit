# 04 · 踩坑清单（52 条）

> 这是整套文档里最值钱的部分。每一条都来自真实故障：**现象 → 原因 → 做法**。
> 引用时请用「坑 #N」。编号固定，不要重排。
> 除另有标注外，均为 `[实测]`。

---

## #1 不要给 `DirectoryMaster.Item` 打 Harmony 补丁

**现象**：整个模组 `Init` 失败，Mods 列表显示红字，但日志里只有一条 `AmbiguousMatchException`。
**原因**：`DirectoryMaster.Item` 有泛型/非泛型两个重载。`[HarmonyPatch(typeof(DirectoryMaster), "Item")]` 在运行时按名字匹配到两个方法，解析补丁时直接抛异常，加载器随之放弃整个程序集。
**做法**：要拦截物品创建，改挂**上层调用点**（如工厂方法、`DecodeSaveItem`、具体物品的构造），或者干脆不拦。任何重载方法（`Item`、`Load`、`Get`）都要先确认只有一个目标签名。

---

## #2 读档期间不要做重活

**现象**：读档后仓库全空 / 物品位置错乱 / 偶发 `GameInventory is invalid`。
**原因**：`SaveManager.DecodeNodes` 正在按顺序重建物品树。此时你创建/移动/销毁物品、建 UI、遍历库存，会干扰它的回填。
**做法**：
- 判断 `SaveManager.IsDecoding`，为 true 时一切操作推迟。
- 重活放到 `ModHook.OnGameLoadedLate`（读档彻底完成的可靠点）。
- UI 创建不要放在 `OnGameLoadedInit/Early`。
- 每帧 ticker 里也要加 `IsDecoding` 门禁。

---

## #3 `MachineHelper.LoadUpgrade` 对没有升级 tag 的机器会空引用

**现象**：读档在中途中断，很多物品没读回来；日志有 `Object reference not set`，堆栈指向 `MachineHelper.LoadUpgrade`。
**原因**：读档对带 `STANDARD_MACHINE_TAG` 的机器会调 `LoadUpgrade`，它取 `GetBodyStorage(machine, 1)` 当模组区，并读 `MODULE_UPGRADE_STAGE_INT`。没有这个 tag 的机器就会在后续逻辑里空引用。
**做法**：
- 自定义机器在工厂里就写好 `MODULE_UPGRADE_STAGE_INT = 0`（或明确挂 `NO_MODULE_INTEGRATION_TAG`）；
- 给 `LoadUpgrade` 打一个**前缀防呆**：目标机器没有该 tag 时直接 `return false`，跳过原方法。

## #4 不要用 PowerShell 做中文文本替换

**现象**：源码里的中文变成「鎵归噺杈撳嚭」，编译出来的 UI 全是乱码。
**原因**：Windows PowerShell 5.x 的 `Get-Content` / `Set-Content` / `-replace` 默认按系统 ANSI（GBK）读写 UTF-8 文件。
**做法**：用能显式指定 UTF-8 的写入方式（编辑器、`[IO.File]::WriteAllText(path, text, [Text.UTF8Encoding]::new($false))`，或专门的写文件工具）。另外，控制台**显示**乱码不代表文件坏了——见 `01` 第 4 节的验证方法。

## #5 机器 `uniqueId` 在工厂执行期间是 0

**现象**：用 `uniqueId` 做「每台机器独立状态」的键，结果所有机器共用一份状态。
**原因**：`DirectoryMaster.Item` 返回后才会给物品分配 `uniqueId`；工厂内部拿到的实例还是 0。
**做法**：不要在工厂里解析 ID。把「分配记录」做成惰性解析：第一次真正需要时（按钮点击、读档后、第一次 tick）再从 `item.uniqueId` 取，并缓存。注意物品被拆/合并时 ID 可能变。

## #6 供电有三条不同路径

**现象**：接上电池后机器行为不一致：有时不扣电、有时扣两次、有时电池空了还在跑。
**原因**：`TryDrawCyclePower`（周期扣电）、`CanPower`（够不够）、`DrawPowerSource`（直接扣）是三条独立入口，各自被不同机器逻辑调用。
**做法**：做「电池集成/电力改造」类模组时三条都要覆盖，并实现「池空回退」——一个电池组抽干后继续找下一个，而不是直接判失败。日志里分别打印各路径的命中情况。

## #7 装 DLL 前必须完全退出游戏

**现象**：`Copy-Item` 报 `The process cannot access the file ... user-mapped section open`，DLL 没更新，但 manifest 已经更新了。
**原因**：Mono 在游戏运行期间内存映射了已加载的 DLL。
**做法**：
- 部署前查进程，存在就等退出；
- **manifest 与 DLL 作为一个整体更新**：先编译到临时目录并校验，再一起复制；任一步失败就回滚 manifest。
- 后台等待游戏退出的脚本可以自动完成复制，但发布前要再次确认版本号与 DLL 一致。

## #8 新模组默认禁用；更新则自动加载

**现象**：第一次放进 `Mods\` 的模组在游戏里毫无反应；更新版本后却直接生效。
**原因**：`modOrder` 里没有的新 ID 默认禁用；已信任的模组只要**没有申请新能力**，指纹变化会被判为 `Updated` 并自动加载。
**做法**：
- 首次测试：进 Mods 菜单启用/信任 → **重启**。
- 发布更新：不要新增 `Capabilities`，否则老玩家要重新信任（`Changed`）。
- 排查「有没有加载」看 `Player.log` 的 `[ModLoader] audit:`。

## #9 引 `UnityEngine.UI.dll`

**现象**：`TextMeshProUGUI.enabled` / `raycastTarget` 报 `CS0012`（类型定义在未引用的程序集）或 `CS1061`。
**原因**：这些成员定义在 `MaskableGraphic`（`UnityEngine.UI`）上，只引 `Unity.TextMeshPro.dll` 不够。
**做法**：引用清单同时加 `UnityEngine.UI.dll` 和 `UnityEngine.UIModule.dll`。

## #10 遍历 UI 节点要防 Unity「假 null」

**现象**：场景切换后，每帧补丁抛 `MissingReferenceException`，界面卡死/无法操作。
**原因**：Unity 的 `== null` 是重载过的：已销毁的 `UnityEngine.Object` 与 `null` 比较返回 true，但**对象引用本身还在**。若你用 `(object)node == null` 或 `ReferenceEquals` 判断，就漏掉了这种情况。
**做法**：
- 一律用 `node != null`（走 Unity 重载）。
- 所有在每帧/每次点击关键路径上的入口都 try/catch。
- 静态持有的 UI 引用在 `ModHook.OnGameLoadedInit` 里统一重置。
- 详细反例见坑 #14。

## #11 不要试图改建原版右键菜单的节点结构

**现象**：把原版 1×7 的按钮格重建为 1×8，元素都建出来了、尺寸也对、父链也对，但**一个像素都不画**；节点的 `gridActiveHier` 是 false，整块留在 `tempRoot` 下。
**原因**：原版菜单的布局/激活由 `PixelWindow` + `GridPixelElement` + 临时根节点协作完成，手工重建的格子不会进入它的激活流程。照抄工坊里现成模组的「`DetachAll` → `new GridPixelElement` → `Destroy(oldGrid.gameObject)`」完整流程也不行（实测）。
**做法**：**加右键菜单项请用独立浮窗**，不要改造原版菜单。见 [05-代码配方](05-代码配方.md) 第 1 节。

## #12 手搓 TMP 文字节点会「框在、字没」

**现象**：浮窗/画布上，背景框和描边都在，文字区域也有尺寸，但屏幕上一个字都没有；`label=True`、文字内容也非空。
**原因**：`TreeNodeRender.InstantiateText()` + 手动 `sizeDelta` 的节点在这套 UI 里不参与渲染；另外 TMP 在**未激活**状态下 `preferredWidth` 可能为 0，先算尺寸会把框缩成一条。
**做法**：
- 用 `new RichTextElement()` + `SetText(...)`（原版菜单项/文字面板的同一个类），渲染链路天然一致。
- 必须先 `SetActive(true)`，再算尺寸/排版。
- 需要自定义配色时继承 `RichTextElement`，改它 `protected` 的 `background` / `insideBorder` / `textNode`（见 05 第 2 节）。

## #13 鼠标移到浮窗上，原版右键菜单会收起

**现象**：浮窗和菜单挂在同一棵 UI 树、同一个 Canvas，鼠标一移过去菜单就消失。
**原因**：`ItemContextHandler.OnEventUpdate` 每帧用 `GraphicRaycaster` 找带 `ContextMenuNode` 标签的节点，浮窗实测命中不了（即使 tag 已设）。
**做法**：给 `ItemContextHandler.FindContextMenuNode(Vector2, Canvas)` 打**后置补丁**：鼠标落在浮窗矩形里就把 `__result` 换成浮窗节点（`RectTransformUtility.RectangleContainsScreenPoint`）。右键释放同样要自己判矩形，因为 `OnEventRelease` 只认它自己窗口里的元素。

## #14 `(object)node != null` 是错误写法

**现象**：为了「躲开 Unity 的 `==` 重载」写成 `(object)node != null`，结果场景切换后判断恒为真，后续访问已销毁节点抛异常；异常从每帧补丁冒回去，打断 `ItemContextHandler.OnEventUpdate`，**读档进店后整局无法操作**。
**原因**：Unity 重载的 `==` 会把已销毁对象判成 `null`；转成 `object` 后调用的是引用比较，永远为真。
**做法**：直接写 `node != null`。这条和坑 #10 是同一条命脉，两个方向都踩过。

## #15 判断「本地是否比工坊新」不能只看版本号

**做法**：拿 `Mods\<模组>\*.dll` 与 `steamapps\workshop\content\4348910\<工坊ID>\*.dll` 做**文件哈希对比**（订阅副本 = 工坊当前内容）。
**注意**：
- 自己发布的物品如果没有订阅副本，只能靠版本号/哈希记录判断。
- **刚上传成功后别用它验证成败**：Steam 客户端要排下载队列，订阅副本可能几分钟甚至几十分钟还是旧版。以上传工具输出的 `RESULT OK` 为准。
- `RESULT FAIL: UNCONFIRMED` 表示「2 分钟内没等到 Steam 最终确认」，可能已提交也可能没有；看 Steam 的 `content_log.txt` 里有没有对应的 `Workshop update changed : Running Update,Committing`。
- `k_EResultFail` 常见于**短时间内连续提交过多**被限流。等 60 秒换个时间点重试，先 `--validate` 排除清单错误。

## #16 绝对不要在模组文件夹里留备份/临时 DLL

**现象**：机器扩格、按钮、所有功能凭空消失，游戏日志里**一条相关日志都没有**。
**原因**：模组扫描器会把 manifest 没列出的可执行文件判成 `payload-file`，输出 `Changed: scan refused (... -> executable content)`，然后**整个模组不加载**。`MachineTweaks.dll.bak-000143`、`.broken-*` 这种名字全都中招。
**做法**：
- 备份放 `Mods\` 之外（工作区 `tmp\backup\`）。
- 发布前扫一遍目录：只允许 `manifest.xml` / 列出的 `*.dll` / `preview.png` / `Textures` / `Sounds` / 纯文本。
- 排查时先搜 `Player.log` 里的 `scan refused`。

## #17 批量放置物品会卡顿（全量 Validate）

**现象**：一键批量输出 70+ 个成品，界面冻结 2.4~2.7 秒。
**原因**：每放一个成品都会触发输出区 `GameGridInventory.Validate` 的全量重排；仓库 1000+ 件时成本极高。
**做法**：
- 循环期间用 Harmony 前缀压掉 `GameGridInventory.Validate`（静态开关），循环结束（`finally`）再统一 `Validate` 一次；
- 更彻底：改成**分帧协程**（例如每帧 8 个，帧末 `Validate` 一次），冻结消失、界面保持响应，总时长基本不变；
- 实测：抑制 Validate 把 2.4~2.7 秒降到 1.4~1.9 秒；剩下的是「创建 N 个 GameItem/Element」本身的成本（每个约 25 ms）。想更快只能减少单次上限或继续分帧。

## #18 `Init` 阶段不能调 `ModHelper.AddNetworkUpgrade`

**现象**：模组列表显示红字错误，开局场景也没注册；日志里 `PlayerStore..ctor` 抛 NRE。
**原因**：`AddNetworkUpgrade` → `NetworkUpgrade.RegisterModUpgrade` 会访问 `PlayerStore.Instance`，而 `Init` 时 `PlayerStore` 还没构造。
**做法**：延迟到 `ModHook.OnGameLoadedNormal` 或 `OnNewGameStarted`，用静态 bool 防重。`AddStartingScenario` 只碰静态列表，`Init` 里调用是安全的。

## #19 `ModifyTag(skipValidate: true)` 写了读不到

**现象**：刚 `ModifyTag("X", ..., skipValidate: true)`，下一行 `IsTag("X")` 返回 false / `GetTagReadonly` 读到 0。
**原因**：`skipValidate:true` 只写 `state`，而 `IsTag` / `GetTagReadonly` 读的是 `modifiedState`。
**做法**：中间必须有一次 `ValidateShapeState()`，或者手动 `item.SyncModifiedState()`。
**相关**：`ModifyTempStatFromBaseByPercentage(item, 10)` 是「**基础值**的 10% 再取整」，基础属性 <10 时结果就是 0——玩家会以为功能没生效。要显示效果，正向属性保底 +1，并同步改 tooltip 文案。

## #20 `WaterHelper.EmptyContainer()` 会把物品改价

**现象**：200 块的香料罐倒空后变成「一瓶水」的价格。
**原因**：`EmptyContainer` 内部会把 `unitValue` 改成 `WaterFeatureHelper.GetWaterPrice(0)`。
**做法**：要清空但保价，用 `WaterHelper.Remove(container, totalParts)`，再 `SyncModifiedState()`。

## #21 原版「速食拉面加水」是死代码

**现象**：想通过原版逻辑给杯面加水，怎么都不触发。
**原因**：`FoodItemHelper.CanCookCupNoodle` 从未被调用，而且用的是旧液体系统（`LIQUID_CONTAINER_CURRENT`），不是新水系统的 `CURRENT_PART_*`。
**做法**：自己接线。另外注意 `GameItem.MayTarget` 的判定是
```csharp
flag = 源.mayThisTargetItemFunc & 目标.mayItemTargetThisFunc   // AND
```
**只给目标加委托没用**——源物品（水壶）那一侧也必须显式允许，否则直接 false。

## #22 自定义液体容器不要在工厂里调 `InitLiquidContainerItem`

**现象**：物品「像没注册」：日志 `[Item Spawner]: 无法解析物品 <id>`、补货失败 `Object reference not set`；但 `dir.Set` 明明执行了。
**原因**：`InitLiquidContainerItem` 会走 `WaterFeatureHelper.InitWaterFeature` → `ItemMouseDragHandler.current`、水特征、`SpriteHelper.UpdateWaterContainerSprite`。在「物品列表 / 商店补货 / 编辑器刷物品」这些上下文里，拖拽状态和 UI 不完整 → NRE，工厂创建直接失败。
**做法**：自定义容器用轻量初始化——只加 `LIQUID_CONTAINER_TAG` + `LIQUID_CONTAINER_CAPACITY` + 清零所有 `CURRENT_PART_*`，完全不碰水特征/贴图系统。清空同样直接清 tag + `SyncModifiedState()`。

## #23 旧档补偿的「期望值」和「实际值」口径必须一一对应

**现象**：读一次档补一份物品，反复读反复补，等于刷物品；或者把已经卖掉的货补回来，凭空生钱。
**原因**：`EmporiumEntry.GetAllOwnedItems()` 只覆盖 `invElement / backInvinvElement / backInvinvElementCounter / frontInvinvElement / docInvElement / showcaseElement / trashInvElement / vending* / afterhour`，**不含** `hirelingInv`（雇工背包）、`soldElement`（已售出）、`hiddenElement`。如果按 `hirelingInvJSON / soldInvJSON` 算期望、却用 `GetAllOwnedItems()` 算实际，就会误判「丢失」。
**做法**：
- 期望和实际都按**同一组根节点**遍历。例：`mainInvJSON ↔ invElement`、`backInvJSON ↔ backInvinvElement`、`hiddenInvJSON ↔ hiddenElement`、`showcaseInvJSON ↔ showcaseElement`。
- 不要用 `soldInvJSON` 补偿（卖掉的再补 = 白送）。
- 补回物品必须带 `IS_OWNED_TAG`（照抄存档 `node.itemState` 自带），否则 `IsItemOwned` 为 false，新物品会被拒绝收纳。
- 用「存档指纹」防重复补偿：按 `mainInvJSON` 的长度 + hash 记录，同一份未保存的旧档反复读不会重复补。

## #24 「面板顺序」是存档格式的一部分

**现象**：调整机器面板顺序后，旧档里的物品全部错位、消失，或塞进错误格子。
**原因**：`SaveManager.DecodeNodes` 回填子物品靠「面板里 inventory 的 BFS 序号」。顺序一变，序号全错。
**做法**：
- 新面板**只追加在末尾**（官方文档也这么要求）。
- 不要删除/重排已有 inventory 面板；加按钮不影响序号（按钮不是 inventory）。
- `MachineHelper.GetModuleInv/GetModules/LockModuleInv` **硬编码取 `GetBodyStorage(machine, 1)`**，即「第二列」，不是「按 role 找模组区」。自定义机器若模组区不在第二列（例如：电源、食材、模组、成品），这些 API 会拿食材槽强转 `GameGridInventory` → `InvalidCastException`。两条路：
  1. 把模组区放在第二列（原版约定）；
  2. 不用这套 API，改用自己的 inventory 引用，并给 `GetModuleInv/GetModules` 打**只认自己 tag 的窄前缀**（例如按 `SMOKER_TAG` 返回 index 2）。

## #25 自定义机器的成品区别写 `mayInventoryAddItemFunc = (it, _) => true`

**现象**：用完的加速器/工具出现在成品格里；成品「没进成品区，直接掉仓库」。
**原因**：
- 很多「用完找地方落脚」的物品会走 `GraphUtils.EmporiumTryAdd`，从**鼠标当前所在库存**开始找位置。成品区全放行就会吸进去。
- `GraphUtils.CanAccept` 内部走 `TryFindOneValidInventorySlot`，对「刚创建、还没进任何库存」的物品判断不可靠，判 false 就绕开成品区。
**做法**：
- 成品区只放行**自己的成品 tag**（原版机器一律 `=> false`）。
- 放置用 `GraphUtils.TryAcceptAll(output, item)`，再用 `item.parentInventory != null` 判断是否真的放进去；失败才走 `EmporiumTryAdd`。
- 成品尺寸别贴着区域尺寸做（例如 3×3 的成品放进 3×3 的区域，一个就满，表现很像「没进成品区」）。

## #26 不要挂 `RenderHandler.current.overlayRoot`

**现象**：HUD 面板「挂上去了」，但屏幕上完全看不见。
**原因**：`overlayRoot` 的 `RectTransform` 是 `0×0`，且带 `RectMask2D`，子节点全被裁掉。
**做法**：自建一个 Overlay Canvas（`renderMode = ScreenSpaceOverlay`，`sortingOrder` 300 左右，`scaleFactor` 抄游戏 UI 的 `windowUICanvas.scaleFactor`），把自己画的面板挂到它下面。

## #27 场景物体的 SpriteRenderer bounds 可能是「整面墙」

**现象**：按 `wall_phone` 的 `SpriteRenderer.bounds.min.y` 算「电话底部」，结果面板跑到屏幕最底下。
**原因**：那个 SpriteRenderer 贴的是整面墙的贴图，bounds 正好等于相机视野（约 9.6×5.4）。
**做法**：用物体的 `BoxCollider2D.bounds`（真实点击区域）。例如 size `(0.855, 0.389)`、offset `(-1.97, -0.17)`；再 `Camera.WorldToScreenPoint` → 减屏幕中心 → 除以 Canvas scale 得 `anchoredPosition`。
**调试**：前 60 秒每 5 秒打一条 `phone / wpos / box / screen / cam / scale / panelSize / ap` 日志，位置不对时先看它。

## #28 `PlayerStore.ExecuteGameOver` 对未知 ending 会回退成「房租」文案

**现象**：自己写的「脱水/破产」结局，弹出来是房租的标题和描述。
**原因**：`ExecuteGameOver(ending)` 内部对未知 id 回退到 `mech_end_rent_*`。
**做法**：不要复用它。照抄它的三件事：
```csharp
GameOverUIManager.Instance.SetEnding("dehydration");
RunStats.OnRunEnded(StoreStation.GetDayCounter(),
                    PlayerStore.Instance.GetTotalEstimatedValue(),
                    PlayerStore.Instance.playerCash);
GameOverUIManager.Instance.DisplayUI("严重脱水", "描述");
```
时机：在 `OnGoingSleepLate` 弹面板正好——`EndOfDayUIManager` 的回调会检查 `GameOverUIManager.Instance.uiPanel.activeSelf`，已显示就不会再开早晨报告。
**防重**：`ExecuteGameOver` 上打一个前缀，用 `GameOverUIManager.Instance.IsShowing` 挡住重复调用。

## #29 借原版字段存状态，别改存档结构

**做法**（没有官方存档扩展入口时的可行方案）：
- `PlayerStore.itemDisplayNameCache` 是 `public Dictionary<string,string>`，会被 ES3 一起写进存档。可以塞一行 `__mymod_state__ = "a|b|c"`。
- 代价：借了原版字段，游戏改字段名就得跟着改；且不要塞大对象。
- 另一条路：把状态挂在**物品自己的 tag** 上（`<PREFIX>_STATE_INT`），跟着物品走、跟着存档走，但只在该物品存在时有意义。
- **不要**自己 `File.WriteAllText` 写存档旁路文件（会触发 `files` 能力，且多存档/云同步会乱）。

## #30 改机器/库存结构时，先发一版「结构版本 tag」并做旧档兼容

**做法**：
1. 每个会变结构的物品，工厂里写一个 `<PREFIX>_LAYOUT_VERSION_INT`；
2. 读档 `onLoaded` 里比较版本，旧版本走「重建/补偿」而不是硬读；
3. 结构变化的那一版在工坊说明里明确写「升级前先把机器里的东西拿出来」；
4. 补偿只保证「不丢」，找回的东西统一进仓库、由玩家自己摆回（不要猜格位）。

**反例**：把 6 对单格槽改成 6×6 网格后，旧档按旧索引回填，子物品全读不进来。日志是 `child item load failure`。

## 自绘窗口、拖拽与搜查（2026-11-07 / 11-08 新增）

## #31 自建窗口不要借用原版 `GameItemElement`

**现象**：把原版物品元素借到自建窗口里显示，移动窗口/定位物品时元素挂错库存、框选失效、错位叠加。
**原因**：`GameItemElement` 的生命周期绑在它所属的 `GameInventory` / `GameItem` 上，不是给你当「图标控件」用的。
**做法**：自绘卡片——只画图标 + 数量角标，物品本体留在原容器。代价是拖拽/框选要自己实现（原版 `ItemMouseDragHandler` / `ItemMultiSelectHandler` 依赖 `GameItemElement`）。

## #32 `GameGridInventory.handler` 的 RectTransform 尺寸是 0

**现象**：按库存节点算鼠标命中，永远判不中；或者点击位置整体偏移。
**原因**：`GameGridInventory.handler` 的 RectTransform 尺寸为 0（实际区域由面板/父节点排版决定）。
**做法**：命中判定改用**面板坐标**（自己维护的 `PixelElement` 矩形 / `_inner`），不要拿网格库存的 handler 当矩形。

## #33 用 `PixelWindow.handler` 判窗口矩形会漏判

**现象**：补丁里用 `PixelWindow.handler` 的矩形判断「鼠标在不在窗口内」，实测在窗口边缘/内部某些位置漏判（表现为终端里出框但选不中）。
**原因**：`PixelWindow.handler` 的 RectTransform 尺寸不是窗口的实际大小；真正的面板区域在 `_inner`（`PixelElement`）上。
**做法**：用面板的 `_inner` 矩形做命中；窗口级只用来判可见性。

## #34 窗口隐藏后，它的矩形仍然会拦截点击

**现象**：装了一个自绘窗口模组后，**关闭窗口**，它曾经覆盖过的屏幕区域（例如展示柜）永久失效：能框选多个物品，但一拖只有 1 个图标跟随，其余留在原地。
**原因**：`PixelWindow.Hide()` 只是 `handler.gameObject.SetActive(false)`，RectTransform 仍停在原位；`RectTransformUtility.RectangleContainsScreenPoint` 对**不可见对象照样返回 true**。于是你的前缀补丁一直认为「鼠标在窗口内」，把原版 `ItemMultiSelectHandler.OnEventPress` 吞掉了——多选 `state` 停在 `Selected`，进不了 `PendingGroupDrag`/`StartGroupDrag`，最后由 `ItemMouseDragHandler` 接管成单件拖拽。选中高亮还在，所以看起来像「框选成功了但拖不动」。
**做法**：
```csharp
bool ContainsScreenPoint(Vector2 screen)
{
    if (!_window.IsVisible()) return false;                 // handler.gameObject.activeSelf
    if (!_inner.gameObject.activeInHierarchy) return false; // 父链可见性
    return RectTransformUtility.RectangleContainsScreenPoint(_inner.rectTransform, screen, null);
}
```
**排查提示**：遇到「原版框选/多选拖拽只在某块屏幕区域失效」，先怀疑自建窗口的矩形命中（尤其有没有判可见性），而不是原版逻辑。自证步骤：打开窗口 → 拖到那块区域 → 关闭 → 再试框选。

## #35 `TryInventorySlot(item, …, item.modifiedShape, …)` 会把原容器坐标套到目标库存

**现象**：一次拖多件，只有第一件进了目标库存，其余留在原处或错位。
**原因**：把源物品的 `modifiedShape`（带原容器里的坐标）传给目标库存的 `TryInventorySlot`，目标按这个坐标找位，第一件之后全部失败。
**做法**：跨库存放置用 `GraphUtils.TryAcceptAll(target, item, amount)` 自动找空位；不要复用源形状。

## #36 目标库存拒绝时，不要「溢出到仓库」

**现象**：把物品拖到交易区/某个窗口，目标拒绝后，物品被塞进了基础物品栏（而不是留在原处）。
**原因**：放置失败后调用了 `GraphUtils.EmporiumTryAdd`（原版溢出链：背包 → 后仓 → 货架 → 展示柜 → 前台）。
**做法**：交互式拖拽的语义是「放不下就留在原处」，只有**产出**才走溢出链。落点失败就什么都不做。

## #37 不要自建 `TMP_InputField`

**现象**：自建搜索框，空文本点击时抛 `TMP_TextUtilities.FindNearestCharacterOnLine` 的 `IndexOutOfRangeException`；或者输入框里文字不渲染。
**原因**：TMP 输入框在空文本/未激活状态下算字符位置会越界；手搓文本节点在这套 UI 里本来就不渲染（坑 #12）。
**做法**：借原版输入框 `LabelerBlueUIManager.Instance.OpenUI(当前词, 回调, 清空回调, 48)`，支持中文输入法，样式也天然一致。

## #38 自绘像素 HUD：`SetPixels32` 的行 0 在底部

**现象**：自己用 `Texture2D` 画的像素屏，字全倒过来（上下翻转）。
**原因**：`Texture2D.SetPixels32` 的行 0 是**底部**，按「0 在顶部」的直觉绘制就会整张翻转。
**做法**：绘制完把行序翻一次再 `SetPixels32`；或者绘制时就用 `y' = height - 1 - y`。
**相关**：像素 HUD 的 PPU 取 200（正好等于 `Emporium_camera` ortho 2.7 / 1080p 下「每世界单位 200 屏幕像素」），1 纹理像素 = 1 屏幕像素，点阵字不糊。

## #39 不要用持久 tag 表达「暗格/隐藏」语义

**现象**：给普通储藏区加 `ITEM_HIDDEN_TAG` 实现「不被搜」，卸载模组后 tag 残留在存档里；或者从暗格取出的物品 tag 被原版剥掉。
**原因**：tag 随 `modifiedState` 进存档；`EmporiumEntry.hiddenElement.onSlotRemoveItemEndFunc` 只在 `IsSmugglerBay` 命中时才保留该 tag。
**做法**：用**纯运行时补丁**改判定函数（`IsSmugglerBay` / `IsBlockSearchContainer` / `FindAllContrabandItem`），读档/卸载都干净。父链判定用 `item.parentInventory.GetParentItem()` 逐层向上，带 **64 层**防死循环。
**注意**：物品 identifier 和「内部库存 identifier」不是一回事——`ShipSystemDirectory` 里三个暗格的 `item2.identifier = "smuggler_bay"` 设的是内部 `GameInventory` 的 id，物品自己的 id 仍是目录 id。

## #40 补丁范围过宽：一个 early return 会连带关掉别的分支

**现象**：想让「禁止逐件购买」的供应商也能赊账，补丁在 `BuildSelling` 里看到 `isRegularSellDisable` 就 `return`，结果这些客户**只能走批发**的按钮（`secondaryButton`）也没被放开，现金不足时仍然灰掉。
**原因**：`isRegularSellDisable` 的语义是「禁止逐件购买」，不是「这个客户不能交易」。一个 early return 把所有后续处理都跳过了。
**做法**：按**按钮/语义分别判断**：`primaryButton` 只在 `!isRegularSellDisable` 时放开；`secondaryButton` 只要 `isOfferWholesale` 就放开。补丁里先写清「我要改的是哪个控件的哪个条件」，再动手。

## #41 大网格拖拽卡死：每次放入都触发「全网格重算」

**现象**：自定义容器网格扩到 15×15、放几十个可交互物品后，框选多件拖动直接卡死/未响应；物品越多越慢。
**原因**：原版 `OnAddedModuleToGrid` / `OnRemovedModuleFromGrid` 每放入**一件**就对整个网格做一次 `ComputeAllModuleTempStat`；该函数对每个物品做 3 次 `ModifyTag`（默认 `skipValidate=false`）→ `ValidateShapeState()` 里还有 `parentInventory.Validate()` 和沿父链递归。拖入 N 件 × 网格 M 件 × 3 次 = 平方级校验。
**做法**：① 槽回调期间用 Harmony 前缀抑制该函数，`Update` 帧末统一重算一次；② 左键按住（拖拽/框选）期间不结算，松手后算；③ 大列表用 `ModifyTag(..., skipValidate:true)` 批量写 TEMP，再逐件 `SyncModifiedState()` 一次（**先 sync 再跑依赖 `modifiedState` 的 `onAnyAction`**）；④ 全仓库扫描（如 `FindHubs`）和「读总数」结果做缓存，只在读档/生成/打开面板时失效。
**详见**：`docs/11-性能优化-大网格拖拽.md`（含代码与顺序说明）。

## 交互委托、批量结算与发布（2026-11-09 ～ 11-15 新增）

## #42 `GameItem.MayTarget` 的委托是 AND 聚合，给目标注册「只收 X」会连带否掉原版工具

**现象**：给自建机器注册「只接受某类物品」的拖拽判定后，原版工具（涡轮增压器）再也拖不上机器——明明它的 `IsTurboBoostEligible` 返回 true。
**原因**：`MayTarget` 里 `flag = flag & 源.mayThisTargetItemFunc & 目标.mayItemTargetThisFunc`。目标侧只要有一个委托返回 false，整体就否决，其它来源的 true 救不回来（`flag2` 才是 OR）。
**做法**：**把交互注册在源物品一侧**（`mayThisTargetItemFunc` / `canThisTargetItemFunc` / `onThisTargetItemFunc`），目标物品**不要**注册任何 target 委托。需要「只对某类目标生效」时，在源侧回调里判断目标是不是自己关心的类型，是就处理、不是就返回 false 让原版继续。

## #43 消耗材料要交给 `EndDrag` 收尾，不要直接 `Destroy()`

**现象**：升级成功、材料也扣了，但拖拽结束时抛异常或输入卡住。
**原因**：`EndDrag` 收尾还会对拖拽中的 `currentItem` 调 `Validate()`；你提前 `Destroy()` 掉它，访问已销毁节点就会抛异常。
**做法**：成功时只把材料从原库存摘出来——`mat.parentInventory.Expel(mat)`，让 `parentInventory` 变 null；`EndDrag` 看到「没放进任何库存」会自己 `Destroy`。

## #44 批量结算不要逐件调用「默认 Validate」的原版 helper

**现象**：100+ 瓶酒/几十个模组时，每日结算或插拔一件会让整个网格重排一次，明显卡顿甚至卡死。
**原因**：这类 helper（例如 `WineHelper.OnAgeWine`、`ModuleEffectHelper.OnAddedModuleToGrid`）内部的 `ModifyTag` 默认 `skipValidate=false` → `ValidateShapeState()` → `parentInventory.Validate()` + 父链递归 + 刷 UI。逐件调用就是 O(n²)。
**做法**：批量循环里 `ModifyTag(..., skipValidate:true)`，循环结束统一 `SyncModifiedState()` / `Validate()` 一次；**先 sync 再跑依赖 `modifiedState` 的 `onAnyAction`**。参考 `docs/11`。

## #45 手动改 `modTrust` 会让整个信任库失效

**现象**：为了「本地模组不用每次点信任」，直接改存档里的 `modTrust`；结果游戏启动后所有本地模组都变回「需要审阅并启用」，日志 `[ModTrust] The trust store does not match its signature; N approval(s) discarded`。
**原因**：`modTrust` 旁边有 `modTrustMac` 签名，不是 `sha256(modTrust.value)`（实测不等），大概率是带设备密钥的 HMAC，手算不出来。签名一坏，整库作废并写回存档。
**做法**：**只改 `modOrder`**（它没有签名），信任交给游戏自己写：进 Mods 菜单点一次「信任/批准」，或对本地文件夹开「开发者模式」。已经踩坏时，用备份里的 `modTrust` + `modTrustMac` 两键**原样合并**回存档（两个都要，不能只补一个）。

## #46 自动部署脚本必须 DLL + manifest 一起复制

**现象**：用后台脚本「等游戏退出 → 复制 DLL → 上传」，结果工坊上的版本号还是旧的。
**原因**：脚本只复制了 DLL，漏了 manifest；上传读的是目录里的旧 manifest。
**做法**：部署脚本把 `manifest.xml` 和 DLL 当成一个整体（先复制 manifest 再复制 DLL，或先写临时目录再整体替换）；上传前 `--validate` 核对输出里的 `version` 是不是你期望的版本。

## #47 想「拖到容器图标上做批量操作」，必须先挡住原版的「存进容器」

**现象**：拖一个反应器/工具到储藏区图标上，物品被存进储藏区，批量逻辑根本不触发。
**原因**：`EndDrag` 先走「插入容器」分支，只要 `MayHaveValidInventorySlot` 返回 true，就不会走到 `Target`。
**做法**：三个补丁配合——
1. `GameItem.MayHaveValidInventorySlot` **前缀**：`this` 是目标容器、拖的是你的特殊物品、且容器里有可处理的物品时返回 false；
2. `GameItem.MayTarget` / `CanTarget` **后置**：让拖拽高亮变绿、显示「使用」；
3. `GameItem.Target` **前缀**：真正执行批量逻辑。
只认 `itemTypes` 里的 `STORAGE`（或你自己的白名单），别误伤展示柜/柜台/机器。

## #48 三套坐标原点：Unity 屏幕、窗口客户区、Windows 光标

**现象**：用 `SetCursorPos` 把光标「吸」到物品上，结果全部错位、光标乱跳，总是吸到屏幕右下角/交易栏边缘。
**原因**：`Input.mousePosition` / `RectTransformUtility.WorldToScreenPoint` 用的是**窗口客户区、左下原点**；`SetCursorPos` 用的是**屏幕坐标、左上原点**。直接混用就是 Y 镜像 + 原点偏移。
**做法**：内部统一用 Unity 屏幕坐标；写光标时 `ClientToScreen(GetForegroundWindow())` 取客户区原点，再做 `Screen.height - y` 翻转。
**相关**：取物品中心别用 `GameItemElement.handler.rectTransform`（尺寸为 0），用 `GameItemElement.rectTransform`（= `middle`）的 `GetWorldCorners()` 取对角中心。

## #49 非矩形大 shape 的创建成本很高

**现象**：满级/异形大机器（几百格）打开窗口有明显一次性卡顿。
**原因**：`SetShape(shapeString, width)` 的非矩形形状会走 `renderDynamicBackground`，每格 5 个 `TreeNodeRender`；400+ 格就是 2000+ 节点，打开窗口时一次性创建。
**做法**：能矩形就矩形（`SetShape(w, h)` 只建 3 个节点）；必须异形时，把窗口打开做成懒加载/按需创建，别在 `onLoaded` 里提前建。

## #50 没有候选目标时，不要对每个候选物品调用「全仓库扫描」的 helper

**现象**：自动投放类 ticker 一开就掉帧，物品越多越卡。
**原因**：helper 内部每次都会 `EmporiumEntry.GetAllOwnedItems()` 找目标（例如「找空瓶」）；对 100 个源物品各调一次 = 每秒 100 次全仓库扫描。
**做法**：先扫一次目标集合，再拿源物品去匹配；最多试固定数量（例如 3 个），失败就等下一 tick。ticker 里也不要每帧 `GetAllOwnedItems`。

## 批量输出与上架（2026-11-19 / 11-24 新增）

## #51 「分帧 + 每帧 Validate」是最差的批量组合

**现象**：批量输出 71 个成品，旧版「协程每帧 8 个 + 每帧 `output.Validate()`」连续掉 9 帧；看起来分帧了，实际更卡。
**原因**：每帧的 `Validate()` 会把**已经放好的成品全部重新验证一遍**——71 件累计约 360 次重复验证；再叠加每件都重扫 72 格统计空格（O(n²)）和每件都调 `GraphUtils.CanAccept`（与 `TryAcceptAll` 重复做落位搜索）。
**做法**（`[实测]` 用户确认「效果不错」）：
1. **同步一次做完，结束只刷一次**（规模 ≤100 件时最划算）；分帧只在「必须保持界面响应」时用，且**每帧不要 Validate**，全部结束或每 N 帧刷一次；
2. 空格数开始时算一次，之后每放一个减成品实际占格；
3. 去掉逐件的 `CanAccept`，由维护的空格数判断，`TryAcceptAll` 的 `leftover` 兜底；
4. `leftover > 0` 且物品 `parentInventory == null` 时销毁，避免漂浮泄漏；
5. 结尾打 `Stopwatch` 总耗时 + 刷新耗时，判断是否值得做对象池。

## #52 大件上架：先预检，再前置

**现象**：4×4 的大件（机器）第一次没买到，之后商人再也不带它。
**原因**：`TryAddDirectSellingItemToTable` 找不到位置时**直接 `Destroy()`**，没有溢出链；上架动作如果追加在原版随机货之后，4×4 会被前面的一堆小件挤到没位置，东西就没了。
**做法**：
1. 用 `Delegate.Combine(action, endAction)` 把上架**前置**到原版货之前（大件先占位）；
2. 上架前 `front.TryFindOneValidInventorySlot(item)` 预检，放不下就 `EmporiumTryAdd` **退回仓库**，绝不让它被 Destroy；
3. 前台已有未售同款时不重复堆叠。
