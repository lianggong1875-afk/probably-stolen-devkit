# 管理器接入

原版顾客支持按职业身份或共用图片声明，见 [职业与图片键](原版职业与图片键.md)。`vanilla_client_` 职业沿用 character/game/key/main 与 sprite-key binding，按 identifier 精确识别，别名合槽；保留 sourceModId 来源隔离、isAug 身体图及当次可信原图。

扫描 ModHelper.GetModFolder 对应实际 mod ID 的 portrait-studio-provider.json，校验 format、contract、role 和完整静态身份。resources 只供图；writer/both 须 hello 验证 instance/revision 与显示协商。清单和握手都通过才进入接口路径。未公开范围保留原兼容。

复用 Catalog.Read(root,expectedId) 校验元数据；它不读取 PNG、不创建桥。资源出口保持自己的 providerId，按目标身份提供 resourceSets，每张图独立 resourceRevision。原路径、用户选择与布局配置保留，映射只在内部完成；跨角色资源先导出到目标身份组。

按实际顾客实例映射 encounter，在同一 surface/encounter 协调全部写图者，沿用原默认来源优先级。显示 epoch 和会话隔离旧事务；同次登场只抽一次，退场不能因 currentClientInstance 清空就清随机结果。来源 SourceChanged 重发相同 epoch 的 show 时重新准备当前意图，保持原 encounter 选择。

select 只存意图。实际显示 plan 后全局预留峰值，再 prepare；全组准备成功后在同一主线程同步 drain 中先 silent、再 presenter commit，同时暂停管理器该表面的旧覆盖。响应 handler 只入队。缺同步 applied 立即同段 rollback；全组成功再 finish。不得仅按 target 全局静默，也不得把 ready 当作已让位。

会话先于显示出现时，silent 的恢复默认也计入计划和预算，prepare 保持画面不变；已有恢复默认才是零增量。不要以临时 presenter 提交原图再外部还原的方式预热，这会让 SDK 的显示所有权与实际画面脱节。

只有 writer、没有托管组件的 custom 表面也走显示事务。由经过握手的清单 target 和 show 建立完整身份及表面记录，保留来源为 presenter；selected 可引用同身份其他提供者的静态资源，original 使用来源保全的原图，三种模式的 layout 均由 SDK 处理。管理器无需读取其 Unity 组件，也不能因此判定无法选图。多 writer 按相同 surface/创建者登场关联协调，唯一 presenter 沿用来源优先级；关联不明则报告冲突。query-state 行保留 show 的 originVisitId，丢事件后按完整分页快照恢复。来源失联按租约撤销该组控制，不能改用名称搜索组件。

预算按 instance 汇总 resident，再预留 peakAdditional；纹理去重、借用、延迟销毁与磁盘 heldResources 都要计入。分页快照收齐后替换保护集。trim 只清 idle。按 [公开协议](静态资源公开协议.md)、[消息 Schema](portrait-studio-wire.schema.json) 和 [完整报文](static-examples.json) 实施扫描、资源、显示、错误和恢复。

## 管理器托管路线

无组件 writer 的发现使用 [公开协议](静态资源公开协议.md) 中的 `portrait-studio-static-active/1`，官方 Lookup 类型为 `Func<string>`。先取得实际活跃 target 列表再 acquire，避免等待 show 的循环依赖。服务仅提供缓存元数据，不取得写权；最多每0.25秒读取一次，精确校验 hello instance、writer revision 和声明范围。实际同时需求超过32时报告上限并保留已有，不抢占轮询。

另读 [托管显示协议](托管显示协议.md)。portrait-studio-managed.json 明确授权管理器负责声明静态位置；资源清单仍为 role=resources。仅存在供图清单不表示托管，不能据此静默作者或退出其他来源。托管路线不使用来源 StaticBridge 事务，管理器自身是该声明的候选呈现者，仍须与其他 writer 逐表面协调并遵守全局预算。

原生表面用管理器已有可信身份和生命周期。custom 通过官方 Expose/Lookup 的 Func<object[]> 只读登记服务取得 Unity 表面和可信原图；按 instance/epoch/当前快照检查生命周期，hidden 同步恢复、rebound/destroyed 仅取消旧写入。管理器缓存已取得的 delegate，写前调用其缓存快照，不每帧重复 Lookup、扫描图片或反射来源。已有选择、布局和预设优先，包默认仅补未设置项。按声明能力判定支持。

## 通用套装下拉框

读取 `Catalog.portraitSets`，每项 `id` 是来源内稳定标识，`name` 是下拉显示名；`entries` 是精确资源引用。用 `GetSet(ref.setId).Identity` 关联目标，按页面 kind/slot 和角色筛选计覆盖数。批量应用只处理声明条目，缺图跳过；不要按文件前缀、枚举顺序或候选序号猜套装。没有 portraitSets 的来源保留当前批量行为。

writer和托管目标均要求条目属于该目标候选；`Catalog.ValidatePortraitSetTargets` 可校验，`ManagedCatalog.Read` 已调用。纯资源来源只列供图，不获得显示权。下拉切换只改UI，应用才创建现有 selected 意图；保留布局、预设、原版限制和随机增量规则。套装不是新的 wire op，不调用来源的设置回调。来源设置的变化不会覆盖管理器选择。

来源索引、通用下拉及批量应用均使用完整资源引用，并用支持 portraitSets 的 Catalog 读取器校验。

显式 portraitSets 优先。已知旧模组的 bank 映射转成同一内部套装模型，来源 ID 与套装 ID 分开；无声明保留现有行为。管理器直接使用作者 SDK 的 Catalog 读取器共享字段校验。

批量条目按完整 Identity 关联，包括 owner 和 slot；自定义 NPC 是身份及 binding 的区别，kind 仍按人物或实际用途填写。管理器内部需保留完整资源引用与身份关联，兼容已有路径选择和布局；同一物理路径不能代替资源身份或修订。切换套装不调用 RegisterPortrait。随机沿用现有角色随机能力，不扩展照片或场景随机。

清单更新后保留稳定套装 ID 并重新解析；套装已失效时提示重选，不自动应用默认套装。来源或目录可用性在点击应用时重新检查。覆盖数按本次页面范围内的实际目标计，可合并到套装选项文字中。作者设置、资源几何及管理器参数的分工见公开协议“设置与保存”和“设置边界”。
