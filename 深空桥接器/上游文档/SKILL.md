# Probably Stolen MOD development facts

Check edition and dynamicModules in get_development_environment or /bridge/status. Workshop runs Compatible (27 tools); local Full adds load_probe_module, call_probe and reload_mod (30 tools). Querying probe sources does not enable executing them. When needed, read README.md and FullSource/BUILD.md, explain Full/local Developer-mode risks and obtain explicit consent before compiling/installing. Follow the Compatible-local approval bootstrap and the player's manual Developer-mode toggle; do not alter loader/trust records. Compile outside game/Workshop folders. Reconnect and verify the running Full edition after restart.

This MOD runs inside the Windows game and provides standard MCP Streamable HTTP. Discover current tools with Tools/list; call get_development_environment for actual Managed/SDK/staging paths, game/Unity versions and module interfaces. get_game_status distinguishes main menu, loaded save, world and active session. Version assumptions expire when the game updates.

For first connection or reconnect, read [AI_GUIDE.md](AI_GUIDE.md). For native APIs, localization and compatibility experience, read [references/ENGINEERING.md](references/ENGINEERING.md). Result and cleanup semantics are in [references/RESULTS.md](references/RESULTS.md). When the player wants to publish a MOD, read [references/WORKSHOP_PUBLISHING.md](references/WORKSHOP_PUBLISHING.md) for Steam-client publishing. Documents are in this package; get_development_environment reports their directory. MCP resources expose this skill, connection guide, engineering and result references from the same files.

The game is Unity + Mono. Decompile the currently installed Assembly-CSharp.dll and inspect the smallest relevant call chain. Use installed game Managed references when compiling. Target the game's framework; modern .NET SDK is a compiler, not the game's runtime. Keep source, decompilation caches and final MODs in your own workspace outside the Steam workshop package and MOD runtime directories.

Useful observations include query_ui (labels and nearby row text), query_items, query_customers, query_localization, inspect_runtime, filtered get_game_logs, get_snapshot and diff_snapshots. Read completeness/truncation fields; detail tools and get_operation can recover retained full results. Tool descriptions give actual arguments and side effects. No prescribed development sequence is required.

For reference UI actions, pass the target row's targetRef unchanged as target_ref. It already carries the observation precondition; no separate token arguments exist. For drag destinations use observation.actionRef, available in view=nodes or get_ui_details. Changed bounded target/container content is rejected; obtain a new observation and verify the intended record. Refs, instanceIds and sibling-index paths can survive a virtualized row being rebound to another record; path order is not visual list order. context.rootRef identifies the source container for a narrowed query. Content guards do not prove business identity or effect. Coordinate-only input has no content guard. Chinese text_contains matches raw component text/owned labels, not nearby context or every game's item name; query_items finds live items. An empty UI query during a transition is one observation: retry within a finite deadline, check searchComplete, then report a timeout instead of assuming permanent absence or repeatedly clicking.

For uncovered behavior, write a C# probe with native Reflection. query_probes exposes reviewed source examples and side effects. Unique assembly identity per build is required; changing a filename does not change identity. Start executes when loaded. Temporary resources need explicit ownership and repeatable cleanup. Loaded assemblies remain until restart.

Before the first experiment needing a save, identify which save the player has designated for testing. If no choice is known, ask once which slot/save can be used; if none exists, offer to create a separate test save through the native UI. Keep the choice for later experiments and restarts. Use query_ui/operate_ui to load it yourself, then verify get_game_status ready, saveSlot and worldId. If the intended save is already ready, continue directly. Do not pick the newest save or assume an internal test-slot number; ask again only when the chosen save is missing or ambiguous. Clarify phrases such as "first save" if they could mean list order, slot number or creation order; identify the intended save by its displayed details and verify the actual slot after loading. Switching away from another loaded save may lose unsaved progress; resolve that with the player before switching.

Use the authorization and backup rules in [README.md](README.md), and inspect the actual saveDirectory. A test session tracks registered cleanup actions, not all game side effects. Native RNG, callbacks, autosaves, third-party hooks and writes may outlive an experiment.

Native MODs use IMod and the game's manifest.xml. Final MODs must run after disabling this MOD and restarting the game, without referencing this MOD's assembly. reload_mod is an optional accelerator for MODs implementing its two lifecycle hooks; the MOD owns unbinding/rebinding existing object callbacks, events and resources. Hook presence does not prove safety, session close retains a successful replacement, and a normal restart is the recovery boundary for uncertain runtime state.

Steam updates only own the downloaded package. Agent projects, backups and finished MODs belong to the player and remain independent of MOD updates or unsubscription.
